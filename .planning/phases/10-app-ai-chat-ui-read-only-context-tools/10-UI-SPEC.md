## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, source-chip inner gaps, compact metadata spacing |
| sm | 8px | Button icon/text gap, message section gap, context-chip gap |
| md | 16px | Drawer body padding, answer card padding, composer padding |
| lg | 24px | Drawer header padding, transcript vertical rhythm, empty state spacing |
| xl | 32px | Major drawer regions, context picker groups |
| 2xl | 48px | Empty state top/bottom padding, mobile drawer safe spacing |
| 3xl | 64px | Reserved for page-level spacing only; do not use inside dense chat content |

Exceptions:
- Header utility trigger uses existing `h-10 w-10` on desktop and must maintain a minimum 44px touch target on mobile.
- Drawer width is fixed by viewport constraints: `min(520px, 100vw)` on desktop and `100vw` on mobile.
- Composer textarea uses `min-height: 44px`, `max-height: 160px`, and grows vertically without moving the drawer header or context bar.
- Source chips may wrap, but each chip must keep a minimum 32px height and 8px horizontal gap.

Use exactly these four sizes for the Phase 10 AI drawer. Do not introduce viewport-scaled type or new negative letter spacing.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 12px | 600 | 1.3 |
| Heading | 20px | 600 | 1.2 |
| Display | 24px | 600 | 1.15 |

Usage:
- Body: message text, answer body, confirmation text, empty/error descriptions.
- Label: context bar labels, source chips, section labels, tool metadata, timestamps.
- Heading: drawer title, answer card title, empty state heading.
- Display: only the initial empty transcript headline; not for repeated answer cards.

## Color

Use semantic Tailwind tokens only. New Phase 10 UI must not use hardcoded palette utilities such as `bg-gray-*`, `text-blue-*`, `bg-emerald-*`, raw hex values, or inline HSL strings.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-background`, `text-foreground` (`--background`, Paper source `#F6F1E8`) | App backdrop visible behind the drawer, drawer outer rhythm, transcript background |
| Secondary (30%) | `bg-card`, `bg-secondary`, `bg-surface-muted`, `border-border` (`--card`, `--secondary`, `--surface-muted`) | Drawer panel, answer cards, context bar, source chips, context picker, input composer |
| Accent (10%) | `bg-primary`, `text-primary`, `ring-ring`, `border-primary/35` (`--primary`, Paper source `#2457FF`) | AI drawer trigger active state, send CTA, selected context option, focus ring, running indicator, links that open referenced Smart-ERD resources |
| Destructive | `bg-destructive`, `text-destructive`, `border-destructive/35` (`--destructive`, Paper source `#C84C3A`) | Local-only "new conversation" confirmation and runtime error emphasis. No project-data destructive action appears in Phase 10. |

Accent reserved for: drawer trigger active state, "질문 보내기" button, selected context check state, keyboard focus ring, running progress indicator, and resource-opening links. Source chips are neutral outline chips by default and must not consume accent unless the user has explicitly selected one as a filter.

## Phase 10 Interaction Contract

### Global Drawer

- The AI surface is a global right-side drawer available from every authenticated app screen.
- The drawer must not render on `/login`, `/signup`, public guide-only unauthenticated routes, or the Electron server setup state before authentication.
- The trigger belongs in the shared header utility rail, not inside a project-only hero or the existing provider status badge.
- The provider status badge remains a status surface. It must not be overloaded as the chat trigger.
- The drawer host lives near the app shell/router layer so open state, messages, and pending execution state survive route changes.
- Drawer close hides the panel but does not reset messages or context.
- `Esc` closes the drawer only when no nested context picker/dialog is active.

### Layout

- Desktop: right drawer width `520px`, max `100vw`, full height below the viewport edge, panel background `bg-card`, border-left `border-border/85`, shadow `shadow-editorial-strong` or equivalent token shadow.
- Mobile: drawer occupies `100vw`, header/context/composer stay fixed within the drawer, transcript scrolls independently.
- Header row: title, provider availability compact status, close icon button, and local-only "새 대화" icon/text action.
- Persistent context bar: always visible under the header. It shows current scope, a manual context selector, and a short confidence/source status.
- Transcript: vertical list of user messages and assistant answer cards. Use neutral surfaces; do not nest cards inside cards.
- Composer: fixed bottom region with textarea, send button, optional cancel-running button, and a short context hint. It must remain usable while the transcript scrolls.

### Context Behavior

- Default context inherits the current route when `teamId` and `projectId` are known.
- Team-only screens such as project list inherit team scope but require explicit project scope for single-project data questions unless the question is team/multi-project oriented.
- Weak-context screens such as team list, dictionary, settings, or generic guide screens require explicit scope before project-data questions run.
- Manual context changes do not reset the conversation.
- Each message records the context that was used at send time. Later route or manual context changes must not rewrite past source chips.
- Multi-project questions may expand to all accessible projects in the current team only.
- All-team/all-project querying across every team is excluded.
- Ambiguous, misspelled, or conflicting project names produce a chooser/confirmation prompt inside the drawer before any answer is generated.

### Send Lifecycle

- Send is disabled when the message is empty, the provider is unavailable, required context is missing, or an execution is already running.
- While running, show `Loader2` animation on the send area and an `aria-live="polite"` status such as `응답을 작성하는 중입니다`.
- `응답 중지` is available during a running execution and maps to the Phase 9 cancel API. It must not clear the user's message or local transcript.
- Runtime failure adds an assistant error card and also shows `toast.error(getErrorMessage(err, t('aiChat.error.fallback')))`.
- Successful answers append a structured answer card with source chips and sectioned content.

### Local Persistence

- Drawer open state and conversation messages survive route changes.
- Messages survive browser refresh through browser-local persistence.
- Use a new `STORAGE_KEYS.AI_CHAT_CONVERSATION_PREFIX` constant. The storage key must include the authenticated login/user identifier so conversations do not bleed across users on the same browser profile.
- Store only rendered chat messages, selected context IDs/names, timestamps, execution IDs, source-chip summaries, and sectioned answer text.
- Never store access tokens, refresh tokens, session cookies, DB credentials, raw prompt bundles, raw provider output, backend environment values, or arbitrary tool payloads in local chat storage.
- `새 대화` is the only reset mechanism. It clears browser-local conversation state after confirmation and does not affect server data.

## Response Presentation Contract

Each assistant answer uses one answer card with this order:

1. Conclusion line: one sentence that answers the question directly.
2. Source chip row: neutral chips formatted as `{project name} - {tool label} {count}` or `{team name} - projects {count}`.
3. `확인된 사실`: factual bullet list from server read tools only.
4. `해석`: inference clearly derived from the facts. Avoid claiming it as source data.
5. `확인이 필요합니다`: explicit confirmation question, missing scope, ambiguous project choice, or follow-up checks.

Rules:
- If the server returned no usable facts, do not fabricate an answer. Show `확인이 필요합니다` first.
- Source chips must include the actual context used, not the currently selected context after the answer completes.
- Counts must refer to the data returned by read tools, not total database counts unless the tool contract says so.
- Read-tool labels in chips are fixed: `overview`, `WBS`, `milestones`, `issues`, `TODO`, `history`.
- Use short bullets. Dense tables are allowed only when the user asked to compare projects or list items.
- Do not show action proposal cards, approval buttons, preview/diff UI, write execution status, audit history, or delete/destructive project controls.

## API and State Contract

- Frontend calls Spring HTTP APIs through typed modules only. No component may call `axiosInstance` directly.
- Frontend must not call Codex, Electron IPC, provider runtime APIs, shell commands, or local filesystem APIs directly.
- Server state uses React Query. Use `queryKeys.aiProvider.*` for provider status/execution and add an `aiChat` namespace for chat/read execution if a separate endpoint is introduced.
- Client-only drawer state and browser-local conversation persistence use Zustand.
- Route context resolution should be a hook that derives current team/project/resource context from route params and known page data where available.
- Context selector data uses existing authorized APIs through React Query. Do not prefetch all project details just to open the drawer.
- Read tools remain server-controlled and summary-first. The UI displays tool metadata but does not assemble AI-visible project data in the browser.

---

## Accessibility Contract

- Drawer uses `role="dialog"` with an accessible title and Radix focus trap behavior.
- Trigger, close, new conversation, send, cancel-running, and context selector buttons have visible text or `aria-label` plus tooltip.
- The context bar announces scope changes with `aria-live="polite"`.
- Running, cancelled, failed, and completed response states are announced through a polite live region.
- Keyboard order: trigger → drawer close/new conversation → context selector → transcript → composer → send/cancel.
- Source chips are readable text, not color-only indicators.
- Error cards use `role="alert"` when appended after a failed execution.
