## Source Audit

This plan covers GOAL chat ask/answer grounding, REQ AI-CHAT-01 and all AI-READ requirements through the chat endpoint, RESEARCH guidance to avoid direct provider/frontend coupling, and CONTEXT decisions D-15, D-23 through D-30. It explicitly uses the resolved response contract from `10-RESEARCH.md`: keep the Phase 9 provider schema, validate provider `answer`, and assemble chat-specific facts/source/context/confirmation data in `AiChatExecutionService`. It excludes server chat history, action proposal UX, approval, and write execution per D-30.

## Must Haves

- `POST /api/ai/chat` accepts authenticated requests only.
- Confirmation-needed responses do not invoke the provider.
- Successful responses include conclusion, confirmed facts, interpretation text, needs-confirmation items, source chips, execution metadata, and status.
- `confirmationCandidates` are first-class response data sourced from `AiChatContextResolver`/read-service gaps, not model prose.
- Provider `answer` maps only to `interpretation`; `confirmedFacts`, `sourceChips`, `context`, `conclusion`, and `needsConfirmation` are produced by server assembler logic.
- Non-empty provider action drafts are not returned to the chat UI and cannot create approval/write UI in Phase 10.
- Provider execution strategy is fixed: extract `AiProviderExecutionRunner` from the provider-invocation, registry, validation, audit, timeout, and cancel-handler code currently inside `AiExecutionGateway`; keep `AiExecutionGateway` as the Phase 9 single-project facade and call the runner from both Phase 9 and Phase 10.
- Synchronous chat cancellation strategy is fixed: `POST /api/ai/chat` returns one final response. It may include a completed `executionId`, but the frontend cannot server-cancel an in-flight chat provider call because no execution ID is available until the response completes. Phase 10 UI `응답 중지` means client-side HTTP abort/stop waiting only.
