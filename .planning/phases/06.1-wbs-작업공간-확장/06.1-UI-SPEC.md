# Phase 06.1 - UI Design Contract: WBS 작업공간 확장

> Visual and interaction contract for the dedicated WBS authoring surface. This spec is the frozen UI input for `06.1-01-PLAN.md` and is ready for `$gsd:execute-phase 6.1`.

---

## Design System

| Property | Value |
|----------|-------|
| App shell | Existing project workspace shell (`Header`, workspace context, project-scoped routes) |
| Component library | Radix UI via local shadcn/ui primitives |
| Icon library | lucide-react |
| Core table primitive | `client/src/components/ui/table.tsx` |
| Existing authoring surface | `client/src/components/wbs/WbsTab.tsx` |
| Existing detailed editor | `client/src/components/wbs/WbsItemFormDialog.tsx` |
| Existing row interaction surface | `client/src/components/wbs/SortableWbsRow.tsx` |

No new visual language is introduced in this phase. The contract extends the current project workspace patterns and keeps the WBS surface aligned with Phase 4/6 project-hub chrome.

## Scope Freeze

This UI phase fixes the following boundaries:

1. The current `wbs` tab remains inside `DiagramsPage`.
2. A dedicated route `/teams/:teamId/projects/:projectId/wbs` is added for full-width authoring.
3. Assignee becomes a visible column in WBS tables and an editable field in the dialog.
4. Quick-add footer rows exist only in the dedicated WBS workspace.
5. The popup dialog remains the canonical detailed editor for milestone, dates, progress, and estimated M/M.

Out of scope for Phase 6.1:

- assignee inline cell editing
- gantt + WBS split view
- slash-command insertion
- resource grade / cost / M/M planning views
- team-member search virtualization

## Screen Inventory

### 1. Project Hub `wbs` tab

Purpose: compact entry and review surface inside `DiagramsPage`.

- Keep the current tab in the hub tab rail.
- Keep the two-pane content relationship: WBS table as primary surface, milestone panel as secondary surface.
- Add a dedicated-page CTA in the WBS card header.
- Keep dialog-based create/edit as the main mutation path inside the tab.
- Do not expose inline quick-add rows here.

### 2. Dedicated WBS workspace page

Purpose: primary authoring route for broad WBS editing and repeated append flows.

- Route: `ROUTES.PROJECT_WBS(teamId, projectId)`
- Layout owner: new `ProjectWbsPage`
- Surface tone: project-planning workspace, not document hub, not preview card
- Width contract: `max-w-none`
- Primary experience appears immediately after a compact top band

### 3. WBS item dialog

Purpose: full-field editor shared by both the compact tab and the dedicated page.

- Keeps all current create/edit responsibilities
- Adds assignee selection
- Remains the only place where milestone mapping, dates, progress, and estimated M/M are edited together

## Information Architecture

### Navigation Contract

**Entry points**

- Project hub tab rail: `documents / overview / wbs / gantt`
- WBS card header CTA: opens the dedicated workspace route
- Dedicated page back action: returns to the project hub with the `wbs` tab selected

**URL ownership**

- Project hub keeps local tab state for the existing shared workspace page
- Dedicated WBS workspace gets its own route so refresh/deep-link/share flows are stable

**Back-stack behavior**

- Entering the dedicated page from the tab pushes a normal route transition
- Returning from the dedicated page should preserve the current team/project context
- It is acceptable for the hub to reopen on the default tab in v1, but the preferred contract is reopening with `wbs` active if tab state is later URL-backed

## Dedicated Page Layout Contract

### Overall shape

The dedicated page is a page-owned tool surface, not a decorative hero-first page.

Structure:

1. Global `Header`
2. Compact top band
3. Main WBS authoring surface
4. Secondary milestone rail

### Top band

The dedicated page uses a compact operational header, not `ProjectWorkspaceHero`.

Required elements:

- back button to the project hub
- eyebrow: `WBS workspace`
- page title: project name
- one-sentence description focused on authoring work
- optional meta pills for team name and current mode
- right-aligned actions:
  - `Add WBS item` button opens the dialog
  - no duplicate "open workspace" CTA on this page

Why:

- the primary experience is the WBS table itself
- a large display hero would delay access to the tool and make the page read like a preview

### Main grid

Desktop (`xl` and up):

- `grid-cols-[minmax(0,2.4fr)_minmax(320px,1fr)]`
- left: WBS workspace content
- right: milestone panel rail

Tablet / mobile:

- single-column stack
- WBS surface first
- milestone panel after the table

### Surface framing

The main WBS surface should not be a card-inside-card composition.

- The page owns the outer spacing and framing.
- The table surface may keep a single operational border/background shell.
- The milestone rail may remain card-framed because it is a secondary panel.
- The main table must not look like an embedded preview dropped into a decorative card.

## Compact Tab Layout Contract

The compact tab remains the canonical hub entry, but it becomes more review-oriented once the dedicated route exists.

### Header row

Left:

- section title
- section description

Right:

- `Open workspace` outline button
- `Add WBS item` primary button when `canEdit === true`

Behavior:

- `Open workspace` is always visible, including read-only mode
- the CTA sits beside the existing add button instead of replacing it
- on narrow widths the buttons may wrap, but the CTA remains above the fold in the card header

### Compact-tab responsibilities

- browse tree structure
- review assignee / dates / progress / milestone mapping
- reorder items
- open full editor dialog
- jump to the dedicated workspace for repeated authoring

### Compact-tab limitations

- no footer quick-add rows
- no page-level inline append
- no new secondary hero copy beyond the existing project-hub framing

## WBS Table Contract

### Shared columns

Both the compact tab and dedicated page use the same semantic column set:

1. `Item`
2. `Assignee`
3. `Period`
4. `Progress`
5. `Est. M/M`
6. `Milestone`
7. `Actions` when editable

### Width guidance

Suggested fixed widths:

| Column | Width |
|--------|-------|
| Item | 320px |
| Assignee | 180px |
| Period | 240px |
| Progress | 120px |
| Est. M/M | 140px |
| Milestone | 220px |
| Actions | 100px |

This intentionally keeps horizontal scroll behavior in the compact tab. The compact tab is allowed to scroll horizontally rather than collapsing the authoring model into stacked cards.

### Assignee cell rendering

Display contract:

- assigned: rounded bordered pill with assignee name
- unassigned: muted text `Unassigned`
- no avatar requirement in Phase 6.1
- no inline dropdown in the table cell

Cell tone:

- assigned pill uses existing `bg-card` / `border-border` semantics
- unassigned state uses `text-muted-foreground`

### Item cell

Keep the current interaction stack:

- collapse toggle when children exist
- drag handle when editable
- depth marker
- inline name edit

Dedicated workspace may widen the first column slightly, but the semantics stay the same.

## Assignee Editing Contract

### Data source

- source: `fetchMembers(teamId)`
- cache key: `queryKeys.teams.members(teamId)`
- allowed values: current team members only
- persisted field: existing `assigneeUserId`

### Dialog field

The assignee field is added to `WbsItemFormDialog`.

Placement:

- same two-column form region as parent / milestone / dates
- preferred order:
  1. parent
  2. assignee
  3. milestone
  4. start date
  5. end date
  6. progress
  7. estimated M/M

Value contract:

- first option: `Unassigned`
- member options show `name` as the primary label
- `loginId` may appear as muted helper text in the dropdown item

Mode rules:

- create: assignee can be empty or set immediately
- edit: assignee can be changed or cleared
- parent stays non-editable in edit mode, matching the existing dialog contract

Error / loading behavior:

- while member options are loading, assignee select is disabled with loading placeholder
- if member fetch fails, assignee field stays visible but disabled, with inline helper copy
- the dialog must still be usable for non-assignee edits if member fetch fails

## Quick-Add Contract

### Scope

Quick-add exists only on the dedicated WBS workspace page.

It does not appear:

- inside the compact hub tab
- inside the milestone panel
- inside the dialog

### Locations

Two quick-add placements are fixed:

1. root footer row at the bottom of the whole table
2. expanded parent footer row after the last visible descendant of an expanded parent group

The root row is mandatory. Parent-group rows are part of the preferred Phase 6.1 contract and use the same component with different `parentId`.

### Default state

Each quick-add row renders as a subtle inline prompt inside table rhythm:

- plus icon
- placeholder copy:
  - root: `Add item at root level`
  - child: `Add sub-item`
- full-row hit target

It should look like a table affordance, not like a separate floating card.

### Editing state

On activation, the row expands into:

- first cell: text input for `name`
- assignee / period / progress / estimated M/M / milestone columns: muted helper text such as `Set in details`
- action cell:
  - `Add`
  - `Cancel`

Input behavior:

- `Enter` submits
- `Escape` cancels and returns to the collapsed prompt state
- empty submit is blocked
- pointer and keyboard activation are equivalent

### Submission behavior

Payload:

- `name`
- implicit `parentId`
- no assignee, milestone, dates, or estimated M/M in quick-add payload
- `progressRate` is pinned to the explicit default `0` for deterministic create semantics

After success:

- new item appears at the bottom of the relevant hierarchy
- success toast appears
- new row gets a brief highlight treatment
- input remains open and focused for the same hierarchy so repeated append is fast

After failure:

- keep the typed name in place
- show inline error or toast
- do not close the row automatically

### Focus contract

Keyboard flow is part of the phase goal.

- tabbing into the prompt activates it cleanly
- after create, focus returns to the same quick-add input
- if a new child is created under a collapsed parent from any other path, that parent auto-expands before focus/highlight logic runs

## Dialog vs. Inline Boundary

This phase keeps a strict responsibility split:

### Quick-add owns

- fast append at the current hierarchy
- name-only creation
- repeated keyboard-first capture

### Dialog owns

- assignee selection
- milestone mapping
- date fields
- progress editing
- estimated M/M editing
- full create/edit confirmation

### Table owns

- tree navigation
- reorder
- lightweight inline edits already proven stable (`name`, `progress`)
- assignee visibility

This split is deliberate. It reduces interaction collision between DnD, dropdowns, and inline creation while still unblocking the user request.

## Copywriting Contract

New or revised copy should stay short and operational.

### Required keys

- `wbs.workspace.title`
- `wbs.workspace.description`
- `wbs.workspace.open`
- `wbs.workspace.backToProject`
- `wbs.field.assignee`
- `wbs.field.unassigned`
- `wbs.form.assignee`
- `wbs.form.assigneePlaceholder`
- `wbs.form.unassigned`
- `wbs.quickAdd.root`
- `wbs.quickAdd.child`
- `wbs.quickAdd.add`
- `wbs.quickAdd.cancel`
- `wbs.quickAdd.setLater`

### Copy intent

- CTA says where the user is going, not how the UI is built
- unassigned copy reads as current state, not as an error
- quick-add helper text reminds the user that details can be completed later in the dialog

## Responsive Contract

### Compact tab

- horizontal scroll remains acceptable for the table
- CTA and create button wrap within the header without overlap
- milestone panel stacks below the table on narrow widths

### Dedicated page

- no `max-w-5xl` clamp
- top band compresses before the table
- WBS surface appears in the first viewport on both desktop and mobile
- quick-add rows remain part of the table flow and never become floating bottom bars

### Mobile caution

Do not attempt to convert the WBS table into cards in Phase 6.1. Card conversion would break tree scanning, DnD mental model, and shared row semantics.

## Accessibility Contract

- all CTA buttons have explicit text labels
- quick-add prompt is keyboard reachable and announces hierarchy context
- assignee select has proper `<Label htmlFor>` wiring
- unassigned state is conveyed as text, not color alone
- action icon buttons keep item-specific `aria-label`
- inline quick-add validation must surface text feedback, not placeholder-only failure

This UI contract is considered complete for Phase 6.1 when the following are true:

1. The compact hub tab still exists and exposes a visible `Open workspace` CTA.
