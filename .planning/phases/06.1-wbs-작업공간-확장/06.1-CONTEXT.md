# Phase 6.1 Context: WBS 작업공간 확장

## Domain Boundary

Phase 5/6에서 WBS 도메인, 마일스톤, 간트 시각화까지는 확보됐지만 현재 WBS authoring surface는 `DiagramsPage` 안의 compact tab에 머물러 있다. 이 phase는 현재 WBS 탭을 유지한 채 더 넓은 전용 WBS 작업공간을 추가하고, 하단 inline append와 assignee 입력 UX를 닫는다.

이 phase는 **WBS 입력/편집 UX 확장**만 다룬다. 인력 등급, 단가, 계획/실적 비교, 비용 집계 같은 resource/MM 계산은 여전히 Phase 7 소관이다.

- **WBS-02**: 각 WBS 항목에 담당자, 시작일, 종료일, 진척률을 설정할 수 있다
- **WBS-06**: 프로젝트 허브의 WBS 탭에서 더 넓은 전용 WBS 작업공간으로 이동할 수 있다

## Prior Decisions

- 현재 `wbs` 탭은 프로젝트 허브 안의 canonical entry로 유지한다
- gantt는 별도 `gantt` 탭에서 폭 제한을 풀었고, WBS는 여전히 `max-w-5xl` 안의 compact table에 머물러 있다
- assignee membership validation은 이미 백엔드 `WbsService.resolveAssignee()`에서 처리한다
- WBS 생성은 `parentId` 기준 append와 `findNextSortOrder()`로 하단 삽입 semantics를 이미 갖고 있다

## Decisions

### 1. 현재 WBS 탭은 유지하고 전용 route를 추가한다

**결정:** `DiagramsPage`의 `wbs` 탭은 compact summary/workbench entry로 유지하고, 더 넓은 전용 페이지를 별도 route로 연다.

- 예시 route: `/teams/:teamId/projects/:projectId/wbs`
- 진입점은 WBS 탭 header CTA 또는 섹션 CTA로 둔다

**Why**

- 사용자 요청이 "현재 화면은 유지하되 링크로 더 크게 보는 페이지"에 가깝다
- 프로젝트 허브 탭 안에 full-width authoring editor까지 밀어 넣으면 `DiagramsPage`가 지나치게 무거워진다
- gantt와 달리 WBS는 tree CRUD, inline add, assignee edit까지 포함해 화면 책임이 더 크다

### 2. assignee는 신규 API 없이 기존 WBS/팀 멤버 계약을 재사용한다

**결정:** DB/Flyway/백엔드 endpoint는 추가하지 않고, 기존 `WbsController` + `WbsService` 계약과 `fetchMembers(teamId)`를 그대로 사용한다.

- dialog/select 옵션은 `queryKeys.teams.members(teamId)`로 캐시한다
- update/create payload는 이미 존재하는 `assigneeUserId`를 채운다

**Why**

- payload, response, membership validation이 모두 이미 구현돼 있다
- 이번 변경의 병목은 데이터 모델이 아니라 FE authoring surface다

### 3. inline append는 전용 작업공간에서만 제공한다

**결정:** Notion-like 하단 추가 row는 전용 WBS 작업공간에만 넣고, 기존 popup dialog는 그대로 유지한다.

- compact 탭은 기존 dialog 중심 UX를 유지한다
- 전용 작업공간은 root/footer 및 expanded parent 하단에 quick-add row를 둔다
- quick-add row는 최소 필드(`name`, `parentId`)만 받아 append 생성하고, 상세 수정은 dialog로 이어간다

**Why**

- 요청사항의 핵심은 "팝업은 유지 + 신규 WBS 화면에서 하단 추가"
- quick-add와 full-field dialog를 분리하면 mutation/state 복잡도가 크게 늘지 않는다
- 서버의 `findNextSortOrder()`가 이미 하단 삽입 semantics를 보장한다

### 4. assignee는 dialog에서 완성하고 목록에는 column으로 드러낸다

**결정:** assignee 편집은 우선 `WbsItemFormDialog`에 team member select를 넣어 닫고, 목록은 assignee column을 추가해 현재 배정 상태를 항상 노출한다.

- compact 탭과 전용 작업공간 모두 assignee column을 표시한다
- Phase 6.1 범위에서 assignee inline cell editor는 필수가 아니다

**Why**

- 가장 작은 변경으로 WBS-02를 닫을 수 있다
- 현재 row component는 inline name/progress만 안정화돼 있어, select/dropdown까지 한 번에 넣으면 DnD와 충돌할 가능성이 높다

### 5. Phase 7은 Phase 6.1 이후로 미룬다

**결정:** 인력 투입(M/M) phase는 inserted Phase 6.1 이후에 시작한다.

**Why**

- Phase 7은 사람 기준 집계/비용 계산이 핵심인데, 그 전에 WBS owner attribution이 안정적으로 입력돼야 한다
- 좁은 WBS 화면에서 assignee 입력이 빠진 상태로 M/M을 얹으면 실제 운영 데이터가 부정확해질 가능성이 높다

## Specifics

- 전용 page는 `gantt`와 마찬가지로 `max-w-none`을 허용하지만, decorative card 안에 전체 editor를 넣지 않는다
- WBS list의 공통 로직은 `WbsTab`에서 page/tab 공용 컴포넌트로 추출하는 쪽이 안전하다
- quick-add row 생성 직후에는 새 item을 optimistic highlight하거나 dialog open으로 이어주는 두 옵션이 있으며, 1차는 생성 성공 toast + row focus 정도면 충분하다
- assignee option label은 `TeamMember.name` 기준으로 표시하고, 필요 시 `loginId`를 보조 텍스트로 붙인다
- existing popup create/edit flow는 남겨서 milestone, dates, progress, estimatedMm 편집을 한 곳에서 유지한다

## Deferred Ideas

- assignee inline cell editor
- slash command / keyboard-only block insertion
- 팀 멤버가 많은 경우 combobox 검색/virtualization
- WBS workspace와 gantt split-view 동시 배치

## Open Risks

- DnD row와 inline quick-add row가 섞일 때 sensor/keyboard focus가 꼬일 수 있다
- 공용 table abstraction 없이 page/tab을 각각 확장하면 WBS mutation 로직이 중복될 수 있다
- assignee column 추가로 compact tab 폭 압박이 더 커질 수 있어, compact tab은 read-heavy surface로 다듬어야 한다
