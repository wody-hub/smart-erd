## WBS 진입 구조

| Option | Description | Selected |
|--------|-------------|----------|
| 현재 `wbs` 탭을 전용 page로 대체 | 프로젝트 허브에서는 WBS를 제거하고 전용 route만 남긴다 | |
| 현재 `wbs` 탭 유지 + 전용 page 추가 | 허브 탭은 compact entry로 남기고 더 넓은 authoring surface는 별도 route로 연다 | ✓ |
| `gantt`와 합쳐 split view로 이동 | WBS/Gantt를 한 화면에서 함께 편집한다 | |

**Decision:** 현재 `wbs` 탭은 canonical entry로 유지하고, `/teams/:teamId/projects/:projectId/wbs` 전용 route를 추가한다.

**Why**

- 현재 사용자 요구는 "지금 화면은 유지하되 더 크게 보는 공간 추가"에 가깝다.
- 허브 탭 안에 full authoring editor를 직접 확장하면 `DiagramsPage` 책임이 과도하게 커진다.
- WBS는 tree CRUD, assignee edit, quick-add까지 포함되어 gantt보다 authoring surface 책임이 크다.

## popup/dialog 유지 범위

| Option | Description | Selected |
|--------|-------------|----------|
| dialog 제거 후 inline-only 전환 | 생성/수정을 모두 표 안에서 처리한다 | |
| dialog 유지 + quick-add만 추가 | 상세 편집은 dialog에 두고, dedicated workspace에서만 최소 생성 row를 추가한다 | ✓ |
| 기존 dialog만 유지 | 새 inline append는 추가하지 않는다 | |

**Decision:** popup dialog는 유지하고, dedicated workspace에서만 최소 필드 quick-add를 추가한다.

**Why**

- 요구사항 핵심은 "팝업은 유지 + 신규 WBS 화면에서 하단 추가"다.
- milestone/date/progress/estimatedMm는 기존 dialog가 이미 책임을 갖고 있어 회귀 위험이 낮다.
- `findNextSortOrder()` 기반 append semantics를 그대로 활용할 수 있다.

## inline append 범위

| Option | Description | Selected |
|--------|-------------|----------|
| compact 탭과 dedicated page 둘 다 quick-add 제공 | 모든 진입면에서 동일하게 하단 append 제공 | |
| dedicated page에만 quick-add 제공 | compact 탭은 read-heavy/dialog 중심으로 유지한다 | ✓ |
| root level에만 quick-add 제공 | 하위 계층 append는 여전히 dialog에서만 처리한다 | |

**Decision:** quick-add는 dedicated page에만 두고, 1차 범위는 root/footer 중심 append semantics를 우선으로 잡는다.

**Why**

- compact 탭은 이미 폭 제약(`min-w-[1080px]`)이 있고 assignee column까지 들어오면 더 압박된다.
- 새 입력 surface는 넓은 페이지에서 먼저 안정화하는 편이 안전하다.
- 서버 append semantics는 이미 있으므로 FE surface만 제한적으로 열면 된다.

## assignee UX 마감선

| Option | Description | Selected |
|--------|-------------|----------|
| inline cell editor까지 포함 | row에서 바로 담당자를 바꿀 수 있게 한다 | |
| dialog select + 목록 column 노출 | 생성/수정 dialog에서 담당자를 선택하고, 목록에는 배정 상태를 항상 노출한다 | ✓ |
| 목록 column만 노출 | 표시만 하고 편집은 후속 phase로 미룬다 | |

**Decision:** assignee는 `WbsItemFormDialog`에서 팀 멤버 select로 편집하고, WBS 목록에는 assignee column을 추가한다.

**Why**

- `assigneeUserId` payload와 서버 validation은 이미 있으므로 FE wiring만 닫으면 된다.
- 현재 row surface는 inline name/progress 편집만 안정화돼 있어 dropdown editor까지 함께 넣으면 DnD 충돌 위험이 커진다.
- 이 범위면 WBS-02를 신규 API 없이 닫을 수 있다.

## route/data 계약

| Option | Description | Selected |
|--------|-------------|----------|
| 신규 API/DB 추가 | dedicated workspace용 별도 endpoint를 만든다 | |
| 기존 WBS/팀 멤버 계약 재사용 | `createWbsItem`, `updateWbsItem`, `fetchMembers(teamId)`를 그대로 쓴다 | ✓ |
| assignee만 임시 mock 처리 | UI만 먼저 만들고 실제 저장은 후속 phase로 미룬다 | |

**Decision:** 신규 API/DB 변경 없이 기존 WBS + 팀 멤버 계약을 재사용한다.

**Why**

- `assigneeUserId`, `assigneeName`, membership validation이 이미 구현돼 있다.
- 이번 phase 병목은 data model이 아니라 authoring surface다.
