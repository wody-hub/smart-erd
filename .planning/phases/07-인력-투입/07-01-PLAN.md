<calculation_contract>

Backend calculation rules to implement exactly:

1. Treat planned period as required: `plannedStartDate`, `plannedEndDate`, `plannedParticipationRate`.
2. Treat actual period as optional but atomic: either all actual fields are blank, or `actualStartDate`, `actualEndDate`, `actualParticipationRate` are all present.
3. Participation rates are integers from 0 through 100 inclusive.
4. Monthly rate is a non-negative KRW integer. `0` is valid for no-charge or internal staffing rows.
5. For each overlapped calendar month, compute raw M/M contribution as `(overlapDays / daysInMonth) * participationRate / 100`.
6. Sum raw monthly contributions, then round total M/M with `RoundingMode.HALF_UP` to scale 2.
7. Round each monthly allocation value with `RoundingMode.HALF_UP` to scale 2 for display.
8. Calculate cost as `roundedTotalMm * monthlyRate`, rounded `HALF_UP` to a KRW integer.
9. Planned and actual calculations are independent.
10. Row-level actual M/M, actual cost, and delta are `null` until actual fields are complete.
11. Summary actual totals treat missing row actuals as zero, so an empty-actual project can show `0.00` actual M/M and `0` actual cost.
12. Summary delta is `actualTotalMm - plannedTotalMm`, rounded to scale 2.

Required deterministic test cases:

- Full single month at 100%: `2026-04-01` to `2026-04-30`, 100%, rate `10000000` -> M/M `1.00`, cost `10000000`
- Half participation full month: same period, 50%, rate `10000000` -> M/M `0.50`, cost `5000000`
- Partial month: `2026-04-16` to `2026-04-30`, 100%, 30-day month -> raw `15/30`, M/M `0.50`
- Cross-month: `2026-04-16` to `2026-05-15`, 100% -> April raw `15/30`, May raw `15/31`, total `0.98`
- Leap-year February: `2028-02-01` to `2028-02-29`, 100% -> M/M `1.00`
- Rounding HALF_UP: use a date/participation combination with a third decimal `5` and assert scale 2 behavior
- Blank actual: actual total fields on row are null, summary actual contributes zero

</calculation_contract>

<risks>

| Risk | Impact | Mitigation |
|------|--------|------------|
| M/M rounding mismatch between row totals, monthly cells, cost, and summary | Users cannot reconcile cost totals | Backend owns all calculation; tests lock raw monthly sum, rounded total, and cost based on rounded total |
| Concurrent duplicate staffing create bypasses service pre-check | API can return a generic 500 or leave confusing duplicate state | Keep DB unique constraint, catch unique-constraint `DataIntegrityViolationException`, map to `ERROR_DUPLICATE_PROJECT_STAFFING_MEMBER`, and test the race path |
| Duplicate staffing policy blocks legitimate split intervals | Some real projects need split staffing | Phase 7 explicitly chooses one row per member; record split intervals as deferred capacity/cost-management work |
| Team membership changes after staffing row creation | Historical rows may reference users no longer active in team | Validate current membership on create; current code has no inactive state, so removed members are missing membership rows; keep existing staffing rows visible as project contract snapshots |
| Matrix becomes unreadable or heavy for long projects | HR-03 comparison fails for 24+ month projects or large teams | Preserve table semantics with local horizontal scroll, sticky identity, fixed widths, 12-month windowing when months exceed 18, and generated 100-row/36-month verification |
| Frontend accidentally recalculates M/M | Backend/frontend drift | Frontend types expose calculated fields and UI displays them; no M/M formula helper in client |
| WBS assignee semantics drift into staffing totals | Wrong source of truth for labor cost | Plan and UI copy keep WBS assignee as reference only; no auto-create or sync code paths |

</risks>
