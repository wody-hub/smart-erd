# 다이어그램 초기 로딩 성능 개선 분석

작성일: 2026-03-10 13:45

## 배경

다이어그램 진입 시 캔버스에 그래프가 표시되기까지 시간이 오래 걸린다.
이전에 이 문제를 해결하려다 sync-stage 상태머신 복잡화로 실시간 동기화 장애가 발생했다
(→ `2026-03-10-1345(종료)-실시간-동기화-오류-원인-분석(by_codex).md` 참고).
해당 변경은 전량 revert 완료 (`680f70b`).

이번 문서는 장애 없이 초기 로딩을 개선하기 위한 근본 원인 분석이다.

## 현재 로딩 시퀀스

```
사용자 진입
  │
  ├─ [1] GET /api/diagrams/{id}  ─────────── ~500ms
  │     └─ flushDiagramSnapshotNow() 동기 실행 포함
  │     └─ 응답: { content(JSON), hasYdocSnapshot: true }
  │
  ├─ [2] Y.Doc 생성 (빈 상태)
  │     └─ hasYdocSnapshot=true → JSON 마이그레이션 스킵 ★ 병목 핵심
  │
  ├─ [3] initYDoc(빈 ydoc) → Zustand에 빈 nodes/edges
  │     └─ 캔버스: 아무것도 안 보임 (오버레이 표시)
  │
  ├─ [4] WS 연결 시작  ───────────────────── ~300ms
  │     └─ ticket 발급 (HTTP) → WebSocket 핸드셰이크
  │
  ├─ [5] SNAPSHOT_REQUEST 전송
  │     └─ 서버: DB 로드 + 디코딩 + N개 전송 ── ~500-1000ms
  │
  ├─ [6] SNAPSHOT_RESPONSE 수신 × N회
  │     └─ Y.applyUpdate × N → observeDeep → 변환 ── ~200-500ms
  │
  └─ [7] 캔버스에 드디어 그래프 표시  ────── 총 1.5~3초+
```

### 핵심 병목: `hasYdocSnapshot=true`일 때 JSON content를 버림

`useYjsCollaboration.ts:65`:
```typescript
if (diagram.content && !diagram.hasYdocSnapshot) {
  migrateJsonToYDoc(ydoc, diagram.content);  // ← hasYdocSnapshot=false일 때만 실행
}
```

API 응답에 **JSON content가 이미 포함**되어 있는데, `hasYdocSnapshot=true`이면 이걸 무시하고
**빈 Y.Doc으로 시작**한다. WS 스냅샷이 도착할 때까지 1~3초를 빈 캔버스로 대기.

5초 내 WS 스냅샷이 안 오면 그제서야 JSON 폴백 발동:
```typescript
// useYjsCollaboration.ts:116-128
if (diagram.hasYdocSnapshot && diagram.content) {
  snapshotFallbackTimer = setTimeout(() => {
    if (getTablesMap(ydoc).size === 0) {
      ydoc.transact(() => migrateJsonToYDoc(ydoc, diagram.content!), 'remote');
    }
  }, 5_000);  // ← 최악 5초 대기
}
```

## 병목 상세

### 병목 1: `flushDiagramSnapshotNow()` — API 응답 지연 (~250-600ms)

**위치:** `DiagramService.java:140`

`getDiagram()` 호출 직전에 인메모리 누적 update를 DB에 동기 flush한다.
매 요청(새로고침/다이어그램 전환)마다 반복.

### 병목 2: WS 연결 + ticket 발급 (~300ms)

**위치:** `YjsProvider.ts:186-270`

ticket HTTP 요청 → WS 핸드셰이크, 2-3번의 네트워크 왕복.

### 병목 3: 서버 스냅샷 DB 로드 + 다중 전송 (~500-1000ms)

**위치:** `SnapshotRequestMessageHandler.java:49-68`

- DB에서 스냅샷 바이트 로드 (TEXT 컬럼)
- `YjsUpdateFormat.decode()`: length-prefixed 디코딩
- **N개 update를 각각 BinaryMessage로 전송** → N번 네트워크 I/O

### 병목 4: 클라이언트 Y.Doc 적용 + 변환 (~200-500ms)

**위치:** `YjsProvider.ts:310-318`, `yjsBridge.ts:48-91`

- 각 SNAPSHOT_RESPONSE마다 `Y.applyUpdate()` 호출
- `observeDeep` 콜백이 매번 전체 Y.Map 순회 (O(테이블 수 × 컬럼 수))

## 이상적인 흐름

> "초기에 API 응답(JSON)으로 캔버스를 즉시 그리고, 뒷단에서 Y.Doc이 연동되면 최신 상태로 교체"

```
사용자 진입
  │
  ├─ [1] API 응답 (content JSON)  ───── ~500ms
  │
  ├─ [2] JSON → Zustand에 즉시 반영 ────── ~30ms
  │     └─ 캔버스에 바로 그래프 표시 ✅ (읽기 전용 preview)
  │
  ├─ [3] WS 연결 + Y.Doc 스냅샷 (백그라운드) ── 병렬 진행
  │     └─ 스냅샷 수신 완료 → Y.Doc에 적용
  │     └─ Y.Doc observeDeep → Zustand 교체 (최신 상태)
  │     └─ 편집 모드 활성화
  │
  └─ 사용자는 ~500ms만에 그래프를 볼 수 있음
```

## 해결 방향 후보

### 방향 A: API preview → Y.Doc 교체 (프론트 주도) ★ 권장

API JSON을 **Y.Doc이 아닌 Zustand에 직접** 넣어 preview를 표시한다.
Y.Doc과 preview가 독립적이므로 CRDT 충돌 위험이 없다.

| 장점 | 단점 |
|------|------|
| CRDT 충돌 없음 (Y.Doc을 건드리지 않음) | preview 중 편집 불가 (읽기 전용) |
| 프론트엔드만 수정 | preview → live 전환 시 노드 위치 점프 가능 |
| 기존 WS 흐름 변경 불필요 | Zustand에 "preview 모드" 개념 추가 필요 |

**구현 개요:**
1. `useCanvasStore`에 `loadPreview(json)` 액션 추가 (Y.Doc 미경유)
2. `useYjsCollaboration`에서 `hasYdocSnapshot=true`여도 `loadPreview()` 호출
3. WS 스냅샷 도착 → `initYDoc(ydoc)` → observeDeep가 Zustand 교체
4. preview 중 편집 잠금 (canEdit=false 또는 별도 플래그)

### 방향 B: 서버가 API 응답에 Y.Doc 바이트 포함 (서버 주도)

`GET /api/diagrams/{id}` 응답에 base64 인코딩된 Y.Doc 스냅샷을 포함한다.
클라이언트가 즉시 `Y.applyUpdate()`로 적용 → WS는 이후 diff만 동기화.

| 장점 | 단점 |
|------|------|
| 단일 HTTP로 전체 상태 로드 | API 응답 크기 증가 (대규모 시 수 MB) |
| WS 스냅샷 요청 불필요 | 서버 변경 필요 (직렬화 + 인코딩) |
| 즉시 편집 가능 (CRDT 정합) | `flushDiagramSnapshotNow()` 여전히 필요 |

## 이전 장애와의 관계

이전 시도 (`5d5915b`, `f3a1192`)에서 방향 A를 **Y.Doc 내부에서** 처리하려 했다:
- `replaceJsonInYDoc()`: Y.Doc을 직접 교체 → CRDT clock 충돌
- `pushFullDocumentUpdate()`: 전체 상태를 WS로 재전송 → snapshot 버퍼 미갱신
- `'remote'` origin 트랜잭션: 서버에 전송되지 않아 동기화 단절

**교훈:** JSON preview는 Y.Doc과 완전히 분리된 경로(Zustand 직접 주입)로 처리해야 한다.
