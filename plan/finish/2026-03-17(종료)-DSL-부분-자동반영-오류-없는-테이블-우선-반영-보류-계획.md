# DSL 부분 자동반영 보류 계획

작성일: 2026-03-17  
상태: 종료, 보류 종료

중요 메모:
- 이 문서는 종료된 보류 계획 문서다.
- 현재는 활성 작업 목록에서 제외한다.
- 다시 검토가 필요하면 새 계획 문서로 재개한다.

## 배경

현재 `다이어그램 - 코드` 자동반영은 DSL 문서 전체에 에러가 하나라도 있으면 중단된다.

원하는 방향은 다음과 같다.

- 여러 테이블을 동시에 수정하는 중에도
- 에러가 없는 테이블은 ERD에 자동반영하고
- 에러가 있는 테이블만 반영에서 제외한다

다만 이 기능은 단순히 `에러 있는 라인만 무시`하는 수준이 아니라, 기존 ERD 상태와 부분 파싱 결과를 안전하게 merge해야 한다.

## 현재 상태 정리

### 1. 자동반영 차단 기준

- DSL 자동반영은 현재 `errorCount > 0`이면 전체를 막는다.
- 즉 기준은 `문서 전체 무오류`다.

### 2. 파서의 실제 능력

- DSL 파서는 에러가 있어도 `tables`, `relations`, `tableRanges`, `diagnostics`를 함께 반환한다.
- 따라서 “오류 없는 테이블 후보를 추출”하는 것 자체는 이론상 가능하다.

### 3. 수동 Apply와 자동반영의 차이

- 자동반영은 전체 에러 기준으로 막히지만
- 수동 Apply는 테이블 결과가 남아 있으면 부분 결과를 반영할 수 있다.
- 즉 현재도 “부분 파싱 결과”는 존재하지만, auto-apply 경로가 이를 사용하지 않는다.

## 왜 지금 바로 하지 않는가

이 기능은 생각보다 위험하다.

### 1. 잘못 구현하면 테이블이 삭제될 수 있다

- 에러 있는 테이블을 `nextTables`에서 빼고 diff를 돌리면
- diff 입장에서는 그 테이블이 “삭제된 것”처럼 보인다
- 결과적으로 기존 ERD의 정상 테이블/관계가 의도치 않게 사라질 수 있다

### 2. “오류 있는 테이블 유지”가 별도 문제다

- 부분 자동반영을 하려면
  - 오류 없는 테이블은 새 코드 기준으로 반영하고
  - 오류 있는 테이블은 현재 ERD 상태를 그대로 보존해야 한다
- 즉 `parsed result`와 `current ERD snapshot`을 섞는 merge 정책이 필요하다

### 3. FK 관계 처리 규칙이 따로 필요하다

- 반영 대상 테이블과 비반영 대상 테이블 사이의 관계를 어떻게 다룰지 결정해야 한다
- 가장 보수적인 정책은 “양쪽 테이블 모두 clean일 때만 relation 갱신”이다
- 그러나 이 경우에도 기존 relation 유지/삭제 정책을 명확히 해야 한다

### 4. 테이블 매칭 안정성이 필요하다

- 헤더 문법이 깨지거나 테이블 선언 자체가 부분적으로 깨진 경우
- 어떤 기존 ERD 테이블을 보존해야 하는지 안정적으로 식별해야 한다
- 현재 구조에서는 이 매칭이 완전히 공짜가 아니다

## 나중에 진행한다면 필요한 설계

### P1. clean table 판정

- `diagnostics`와 `tableRanges`를 연결해
- 어떤 테이블 블록이 에러를 포함하는지 판정한다

권장 규칙:
- warning은 clean으로 본다
- error만 dirty로 본다
- 테이블 범위 밖의 전역 에러는 전체 자동반영을 막는다

### P2. current ERD 보존 merge

- clean table은 새 parsed table로 교체
- dirty table은 현재 ERD snapshot을 그대로 유지
- diff 입력은 “clean parsed tables + preserved current tables”로 재구성한다

### P3. relation merge 정책

권장 1차 정책:
- 양쪽 endpoint table이 모두 clean일 때만 relation 재계산
- dirty table이 하나라도 걸린 relation은 현재 ERD relation을 유지

### P4. auto-apply gate 재설계

- 현재의 `errorCount > 0` 전역 차단을 바로 없애지 않는다
- 아래 조건을 모두 만족할 때만 부분 자동반영 허용
  - 전역 문법 붕괴가 아님
  - clean table을 안정적으로 식별 가능
  - preserved current tables를 merge할 수 있음

### P5. 관찰/롤백 장치

- 초기 rollout은 feature flag 또는 local override 뒤에 둔다
- 자동반영 결과 로그를 남기고, fallback 경로를 명확히 둔다

## 권장 접근 순서

1. 구현 전 `partial apply merge policy` 문서 확정
2. 파싱 결과에서 clean/dirty table 판정용 helper 추가
3. current ERD 보존 merge spike
4. relation 보존 정책 검증
5. feature flag 뒤에서 제한 rollout

## 결론

이 기능은 **가능은 하지만, 현재 구조에서 안전하게 넣으려면 별도 설계 작업이 먼저 필요한 주제**다.

따라서 지금은:
- 자동반영은 기존 정책 유지
- 필요 시 수동 Apply 사용
- 본 문서는 미래 작업 후보로만 보존

다시 말해, **사용자 지시가 있기 전까지는 이 계획을 실행하지 않는다.**
