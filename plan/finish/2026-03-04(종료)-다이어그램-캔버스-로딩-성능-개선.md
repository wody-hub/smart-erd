# 다이어그램 캔버스 로딩 성능 개선 계획

## 현상

다이어그램 페이지 진입 시 캔버스에 테이블 노드가 표시되기까지 체감 1.8s ~ 6.8s 소요.

## 원인 분석

총 지연은 3개 계층의 직렬 처리가 누적된 결과이다.

```
[1] fetchDiagram API (800ms-1.3s)
    ├─ verifyReadAccess: User + Team + Project 조회       ~50ms
    ├─ findDiagramByProjectAndId + @EntityGraph            ~50ms
    ├─ flushDiagramSnapshotNow (동기 블로킹)              ~500ms-1s  ⚠️
    └─ existsYdocSnapshotById (별도 쿼리)                  ~30ms

[2] Yjs 초기화 + WS 연결 (200ms-500ms)
    ├─ Y.Doc 생성 + initYDoc                               ~20ms
    ├─ WS 티켓 발급 API                                    ~100ms
    └─ WebSocket 핸드셰이크                                ~200ms

[3] WS 스냅샷 폴백 타이머 (최대 5000ms)                    ⚠️⚠️
    └─ hasYdocSnapshot=true일 때 SNAPSHOT_REQUEST 대기
       → 5초 내 미수신 시 JSON content로 폴백
```

### 병목 1: `flushDiagramSnapshotNow` 동기 블로킹 (500ms-1s)

```java
// DiagramService.java:136-143
public DiagramDetailResponse getDiagram(...) {
    final var project = verifyReadAccess(loginId, teamId, projectId);
    final var diagram = findDiagramByProjectAndId(project, diagramId);
    diagramSnapshotService.flushDiagramS  napshotNow(diagram.getId());  // ⚠️
    final var hasSnapshot = diagramRepository.existsYdocSnapshotById(diagramId);
    return DiagramDetailResponse.from(diagram, project.getId(), hasSnapshot);
}
```

`flushDiagramSnapshotNow()`는 인메모리 Yjs update를 DB에 동기적으로 병합/저장한다:
1. `synchronized(flushLock)` 락 획득
2. `drainAndMergeUpdates()` — 인메모리 update 병합
3. `combineSnapshotAndUpdates()` — 기존 스냅샷 + 신규 update 결합
4. `updateYdocSnapshotById()` — DB UPDATE 실행

### 병목 2: WS 스냅샷 5초 폴백 (최대 5s)

```typescript
// useYjsCollaboration.ts
const WS_SNAPSHOT_FALLBACK_MS = 5_000;

if (diagram.hasYdocSnapshot && diagram.content) {
  snapshotFallbackTimer = setTimeout(() => {
    if (getTablesMap(ydoc).size === 0) {
      ydoc.transact(() => migrateJsonToYDoc(ydoc, diagram.content!), 'remote');
    }
  }, WS_SNAPSHOT_FALLBACK_MS);  // 5초 대기
}
```

`hasYdocSnapshot=true`이면 WS 서버에 SNAPSHOT_REQUEST를 보내고 응답을 기다린다.
WS 서버가 응답하지 않으면(연결 실패, 서버 부하 등) 5초 후에야 JSON content로 폴백한다.

### 부수 병목: existsYdocSnapshotById 별도 쿼리

`findDiagramByProjectAndId`로 이미 Diagram을 로딩한 뒤,
`existsYdocSnapshotById`로 다시 diagram 테이블을 조회한다.
ydocSnapshot BYTEA 컬럼을 SELECT하여 null 여부를 확인하는 방식.

## 개선안

### 우선순위 0: API 선렌더 + Yjs authoritative handoff (신규)

**목표:** 최초 진입 시 API 응답만으로 즉시 캔버스를 렌더하고, Yjs 스냅샷/업데이트 수신 시점에만 실시간 상태로 전환한다.

**핵심 원칙:**
- `hasYdocSnapshot=true` 경로에서는 API JSON을 Y.Doc에 즉시 주입하지 않는다. (CRDT 충돌/역전 위험 방지)
- API JSON은 "초기 화면 표시용(preview)"으로만 사용한다.
- `syncStage === 'yjs-live'` 전에는 편집을 **완전 차단**한다. (읽기/탐색만 허용)

**상태 전이:**

```
boot ──(useQuery)──┬──(content 파싱 성공)──→ [api-preview] ──┬──(WS 스냅샷 + 리비전 통과)──→ [yjs-live]
                   │                                        ├──(SYNC_STEP2, 레거시)──────────→ [yjs-live]
                   │                                        └──(2초 타임아웃)──────────────────────┐
                   │                                                                              │
                   └──(content=null/손상)──→ [api-preview-empty] ──┬──(SYNC_STEP2 수신)──→ [yjs-live]   │
                                                                   └──(2초 타임아웃)──┐    ▲            │
                                                                                     │    │            │
                                                                                     ▼    │(재시도 성공)│
                                                                [yjs-timeout-degraded] ◄──┘ ◄──────────┘
                                                                          │
                                                                    (자동 재시도 3회 소진)
                                                                          ▼
                                                                 [yjs-failed-readonly]
                                                                          │
                                                                    (수동 "다시 시도")
                                                                          ▼
                                                                 [yjs-timeout-degraded] (카운터 초기화)
```

- `boot` → `api-preview`: `useQuery` 성공 + `diagram.content !== null` (content 파싱 성공 시점)
- `boot` → `api-preview-empty`: `diagram.content` 파싱 실패 시(손상 JSON) 빈 캔버스로 안전 강등 후 sync-only handoff를 시도한다.
- `boot` → `api-preview-empty`: `content=null` (신규 다이어그램 또는 비정상 조합)에서도 WS sync 확정 전까지는 읽기전용으로 대기한다.
  - `content=null && hasYdocSnapshot=true`는 비정상 조합으로 간주하지만, 동일하게 `api-preview-empty` 경로로 처리한다.
- `api-preview-empty` → `yjs-live`: WS 연결 + 초기 sync ack(`SYNC_STEP2` 수신) 확인 시
- `api-preview-empty` → `yjs-timeout-degraded`: 2초 내 `SYNC_STEP2` 미수신 시 (이후 재시도 시에도 `SYNC_STEP2` 대기 — `SNAPSHOT_REQUEST` 아님)
- `api-preview` → `yjs-live` (**2가지 서브경로**):
  - `hasYdocSnapshot=true`: WS `SNAPSHOT_RESPONSE` 수신 + 리비전 검증(`wsSnapshotRevision >= contentRevision`) 통과 시
  - `hasYdocSnapshot=false` (레거시/NON_YJS_UPDATE 후): `snapshotRevision=null`이므로 리비전 검증 스킵. WS `SYNC_STEP2` 수신 확인 후 JSON→Y.Doc 마이그레이션 실행 → 전환. (마이그레이션은 기존 가드 `getTablesMap(ydoc).size === 0` 조건을 유지하여, 이미 peer 데이터가 있는 Y.Doc에는 중복 주입하지 않는다)
- `api-preview` → `yjs-timeout-degraded`: 2초 내 WS 응답 미수신 시 (hasYdocSnapshot=true: `SNAPSHOT_RESPONSE` 미수신 / hasYdocSnapshot=false: `SYNC_STEP2` 미수신)
- `yjs-timeout-degraded` → `yjs-live`: 재시도 성공 시 (snapshot 모드: 스냅샷 수신 + 리비전 검증 통과 / sync-only 모드: `SYNC_STEP2` 수신)
- `yjs-timeout-degraded` → `yjs-failed-readonly`: 자동 재시도 3회 소진 시
- `yjs-failed-readonly` → `yjs-timeout-degraded`: 사용자 수동 "다시 시도" 클릭 시 (카운터 초기화)

**SyncStage 타입 (TS 컨벤션: kebab-case 리터럴 유니온):**
```typescript
type SyncStage =
  | 'boot'
  | 'api-preview'
  | 'api-preview-empty'
  | 'yjs-live'
  | 'yjs-timeout-degraded'
  | 'yjs-failed-readonly';
```

**서버 필드 계약 (필수 추가):**
- REST `GET /diagram/{id}` 응답에 아래 필드를 추가한다.
  - `contentRevision: string` — API `content`가 생성된 기준 리비전(단조 증가, Java `long`을 문자열로 직렬화)
  - `snapshotRevision: string | null` — DB `ydoc_snapshot`이 반영한 `content_revision` 기준값(Java `long` 문자열)
  - `snapshotUpdatedAt: string | null` — snapshot 저장 시각(ISO-8601)
- WS 스냅샷 응답에 리비전 메타를 **바이너리 헤더로 인라인** 포함한다.
  - `SNAPSHOT_RESPONSE` 바이너리 포맷을 확장한다 (별도 `SNAPSHOT_META` 메시지 불필요).
  - `wsProtocolVersion >= 2`: `[1byte 타입코드][8byte snapshotRevision (big-endian long)][나머지 Yjs 바이너리]`
  - `wsProtocolVersion == 1` (하위호환): 기존 포맷 유지 `[1byte 타입코드][Yjs 바이너리]`
  - 단일 바이너리 프레임으로 원자적 전달 — 별도 메시지 순서 보장 문제 없음.
- **WS `snapshotRevision`의 출처:** 서버는 `SNAPSHOT_RESPONSE` 전송 시 DB `diagram.snapshot_revision` 컬럼 값을 읽어 헤더에 포함한다. (`snapshot_revision`은 해당 snapshot이 반영한 content 기준 리비전)
- **WS 헤더/페이로드 원자성 규칙:** `SNAPSHOT_RESPONSE` 생성 시 `ydoc_snapshot`과 `snapshot_revision`을 동일 DB 조회 결과에서 함께 읽어 단일 바이너리 프레임으로 구성한다. (헤더 리비전과 payload 스냅샷의 시점 불일치 금지)
- handoff 조건은 `wsSnapshotRevision >= contentRevision`을 만족할 때만 `yjs-live`로 전환한다.
- `snapshotRevision == null` (기존 마이그레이션 전 다이어그램): 리비전 검증을 스킵하고 기존 동작과 동일하게 처리한다.
- FE 파싱 규칙:
  - **WS 바이너리 (v2):** 8byte 리비전은 `DataView.getBigInt64()`로 `BigInt` 파싱한다. (`number` 변환 금지, 정밀도 손실 방지)
  - **REST JSON:** `contentRevision`/`snapshotRevision` 문자열을 `BigInt(string)`으로 파싱하여 내부 저장한다.
  - **비교 시:** WS `BigInt`와 REST `BigInt` 간 `>=` 연산으로 통일한다. (`number`와 `BigInt` 혼합 비교 금지 — TypeScript 런타임 에러)

**WS 프로토콜 버전 협상:**
- 클라이언트가 WS 연결 URL 쿼리파라미터로 버전을 전달한다: `?protocolVersion=2`
- 서버는 클라이언트 버전에 따라 `SNAPSHOT_RESPONSE` 포맷을 분기한다.
- 미전달 시 `protocolVersion=1`로 간주 (하위호환).
- 입력 검증: 허용값은 `1 | 2`만 인정한다. 그 외 값은 `1`로 강등하고 warn 로그를 남긴다.

**`saveDiagram` snapshot 무효화 정책 변경 (필수):**
- 현재 `saveDiagram`은 `ydocSnapshot = null`로 스냅샷을 무효화한다.
- **변경:** content를 갱신하는 **모든 엔트리포인트**에서 기본적으로 `ydocSnapshot`을 건드리지 않는다. content만 갱신한다.
  - 대상 예: `saveDiagram`, DSL/DLL 변환 기반 저장, 코드→ERD 반영 저장 경로
- **이유:** snapshot을 null로 밀면 `hasYdocSnapshot=false`가 되어, 활성 WS 협업 중에도 다음 클라이언트가 JSON→Y.Doc 마이그레이션 경로로 진입 → CRDT 충돌 위험. 새 아키텍처에서는 preview가 항상 content JSON을 보여주므로 "stale snapshot 우선 로딩 방지"가 불필요하다.
- **저장 소스 구분 규칙(필수):**
  - `saveSource=YJS_BACKUP` (기본): 위 정책 적용 (`ydocSnapshot` 유지, `contentRevision`만 증가)
  - `saveSource=NON_YJS_UPDATE` (관리자/외부 동기화/일괄수정): `ydocSnapshot`을 `null`로 무효화하고 `snapshotRevision`도 `null`로 리셋하여 `hasYdocSnapshot=false` 경로를 강제한다. (데이터 일관성: null snapshot에 non-null revision이 남는 상태를 방지)
  - API/서비스 레이어에 `saveSource` 파라미터를 추가하고, 기본값은 하위호환을 위해 `YJS_BACKUP`으로 둔다.
  - 권한 정책: 일반 사용자 API는 `YJS_BACKUP`만 허용한다. `NON_YJS_UPDATE`는 내부 배치/관리자 경로에서만 사용 가능하며, 외부 요청으로 들어오면 403 처리한다.
- **기존 코드 삭제 대상:**
  ```java
  // DiagramService.java — content 저장 엔트리포인트들에서 아래 패턴 제거
  diagram.updateYdocSnapshot(null);
  ```

**리비전 생성/증분 규칙 (필수 확정):**
- `diagram` 엔티티에 `content_revision BIGINT NOT NULL DEFAULT 1` / `snapshot_revision BIGINT NULL`를 둔다.
- `contentRevision` 증가 규칙:
  - REST `saveDiagram(content)` 성공 시 같은 DB 트랜잭션에서 `content_revision = content_revision + 1`.
  - 기본 경로(`saveSource=YJS_BACKUP`)에서는 `ydocSnapshot`/`snapshot_revision`을 건드리지 않는다. (snapshot 바이너리와 리비전은 flush 경로에서만 갱신)
  - 예외 경로(`saveSource=NON_YJS_UPDATE`)에서는 `ydocSnapshot = null`, `snapshot_revision = null`로 리셋한다.
- `snapshotRevision` 증가 규칙:
  - snapshot flush/compaction 저장 성공 시 같은 트랜잭션에서 `SELECT content_revision FROM diagram WHERE id = ? FOR UPDATE` 후 `snapshot_revision = content_revision`.
  - `FOR UPDATE`로 `saveDiagram`과의 동시 실행 시 직렬화를 보장한다.
- **리비전 역전 허용 범위:**
  - `saveDiagram` 직후 `contentRevision > snapshotRevision`이 되는 것은 정상이다. (content만 올라가고 snapshot은 아직 flush 안 됨)
  - 이 상태에서 클라이언트가 접속하면: `wsSnapshotRevision < contentRevision` → handoff 보류 → WS가 flush 후 새 snapshot을 보내면 통과.
  - flush가 한 번도 안 일어나는 극단적 지연 시: 재시도 3회 소진 → `yjs-failed-readonly` → 사용자 수동 재시도.
- 원자성 규칙:
  - `content` 본문 저장과 `content_revision` 증가는 같은 트랜잭션에서 커밋한다.
  - `ydoc_snapshot` 저장과 `snapshot_revision/snapshot_updated_at` 갱신도 같은 트랜잭션에서 커밋한다.
  - 리비전 필드와 페이로드가 분리 커밋되면 배포 불가(DoD 실패).

**`NON_YJS_UPDATE` 실행 가드(세션 정합성):**
- `saveSource=NON_YJS_UPDATE`는 기본적으로 활성 협업 세션이 없는 경우에만 허용한다.
- 권한 검증(내부/관리자 전용) 통과 후 활성 room 검사 단계로 진입한다.
- 활성 room이 있으면 요청을 409로 거절한다. (운영자 강제 모드는 별도 내부 경로에서 room invalidate + reconnect 선행 후 허용)
- 일반 사용자 경로에서는 강제 모드를 노출하지 않는다.

**기존 데이터 마이그레이션:**

운영/스테이징은 명시적 migration 스크립트로 적용한다. (`ddl-auto:update` 의존 금지)
```sql
-- V20260304_01__diagram_revision_columns.sql
ALTER TABLE diagram ADD COLUMN content_revision BIGINT NOT NULL DEFAULT 1;
ALTER TABLE diagram ADD COLUMN snapshot_revision BIGINT NULL;
ALTER TABLE diagram ADD COLUMN snapshot_updated_at TIMESTAMPTZ NULL;
```

컬럼 추가 이후 DML 백필을 1회 실행한다:
```sql
-- 기존 스냅샷이 있는 다이어그램: snapshot_revision을 content_revision과 동일하게
-- (migration 적용 후 한 번만 실행)
UPDATE diagram SET snapshot_revision = content_revision
  WHERE ydoc_snapshot IS NOT NULL AND snapshot_revision IS NULL;
```
- `content_revision = 1` (엔티티 기본값): 기존 다이어그램 모두 동일 초기 리비전
- `snapshot_revision = 1` (스냅샷 있는 경우): `wsSnapshotRevision(1) >= contentRevision(1)` → handoff 정상 통과
- `snapshot_revision = null` (스냅샷 없는 경우): 리비전 검증 스킵 → `hasYdocSnapshot=false` 경로로 처리
- `WHERE snapshot_revision IS NULL` 조건으로 멱등성 보장 (재실행 안전)

**구현 단계 (FE):**
1. `DiagramPage`에서 `diagram.content`를 파싱해 preview graph(`nodes/edges/groups`)를 생성한다.
   - 파싱 실패 시 `api-preview-empty`로 강등하고 `t('erd.sync.previewParseFailed')` 경고를 1회 노출한다.
2. `ERDCanvas`는 `store nodes/edges`가 비어 있고 `syncStage !== 'yjs-live'`일 때 preview graph를 렌더한다.
   - preview 활성 시 캔버스에 시각적 구분을 적용한다 (opacity 70% + 점선 overlay).
   - 다이어그램 변경(diagramId 변경) 시 store를 초기화하여 잔여 데이터 방지.
3. `useYjsCollaboration` 반환값에 `syncStage`를 추가한다. 경로는 `content` 유무와 `hasYdocSnapshot` 조합으로 결정한다:
   - `content=null` (신규): `api-preview-empty` → WS `SYNC_STEP2` 수신 확인 → `yjs-live`. (2초 미수신 시 `yjs-timeout-degraded`)
   - `content !== null && hasYdocSnapshot=false` (레거시/NON_YJS_UPDATE 후): `api-preview` → WS `SYNC_STEP2` 수신 확인 → JSON→Y.Doc 마이그레이션 → `yjs-live`. (`snapshotRevision=null`이므로 리비전 검증 스킵. 2초 미수신 시 `yjs-timeout-degraded`)
   - `content !== null && hasYdocSnapshot=true` (정상): `api-preview` → WS `SNAPSHOT_RESPONSE` + 리비전 검증 통과 → `yjs-live`. (2초 미수신 시 `yjs-timeout-degraded`)
4. handoff 시점(`yjs-live`)에 preview 표시를 중단하고 Y.Doc(store) 데이터만 렌더한다.
   - 전환 시 `fitView()` 자동 호출로 뷰 정리 (preview↔live 레이아웃 차이 완화).
5. 2초 내 Yjs 미수신 시 `yjs-timeout-degraded`로 전환하고 preview를 유지한다.
6. 편집 액션 게이트를 `canEdit && syncStage === 'yjs-live'`로 통일한다.
   - 차단 대상: 테이블/컬럼 생성·수정·삭제, 엣지 연결/삭제, 레이아웃 적용, DDL/Dsl import, 자동백업/수동저장, 우클릭 컨텍스트 메뉴
   - 허용 대상: 팬/줌/선택/검색/사이드바 조회
   - 비활성 시각 처리: `opacity-50 cursor-not-allowed` + 툴팁 표시
7. `snapshotRevision < contentRevision`이거나 리비전 메타 불일치면 handoff를 보류하고 재요청한다.
8. 재시도 정책을 고정한다.
   - 자동 재시도: 최대 3회 (`1s → 2s → 4s`, jitter ±20%), 총 최대 ~13초
   - 재시도 동작은 **handoff 모드**에 따라 분기한다:
     - `snapshot` 모드 (`hasYdocSnapshot=true` origin): 각 재시도마다 `SNAPSHOT_REQUEST` 전송 + 2초 응답 대기
     - `sync-only` 모드 (`hasYdocSnapshot=false` 또는 `api-preview-empty` origin): 각 재시도마다 WS 재연결(필요시) + `SYNC_STEP2` 2초 대기 (`SNAPSHOT_REQUEST` 전송 안 함)
   - `useDiagramSyncStage`가 초기 진입 시 `handoffMode: 'snapshot' | 'sync-only'`를 결정하여 재시도 루프에서 참조한다.
   - **WS 연결 자체가 끊긴 경우:** 재시도 시 먼저 `WebSocket.readyState`를 확인한다. `CLOSED`/`CLOSING` 상태면 WS 재연결을 먼저 시도하고, 연결 성공 후 `handoffMode`에 따라 동작한다 (snapshot: `SNAPSHOT_REQUEST` 전송 / sync-only: `SYNC_STEP2` 대기). WS 재연결 실패 시 해당 재시도 회차는 실패로 카운트한다.
   - 3회 실패 시 `yjs-failed-readonly` 전환(preview 유지, 편집 영구 차단)
   - 사용자 수동 재시도 버튼으로 카운터를 초기화하고 즉시 재시도 (WS 재연결 포함)
9. WS v2 바이너리 파싱 방어 규칙을 적용한다.
   - `protocolVersion >= 2`인데 `SNAPSHOT_RESPONSE payload.length < 9`면 malformed frame으로 간주
   - 처리: 해당 프레임 드롭 + warn 로그 + 연결 유지, 동일 오류 3회 연속 시 reconnect
   - `protocolVersion == 1` 경로에는 기존 파서 유지 (헤더 파싱 금지)

**구현 단계 (BE):**
- `flushDiagramSnapshotNow` 제거(또는 비동기화)와 함께, API는 "빠른 초기 페인트용 JSON + snapshot 존재 플래그" 전달에 집중한다.
- `DiagramDetailResponse`에 `contentRevision/snapshotRevision/snapshotUpdatedAt` 필드를 추가한다.
- WS `SNAPSHOT_RESPONSE` 바이너리에 리비전 헤더를 인라인 포함한다 (v2 포맷).
- WS 프로토콜 버전을 협상한다.
  - 클라이언트 연결 URL의 `?protocolVersion=N`을 읽어 세션에 바인딩
  - `protocolVersion >= 2`: 확장 바이너리 포맷 (리비전 헤더 포함)
  - `protocolVersion == 1` 또는 미전달: 기존 포맷 (하위호환 유지)
- snapshot flush 시 `content_revision`을 `FOR UPDATE`로 읽어 동시 트랜잭션 격리를 보장한다.

**Content staleness 허용 범위:**
- Yjs 협업 모드에서 `diagram.content`는 수동 저장/자동백업 시에만 갱신된다.
- preview는 **마지막 저장 시점의 스냅샷**이므로, 최신 Yjs 상태와 차이가 있을 수 있다.
- 이는 의도된 동작이며, handoff 시 Y.Doc(최신 상태)로 전환되면서 해소된다.
- 수용 기준: preview → yjs-live 전환 시 레이아웃 변경은 불가피하며 허용한다. `fitView()` 호출로 시각적 충격을 완화한다.
- 장기 개선: snapshot flush 시 `content` 필드도 동기화하여 preview 신선도를 높이는 것을 별도 이슈로 검토한다.

**수용 기준 (Acceptance):**
- API 응답 완료 직후(WS 연결 전) 테이블이 즉시 보인다.
- `hasYdocSnapshot=true`에서 `wsSnapshotRevision >= contentRevision`일 때만 `yjs-live` 전환된다.
- `snapshotRevision == null`(마이그레이션 전 다이어그램)에서는 리비전 검증을 스킵하고 기존 동작과 동일하게 처리된다.
- WS 미연결/지연 상황에서 2초 후에도 빈 캔버스가 아닌 preview가 유지된다.
- `hasYdocSnapshot=true` 경로에서 API JSON이 Y.Doc로 직접 주입되지 않는다.
- `api-preview`/`api-preview-empty`/`yjs-timeout-degraded`/`yjs-failed-readonly` 상태에서는 편집이 완전 차단된다.
- 자동 재시도 3회 실패 시 `yjs-failed-readonly`로 고정되고, 수동 재시도 동작이 가능하다.
- `wsProtocolVersion=1`(구버전) 클라이언트가 연결돼도 기존 협업 기능이 깨지지 않는다.
- preview → yjs-live 전환 시 `fitView()` 호출로 뷰가 정리된다.
- `content=null` (신규 다이어그램)에서도 WS sync 확정 전에는 `api-preview-empty` 읽기전용 상태로 진입하고, sync ack 이후에만 편집 가능해진다.
- `hasYdocSnapshot=false && content !== null` (레거시 다이어그램)에서 `api-preview` → WS `SYNC_STEP2` 수신 → JSON→Y.Doc 마이그레이션(`getTablesMap(ydoc).size === 0` 가드 적용) → `yjs-live` 경로가 정상 동작한다.
- `diagram.content` 파싱 실패 시 `api-preview-empty`로 안전 강등되고 sync-only 경로로 복구 가능하다.

### 우선순위 1: WS 스냅샷 폴백 타임아웃 단축 (5s → 2s)

**효과:** 최대 3초 지연 감소
**난이도:** 낮음 (상수 1개 변경)
**위험도:** 중간 (느린 네트워크에서 timeout 빈도 증가 가능, retry/backoff로 완화)

```typescript
// useYjsCollaboration.ts
const WS_SNAPSHOT_FALLBACK_MS = 2_000;  // 5000 → 2000
```

### 우선순위 2: `flushDiagramSnapshotNow` 제거 또는 비동기화

**효과:** 500ms-1s 지연 제거
**난이도:** 중간

**방안 A — flush 제거 (권장):**
- getDiagram 응답에서 flush를 제거한다.
- 어차피 WS 연결 후 서버가 최신 스냅샷을 전송하므로, REST 응답 시점에 flush할 필요가 없다.
- `hasYdocSnapshot` 판정은 flush 없이도 기존 스냅샷 존재 여부로 충분하다.

**방안 B — 비동기 flush:**
- `CompletableFuture.runAsync()`로 별도 스레드에서 실행.
- REST 응답은 즉시 반환, flush는 백그라운드에서 완료.
- 단점: flush 완료 전에 WS 스냅샷 요청이 올 수 있어 타이밍 주의 필요.

### 우선순위 3: `existsYdocSnapshotById` 통합

**효과:** 30ms 지연 감소
**난이도:** 낮음

```java
// 현재: 2번의 SELECT
findDiagramByProjectAndId(project, diagramId);      // SELECT + EntityGraph
existsYdocSnapshotById(diagramId);                    // SELECT ydoc_snapshot

// 개선: 1번의 SELECT로 통합
// DiagramRepositoryCustomImpl에 통합 메서드 추가
// ydoc_snapshot IS NOT NULL을 projection에 포함
@EntityGraph(attributePaths = { "dictionarySet" })
@Query("SELECT d, (d.ydocSnapshot IS NOT NULL) FROM Diagram d WHERE d.project = :project AND d.id = :id")
```

또는 Diagram 엔티티에 `@Formula("ydoc_snapshot IS NOT NULL")` 가상 필드를 추가.

### 우선순위 4: React Query staleTime 연장 (다이어그램 전용)

**효과:** 페이지 재방문 시 불필요한 리페칭 방지
**난이도:** 낮음

```typescript
// DiagramPage.tsx
const { data: diagram } = useQuery({
  queryKey: queryKeys.diagrams.detail(...),
  queryFn: () => fetchDiagram(...),
  staleTime: 5 * 60 * 1000,  // 30s → 5분
});
```

  - `SyncStage` 전이: `boot → api-preview → yjs-live` (snapshot 모드), `boot → api-preview → yjs-live` (sync-only 모드, 레거시), `boot → api-preview-empty → yjs-live`, `api-preview → yjs-timeout-degraded`, `api-preview-empty → yjs-timeout-degraded`, `yjs-timeout-degraded → yjs-live` (재시도 성공), `yjs-timeout-degraded → yjs-failed-readonly` (3회 소진)
  - 리비전 가드: `wsSnapshotRevision < contentRevision`이면 handoff 금지
  - 리비전 가드: `snapshotRevision == null`이면 리비전 검증 스킵
  - retry 정책: backoff 시퀀스/최대 3회/실패 시 `yjs-failed-readonly` 전이
  - v2 바이너리 포맷 파서: 리비전 헤더 추출 + Yjs 바이너리 분리
  - v2 바이너리 포맷 파서: payload < 9 malformed 방어 처리
- 통합 테스트
  - `hasYdocSnapshot=true`에서 API 선렌더 후 WS 도착 시 handoff 동작
  - `hasYdocSnapshot=true` + stale snapshot 메타에서 preview 유지 + 재요청 동작
  - `hasYdocSnapshot=false` 레거시 마이그레이션 회귀 여부
  - 기존 다이어그램 (`snapshotRevision=null`) 마이그레이션 호환성
  - WS `protocolVersion` 1/2별 바이너리 포맷 분기 호환성
  - `saveDiagram` + `flushSnapshot` 동시 실행 시 리비전 일관성 (`FOR UPDATE` 검증)
  - `saveSource=NON_YJS_UPDATE` 경로에서 snapshot 무효화/재동기화 동작
  - 활성 협업 세션 존재 시 `saveSource=NON_YJS_UPDATE` 요청 409 거절 검증
- E2E
  - 최초 진입 시 빈 캔버스 노출 시간 측정(회귀 기준선 비교)
  - 네트워크 throttling(느린 WS)에서 2초 후 degraded preview 유지 확인
  - degraded 상태 편집 완전 차단 확인(키보드/버튼/컨텍스트 메뉴/API 호출 모두 차단)
  - 2클라이언트 동시 접속에서 handoff 경쟁 시 정합성 유지 확인
  - `다시 시도` 클릭 시 재연결 루프 재개 및 성공 시 `yjs-live` 복귀 확인
  - feature flag off 시 기존 동작 회귀 확인

## 롤백 전략

- FE feature flag(`VITE_ENABLE_DIAGRAM_API_PREVIEW`)로 preview handoff 기능을 즉시 비활성화 가능하게 한다.
  - `.env.production`에서 `false`로 변경 후 재배포.
- 문제 발생 시 순서대로 롤백:
  1. feature flag `false` → preview handoff 비활성화 (FE 재배포)
  2. WS 폴백 시간 2s → 5s 복귀
  3. FE에서 v2 바이너리 파싱 비활성화 (`protocolVersion=1` 경로 강제)
  4. BE에서 v2 바이너리 포맷 송신 중지 (기존 v1 only)
  5. 필요 시 BE flush 제거 변경만 되돌림
- 롤백 후에도 데이터 정합성은 Y.Doc snapshot 기준으로 유지한다.
- 리비전 컬럼은 롤백 시에도 삭제하지 않는다 (무해한 추가 컬럼).

## 제약사항

- Yjs 협업 레이어(WS 연결, 스냅샷 전송)와 깊이 연결되어 있으므로 단계적 적용 권장
- flush 제거 시 WS 스냅샷 전송 로직이 최신 상태를 보장하는지 검증 필요
- 폴백 타임아웃 단축은 네트워크가 매우 느린 환경에서 `yjs-timeout-degraded` 빈도가 증가할 수 있음
- preview와 Y.Doc를 혼합 렌더하면 정합성 이슈가 생길 수 있으므로, handoff 시점 전후 단일 소스 원칙을 유지해야 함
- preview는 마지막 저장 시점의 `content` 기반이므로 최신 Yjs 상태와 차이가 있을 수 있음 (의도된 동작)
- 리비전 필드 도입 시 DB/캐시/WS 경로가 동일 리비전 체계를 공유해야 하며, 일관성 깨짐 시 handoff가 지속 보류될 수 있음
- `FOR UPDATE` 격리로 flush/save 동시 실행 시 직렬화를 보장하지만, 대기 시간이 추가될 수 있음
- WS 프로토콜 버전 협상은 URL 쿼리파라미터 방식이므로, 프록시/로드밸런서가 쿼리파라미터를 보존하는지 확인 필요
