# 다이어그램 작업 모드 3분리 설계 계획

작성일: 2026-03-17  
상태: 설계 초안, 미착수

중요 메모:
- 이 문서는 `양방향 동기화 / 코드 위주 VIEW / ERD 전용` 3모드 설계안이다.
- 현재는 **구현 전 설계 정리 단계**이며, 바로 코드 변경을 시작하지 않는다.
- 이후 실제 구현은 사용자가 명시적으로 지시할 때만 착수한다.

## 배경

현재 다이어그램 화면은 사실상 하나의 작업 모드에 가깝다.

- 코드 편집 가능
- ERD 직접 편집 가능
- 코드 -> ERD 자동반영
- ERD -> 코드 자동반영

이 구조는 기능적으로 강력하지만, 코드 중심 작업에서는 다음 문제가 크다.

- 자동반영 중 메인 스레드 부하가 큼
- 타이핑 중 ERD/Y.Doc 반영까지 이어져 체감 지연이 생김
- 사용자는 코드만 빠르게 다루고 싶은데 ERD 편집 기능까지 항상 같이 활성화됨

따라서 작업 목적에 따라 모드를 분리하는 설계가 필요하다.

## 목표

다이어그램 화면을 다음 3가지 작업 모드로 분리한다.

1. 양방향 동기화 모드
2. 코드 위주 모드
3. ERD 전용 모드

핵심 목표는 다음과 같다.

- 코드 중심 작업에서는 ERD를 `미리보기` 수준으로 가볍게 본다
- ERD 중심 작업에서는 코드 자동동기화를 끄고 캔버스 조작에 집중한다
- 현재 양방향 모드는 유지하되, 무거운 동작은 꼭 필요할 때만 사용하게 만든다

## 현재 구조 요약

현재 주요 경계는 아래와 같다.

- 화면 진입/구성: `client/src/pages/diagram/DiagramPage.tsx`
- 코드 패널: `client/src/components/erd/DslCodeEditorPanel.tsx`
- SQL/DSL 탭 패널: `client/src/components/erd/DdlCodeEditorPanel.tsx`
- ERD 캔버스: `client/src/components/erd/ERDCanvas.tsx`
- 코드 <-> ERD 자동 동기화: `client/src/hooks/useBidirectionalCodeSync.ts`
- 코드 결과를 실제 ERD에 반영: `client/src/hooks/useApplyToErd.ts`
- ERD 편집 권한 컨텍스트: `client/src/components/erd/ErdPermissionContext.tsx`

문제는 현재 `canEdit`가 주로 “편집 가능 여부”만 의미하고, 실제 작업 모드 차이는 표현하지 못한다는 점이다.

즉 지금 구조에는 다음 구분이 없다.

- 코드가 권위 소스인지
- ERD가 권위 소스인지
- ERD가 실제 persisted 데이터인지 preview인지
- 코드 자동반영을 켤지 끌지
- ERD -> 코드 생성은 자동인지 수동인지

## 핵심 설계 원칙

### 1. 모드는 권한이 아니라 작업 모델이다

이번 설계에서 모드는 단순히 `수정 가능/불가`가 아니다.

모드는 아래를 함께 결정해야 한다.

- 코드 편집 가능 여부
- ERD 편집 가능 여부
- 코드 -> ERD 자동반영 여부
- ERD -> 코드 자동반영 여부
- ERD 캔버스의 데이터 소스

### 2. 코드 위주 모드의 ERD는 persisted ERD가 아니라 preview여야 한다

이게 가장 중요하다.

코드 위주 모드에서도 계속 실제 Y.Doc ERD를 갱신하면 성능 이점이 거의 없다.

따라서 코드 위주 모드에서는:

- 코드 편집 결과를 파싱해서
- 별도 preview graph를 만들고
- 캔버스는 그 preview를 렌더만 해야 한다

실제 published ERD/Y.Doc은 `ERD 적용` 같은 명시적 액션 때만 갱신한다.

### 3. 양방향 모드는 유지하되 “고비용 모드”로 취급한다

현재의 강한 동기화 경험이 완전히 사라지면 안 된다.

다만 앞으로는:

- 즉시성
- 편의성
- 성능 비용

이 세 가지를 tradeoff하는 `전문가용 모드`로 보는 게 맞다.

### 4. 작업 모드 자체는 협업 상태가 아니라 로컬 작업 선호다

작업 모드는 `Y.Doc`이나 awareness로 전파하면 안 된다.

같은 다이어그램을 같이 보고 있어도:

- 한 사용자는 `양방향`
- 다른 사용자는 `코드 위주`

로 일할 수 있어야 한다.

따라서 작업 모드는 협업 데이터가 아니라 **로컬 UI 상태**여야 한다.

### 5. 코드 위주 모드는 “draft 보존 + 공유”가 같이 설계되어야 한다

현재 저장/자동백업은 persisted ERD/Y.Doc 기준이다.

하지만 코드 위주 모드에서는:

- 코드 편집 결과가 preview에만 반영되고
- 실제 ERD에는 아직 commit되지 않을 수 있다

즉 이 모드에서 코드를 별도 draft로 보존하지 않으면, 사용자가 적용 전 작업을 잃을 수 있다.

그리고 협업 요구까지 포함하면, draft는 단순 로컬 캐시가 아니라 `shared schema draft 계층`까지 같이 설계되어야 한다.

따라서 코드 위주 모드는 preview만이 아니라 아래 두 가지를 같이 가져가야 한다.

- **shared schema draft 정책**
- **crash recovery용 local draft 정책**

## 제안 모드 정의

### A. 양방향 동기화 모드

현재 동작을 계승하는 기본 호환 모드다.

특성:

- 코드 편집 가능
- ERD 편집 가능
- 코드 -> ERD 자동반영 활성
- ERD -> 코드 자동생성 활성
- 캔버스 데이터 소스: persisted Y.Doc

용도:

- 소규모/중간 규모 다이어그램
- 코드와 ERD를 함께 즉시 맞추며 작업할 때
- 기존 사용자의 습관을 유지할 때

주의:

- 가장 무거운 모드
- 성능 이슈가 가장 잘 드러나는 모드

### B. 코드 위주 모드

dbdiagram 같은 코드 중심 작업 모드다.

특성:

- 코드 편집 가능
- ERD 직접 편집 불가
- 코드 -> ERD 자동반영 비활성
- ERD -> 코드 자동생성 비활성
- 1차는 `DSL 탭`만 지원
- 캔버스 데이터 소스: `DSL parsed schema -> preview graph`
- `ERD 적용` 버튼으로만 실제 persisted ERD 갱신
- 공유 원본은 `schema draft`이고, `local recovery draft`는 브라우저 복구 보조 계층이다
- 코드는 schema draft를 빠르게 편집하는 로컬 입력기 역할을 한다

용도:

- 테이블을 많이 입력하는 초기 설계 단계
- 코드 중심으로 빠르게 반복 편집할 때
- 타이핑 성능을 최우선으로 둘 때

UX 방향:

- 캔버스의 구조 편집은 read-only
- 테이블 위치 이동은 허용
- 선은 직접 편집하지 않고 자동 정렬만 유지
- 대신 코드 결과를 빠르게 시각적으로 확인할 수 있음

### C. ERD 전용 모드

캔버스 중심 편집 모드다.

특성:

- 코드 패널 숨김
- ERD 직접 편집 가능
- 코드 -> ERD 자동반영 비활성
- ERD -> 코드 자동생성 비활성
- 캔버스 데이터 소스: persisted Y.Doc
- 1차는 코드 preview / 코드 read-only panel / 코드 보기 기능을 두지 않음
- 필요하면 이후 별도 기능으로 `수동 export`만 추가 검토

용도:

- 노드 배치, 그룹, 라우팅, 컬럼 UI 편집
- 협업 캔버스 위주 작업
- 코드보다 시각 설계가 중요한 단계

정책:

- `ERD 전용 모드`에서는 코드 자체를 작업 surface로 제공하지 않는다
- 사용자는 캔버스 편집과 persisted ERD 저장에만 집중한다
- 코드가 필요하면 모드를 `양방향` 또는 `코드 위주`로 전환해야 한다

## 모드별 capability matrix

| 항목 | 양방향 | 코드 위주 | ERD 전용 |
| --- | --- | --- | --- |
| 코드 편집 | O | O | X |
| ERD 편집 | O | X | O |
| 코드 -> ERD 자동반영 | O | X | X |
| ERD -> 코드 자동생성 | O | X | X |
| ERD 데이터 소스 | persisted | preview | persisted |
| `ERD 적용` 버튼 | 선택 | 핵심 | 비노출 또는 무의미 |
| 성능 우선순위 | 낮음 | 매우 높음 | 중간 |

추가 UX 규칙:

- 기존 헤더의 `백업` 버튼은 persisted diagram save를 뜻한다
- `코드 위주 모드`에서는 이 버튼이 draft save로 오해되지 않도록 기본적으로 숨긴다
- `코드 위주 모드`의 draft 저장은 헤더 저장 버튼이 아니라 `shared schema draft + local recovery draft` 정책으로 처리한다
- `코드 위주 모드`의 캔버스 툴바는 read-only preview 기준으로 축소한다
- `코드 위주 모드`에서는 preview sync 배너를 노출하지 않는다
- `ERD 전용 모드`에서는 코드 패널 toggle 자체를 숨기고, 코드 관련 단축키/배너/패널을 노출하지 않는다

## 제안 상태 모델

새 work mode 컨텍스트를 도입한다.

예시:

```ts
type DiagramWorkMode = 'sync' | 'code' | 'erd';

interface DiagramWorkModeCapabilities {
  mode: DiagramWorkMode;
  canEditCode: boolean;
  canEditCanvas: boolean;
  enableCodeToErdAutoSync: boolean;
  enableErdToCodeAutoSync: boolean;
  canvasSource: 'persisted' | 'preview';
  showCodePanel: boolean;
  persistCodeDraft: boolean;
}
```

이 컨텍스트는 `DiagramPage`에서 계산하고, 하위 컴포넌트는 `canEdit` 대신 capability를 소비한다.

추가 원칙:

- 모드 값은 다이어그램별 로컬 저장이 가능해야 한다
- 기본값은 `sync`
- 저장 위치는 `localStorage` 같은 클라이언트 로컬 스토리지를 권장한다
- 협업 provider/Y.Doc에는 싣지 않는다

## 데이터 흐름 설계

### 1. 양방향 동기화 모드

- 현재 구조를 최대한 유지한다
- `useBidirectionalCodeSync` 활성
- `useApplyToErd` 자동/수동 둘 다 활성
- ERD 캔버스는 persisted store 사용

### 2. 코드 위주 모드

- `useBidirectionalCodeSync` 비활성
- `useApplyToErd`는 수동 경로만 사용
- DSL 탭의 shared schema draft를 기준으로 preview graph 생성
- `ERDCanvas`는 persisted store 대신 preview nodes/edges 렌더
- 코드 텍스트는 local-only 입력 상태로 유지하고, 브라우저 local draft는 crash recovery 용도로만 별도 보존한다
- Yjs 연결은 `persisted layer`와 `shared schema draft layer`를 모두 유지하되, 둘의 의미를 분리한다
- auto backup은 shared schema draft를 published ERD 변경으로 오인하지 않도록, persisted backup과 draft snapshot을 별도 타입으로 구분한다

즉:

```text
shared schema draft
 -> preview graph
 -> read-only canvas render
 -> draft positions shared
 -> explicit "ERD 적용"
 -> persisted Y.Doc update
 -> shared schema draft clear or baseline refresh
```

위 규칙은 아래처럼 더 구체화한다.

- 기존 persisted 테이블의 위치 이동은 즉시 persisted Y.Doc 좌표에도 반영한다
- 아직 persisted에 없는 신규 draft 테이블 위치만 shared schema draft `positions`에 유지한다
- `ERD 적용` 후 shared schema draft와 persisted 결과의 `schemaHash`가 같아지면 draft clear, 다르면 baseline refresh만 수행한다

### 3. ERD 전용 모드

- 캔버스 편집만 활성
- 코드 패널 숨김
- ERD -> 코드 자동생성 없음
- 1차는 코드 보기/코드 복사/코드 preview를 제공하지 않음
- 필요하면 이후 별도 기능으로 `수동 export`만 추가 검토

## preview graph 설계

코드 위주 모드의 핵심 신규 계층이다.

새 helper가 필요하다.

예시:

- `buildPreviewGraphFromDslParsedSchema`
- 입력: DSL parsed schema, 사전 데이터, 필요 시 layout option
- 출력: `Node<TableNodeData>[]`, `Edge[]`

이번 결정 기준으로 1차는 DSL 전용 helper로 고정한다.

즉:

- 코드 위주 모드의 preview는 DSL 탭에서만 활성
- SQL 탭은 1차 범위에서 preview 대상이 아님
- SQL 탭은 기존 동작을 유지한다

추가 원칙:

- `코드 위주 모드`에서 SQL 탭으로 전환하면 preview canvas는 갱신하지 않는다
- SQL 탭 상태에서는 `ERD 적용`도 preview 기반 수동 적용이 아니라 기존 SQL apply 경로를 유지한다
- 즉 1차의 `코드 위주 모드`는 실질적으로 `DSL 중심 모드`에 가깝다

preview graph의 원칙:

- preview graph 그 자체는 published ERD가 아니다
- preview graph는 협업 저장 대상이 아니라 local-derived view다
- 기존 persisted 테이블/엣지의 좌표와 선 표현은 persisted Y.Doc을 그대로 읽는다
- preview 전용 신규 테이블/엣지는 shared schema draft를 다시 파싱해서 각 클라이언트가 동일하게 계산한다
- `ERD 적용` 시에만 현재 preview 구조를 persisted Y.Doc으로 승격한다

즉 preview는 “빠르고 안전한 시각화”가 목적이다.

추가 원칙:

- 기존 `ERDCanvas`에 persisted/preview 두 데이터 소스를 억지로 섞지 않는다
- 1차는 `PreviewCanvas` 래퍼나 data adapter를 따로 두는 편이 안전하다
- 기존 `ERDCanvas`는 persisted store + 협업 편집에 집중하게 유지한다

### shared schema draft 계층 설계

`code` 모드 협업을 위해, published ERD와 별도로 아래 draft 계층을 둔다.

예시:

```ts
interface SharedSchemaDraft {
  mode: 'dsl';
  baselineRevision: string;
  schemaHash: string;
  tables: DraftTable[];
  relations: DraftRelation[];
  positions: Record<string, { x: number; y: number }>;
  updatedAt: number;
}
```

핵심 규칙:

- 협업 원본은 코드가 아니라 `schema draft`다
- 코드는 shared 대상이 아니며, 각 클라이언트가 schema draft를 편집하기 위한 로컬 입력기다
- preview graph는 shared schema draft에 저장하지 않는다
- 기존 persisted 테이블/엣지는 이 draft 계층에 복제하지 않고, persisted Y.Doc presentation을 계속 단일 진실 원천으로 사용한다
- 테이블 위치는 사용자가 직접 의도한 정보이므로 schema draft의 일부로 공유한다
- 기존 persisted 테이블 위치는 draft에만 가두지 않고, 이동 시 즉시 persisted Y.Doc 좌표와도 동기화한다
- 신규 draft 테이블 위치는 persisted 승격 전까지 schema draft `positions`에서 공유한다
- 선은 shared 대상이 아니며, 각 클라이언트가 자동 정렬로 계산한다
- 로컬 코드에 문법 오류가 있으면 shared schema draft는 마지막 정상 상태를 유지한다
- blank code는 사용자가 명시적으로 비우는 의도를 확인한 경우에만 shared schema draft clear 후보가 된다
- localStorage draft는 `shared schema draft 미전송 시 복구`와 `브라우저 crash recovery` 용도만 가진다

즉, 협업 기준은 아래 2층이다.

- `persisted ERD layer`
- `shared schema draft layer`

## UI/UX 제안

### 모드 전환 위치

가장 자연스러운 위치는 상단 툴바다.

예시:

- `양방향`

- `ERD 전용`

세그먼트 버튼이나 드롭다운 모두 가능하지만, 이 기능은 자주 바꿀 수 있으므로 3버튼 segmented control이 더 적합하다.

  - `ERD 전용 모드에서는 코드 패널을 표시하지 않습니다.`

  - FK connect

- read-only generated code panel

- persisted ERD와 preview가 다른 상태에서 `양방향`으로 돌아갈 때 어떤 기준을 쓸지

권장 1차:

- draft는 유지하되 자동 commit은 하지 않음
- 코드 위주 -> 양방향 전환 시 확인 배너 또는 상태 배지 노출

## 저장/백업 정책

이 설계에서 가장 빠지기 쉬운 부분이다.

현재 자동백업은 persisted Y.Doc만 저장한다.

따라서 3모드 도입 시 저장 정책을 분리해야 한다.

### 양방향 / ERD 전용

- 지금과 동일하게 persisted ERD/Y.Doc 기준 저장
- auto backup 그대로 유지

### 코드 위주

- preview graph 그 자체는 published ERD 저장 대상이 아님
- 하지만 code mode draft는 아래 두 층으로 저장된다

권장 1차:

- shared schema draft 저장
  - Y.Doc 내 별도 `shared schema draft layer`
  - 협업과 서버 persistence 대상
- local recovery draft 저장
  - 브라우저 localStorage
  - crash recovery와 임시 복구 용도

즉 코드 위주 모드에서 저장 의미는 세 층으로 나뉜다.

- published diagram save
- shared schema draft save
- local recovery draft save

추가 UX 원칙:

- `Header`의 기존 `백업` 버튼은 persisted ERD/Y.Doc 저장 전용 의미를 유지한다
- 따라서 `코드 위주 모드`에서는 이 버튼을 숨기거나, 최소한 draft 저장과 구분되는 별도 라벨로 바꾸지 않으면 안 된다
- 1차는 혼동을 줄이기 위해 `코드 위주 모드`에서 헤더 `백업` 버튼을 숨기는 쪽을 권장한다
- code mode draft는 shared schema draft layer와 local recovery draft로 자동 저장하고, `ERD 적용`만 published persisted 변경 액션으로 본다

추가 원칙:

- `useAutoBackup`는 code mode의 shared schema draft를 published diagram backup으로 취급하면 안 된다
- persisted Y.Doc의 published layer가 실제로 바뀐 경우에만 기존 backup 대상으로 본다
- shared schema draft snapshot은 별도 복구 정책으로 다루고, published restore와 섞지 않는다

### 단일 사용자 안정성 원칙

코드 위주 모드는 협업을 지원하지만, 단일 사용자도 항상 같은 협업 저장 경로를 탄다.

따라서 아래 원칙을 추가로 둔다.

- preview graph 재계산 결과는 shared schema draft 저장 트리거가 아니다
- 서버 snapshot 저장 트리거는 `schema draft 변경`, `의도된 blank 상태 변경`, 명시적 위치 이동처럼 의미 있는 draft 변경에 한정한다
- keepalive/pagehide 저장은 실제 페이지 이탈 시점에만 사용하고, 일반 렌더/effect 정리에서는 발사하지 않는다

즉 협업을 유지하되, 단일 사용자에서 preview 내부 계산 때문에 저장 상태가 흔들리지 않게 한다.

## 리스크

### 1. 코드 위주 preview와 persisted ERD의 차이

preview는 persisted ERD와 다를 수 있다.

예:

- 수동 경로 편집
- 그룹 정보
- headerColor
- manual side
- custom layout

이 차이는 허용해야 한다.
코드 위주 모드는 “빠른 구조 preview”이기 때문이다.

### 2. 협업 의미 차이

작업 모드는 로컬이지만, 다이어그램 표현 자체는 모드와 무관하게 공유되어야 한다.

따라서 `code` 모드는 다음처럼 나눈다.

- 작업 모드 선택 자체는 로컬 UI 상태
- published ERD는 기존 persisted Y.Doc 협업 상태
- code mode의 협업 단위는 `schema draft + baseline revision + 위치 정보`다
- 코드 텍스트는 협업 데이터가 아니라, 공유된 schema draft를 빠르게 수정하는 로컬 입력기다
- preview graph는 공유 데이터가 아니라, 공유된 schema draft에서 각 클라이언트가 로컬로 파생한다

즉 협업 기준은 “모드”가 아니라 “어느 계층을 보고 편집하느냐”다.

### 2-1. code 모드 신규 preview 구조 공유 방식

선택지는 세 가지다.

1. 코드 입력마다 실제 persisted ERD를 바로 갱신
2. 별도 `shared preview draft layer`를 두고, apply 시에만 persisted 승격
3. schema draft를 공유하고, preview는 로컬에서만 파생 렌더

기존 권장안은 2번이었지만, 실제 운영/디버깅 결과 3번으로 바꾼다.

이유:

- 1번은 성능 이점이 거의 사라진다
- 2번은 preview graph 재계산, overlay 저장, 서버 snapshot 저장이 서로 엮여 단일 사용자 작업에서도 stale/keepalive/pending 문제가 생기기 쉽다
- 3번은 preview 구조 자체를 직접 공유하지 않지만, 협업에서 실제로 필요한 것은 우선 `스키마`이며 preview는 같은 schema draft에서 항상 다시 만들 수 있다
- 3번은 협업은 유지하면서도 저장 의미를 단순하게 만들고, 서버 저장 트리거를 `schema draft 변경` 중심으로 좁힐 수 있다

따라서 문서의 기본 권장안은:

- `persisted ERD`는 published diagram
- `shared schema draft`는 code mode 협업 layer
- preview는 `shared schema draft + persisted ERD presentation`에서 각 클라이언트가 로컬로 생성
- `ERD 적용`은 shared schema draft에서 파생된 현재 preview를 persisted로 승격하는 명시적 액션

### 2-2. 다른 모드에서 schema draft를 보는 방식

작업 모드는 로컬이지만, schema draft는 다른 사용자가 같은 구조 초안을 기준으로 작업하거나 읽을 수 있어야 한다.

권장 1차:

- `code` 모드: 로컬 코드 입력으로 shared schema draft를 편집하고, preview는 로컬 파생 렌더
- `sync` / `erd` 모드: persisted graph 위에 shared schema draft를 read-only overlay로 렌더
- draft 객체는 `공유 초안` 상태로 표시하고, 다른 모드에서는 직접 편집하지 않는다
- 코드는 필요할 때만 `code` 모드로 전환해 로컬에서 다시 생성/편집한다

즉 “스키마는 공유”, “preview는 모드 로컬 파생”, “persisted ERD는 별도 진실 원천” 원칙으로 간다.

### 2-3. 작업 모드 동기화 금지

작업 모드를 협업 상태로 전파하면:

- 다른 사용자의 화면 구조가 강제로 바뀌고
- 로컬 성능 선택이 협업 데이터가 되어 버린다

따라서 작업 모드는 반드시 로컬 전용 상태여야 한다.

### 3. 모드 전환 시 상태 혼란

모드를 바꿀 때:

- 현재 코드 변경이 미적용 상태인지
- preview인지 persisted인지

를 분명히 알려야 한다.

특히 코드 위주 -> 양방향 전환 시:

- 즉시 auto-sync 재개
- 또는 사용자 확인 후 적용

정책이 필요하다.

권장 1차:

- 코드 위주 -> 양방향 전환 시 자동반영을 즉시 강제하지 않는다
- 사용자가 `ERD 적용` 또는 이후 명시적 수정으로 반영하도록 둔다

### 3-1. 코드 위주 모드 apply 시 persisted ERD 충돌

코드 위주 모드는 shared schema draft + local preview를 기반으로 작업하므로,
다른 사용자가 persisted ERD를 바꾸는 동안 shared schema draft가 오래 열려 있을 수 있다.

이 상태에서 `ERD 적용`을 누르면:

- schema draft에서 파생된 preview가 더 최신 persisted ERD를 덮어쓸 수 있다

따라서 1차 구현에도 아래 규칙이 필요하다.

- shared schema draft 생성 시 persisted baseline revision 저장
- `ERD 적용` 시 현재 persisted revision과 shared schema draft baseline 비교
- 다르면 즉시 overwrite 하지 않고 충돌 안내
- 사용자가 rebase preview/새로고침/강제 적용 중 하나를 고르게 한다
- `ERD 적용` 성공 후 shared schema draft와 persisted 결과의 `schemaHash`가 같으면 shared schema draft를 clear한다
- `ERD 적용` 성공 후에도 shared schema draft가 더 남아 있으면 clear하지 않고 baseline만 최신 persisted revision으로 갱신한다

### 3-2. 코드 위주 모드의 코드 에디터 락 오해 위험

현재 코드 에디터는 커서 위치를 기준으로 `editingTableKey` 성격의 락을 발행한다.

하지만 `코드 위주 모드`에서는:

- 에디터가 shared schema draft를 편집하고
- 캔버스는 local preview를 보고
- 특정 persisted 테이블을 “실제로 편집 중”이라고 보기 어렵다

따라서 1차 구현 원칙:

- `코드 위주 모드`에서는 `useCodeEditorTableLock` 기반 persisted table lock 발행을 비활성화한다
- 필요하면 로컬 UI 강조만 하고, awareness/Yjs lock으로 전파하지 않는다
- `양방향 모드`에서만 현재의 code editor table lock을 유지한다

### 4. 기존 ERDCanvas에 분기 과다 주입 위험

현재 `ERDCanvas`는:

- store 구독
- 협업 awareness
- edge editing
- export
- toolbar

를 모두 함께 가진다.

여기에 preview/persisted 분기를 직접 많이 넣으면 컴포넌트 복잡도가 급격히 커질 수 있다.

따라서 1차 구현은:

- `ERDCanvas`는 persisted 전용
- preview는 별도 wrapper/adapter

로 분리하는 것이 clean/arch 측면에서 더 안전하다.

### 5. 현재 ERD -> 코드 초기 채우기와 draft 복원 순서 충돌

현재 DSL 코드 패널은 초기 진입 시 ERD에서 코드를 한 번 생성해 채운다.

이 동작은 지금 구조에선 자연스럽지만, 코드 위주 모드에서는 문제가 된다.

- shared schema draft 또는 local recovery draft가 있는데
- 초기 ERD -> DSL 채우기가 먼저 실행되면
- draft가 덮일 수 있다

따라서 코드 위주 모드에서는:

- shared schema draft 복원이 최우선
- shared schema draft가 없고 local recovery draft가 있으면 그 다음으로 복원
- 둘 다 없을 때만 ERD -> DSL 초기 생성

순서를 명확히 강제해야 한다.

## 권장 결론

이 작업은 충분히 가치가 있다.

특히 성능 때문에라면 핵심은 단순한 on/off가 아니라:

- `양방향 모드`는 유지
- `코드 위주 모드`는 preview canvas 기반으로 분리
- `ERD 전용 모드`는 코드 자동생성 없이 캔버스 편집에 집중

으로 나누는 것이다.

가장 중요한 한 줄 결론:

**코드 위주 모드에서 ERD는 published persisted Y.Doc가 아니라 preview graph를 보여줘야 한다.**

다만 협업 목표까지 포함하더라도, shared 대상은 preview graph나 코드 text가 아니라 `shared schema draft`여야 한다.

즉:

- 코드는 shared schema draft를 빠르게 편집하는 로컬 입력기로 사용하고
- preview는 각 클라이언트가 shared schema draft에서 로컬로 다시 만들고
- persisted ERD 변경은 `ERD 적용` / `최종 저장`에서만 수행한다

이 원칙을 지키면 현재의 “양방향이 너무 느리다” 문제를 구조적으로 분리할 수 있다.
