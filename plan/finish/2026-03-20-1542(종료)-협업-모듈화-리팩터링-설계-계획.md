## 1. 왜 지금 구조를 다시 잡아야 하는가

현재 협업 기능은 동작 자체는 고도화되어 있지만, 다음 문제가 누적되어 있다.

- WebSocket, Yjs, room lifecycle, snapshot, presence, handoff, preview fallback이 `diagram` 도메인과 섞여 있다.
- authoritative content 저장, snapshot 저장, warm room state 정렬 규칙이 여러 클래스에 흩어져 있다.
- 프론트는 `useYjsCollaboration` 안에서 transport, preview, fallback, 상태 전이를 같이 처리한다.
- 코드 모드, 양방향 모드, ERD-only 모드의 상태 의미가 문서보다 코드에 더 강하게 박혀 있다.
- 새로운 협업 형상이나 다른 프로젝트로 확장할 때 diagram-specific 결합을 다시 풀어야 한다.

이 상태에서 단순히 공통 인터페이스 몇 개를 추출하는 수준으로는 장기 안정성과 확장성을 확보하기 어렵다.

이번 설계의 목표는 `다이어그램 협업 기능 공통화`가 아니라, 더 큰 관점의 **협업 플랫폼 아키텍처**를 정의하는 것이다.

---

## 2. 아키텍처 목표

이번 재설계의 최상위 목표는 아래 네 가지다.

1. 협업 기능을 `도메인 기능`이 아니라 `플랫폼 기능`으로 재정의한다.
2. 저장/복구/재접속/협업 상태 전이를 1급 설계 요소로 끌어올린다.
3. 다이어그램을 협업 플랫폼의 첫 번째 채널 구현체로 재구성한다.
4. 이후 다른 형상, 다른 프로젝트, 다른 화면 설계가 와도 기존 코어를 흔들지 않고 붙일 수 있게 한다.

추가 목표:

- 장기적으로 `기능 추가`, `새로운 시스템 구축`, `새 협업 형상 추가`에 유연하게 대응
- 현재 반복적으로 나타난 stale snapshot, preview blank, handoff mismatch, session lifecycle 회귀를 구조적으로 줄임
- 현재 wire protocol, 브라우저 협업 smoke, authoritative save 의미를 유지한 채 마이그레이션 가능

비목표:

- 1차에서 Yjs를 제거하거나 다른 CRDT 엔진으로 바꾸지 않는다.
- 1차에서 WebSocket 메시지 타입과 `/ws/diagram/*` 경로를 바꾸지 않는다.
- 1차에서 editor-local UX 훅을 공통 collaboration 모듈로 올리지 않는다.

## 3. 핵심 설계 원칙

### 3.1 계층 원칙

이번 구조는 아래 4계층을 분리 기준으로 삼는다.

1. `domain`
- 다이어그램 자체의 비즈니스 규칙
- 테이블, 관계, 발표용 persisted content, 사전 반영 규칙
- 협업 엔진 구현 상세를 몰라야 한다.

2. `application`
- 저장, 최종 확정, ticket 발급, snapshot reconcile, handoff 조립, afterCommit 정렬 같은 유스케이스 orchestration
- 여러 정책을 조합하지만 transport/프레임워크에는 의존하지 않는다.

3. `collaboration`
- 공통 협업 커널
- 세션, room, snapshot, handoff, presence, 프로토콜 정책, 프론트 상태 머신을 담당
- 형상 비즈니스를 직접 알지 않는다.

4. `infrastructure`
- websocket transport
- spring wiring / config
- persistence adapter
- 외부 시스템 연동

### 3.2 1급 설계 축

아래 4개는 시스템의 1급 개념으로 정의한다.

1. `authoritative content`
- 최종 persisted content
- 최종 truth

2. `persisted collaboration snapshot`
- 협업 복구용 persisted CRDT snapshot

3. `warm room state`
- 메모리상의 최신 협업 상태
- handoff에 활용되지만 authoritative truth는 아님

4. `frontend collaboration state machine`
- preview
- hydrating
- live
- degraded
- reconnecting

이 4개의 우선순위와 정렬 시점이 불명확하면, 앞으로 다른 형상을 붙일 때도 같은 문제가 반복된다.

### 3.3 패턴 원칙

주 패턴:

- `Ports & Adapters`
- `Plugin / Strategy`
- `State Machine`
- `Command + Policy`

보조 패턴:

- `Template Method`
  - WebSocket lifecycle skeleton 정도에만 사용

패턴 적용 원칙:

- 상속보다 조합 우선
- 공통 커널은 구체 구현체를 import하지 않음
- 정책은 인터페이스 단위로 쪼개고 registry/factory가 조립
- 프론트 상태 전이는 hook 분리보다 상태 의미를 먼저 고정

## 5. 채널 플러그인 모델

다이어그램은 이제 “협업 엔진의 첫 구현체”가 아니라, **협업 플랫폼의 첫 번째 채널 플러그인**으로 다룬다.

### 5.1 백엔드 채널 플러그인 구성요소

#### `ChannelDefinition`
- 채널 타입
- 리소스 키 구조
- 정책 집합 wiring

#### `AccessPolicy`
- 채널 리소스 접근 검증

#### `SnapshotStore`
- persisted collaboration snapshot load/save

#### `HandoffPolicy`
- warm room state / cached snapshot / persisted snapshot 조합 규칙

#### `PresencePolicy`
- participant / snapshot / peer join/leave 모델 규칙

#### `BootstrapProvider`
- 협업 시작 시 authoritative bootstrap 제공

### 5.2 프론트 채널 플러그인 구성요소

#### `FrontendBinding`
- Y.Doc <-> store 연동

#### `PreviewPolicy`
- preview/hydrating/live/degraded 전이 조건
- fallback timeout

#### `YjsDocumentAdapter`
- bootstrap -> Y.Doc 적용
- current Y.Doc -> snapshot 추출

#### `ChannelPlugin`
- ticket 요청
- binding 생성
- preview policy 제공
- document adapter 제공

### 5.3 원칙

- 새 형상은 위 세트만 구현하면 붙을 수 있어야 한다.
- 공통 collaboration core는 diagram-specific field를 알지 않아야 한다.
- 특정 형상의 특수 규칙은 channel plugin 내부 policy로 수렴해야 한다.

## 6. 상태 소유권과 정합성 계약

### 6.1 상태 우선순위

우선순위는 아래와 같이 고정한다.

1. `authoritative persisted content`
2. `persisted collaboration snapshot`
3. `warm room state`

의미:

- room state는 persisted content를 덮어쓰는 truth가 아니다.
- handoff 때만 조합 소스로 사용된다.
- persisted content 저장 성공 후에는 room/cache가 persisted 기준으로 정렬되어야 한다.

### 6.2 저장 계약

#### authoritative save
- 최종 content 저장
- 최종 비즈니스 truth 확정
- application layer 유스케이스가 소유

#### collaboration snapshot save
- Yjs snapshot 영속
- 협업 재접속/복구용
- application layer command가 orchestration

#### warm room state
- 인메모리 협업 상태
- 빠른 relay/handoff에 사용
- persisted truth를 대체하지 않는다

### 6.3 정렬 시점 계약

- authoritative save 성공
- DB commit 완료
- 그 이후 `afterCommit`에서만 room/cache reconcile 수행

금지:

- DB commit 전에 room state 교체
- stale room state가 persisted snapshot보다 우선되는 handoff

### 6.4 handoff 정책 계약

`SnapshotRequestMessageHandler` 류의 현재 warm handoff 로직은 단순 snapshot load가 아니라 별도 정책으로 승격한다.

정책:

- pending updates가 있으면 `warm room state + persisted snapshot`을 조합
- 아니면 cached snapshot 사용
- 그것도 없으면 persisted snapshot 사용

즉 handoff는 단순 store read가 아니라 `HandoffPolicy`가 결정한다.

### 6.5 구버전 클라이언트 호환

- snapshot 없는 구형 저장 요청은 호환성 경로로 처리
- cache clear와 room discard를 분리
- active room이 있는 동안은 warm state를 함부로 버리지 않음

## 7. 프론트 협업 상태 머신

프론트는 단순 hook 분리가 아니라 상태 머신 기준으로 정리한다.

### 7.1 상태

- `preview`
- `hydrating`
- `live`
- `degraded`
- `reconnecting`

### 7.2 이벤트

- bootstrap loaded
- ws connected
- remote snapshot arrived
- fallback timeout
- disconnect
- reconnect success

### 7.3 상태 의미

#### `preview`
- API content로 임시 화면 표시

#### `hydrating`
- Y.Doc / remote snapshot을 기다리는 중

#### `live`
- 실시간 협업 상태가 활성화된 상태

#### `degraded`
- remote snapshot을 받지 못해 fallback 경로로 살아 있는 상태

#### `reconnecting`
- 연결은 끊겼지만 문서/화면은 유지하며 재접속 대기

### 7.4 기대 효과

- 첫 로딩 blank 방지
- fallback 꼬임 방지
- reconnect 흔들림 감소
- 상태 전이 기준이 문서와 코드에서 일치

## 8. 아키텍처 패턴 적용 규칙

### 8.1 Ports & Adapters

적용 대상:

- snapshot store
- bootstrap provider
- presence policy
- access policy
- frontend binding

원칙:

- port는 공통 collaboration이 정의
- adapter/plugin 구현은 domain/diagram 또는 frontend channel plugin이 제공

### 8.2 Strategy / Policy

적용 대상:

- handoff policy
- preview policy
- access policy
- presence policy

원칙:

- 상태 결정 규칙을 `if/else` 분기 덩어리로 남기지 않는다.
- 정책은 교체 가능하고 조합 가능해야 한다.

### 8.3 State Machine

적용 대상:

- 프론트 preview/live/degraded/reconnecting 흐름
- 필요 시 백엔드 room lifecycle도 후속 차수에서 적용

### 8.4 Command

적용 대상:

- snapshot save command
- authoritative save command
- reconcile command
- issue ticket command

### 8.5 Template Method

적용 범위:

- websocket lifecycle skeleton
- provider 연결/정리 skeleton

제한:

- 공통 정책 로직을 상속 계층으로 해결하지 않는다.

## 11. 최종 결론

이번 작업은 `diagram 협업 코드 공통화`가 아니라, **장기 확장 가능한 협업 플랫폼 아키텍처를 세우는 작업**으로 정의한다.

핵심은 아래다.

- `domain / application / collaboration / infrastructure` 4계층 분리
- `authoritative content / persisted snapshot / warm room state / frontend state machine` 4축을 1급 개념으로 승격
- diagram을 첫 번째 채널 플러그인으로 재구성
- 패턴은 `Ports & Adapters + Plugin/Strategy + State Machine + Command`

즉 1차부터 목표를 낮은 seam extraction이 아니라, **앞으로 안 흔들릴 플랫폼 기준선 고정**으로 잡는다.
