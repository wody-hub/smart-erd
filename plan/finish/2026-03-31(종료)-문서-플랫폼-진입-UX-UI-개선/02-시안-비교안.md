# 02. 시안 비교안

> 상태: 기준안 선정 완료

## 목적

이 문서는 `문서 플랫폼 진입 UX/UI 개선`의 시각 방향을 실제 구현 전에 비교하기 위한 기준안이다.

이번 시안은 아래 전제를 공유한다.

- 상위 UX는 `diagram tool`이 아니라 `document workspace`처럼 보여야 한다
- `ProjectsPage`는 카드형
- `DiagramsPage`는 dense list형
- `Dictionary`는 팀 자산 허브
- `Screen Spec` 플러그인까지 수용 가능한 쉘을 먼저 만든다

시안은 3개다.

1. **Variant A, Editorial Workspace**
- 문서성, 정돈감, 여백을 강조한다
- 차분한 타이포그래피와 넓은 본문 폭을 사용한다
- 팀 / 프로젝트 / 문서 맥락을 읽기 쉽게 보여준다
- 추천 상황:
  - 기술 문서, ERD, 화면기획이 한 제품에 같이 올라갈 때
  - 과장된 대시보드 느낌보다 신뢰감 있는 도구 느낌이 중요할 때

2. **Variant B, Operational Dashboard**
- 활동성, 상태성, 최근 수정, 협업 메타를 더 앞세운다
- 팀 홈과 문서 허브의 대시보드 감각이 강하다
- 추천 상황:
  - 협업 상태, 최근 작업, 빠른 액션을 많이 보는 조직
  - 운영 관점에서 “무엇이 바뀌었는가”를 강조하고 싶을 때

3. **Variant C, Minimal Productivity Shell**
- 시각 장식을 최대한 줄이고 생산성 도구 느낌에 집중한다
- 리스트와 헤더를 가장 단단하게 쓰고, 크롬은 최소화한다
- 추천 상황:
  - Linear 류의 dense utility UX를 선호할 때
  - 추후 문서 타입이 많아져도 가장 무난하게 확장하고 싶을 때

## 권장안

현재 기준 추천은 **Variant A와 C의 절충**이다.

- 상위 쉘과 팀 / 프로젝트 맥락은 **A의 문서성**
- 문서 허브 리스트와 액션 구조는 **C의 생산성**
- B의 운영 메타는 `ProjectsPage` 또는 `Documents` 상단 보조 영역까지만 제한

이유:

- 화면기획 플러그인까지 염두에 두면 너무 대시보드형으로 가는 건 금방 산만해진다
- 반대로 지나치게 미니멀하면 팀 / 프로젝트 / 자산 구조가 약해진다
- 결국 가장 좋은 방향은
  - 상위는 calm workspace
  - 하위 문서 목록은 dense productivity
  조합이다

## 최종 선정 방향

최종 기준안은 아래처럼 고정한다.

- **Header / TeamsPage / ProjectsPage / DictionaryPage는 Variant A**
- **DiagramsPage(Document hub)는 Variant C**
- **Variant B의 운영 메타는 보조 슬롯에만 제한적으로 차용**

이 조합을 선택한 이유는 세 가지다.

1. **화면기획 플러그인과 가장 잘 맞는다**
- 화면기획 플러그인은 대시보드보다 문서성, 산출물 품질, 구조적 신뢰감이 중요하다
- 따라서 상위 쉘은 `Editorial Workspace` 톤이 더 맞다

2. **문서 허브는 비교와 최근성이 중요하다**
- ERD, 앞으로 들어올 Markdown, Screen Spec 문서는 결국 운영 목록처럼 비교하고 열게 된다
- 그래서 문서 허브는 `Minimal Productivity Shell`의 dense list가 더 적합하다

3. **운영 메타는 전면이 아니라 보조가 맞다**
- 협업 상태, 최근 수정, 경고 배지는 중요하지만 제품의 주인공이 되면 산만해진다
- 이 메타는 상단 보조 영역이나 row 메타 안으로 제한한다
