# 03. 기준 시안 선정

## 선정 결과

문서 플랫폼 진입 UX/UI 개선의 기준 시안은 아래 조합으로 확정한다.

- **상위 쉘 기준안: Variant A, Editorial Workspace**
- **문서 허브 기준안: Variant C, Minimal Productivity Shell**
- **보조 메타 참조안: Variant B, Operational Dashboard 일부만 차용**

즉, 제품 전체를 하나의 시안으로 통일하지 않고,

- 상위는 **문서성**
- 하위 문서 목록은 **생산성**

으로 나누는 하이브리드 전략을 쓴다.

## 왜 이 조합인가

### 1. 화면기획 플러그인까지 고려하면 상위는 문서성 톤이 맞다

[화면기획 플러그인 설계](/Users/j.jaeyo/Project/ETC/smart-erd/plan/2026-03-25-1445-화면기획-플러그인-설계/00-개요.md) 기준으로 이 제품은 장기적으로

- ERD
- Markdown
- Screen Spec

을 같은 플랫폼에 올리게 된다.

특히 Screen Spec은 단순 데이터 편집이 아니라

- 화면
- 컴포넌트
- 인스턴스
- 화면 흐름
- 산출물

을 다루는 문서형 도구다.

그래서 상위 쉘이 너무 운영 대시보드처럼 보이면 안 된다.

필요한 건:

- 신뢰감
- 문서성
- 맥락 인지
- 차분한 탐색 경험

이고, 이건 Variant A가 가장 잘 맞는다.

### 2. 문서 허브는 결국 운영 목록이다

반면 `Documents` 허브는

- 무엇이 최근에 수정됐는지
- 어떤 문서가 중요한지
- 어떤 상태인지

를 빨리 비교하고 열 수 있어야 한다.

이건 카드보다 **dense list**가 강하다.

즉 문서 허브의 핵심 경험은 감상보다 운영에 가깝고,
이 역할은 Variant C가 더 잘 수행한다.

### 3. Variant B는 주인공이 아니라 보조 재료다

Variant B의 장점은 있다.

- 최근 활동
- 협업 상태
- 빠른 메타 인지

하지만 이걸 화면 전면에 두면 제품이 금방 산만해진다.

따라서 B는 아래처럼 제한한다.

- ProjectsPage 상단 보조 영역
- DiagramsPage row 메타
- 협업 상태 chip / recent activity summary

정도까지만 사용한다.

## 페이지별 적용 규칙

### Header

기준: **Variant A**

- breadcrumb와 현재 맥락을 가장 먼저 읽히게 한다
- 제품명보다 `Team / Project / Section`이 실제 작업 맥락을 전달하는 역할을 해야 한다
- 우측 유틸은 얌전해야 한다

### TeamsPage

기준: **Variant A**

- 팀 선택은 entity list가 아니라 workspace 선택처럼 보여야 한다
- 카드는 넉넉한 여백과 짧은 설명을 가진다
- 협업 시작의 톤이 읽혀야 한다

### ProjectsPage

기준: **Variant A**

- 팀 홈 역할
- 프로젝트 카드는 text-first workspace card
- `새 프로젝트`만 primary
- `Dictionary / Members / Settings`는 utility cluster로 내린다

### DiagramsPage

기준: **Variant C**

- dense list 기본
- 문서 타입 badge + 제목 + 최근 수정 + 협업 상태 + 연결 자산을 빠르게 훑게 만든다
- project context header는 A의 calm tone을 유지하되, 리스트 본문은 C의 생산성 톤으로 간다

### DictionaryPage

기준: **Variant A**

- 팀 자산 허브처럼 보여야 한다
- 문서 작업을 위한 기반 자산이라는 설명이 먼저 와야 한다
- 관리 액션은 utility로 내리고, 실제 작업 영역은 안정적으로 보이게 한다

## 구현 규칙

1. **상위 쉘은 여백이 있고 차분해야 한다**
- 큰 제목, 분명한 컨텍스트, 과하지 않은 색 사용

2. **문서 목록은 조밀해야 한다**
- dense list
- 비교 가능한 row 메타
- 카드 남발 금지

3. **운영 메타는 보조**
- 최근 활동
- 경고
- 협업 상태
- 알림성 정보는 보조 영역 또는 row 메타 안으로 제한

4. **문서 타입이 늘어나도 구조는 유지**
- ERD
- Markdown
- Screen Spec

중 무엇이 추가돼도

- Header 구조
- Project workspace 구조
- Document hub 구조

는 유지돼야 한다

## 다음 구현 순서

1. `Header`를 Variant A 톤으로 재설계
2. `ProjectsPage`를 Variant A 기준으로 재구성
3. `DiagramsPage`를 A의 상단 + C의 dense list 조합으로 구현
4. `DictionaryPage`를 A 기준 자산 허브로 재정리
5. 브라우저 검증 후, 이 쉘 위에서 Markdown 플러그인 1단계 착수
