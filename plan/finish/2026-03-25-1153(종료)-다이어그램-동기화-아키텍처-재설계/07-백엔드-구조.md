# 07. 백엔드 구조

## 백엔드 목표

프론트가 플랫폼 코어 + 플러그인 구조로 가려면, 백엔드도 같은 원칙을 따라야 한다.

즉 백엔드 역시:

- transport
- session / room
- document sync
- lock
- presence
- persistence
- plugin registry

를 분리해야 한다.

핵심은 `백엔드 코어가 ERD 도메인 의미를 직접 해석하지 않는 것`이다.

## 권장 패키지 구조

```text
src/main/java/com/smarterd/
├── collaboration/
│   ├── transport/
│   ├── session/
│   ├── router/
│   ├── handler/
│   ├── document/
│   ├── lock/
│   ├── presence/
│   ├── persistence/
│   └── plugin/
│
└── domain/
    ├── diagram/
    │   └── collaboration/
    ├── screen/
    │   └── collaboration/
    └── design/
        └── collaboration/
```

## 코어 모듈 책임

| 패키지 | 책임 |
|------|------|
| `transport/` | WebSocket 수명주기, 인증, rate limiting |
| `session/` | 문서 세션 open/close, room join/leave |
| `router/` | 메시지 타입 라우팅 |
| `handler/` | document / lock / presence / handoff 채널 처리 |
| `document/` | 공유 문서 상태 relay와 revision 관리 |
| `lock/` | generic scope lock 상태와 TTL 정리 |
| `presence/` | 참여자/awareness 관리 |
| `persistence/` | snapshot 저장, checkpoint, recovery bootstrap, migration |
| `plugin/` | 문서 타입별 plugin lookup과 codec 연결 |

## 미래 서비스 분리 전제의 모듈 경계

이번 문서는 당장 MSA로 쪼개는 설계가 아니다.  
대신 나중에 분리할 수 있도록 현재 코드 수준에서 모듈 경계를 먼저 고정한다.

| 모듈 경계 | 현재 책임 | 현재 코드 위치 | 나중에 분리 가능 여부 |
|------|------|------|------|
| `document-metadata` | 문서 기본 메타, `pluginId`, `engineId`, 권한/라우팅 기준 | 현재는 bootstrap/load 메타로 암묵 존재 | 높음 |
| `collaboration-runtime` | room/session, engine delta relay, handoff, lock, presence | `collaboration/transport`, `session`, `router`, `handler`, `document`, `lock`, `presence` | 높음 |
| `document-persistence` | snapshot, checkpoint, recovery, codec, migration | `collaboration/persistence` | 높음 |
| `asset-lifecycle` | upload token, reference marking, preload, GC | `AssetLifecycleService` 중심 | 높음 |
| `plugin-domain` | ERD/화면기획/디자인의 도메인 규칙, serializer, resolver, validation | `domain/diagram`, `domain/screen`, `domain/design` | 높음 |

핵심 규칙:

- `collaboration-runtime`은 하나의 강한 일관성 경계로 본다.
- live collaborative state와 live revision의 authoritative owner는 `collaboration-runtime`이다.
- `lock`, `presence`, `handoff`를 초기에 별도 서비스로 나누지 않는다.
- `document-persistence`는 runtime의 downstream 저장 경계이며, checkpoint된 snapshot/revision을 영속화하지만 live revision owner는 아니다.
- `plugin-domain`은 기능/도메인별로 따로 분리할 수 있지만, 공통 협업 상태 관리는 `collaboration-runtime`을 통한다.
- `plugin-domain`은 도메인 규칙을 소유하지만, live collaborative state 자체는 소유하지 않는다.
- `document-metadata`는 가장 먼저 분리해도 되는 후보지만, 협업 중 authoritative source는 아니다.

## document-metadata 최소 계약

`document-metadata`는 bootstrap과 접근 제어를 위한 얇은 경계다.  
이 모듈이 협업 상태를 직접 소유하지는 않지만, 어떤 plugin/engine으로 문서를 열어야 하는지는 authoritative 하게 제공해야 한다.

```java
public record DocumentMetadata(
    @NonNull Long documentId,
    @NonNull String pluginId,
    @NonNull String engineId,
    @NonNull String ownerId,
    @NonNull Set<String> memberIds
) {}
```

```java
public interface DocumentMetadataService {
    @NonNull DocumentMetadata loadDocumentMetadata(@NonNull Long documentId, @NonNull String requesterId);
}
```

규칙:

1. `pluginId`, `engineId`, 접근 권한 판단의 authoritative source는 `DocumentMetadataService`다.
2. `DocumentMetadataService`는 live room 상태, lock 상태, revision을 직접 관리하지 않는다.
3. bootstrap은 메타 조회 후에만 runtime/persistence로 진입한다.

```java
public record DocumentBootstrapHeader(
    int pluginSchemaVersion,
    int snapshotFormatVersion,
    @Nullable Integer artifactVersion,
    long revision,
    boolean snapshotAvailable,
    boolean artifactAvailable
) {}
```

```java
public interface DocumentBootstrapReader {
    @NonNull DocumentBootstrapHeader loadBootstrapHeader(@NonNull Long documentId);
}
```

추가 규칙:

4. `DocumentMetadataService`는 bootstrap header를 소유하지 않는다.
5. bootstrap header의 authoritative source는 `document-persistence`다.

## 모듈 경계 가드레일

아래와 같이 쪼개면 안 된다.

- `lock`만 별도 서비스
- `presence`만 별도 서비스
- `handoff`만 별도 서비스
- `snapshot codec`만 별도 서비스

아래처럼 묶어야 한다.

- `collaboration-runtime` = transport + session + router + handler + document + lock + presence
- `document-persistence` = snapshot + checkpoint + bootstrap + migration
- `plugin-domain` = ERD / screen / design 각 도메인 규칙
- `asset-lifecycle` = binary asset와 reference 정합성

## 플러그인 모듈 책임

문서 타입별 backend plugin은 아래 역할만 맡는다.

| 역할 | 설명 |
|------|------|
| Scope Resolver | lock scope 의미 해석 |
| Compatibility Serializer | `content` 같은 파생 저장물 생성 |
| Compatibility Artifact Codec | artifact 기반 legacy/fallback 복원 |
| Asset Reference Extractor | snapshot에서 참조 중인 asset 식별 |
| Plugin Schema Migrator | plugin schema 버전 업그레이드 |
| Artifact Migrator | artifact 버전 업그레이드 |
| Domain Validation Hook | 필요 시 domain 무결성 검증 |

즉 backend plugin도 `table` 같은 의미를 코어에 올리지 않는다.

## 메시지 구조

메시지 채널은 하나의 연결에서 타입으로 분리한다.

```text
/ws/document/{documentId}
├── document channel  -> engine delta relay / handoff
├── lock channel      -> scope lock acquire/release/heartbeat
├── presence channel  -> awareness / pointer / selection / viewport / tool state
└── control channel   -> ping / health / protocol upgrade
```

핵심은 `document channel`이 플러그인 command를 실행하지 않는다는 점이다.  
서버는 delta relay와 persistence coordinator에 가깝고, 도메인 의미는 plugin artifact codec/resolver를 통해서만 안다.

## Room과 Session

```java
public final class DocumentRoomManager {
    public JoinResult join(@NonNull Long documentId, @NonNull WebSocketSession session, @NonNull UserPrincipal principal);
    public LeaveResult leave(@NonNull Long documentId, @NonNull WebSocketSession session);
    public void broadcastExcept(@NonNull Long documentId, @NonNull WebSocketSession except, @NonNull ByteBuffer payload);
    public void sendTo(@NonNull WebSocketSession session, @NonNull ByteBuffer payload);
}
```

이 매니저는 아래만 책임진다.

- 세션 등록/해제
- room broadcast
- 현재 참여자 목록 연계

아래는 책임지지 않는다.

- 테이블/섹션/프레임 의미 해석
- 스냅샷 직렬화 규칙
- 플러그인별 도메인 검증

## Plugin bootstrap 계약

문서 bootstrap과 recovery는 `documentId`만으로는 부족하다.  
반드시 어떤 플러그인으로 해석해야 하는지 같이 내려와야 한다.

```java
public record PersistedDocument(
    @NonNull Long documentId,
    @NonNull String pluginId,
    @NonNull String engineId,
    int pluginSchemaVersion,
    int snapshotFormatVersion,
    @Nullable Integer artifactVersion,
    long revision,
    @NonNull byte[] snapshot,
    @Nullable byte[] compatibilityArtifact
) {}
```

```java
public record DocumentCheckpoint(
    @NonNull Long documentId,
    @NonNull String pluginId,
    @NonNull String engineId,
    int pluginSchemaVersion,
    int snapshotFormatVersion,
    @Nullable Integer artifactVersion,
    long revision,
    @NonNull byte[] snapshot,
    @Nullable byte[] compatibilityArtifact
) {}
```

```java
public final class DocumentPersistenceCoordinator {
    public void checkpoint(@NonNull DocumentCheckpoint checkpoint);
    public Optional<PersistedDocument> load(@NonNull Long documentId);
}
```

bootstrap 규칙:

1. 먼저 `DocumentMetadataService`로 `pluginId`, `engineId`, 권한을 확인한다.
2. 다음으로 `DocumentBootstrapReader`에서 persistence header를 읽는다.
3. load 결과에는 `pluginId`와 `engineId`가 metadata와 일치하는 값으로 포함된다.
4. 서버와 클라이언트는 모두 `pluginId`로 plugin registry를, `engineId`로 engine registry를 조회한다.
5. plugin 또는 engine을 찾지 못하면 복구를 진행하지 않고 fail-fast 한다.
6. plugin이 해당 `engineId`를 지원하지 않으면 fail-fast 한다.
7. snapshot decode는 core `DocumentSnapshotCodec`와 `SharedDocumentEngine`가 담당한다.
8. artifact fallback은 `ArtifactFallbackCapableCollaborationPlugin`인 경우에만 수행한다.
9. plugin schema version 또는 artifact version이 지원 범위를 벗어나면 migrator capability를 적용하거나 fail-fast 한다.
10. checkpoint write도 같은 메타를 모두 명시적으로 보존해야 한다.

## Persistence 구조

저장은 코어에서 관리하되, 플러그인이 파생 저장물을 제공할 수 있게 한다.

저장 규칙:

1. snapshot이 primary다.
2. `content` 같은 compatibility artifact는 secondary다.
3. artifact 생성은 plugin serializer가 맡는다.
4. asset binary는 별도 asset storage에 저장하고, snapshot은 reference만 가진다.
5. plugin의 `AssetReferenceExtractor`는 checkpoint 시 참조 asset 목록을 계산한다.
6. 저장 트리거는 persistence coordinator가 일원화한다.
7. live revision 증가와 ordering의 authoritative owner는 `collaboration-runtime`이다.
8. `document-persistence`는 runtime이 넘긴 revision/snapshot을 영속화하는 downstream이다.
9. snapshot format version은 core가 관리하고, plugin schema version은 plugin이 관리한다.
10. write path는 `DocumentCheckpoint`를 통해 load path와 대칭을 맞춘다.

runtime -> persistence 전달 규칙:

1. future split을 고려해 checkpoint 전달은 `at-least-once`를 기본으로 본다.
2. `document-persistence`는 같은 `documentId + revision` 조합에 대해 idempotent 해야 한다.
3. persistence가 일시 실패해도 live authoritative state는 여전히 `collaboration-runtime`에 있다.
4. shutdown flush 실패 시에도 마지막 authoritative live revision 판단은 runtime 기준이며, persistence는 최신 durable checkpoint 기준으로 복구한다.

capability 규칙:

- backend도 null 반환으로 capability를 판정하지 않는다.
- registry는 `BaseCollaborationPlugin`만 보관하고, coordinator/handler가 capability interface로 narrowing 한다.
- 즉 `instanceof ArtifactFallbackCapableCollaborationPlugin` 같은 방식으로만 분기한다.

plugin-domain의 기본값:

- 현재 단계에서 `plugin-domain`은 기본적으로 in-process plugin SPI로 유지한다.
- 즉 `ERD`, `screen`, `design`은 우선 같은 프로세스 안에서 모듈로 분리하고, 경계가 충분히 안정된 뒤에만 별도 서비스 후보로 검토한다.

## Asset 구조

wireframe / design 문서는 이미지, 아이콘, 첨부 같은 외부 asset을 포함할 수 있다.  
이 경우 문서 본문과 asset binary를 같은 저장 경로로 취급하면 복구와 GC가 꼬인다.

```java
public interface AssetLifecycleService {
    @NonNull Collection<AssetTicket> prepareUpload(@NonNull Long documentId, @NonNull Collection<AssetRef> refs);
    void markReferenced(@NonNull Long documentId, @NonNull Collection<AssetRef> refs);
    void garbageCollectUnreferenced(@NonNull Long documentId);
}
```

규칙:

1. snapshot은 asset binary를 직접 저장하지 않고 reference만 가진다.
2. checkpoint 시점에 현재 snapshot이 참조하는 asset 목록을 계산한다.
3. bootstrap 시 asset manifest를 기반으로 필요한 asset preload를 준비한다.
4. asset orphan 정리는 문서 checkpoint 성공 후 별도 단계로 수행한다.

락은 generic scope lock으로 통일한다.

## 구현 가드레일

백엔드 코어에서 금지하는 것:

- `table`, `column`, `edge` 전용 필드와 분기
- 특정 plugin 전용 JSON 구조 하드코딩
- 도메인 검증과 transport 처리의 혼합

플러그인으로 내리는 것:

- ERD snapshot compatibility artifact 생성
- scope 해석
- 필요한 도메인 validation hook

이번 백엔드 구조의 목적은 단순하다.  
`스마트 ERD의 협업 서버`를 넘어서 `협업 문서 플랫폼 서버`가 되도록 코어와 도메인을 분리한다.

## Graceful Shutdown

Graceful shutdown도 코어 관점에서 정의해야 한다.

```java
public final class CollaborationShutdownHook implements SmartLifecycle {
    private final DocumentRoomManager roomManager;
    private final DocumentPersistenceCoordinator persistenceCoordinator;
    private final CollaborationProperties properties;
}
```

종료 규칙:

1. 타임아웃 내에서 dirty document checkpoint를 최대한 flush 한다.
2. flush 실패가 있어도 shutdown이 무한 대기하지 않게 한다.
3. 모든 WebSocket 세션을 정리된 순서로 닫는다.
4. plugin별 artifact 생성 실패가 전체 종료를 막지 않게 격리한다.

## 보안 고려사항

### CRDT delta relay 무검증 위험

서버가 delta 바이너리를 거의 relay만 하는 구조라면, 악의적 클라이언트가 조작된 payload를 보낼 위험이 있다.

대응 단계:

| 단계 | 전략 | 비용 |
|------|------|------|
| v1 | relay 중심 + 클라이언트 apply 실패 시 재동기화 | 낮음 |
| v2 | 서버 shadow state로 기본 무결성 검증 | 중간 |
| v3 | plugin validation hook까지 포함한 완전 검증 | 높음 |

### Presence / Awareness 스푸핑

presence payload의 사용자 식별 정보는 세션 principal 기준으로 검증해야 한다.  
payload 내부 userId/clientId를 그대로 신뢰하면 안 된다.

### PluginId 스푸핑

bootstrap, load, lock scope, persistence에 사용되는 `pluginId`는 서버 저장 메타와 registry 기준으로 검증해야 한다.  
클라이언트가 임의 `pluginId`를 보내는 것만으로 문서 해석기가 바뀌면 안 된다.

## Legacy 마이그레이션 경계

기존 smart-erd 문서는 새 메타가 없을 수 있다. 이 경우 전환 규칙을 문서에 명시해야 한다.

1. `pluginId`와 `engineId`가 없는 기존 문서는 기본적으로 `pluginId='erd'`, `engineId='yjs'`로 간주한다.
2. 가능하면 오프라인 백필 마이그레이션으로 `pluginId='erd'`, `engineId='yjs'`, `pluginSchemaVersion`, `snapshotFormatVersion`을 채운다.
3. 오프라인 백필이 어려우면 첫 load 시 lazy migration을 허용할 수 있다.
4. snapshot이 없고 legacy `content`만 있는 문서는 ERD plugin의 artifact codec이 초기 snapshot을 복원한다.
5. lazy migration이 성공하면 다음 저장 시 새 메타를 영구 반영한다.

## 현행 대비 변경 요약

| 현행 컴포넌트 | 목표 구조 | 변경 이유 |
|-------------|------|----------|
| 거대 WebSocket handler | transport + router + channel handler | SRP |
| 도메인별 얽힌 snapshot 처리 | core snapshot codec + persistence coordinator + plugin artifact codec | 저장 경계 분리 |
| ERD 전용 room/lock 결합 | document room + generic scope lock | 재사용성 |
| 문서 타입별 ad-hoc bootstrap | persisted metadata + plugin registry | 확장성 |
| 도메인별 직접 직렬화 | snapshot primary + compatibility artifact secondary | 마이그레이션 안정성 |
