## 이 문서를 왜 다시 쓰는가

이번 재설계는 단순히 ERD 편집기의 버그를 고치는 수준이 아니다. 현재 시스템은 기능이 계속 추가되면서 아래 관계가 과도하게 얽혀 있다.

- Code 편집
- ERD 편집
- 양방향 동기화
- 실시간 협업 전파
- 서버 저장
- 복구와 재진입

그 결과, 동기화 오류, 저장 경로 중복, 성능 저하, 커서 튐 같은 사이드 이펙트, 개념 충돌이 반복되고 있다.  
사용자 요구사항의 핵심은 다음과 같다.

- 프로세스를 단순화하고 싶다.
- 필요하면 완전히 뜯어고쳐도 된다.
- 다른 사이드 이펙트 없이 기능적으로 안전해야 한다.
- ERD만이 아니라 앞으로 화면 기획서, 디자인 등 다른 협업 메뉴에도 재사용 가능한 구조여야 한다.
- 유지보수, 신규 기능 추가, 업무영역 분리, SOLID 원칙을 실제 구현 가능한 수준으로 달성해야 한다.

즉 이번 문서의 최종 목표는 `ERD 전용 구조 개선`이 아니라 `재사용 가능한 협업 문서 플랫폼 코어 설계`다.  
ERD는 그 코어 위에 올라가는 첫 번째 플러그인으로 다룬다.

## 사용자 요구사항 체크리스트

아래 항목은 이번 설계에서 빠뜨리면 안 되는 필수 요구다.

| 요구사항 | 반영 방식 |
|------|------|
| Code - ERD - 동기화 - 저장 관계를 단순화 | 공통 플랫폼 코어와 문서 플러그인으로 경계 분리 |
| 기능 추가로 누적된 뒤엉킨 프로세스 해소 | 입력, 공유 상태, 투영, 동기화, 저장, 락 책임을 분리 |
| 동기화/저장/성능 이슈 근본 해결 | 로컬 입력 계약과 원격 동기화 계약을 분리 |
| 완전 재설계 허용 | 현행 구조 호환보다 장기 구조를 우선하되, 단계적 마이그레이션으로 적용 |
| 전체 데이터가 아닌 변경분만 전송 | 원격 전파는 engine delta 기준으로 유지하고, v1 기본 구현은 Yjs update 사용 |
| 중앙 데이터 기준으로 Code/ERD 표현 | 공유 권위 상태를 플랫폼 코어의 DocumentStore로 통합 |
| 유형/버전 기반 스킵 | origin/version은 유지하되 dirty draft 보호와 projector skip 정책을 추가 |
| 백엔드도 단순 데이터 관리와 릴레이 중심 | transport/router/handler/persistence/plugin registry로 분리 |
| 테이블 락은 별도 관심사 | 코어는 generic scope lock, ERD는 `table` scope resolver로 구현 |
| ERD 외 다른 메뉴도 붙일 수 있어야 함 | 화면기획서/디자인도 같은 코어 위의 plugin으로 확장 가능하도록 설계 |
| SOLID + 디자인 패턴 적극 적용 | core/plugin/contracts/ports 기준으로 SRP, OCP, DIP를 실제 구조에 반영 |
| 유지보수성과 신규 기능 확장성 확보 | 코어는 도메인을 모르고, 문서 타입은 플러그인으로만 확장 |

## 사용자 초기 구상 보존 메모

아래 내용은 최초 요청에서 나온 구상을 잊지 않기 위해 그대로 보존하는 메모다.  
최종 설계는 이 구상을 확장하고 일반화하는 방향으로 정리한다.

### 1. 중앙의 문서 데이터

사용자 구상의 핵심은 “중앙의 다이어그램 데이터가 있고, 프론트와 백엔드가 이 데이터를 중심으로 연결된다”는 점이었다.

- 프론트엔드에는 문서 데이터를 관리하고 서버와 연결하는 기능이 필요하다.
- 백엔드도 해당 문서 데이터를 관리하고 각 클라이언트와 연결하는 기능이 필요하다.
- 이때 프론트와 백엔드는 “문서 데이터 자체”와 “변경된 데이터”를 중심으로 연결된다.
- 전체 문서를 매번 밀어 넣는 대신, 가능한 한 변경분만 전송하는 프로토콜이 필요하다.

최종 설계에서는 이 개념을 `Shared Authoritative State + delta transport`로 일반화한다.

### 2. Code / ERD는 문서 데이터 기반 표현

사용자 구상에서는 Code와 ERD가 다이어그램 데이터를 기반으로 작성되고 표현된다고 봤다.

- 코드 에디터에서 입력이 발생하면 문서 데이터로 전달한다.
- 문서 데이터가 갱신되면 Code와 ERD에 업데이트를 전달한다.
- 전달 시 업데이트 유형과 버전을 함께 실어, 내가 보낸 변경이면 스킵하고 신규 버전이면 반영한다.
- 반영 성공 후 백엔드로 전달하고, 백엔드는 이를 다른 클라이언트에 전달한다.
- 다른 클라이언트는 자기 변경이 아닌 경우에만 반영한다.

최종 설계에서는 이 사고를 다음처럼 정리한다.

- Code와 ERD는 모두 공유 상태의 projection이다.
- 유형/버전 사고는 유지하되, `origin/requestId/revision`과 `dirty draft 보호`를 함께 사용한다.
- View 반영 성공을 서버 전송의 선행조건으로 두지는 않는다.
- 대신 공유 상태 변경 즉시 원격 delta 전파, View 반영은 각 projector가 독립적으로 처리한다.

### 3. 락은 별도 관심사

사용자 구상에서는 협업 환경 때문에 테이블 수정 선점 기능이 중요하고, 이 락 정보는 본 데이터 처리와 분리된 별도 연결/기능으로 관리하고 싶다는 의도가 있었다.

- 락 정보는 문서 데이터를 참조하지만 별도 정보로 관리
- 각 클라이언트에서도 락 상태를 별도 관리
- 데이터 처리 채널의 부하와 책임을 줄이기 위해 분리

최종 설계에서는 “별도 관심사”라는 의도는 유지하되, 연결은 단일화한다.

- 락은 동기화 본체와 다른 책임으로 분리
- 다만 연결은 별도 WebSocket이 아니라 하나의 연결에서 메시지 타입 채널로 분리
- 코어는 `scope lock`만 알고, ERD는 이를 `table scope`로 매핑

### 4. SOLID와 패턴은 구현 가능한 수준이어야 한다

최초 요청의 마지막 문장은 매우 중요하다.

- SOLID 원칙을 반드시 준수해야 한다.
- 가능하면 디자인 패턴도 적극 채용해야 한다.
- 실제 구현이 아니라 분석 및 설계여야 한다.

이번 문서군은 이 요청을 다음 기준으로 해석한다.

- 문서상 슬로건이 아니라, 실제 인터페이스와 모듈 경계로 떨어져야 한다.
- ERD뿐 아니라 다른 메뉴를 붙였을 때도 구조가 유지되어야 한다.
- 그래서 `재사용 가능한 모듈화`를 검증 기준으로 삼는다.

## 최종 방향 요약

이번 설계의 최종 결론은 아래 한 줄로 요약된다.

`협업 플랫폼 코어를 만들고, ERD를 첫 번째 문서 플러그인으로 재배치한다.`

이 방향을 택하는 이유는 명확하다.

1. 지금 문제는 ERD 내부 로직만의 문제가 아니라, 협업형 문서 시스템의 공통 관심사가 ERD 코드에 섞여 있다는 점이다.
2. 앞으로 화면 기획서, 디자인 문서, 다른 협업 메뉴를 추가할 계획이라면, ERD 전용 용어와 구조로는 재사용 가능한 모듈화를 만들 수 없다.
3. 재사용성과 SOLID를 실제로 달성하려면 코어가 `table`, `edge`, `dsl`, `reactflow`, `monaco`를 몰라야 한다.

## 범위

### 이번 문서가 다루는 범위

- 협업 문서 플랫폼 코어의 책임 정의
- 문서 플러그인 계약 정의
- ERD를 첫 번째 플러그인으로 올리는 구조
- 로컬 입력, 공유 상태, 원격 동기화, 저장, 락, 프레즌스의 경계
- 프론트엔드/백엔드 모듈 분리 기준
- 향후 MSA 전환을 고려한 모듈 경계 기준
- SOLID와 디자인 패턴이 실제 코드 구조로 이어질 수 있는 계약

### 이번 문서가 바로 하지 않는 것

- 모든 현행 구현의 즉시 폐기
- `content` 계약의 즉시 제거
- ERD 외 메뉴의 구체 UI 설계
- CRDT 교체나 저장소 교체 자체를 목표로 한 재설계
- 즉시 서비스 분리 자체를 목표로 한 MSA 전환

## 설계 대상의 용어 정의

| 용어 | 의미 |
|------|------|
| Collaboration Core | 동기화, 세션, 저장, 락, 프레즌스 같은 공통 플랫폼 영역 |
| Document Plugin | ERD, 화면 기획서, 디자인처럼 문서 타입별 도메인 구현 |
| Shared Authoritative State | 협업 대상이 되는 공유 권위 상태. 코어는 `SharedDocumentEngine` 계약만 알고, v1 기본 구현은 Y.Doc 기반이다 |
| Local Draft | 사용자가 타이핑 중인 로컬 편집 버퍼. 파싱/검증 성공 전까지 공유되지 않음 |
| Projection | 공유 상태를 View가 소비 가능한 형태로 변환한 결과 |
| Compatibility Artifact | 과도기 동안 유지하는 파생 저장물. 예: `content` JSON |
| Asset Lifecycle | 이미지/아이콘/첨부처럼 문서 외부 binary asset의 참조, 업로드, 복구, GC를 관리하는 공통 계약 |

## 핵심 설계 원칙

1. **권위 상태는 하나만 둔다.**  
   공유 대상은 플랫폼 코어의 `DocumentStore`이며, 코어는 `SharedDocumentEngine` 계약에 의존한다. v1 기본 엔진은 Y.Doc이지만, 코어 계약은 특정 엔진에 고정하지 않는다.

2. **로컬 draft와 공유 상태를 분리한다.**  
   코드 편집기나 텍스트 편집기의 불완전 입력은 로컬 draft에만 존재한다. 파싱/검증 성공 전까지는 공유 상태에 반영하지 않는다.

3. **Command와 네트워크 payload를 분리한다.**  
   `Command`는 로컬 입력 계약이다.  
   원격 동기화의 canonical payload는 `SharedDocumentEngine`이 정의하는 delta 프로토콜이며, v1 기본 구현은 Yjs update다.

4. **코어는 도메인을 모른다.**  
   코어에는 `table`, `column`, `erd`, `dsl` 같은 용어가 들어가면 안 된다. 그런 개념은 플러그인으로 내린다.

5. **뷰는 projection만 담당한다.**  
   Code View, ERD View, 화면 기획 View, 디자인 View는 모두 권위 상태를 직접 수정하지 않는다.

6. **락은 generic scope lock이다.**  
   코어는 `scopeId`, `scopeType`, `mode`만 안다.  
   ERD의 테이블 락, 화면 기획서의 섹션 락, 디자인의 프레임 락은 각 플러그인이 scope resolver로 정의한다.

7. **저장은 플랫폼 코어가 주관한다.**  
   스냅샷 저장, unload 저장, 복구 bootstrap은 코어가 맡고, 플러그인은 필요하면 호환용 파생 저장물을 제공한다.

8. **asset과 문서 본문을 구분한다.**  
   이미지/아이콘/첨부 같은 binary asset은 snapshot과 별도 lifecycle로 관리한다. 문서 본문은 asset reference만 가진다.

9. **ephemeral 협업 상태를 별도 채널로 다룬다.**  
   포인터, selection box, viewport, active tool 같은 캔버스 협업 상태는 shared authoritative state와 분리하고 presence 계층에서 다룬다.

10. **재사용 가능한 모듈화가 검증 기준이다.**  
   설계 완료의 기준은 ERD가 잘 동작하는 것만이 아니다.  
   두 번째 문서 타입을 코어 수정 최소화로 올릴 수 있어야 한다.

11. **서비스 분리보다 모듈 경계를 먼저 고정한다.**  
   당장은 모듈러 모놀리스를 유지하더라도, 나중에 `document-metadata`, `collaboration-runtime`, `asset-lifecycle`, `plugin-domain` 단위로 분리 가능한 경계를 먼저 세운다.

12. **모듈별 authoritative owner를 문서에 명시한다.**  
   특히 `document-metadata`, `collaboration-runtime`, `document-persistence`, `plugin-domain`은 “무엇을 소유하는가 / 소유하지 않는가”를 먼저 고정한다.

## 구현 완료 판단 기준

이번 재설계가 성공했다고 보기 위한 기준은 아래와 같다.

- ERD 기능이 기존보다 덜 꼬이고, 코드 입력과 시각 편집의 사이드 이펙트가 줄어든다.
- 저장/동기화/락/프레즌스의 책임이 서로 섞이지 않는다.
- 코어 모듈은 ERD 도메인 용어를 몰라도 된다.
- ERD는 플러그인으로 붙는다.
- wireframe나 design canvas도 코어 재설계 없이 plugin + adapter 조합으로 올릴 수 있다.
- 두 번째 문서 타입을 붙일 때 코어를 다시 뜯어고치지 않아도 된다.
- 향후 서비스 분리 후보 모듈이 코드 구조만 봐도 식별 가능하다.
- SOLID 원칙이 “문서상 구호”가 아니라 인터페이스와 모듈 구조로 드러난다.
