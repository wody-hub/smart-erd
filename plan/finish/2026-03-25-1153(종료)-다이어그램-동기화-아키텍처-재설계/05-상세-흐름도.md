# 05. 상세 흐름도

## 흐름 A: 텍스트형 편집기 입력

이 흐름은 ERD DSL뿐 아니라, 화면 기획서의 마크업/JSON 편집기 같은 텍스트 기반 메뉴에도 재사용된다.

```text
[Text Editor Adapter]
    │ 사용자 입력
    ▼
[Local Draft Store]
    │ dirty=true
    ▼
[Parser / Validator] (plugin 내부)
    ├─ 실패 -> diagnostics 갱신 후 종료
    └─ 성공 -> parsed result 생성
    ▼
[Diff / Command Translator] (plugin 내부)
    │ DocumentCommand[] 생성
    ▼
[Mutation Policy]
    │ plugin command -> DocumentMutation
    ▼
[DocumentStore]
    │ shared state 반영
    │ revision 증가
    ▼
[ChangeBus] ── emit ──┬───────────────┬──────────────────┬─────────────────┐
                      │               │                  │                 │
                      ▼               ▼                  ▼                 ▼
               [Projector]   [CollaborationRuntime] [UndoManager] [PersistenceCoordinator]
```

핵심 규칙:

- parse 실패 draft는 local에만 남는다.
- parse 성공 전에는 shared state를 건드리지 않는다.
- projector는 dirty draft가 살아 있으면 본문 overwrite를 하지 않는다.

## 흐름 B: 시각 편집기 입력

이 흐름은 ERD 캔버스와 디자인 캔버스처럼 구조화된 편집기에 해당한다.

```text
[Canvas Adapter]
    │ 드래그, 리사이즈, 연결, 속성 변경
    ▼
[Plugin Input Adapter]
    │ UI 이벤트 -> DocumentCommand
    ▼
[Mutation Policy]
    │ command -> mutation
    ▼
[DocumentStore]
    │ shared state 반영
    ▼
[ChangeBus]
    ├─ plugin projector -> 새 view model 생성
    ├─ collaboration runtime -> 원격 delta 전송
    └─ persistence coordinator -> checkpoint 후보 갱신
```

이 경로는 parser가 필요 없다는 점만 다르고, 나머지는 텍스트형 편집기와 같은 코어를 사용한다.

## 흐름 C: 원격 변경 수신

```text
[WebSocket Transport]
    │ remote delta 수신
    ▼
[CollaborationRuntime]
    │ envelope 검증
    │ document channel update 적용
    ▼
[DocumentStore]
    │ CRDT merge
    ▼
[ChangeBus]
    ├─ projector 갱신
    ├─ undo stack 정책 반영
    └─ persistence coordinator 상태 갱신
```

추가 규칙:

- dirty draft가 없는 view는 즉시 projection 갱신
- dirty draft가 있는 text editor는 “원격 변경 있음” 상태만 표시
- 실제 본문 병합 전략은 plugin 정책이 결정

## 흐름 D: dirty draft 재조정

`dirty draft`가 있는 동안 원격 변경이 들어오면 아래 순서를 따른다.

```text
[CollaborationRuntime]
    │ remote revision 수신
    ▼
[Draft Coordinator]
    │ 현재 draft 상태 확인
    ├─ clean
    │   -> 즉시 projector 갱신
    └─ dirty-valid / dirty-invalid
        -> remote-pending 전이
        -> editor 본문 overwrite 금지
        -> "원격 변경 있음" 상태 표시
```

사용자 선택 또는 plugin 정책에 따라 후속 동작:

```text
1. acceptRemote
   -> local draft 폐기
   -> remote revision 적용
   -> clean

2. keepLocalAndRebase
   -> latest shared state를 base로 재설정
   -> local draft 재파싱
   -> 성공: dirty-valid
   -> 실패: dirty-invalid 유지

3. compareLater
   -> pending 상태 유지
   -> save/release 정책은 제한
```

저장 및 이탈 규칙:

- `dirty-invalid` 또는 `remote-pending` 상태에서는 shared save를 막는다.
- 이 상태에서 페이지를 이탈하면 local recovery cache에만 draft를 남길 수 있다.
- authoritative snapshot에는 parse/validate된 shared state만 저장한다.

락 상호작용 규칙:

- `remote-pending`에 진입한 상태에서 현재 scope lock을 이미 보유 중이면 `reconcile grace window`로 전환한다.
- grace window 동안에는 heartbeat를 유지할 수 있다.
- grace window 길이는 클라이언트가 아니라 서버 정책값 `reconcileHoldGraceMillis`를 따른다.
- 사용자가 `acceptRemote` 또는 `keepLocalAndRebase`를 선택하면 lock을 유지한 채 후속 편집을 계속할 수 있다.
- 사용자가 `compareLater`를 선택하거나 grace window가 만료되면 lock을 해제하고 readonly pending 상태로 내려간다.

## 흐름 E: 저장

저장은 코어가 주관하고, 플러그인은 필요하면 파생 저장물을 제공한다.

```text
[PersistenceCoordinator]
├─ checkpoint save
│   ├─ DocumentStore snapshot 추출
│   ├─ plugin asset binding으로 referenced asset manifest 추출
│   ├─ plugin serializer로 compatibility artifact 생성
│   ├─ AssetRuntime이 필요한 asset upload / reference 정합성 보장
│   └─ 서버 저장
│
└─ unload save
    ├─ keepalive 요청
    └─ 마지막 snapshot 저장
```

저장 규칙:

- primary 저장물은 snapshot
- secondary 저장물은 plugin serializer가 만드는 compatibility artifact
- binary asset은 snapshot 외부에 저장하고, 문서 본문은 asset reference만 가진다
- asset manifest는 checkpoint와 함께 기록하거나 재계산 가능해야 한다
- plugin은 저장 시점을 결정하지 않고, 저장 형식 일부만 제공한다
- `dirty-invalid` 또는 `remote-pending` 상태에서는 shared save 버튼을 비활성화한다
- 필요하면 `Save Local Draft` 같은 비공유 임시 저장만 별도 제공할 수 있다

## 흐름 F: 문서 초기 진입

```text
[DocumentPageHost]
    │
    ├─ 1. DocumentMetadataService로 문서 메타 조회
    │    -> { documentId, pluginId, engineId, ownerId, memberIds }
    ├─ 2. DocumentPersistence에서 bootstrap header 조회
    │    -> { pluginSchemaVersion, snapshotFormatVersion, artifactVersion,
    │         revision, snapshotAvailable, artifactAvailable }
    ├─ 3. PluginRegistry에서 pluginId로 plugin 결정
    ├─ 4. EngineRegistry에서 engineId로 engine 결정
    │    -> plugin.supportedEngineIds 포함 여부 검증
    ├─ 5. core 초기화
    │    ├─ DocumentStore
    │    ├─ SharedDocumentEngine
    │    ├─ DocumentSnapshotCodec
    │    ├─ CollaborationRuntime
    │    ├─ PresenceRuntime
    │    ├─ AssetRuntime
    │    ├─ ScopeLockRuntime
    │    └─ PersistenceCoordinator
    ├─ 6. plugin wiring
    │    ├─ input adapters
    │    ├─ projectors
    │    ├─ artifact serializer
    │    ├─ artifact codec
    │    ├─ asset binding
    │    ├─ presence mapper
    │    └─ scope resolver
    ├─ 7. snapshot bootstrap / fallback hydrate
    │    ├─ snapshot 있으면 core DocumentSnapshotCodec + SharedDocumentEngine으로 hydrate
    │    └─ snapshot 없고 artifact 있으면 plugin artifact codec으로 fallback hydrate
    ├─ 8. asset preload
    │    └─ asset manifest 기준으로 필요한 이미지/아이콘/font 미리 로드
    └─ 9. live session 진입
```

pluginId가 없거나 registry에서 plugin을 찾을 수 없으면 live 진입을 중단하고 fail-fast 한다.
engineId가 없거나 registry에서 engine을 찾을 수 없어도 fail-fast 한다.
plugin이 해당 engineId를 지원하지 않으면 fail-fast 한다.
snapshot format version 또는 plugin schema version을 지원하지 않아도 fail-fast 한다.

핵심 규칙:

- `DocumentMetadataService`는 문서 식별, plugin/engine 선택, 접근 권한만 제공한다.
- `pluginSchemaVersion`, `snapshotFormatVersion`, `artifactVersion`, `revision`, snapshot/artifact 존재 여부는 persistence bootstrap header가 제공한다.

## 흐름 G: 락 기반 편집 보호

락은 코어에서 generic하게 처리하고, 플러그인이 scope를 해석한다.

```text
[Plugin Scope Resolver]
    │ command 또는 focus 대상 분석
    ▼
[ScopeLockRuntime.acquire(scopeRef)]
    │
    ├─ 획득 성공 -> 편집 진행
    └─ 획득 실패 -> readonly / conflict UI 표시
```

ERD 예시:

- `table/주문` scope 획득

화면 기획서 예시:

- `section/결제영역` scope 획득

디자인 예시:

- `frame/landing-hero` scope 획득

wireframe / 자유형 캔버스 예시:

- 기본 드로잉은 optimistic merge + presence 위주
- 필요한 경우에만 `frame`, `group`, `document` scope로 승격

## 흐름 H: 두 번째 문서 플러그인 추가

이번 구조의 재사용성을 검증하려면 ERD 다음 플러그인을 붙일 수 있어야 한다.

```text
1. 새 plugin 패키지 생성
2. plugin의 `supportedEngineIds` 결정
3. Input Adapter / Projector / Scope Resolver 구현
4. 필요한 capability 결정
   - TextInputPipeline
   - Artifact Serializer / Artifact Codec
   - AssetBinding
   - PresenceMapper
5. 필요 시 SharedDocumentEngine 추가 등록
6. PluginRegistry 등록
7. 기존 core 수정 없이 DocumentPageHost에서 선택 가능
```

이 흐름이 성립해야 이번 재설계가 `ERD 전용 리팩터링`이 아니라 `협업 문서 플랫폼`이라고 부를 수 있다.

## 흐름 I: 자유형 캔버스 플러그인

`tldraw`/`Excalidraw` 같은 wireframe 메뉴는 아래 규칙을 따른다.

```text
[Canvas Adapter]
    │ shape 이동/리사이즈/연결/텍스트 편집
    ▼
[Plugin Input Adapter]
    │ 라이브러리 이벤트 -> DocumentCommand
    ▼
[Mutation Policy]
    │ scene mutation 생성
    ▼
[DocumentStore]
    │ shared scene state 반영
    ▼
[Projector]
    │ canvas engine이 소비할 scene model projection
```

핵심 규칙:

- `tldraw`/`Excalidraw`는 코어 위의 canvas adapter로 붙는다.
- 그 자체의 협업 엔진을 권위 상태로 삼지 않고, 코어의 shared authoritative state를 소비하는 방향을 기본값으로 둔다.
- pointer, selection box, viewport, active tool은 `PresenceRuntime` 경로로만 동기화한다.
- 이미지/아이콘 같은 asset은 `AssetRuntime` 경로로만 관리한다.
