# 08. 디자인 패턴 매핑

## 적용 패턴 요약

| 패턴 | 적용 위치 | 역할 |
|------|------|------|
| Plugin | Base Plugin + Capability Interface | 문서 타입 확장 포인트 |
| Mediator | DocumentStore | 공유 상태 변경의 단일 중재자 |
| Command | DocumentCommand | 로컬 입력 표준화 |
| Observer | ChangeBus | 변경 이벤트 발행 |
| Strategy | Projector / Artifact Serializer / Artifact Codec / Asset Binding / Presence Mapper / ScopeResolver | 플러그인별 전략 교체 |
| Adapter | Text/Canvas/Form Input Adapter | 이질적 입력을 공통 계약으로 변환 |
| Facade | PersistenceCoordinator / CollaborationRuntime | 복합 하위 시스템 은닉 |
| Chain of Responsibility | MessageRouter | 채널별 handler 라우팅 |
| Template Method | MessageHandler | 채널별 처리 뼈대 공통화 |

## 핵심 패턴 설명

### 1. Plugin

가장 중요한 패턴이다.  
ERD, 화면 기획서, 디자인 문서는 코어의 수정 대상이 아니라 플러그인 추가 대상이어야 한다.

```text
Core는 plugin interface만 알고,
ERDPlugin / ScreenSpecPlugin / DesignPlugin은 그 계약을 구현한다.
```

base plugin에 모든 책임을 몰아넣지 않고, 텍스트 입력이나 artifact fallback 같은 기능은 capability interface로 분리한다.

### 2. Mediator

공유 상태 변경의 중심은 `DocumentStore`다.  
View끼리 직접 대화하지 않고, 모두 DocumentStore와 ChangeBus를 통해 만난다.

### 3. Strategy

재사용성을 실제로 만들려면 아래가 전략 교체 지점이어야 한다.

- projector
- artifact serializer
- artifact codec
- asset binding
- presence mapper
- migrator
- scope resolver
- parser / validator

즉, 플러그인 추가는 전략 추가다.

### 4. Adapter

Monaco, React Flow, form UI 같은 구체 라이브러리는 adapter 뒤로 숨긴다.  
그래야 미래에 editor나 canvas 구현이 바뀌어도 core와 plugin domain은 덜 흔들린다.

## SOLID 원칙 매핑

### S — 단일 책임 원칙

이번 구조에서 책임은 아래처럼 쪼갠다.

| 모듈 | 책임 |
|------|------|
| DocumentStore | 공유 권위 상태 |
| CollaborationRuntime | 원격 delta 동기화 |
| PersistenceCoordinator | 저장 트리거와 checkpoint |
| ScopeLockRuntime | 락 수명주기 |
| PresenceRuntime | 참여자 / awareness |
| AssetRuntime | asset lifecycle |
| Plugin Projector | view projection |
| Plugin Serializer | 파생 저장물 생성 |
| Plugin ScopeResolver | scope 계산 |

### O — 개방 폐쇄 원칙

새 문서 타입 추가 시 기대하는 흐름은 다음과 같다.

```text
1. 새 plugin 구현
2. registry 등록
3. core 수정 최소화 또는 무수정
```

이 흐름이 안 되면 설계가 OCP를 달성하지 못한 것이다.

### L — 리스코프 치환 원칙

아래 구현체들은 상위 계약을 만족해야 한다.

- `ERDPlugin` / `ScreenSpecPlugin` / `DesignPlugin`
- `TextInputCapablePlugin` / `ArtifactFallbackCapablePlugin`
- `AssetCapablePlugin` / `PresenceCapablePlugin`
- `BaseCollaborationPlugin` / backend capability interfaces
- `Projector` 구현체
- `CompatibilityArtifactSerializer` 구현체
- `CompatibilityArtifactCodec` 구현체
- `MessageHandler` 구현체

호출자는 구체 타입을 몰라도 같은 계약으로 사용할 수 있어야 한다.

### I — 인터페이스 분리 원칙

큰 인터페이스 하나로 몰아넣지 않는다.

예시:

```typescript
interface DocumentMutationPort {
  applyMutation(mutation: DocumentMutation, meta: MutationMeta): void;
}

interface DocumentReadExecutor {
  getRevision(): number;
  execute<T>(query: DocumentReadQuery<T>): T;
}

interface DocumentSubscriptionPort {
  subscribe(listener: (event: DocumentChangeEvent) => void): Unsubscribe;
}

interface DocumentReadQuery<T> {
  run(context: DocumentReadContext): T;
}

interface DocumentReadContext {
  getEntity(ref: DocumentEntityRef): DocumentEntity | null;
  listRelated(ref: DocumentEntityRef, relation: string): DocumentEntityRef[];
  getProperty(ref: DocumentEntityRef, key: string): unknown;
}

interface ScopeResolver {
  resolveAffectedScopes(command: DocumentCommand): ScopeRef[];
}

interface CompatibilityArtifactSerializer {
  build(snapshot: Uint8Array): Uint8Array | null;
}

interface CompatibilityArtifactCodec {
  restoreSnapshot(artifact: Uint8Array, artifactVersion: number): Uint8Array;
}
```

### D — 의존성 역전 원칙

가장 중요한 원칙이다.

상위 모듈은 구체 구현이 아니라 계약에 의존한다.

좋은 예:

- View -> Adapter / Port
- Core -> Plugin Interface
- Backend Router -> MessageHandler

나쁜 예:

- View -> Y.Doc 직접 호출
- Core -> `ErdTableScopeResolver`
- Persistence -> ERD JSON 구조 직접 조립

## 구현 가드레일

아래와 같은 구조가 나오면 설계를 어긴다.

1. core 패키지에 `table`, `edge`, `dsl` 용어가 등장하는 경우
2. plugin이 transport 구현을 직접 호출하는 경우
3. projector가 저장 API를 직접 호출하는 경우
4. backend handler가 ERD 도메인 의미를 직접 해석하는 경우
5. draft 보호 규칙 없이 projection overwrite를 허용하는 경우
6. load는 버전 메타를 보는데 checkpoint write는 그 메타를 기록하지 않는 경우
7. 지원하지 않는 capability를 null 반환 규칙에만 의존하는 경우
8. 캔버스형 문서의 pointer/selection/asset lifecycle을 코어 바깥 임시 규칙으로 흘려보내는 경우
9. `engineId` 없이 plugin 메타만으로 bootstrap 하려는 경우

## 이번 문서군에서 노리는 설계 품질

이번 설계는 “패턴을 많이 썼다”가 목적이 아니다.  
패턴은 아래 목적을 달성하기 위해서만 사용한다.

- 재사용 가능한 모듈화
- 문서 타입 추가 시 코어 안정성 유지
- 유지보수 범위 축소
- 협업/저장/락/투영의 경계 명확화
- SOLID를 실제 구현 가능한 형태로 강제
