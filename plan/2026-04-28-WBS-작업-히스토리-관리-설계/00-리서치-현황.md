# WBS 작업 히스토리 관리 리서치

## 대상 이슈

- parent issue: [RIS-247](/RIS/issues/RIS-247)

## 사용자 요청 재정리

- WBS 항목마다 Notion/Monday.com처럼 문서화와 댓글 흐름이 필요하다.
- 문서에는 태그를 달고, 태그 중심으로 조회하는 별도 탭이 필요하다.
- WBS와 별개인 개인 TODO 공간이 필요하지만, 일부 TODO는 WBS와 연결되어 공유 진척 관리에 참여해야 한다.
- 작업 순서는 `RESEARCH -> 분석 -> 정책서 생성 -> 기획서 생성` 이다.

## 현재 코드베이스 관찰

### 1. WBS는 트리/일정/진척 중심이며 협업 문서 개념이 없다

- 백엔드 WBS 도메인은 `src/main/java/com/smarterd/domain/pm/wbs` 에만 존재한다.
- `WbsItem` 은 이름, 부모, 담당자, 기간, 진척률, 예상 M/M, 마일스톤만 가진다.
- `WbsService` 는 CRUD와 reorder만 제공하며, 문서/댓글/태그 참조 필드가 없다.
- 프런트 타입 `client/src/types/wbs.ts` 도 동일하게 문서 연결 정보가 없다.

해석:

- 지금 WBS에 필요한 것은 "기존 WBS를 더 똑똑하게 수정" 하는 수준이 아니라, 별도 협업 아티팩트와 연결 모델을 추가하는 일이다.

### 2. 프로젝트 문서 플랫폼은 이미 있다

- 문서 타입 공통 계약은 `client/src/types/document.ts` 에 있다.
- 문서 허브와 생성 다이얼로그는 `client/src/components/workspace` 아래에 존재한다.
- markdown 문서는 `src/main/java/com/smarterd/domain/markdown/service` 에서 템플릿과 descriptor를 제공한다.
- 화면기획/ERD도 같은 문서 플랫폼 위에서 움직인다.

해석:

- 새 "작업 문서" 기능을 WBS 안에 독립 저장소로 따로 만들기보다, 기존 프로젝트 문서 플랫폼을 재사용하는 쪽이 훨씬 안전하다.

### 3. 프로젝트 이슈는 존재하지만 댓글 스레드가 없다

- `src/main/java/com/smarterd/domain/pm/issue/entity/ProjectIssue.java` 는 제목/설명/상태/우선순위/담당자만 가진다.
- 현재 issue 모듈에는 댓글 엔티티나 활동 로그 엔티티가 없다.
- 프런트 `client/src/types/issues.ts` 도 동일하게 댓글 모델이 없다.

해석:

- 사용자가 원하는 "작업별 댓글" 은 현재 이슈 모듈로도 바로 충족되지 않는다.
- 따라서 댓글 기능을 새로 만들 때 WBS 전용 댓글, 이슈 전용 댓글을 각각 만들면 중복이 커진다.

### 4. 프로젝트 허브는 WBS / Gantt / Issues / Staffing / Documents 탭을 이미 갖고 있다

- `client/src/pages/diagram/DiagramsPage.tsx` 기준으로 프로젝트 허브 탭 구조가 이미 존재한다.
- 따라서 "태그 탭", "내 작업 탭" 을 같은 허브 정보구조 안에 추가하는 방향이 자연스럽다.

### 5. Gantt는 WBS를 기반으로 보고 있지만 자체 편집 제한이 있다

- 최근 변경 중인 `client/src/components/gantt/GanttTab.tsx` 와 `client/src/components/wbs/*` 를 보면 WBS/Gantt 연동은 계속 확장 중이다.
- 사용자의 "WBS 참조 TODO는 일정 리스크 관리 대상" 요구를 만족하려면 TODO가 WBS/Gantt 양쪽에서 가시화되어야 한다.

## 핵심 문제 정의

### 문제 1. 작업 맥락과 문서 맥락이 분리되어 있다

- WBS는 일정과 구조를 관리한다.
- 문서는 문서 허브에서 따로 관리된다.
- 둘을 연결하는 공식 참조 구조가 없다.

### 문제 2. 공개 범위가 다른 작업을 한 모델에 담기 어렵다

- WBS는 프로젝트 공유 객체다.
- 사용자가 원하는 TODO는 기본적으로 개인 작업 공간이다.
- 단, WBS에 참조되면 일부 메타데이터와 진척은 공유되어야 한다.

### 문제 3. 댓글/작업 히스토리의 기준 엔터티가 없다

- 댓글이 WBS 항목에 직접 붙는지
- 문서에 붙는지
- TODO에 붙는지
- activity log와 사용자 코멘트를 분리하는지

이 기준이 먼저 정해져야 한다.

## 경쟁 구조 비교

### 안 A. WBS 항목에 문서 본문/댓글/태그를 직접 넣는다

장점:

- 빠르게 붙이는 느낌이 든다.

단점:

- WBS 엔터티가 일정, 문서, 댓글, 태그, 권한 책임을 모두 떠안는다.
- 문서 허브 재사용이 어렵다.
- 태그 조회 탭이 WBS 종속으로 굳는다.

판단:

- 단기 구현은 쉬워 보이지만, 장기적으로 문서 플랫폼 방향과 충돌한다.

### 안 B. 문서는 독립 엔터티로 두고 WBS/TODO/이슈가 참조한다

장점:

- 문서 허브, markdown, 향후 화면기획/설계 문서와 같은 플랫폼 철학을 유지할 수 있다.
- 태그 인덱스도 문서 중심으로 만들 수 있다.
- 댓글/활동 로그를 문서와 작업 객체 양쪽에 공통화할 가능성이 생긴다.

단점:

- 참조 테이블과 권한/노출 규칙을 추가 설계해야 한다.

판단:

- 본 이슈 목표와 현재 코드 구조를 같이 보면 이 안이 기본안이다.

## 이번 리서치 결론

- `WBS 자체에 문서 기능을 내장` 하는 접근보다 `프로젝트 문서 + 작업 참조 + 태그 인덱스 + 개인 TODO` 조합이 맞다.
- 댓글은 WBS 전용으로 만들기보다 `작업 객체 공통 comment/thread 모델` 로 가야 중복을 막을 수 있다.
- 구현 순서는 한 번에 끝내기보다 아래 순서가 안전하다.

1. 작업-문서-태그-개인 TODO의 정책 경계 확정
2. 참조/노출 규칙 설계
3. 데이터 모델과 탭 구조 설계
4. 단계별 구현
