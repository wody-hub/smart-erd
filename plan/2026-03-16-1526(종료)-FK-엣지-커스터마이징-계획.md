# FK 엣지 커스터마이징 계획

> 작성일: 2026-03-16 15:26
> 상태: 종료, 1차 구현 완료

중요 메모:
- 이 문서는 종료된 계획 문서다.
- P1, P2, P3 1차 범위는 현재 코드베이스에 반영 완료로 본다.
- 이후 남는 UX 고도화나 추가 개선은 별도 계획으로 분리한다.

## 배경

현재 FK 연결선(엣지)은 `getSmoothStepPath()`로 자동 계산되며, 사용자가 다음 항목을 조정할 수 없다.

1. 핸들 위치 변경
2. 엣지 라우팅 타입 변경
3. 엣지 경로 수동 조정

다만 이 영역은 단순 렌더링 문제가 아니다. 현재 ERD 캔버스의 영속 상태는 React Flow 로컬 state가 아니라 `Y.Doc`이 source of truth이고, Zustand store는 이를 투영한 뷰 상태다. 따라서 FK 엣지 커스터마이징은 렌더러만 바꾸는 방식으로는 끝나지 않는다.

## 현재 구현 상태

| 영역 | 현재 | 파일 |
|------|------|------|
| 핸들 위치 | `target=Left`, `source=Right` 고정 | `StaticColumnRow.tsx`, `EditableColumnRow.tsx` |
| 엣지 라우팅 | `getSmoothStepPath()` 고정 | `ErdRelationEdge.tsx` |
| 엣지 데이터 | `relationType`만 보유 | `types/erd.ts` |
| 엣지 영속화 | `source`, `target`, `sourceHandle`, `targetHandle`, `relationType`만 Y.Doc에 저장 | `yjsBridge.ts` |
| 엣지 생성/삭제 | Y.Doc transaction 기반 | `canvasTableActions.ts`, `canvasSyncActions.ts` |
| 컨텍스트 메뉴 | 삭제만 지원 | `EdgeContextMenu.tsx` |
| 코드/DDL 동기화 | relation key 기준으로 edge를 재생성/갱신 가능 | `erd-diff-plan.ts`, `erd-diff-apply.ts`, `canvasStoreHelpers.ts` |

## 아키텍처 제약

- 영속 상태의 기준은 `Y.Doc`이다. 엣지 커스터마이징 메타도 최종적으로 `edge Y.Map`에 저장되어야 한다.
- 로컬 store는 영속 메타 저장소가 아니다. `useCanvasStore`에는 transient UI 상태만 둘 수 있다.
- 1차 입력 장치 범위는 `mouse + trackpad`다. 터치 입력 UX는 이번 계획 범위에서 제외한다.
- waypoint 편집 충돌 제어는 기존 테이블 편집 락과 분리된 `edge soft-lock`으로 다룬다. 엣지 편집이 같은 테이블의 다른 일반 편집까지 막으면 안 된다.
- 기존 `table lock` 소비 지점과 새 `edge soft-lock` 소비 지점은 분리한다. `edge soft-lock`를 기존 `hasLocks`에 그대로 합치지 않는다.
- 구조를 바꾸는 액션(`Apply`, `DDL import`, `replaceFromDdl`, `full-replace-fallback`)만 `hasBlockingStructureLocks = hasTableLocks || hasAnyActiveEdgeDrag` 기준으로 차단한다.
- waypoint 드래그 중간 상태는 영속 데이터가 아니라 transient preview다. 로컬 preview는 `useCanvasStore.internal` 같은 비렌더 mutable state에 두지 않고, edge preview 전용 collaboration/UI slice 또는 별도 맵에 둔다. 협업 공유는 awareness로 전파한다.
- waypoint 편집 시작 시 기존 테이블 편집 상태는 해제한다. awareness에는 `editingTableKey`와 `editingEdgeId`를 동시에 싣지 않는다.
- edge 편집 awareness가 활성화된 동안 `selectedNodeId`는 `null`이어야 한다. 기존 `selectedNodeId` fallback이 edge 편집을 테이블 락으로 오인하면 안 된다.
- 원격 락 계산에서 `editingEdgeId`가 있는 awareness는 `selectedNodeId` fallback lock 후보에서 제외한다.
- 고빈도 waypoint preview는 참여자 UI까지 광범위하게 리렌더시키지 않도록 awareness 소비를 분리한다. `remoteCursors` 공용 구독만으로 처리하지 않고, preview/edge-lock은 `remoteCursors`와 분리된 전용 store slice 또는 별도 맵으로 관리한다.
- 새 엣지 메타는 아래 경로를 모두 통과해도 유지되어야 한다.
  - `yEdgesMapToEdges()`
  - `createEdgeYMap()`
  - `yDocToJson()`
  - `migrateJsonToYDoc()`
  - `erd-diff-plan/builder/apply`
  - DDL import / code sync edge 생성 경로
- 코드/DDL sync는 edge를 update할 수도 있고 add/delete로 재생성할 수도 있다. 따라서 커스텀 메타의 보존/초기화 정책을 명시해야 한다.

## 우선순위

| 순서 | 기능 | 난이도 | 판단 |
|------|------|--------|------|
| **P1** | 엣지 라우팅 타입 변경 | 낮음 | 현재 구조에 가장 자연스럽게 들어간다 |
| **P2** | 테이블 단위 핸들 레이아웃 변경 | 중간 | 데이터 모델을 명확히 좁히면 구현 가능하다 |
| **P3-spike** | waypoint 편집 설계 검증 | 높음 | 바로 구현보다 사전 실험이 필요하다 |
| **P3-impl** | waypoint 편집 구현 | 매우 높음 | spike 승인 후 별도 착수 |

핵심 원칙은 다음과 같다.

- P1은 바로 구현 가능한 기능으로 분리 배포한다.
- P2는 "컬럼 단위 자유 배치"가 아니라 "테이블 단위 레이아웃 전환"으로 축소한다.
- P3는 straight routing 전용 1차 구현 가능성부터 검증한다.
- P3는 `edge soft-lock + 로컬 preview + awareness preview 실시간 공유 + pointerup 최종 commit` 모델을 기본으로 한다.

## P1. 엣지 라우팅 타입 변경

### 목표

엣지별로 `smoothstep` / `bezier` / `straight` 라우팅 타입을 선택할 수 있게 한다.

### 데이터 변경

```typescript
type EdgeRoutingType = 'smoothstep' | 'bezier' | 'straight';

interface ERDEdgeData {
  relationType: 'identifying' | 'non-identifying';
  routingType?: EdgeRoutingType; // 기본값: 'smoothstep'
}
```

### 저장/복구 경계

- `edge.data.routingType`는 렌더 전용 값이 아니라 영속 메타다.
- Y.Doc 스키마

```text
edges.<edgeId>.routingType: string
```

- 아래 모든 경로가 `routingType`을 읽고 써야 한다.
  - `yEdgesMapToEdges()`
  - `createEdgeYMap()`
  - `migrateJsonToYDoc()`
  - `yDocToJson()`
  - diff plan/build/apply 경로
  - DDL import, code sync, 수동 FK 생성 경로의 기본 edge 생성

### 구현 주의사항

- `createEdgeYMap()`은 1곳이 아니라 2곳이다. `routingType` 추가 시 두 함수 모두 `edge Y.Map`에 새 필드를 써야 한다.
  - 공개 함수: `client/src/collaboration/yjsBridge.ts`의 `createEdgeYMap()` — 일반 edge 생성 경로
  - 내부 함수: `client/src/lib/erd-diff-apply.ts`의 `createEdgeYMap()` — DDL import / code sync / diff apply 경로
- `migrateJsonToYDoc()`는 신규 `routingType`만 추가로 옮기는 경로가 아니다. legacy JSON edge migration에서 기존 `relationType`과 신규 edge 메타를 함께 보존해야 하며, 현재 있는 메타를 누락한 채 새 필드만 복사하는 식으로 구현하면 안 된다.
- 따라서 P1 구현 검증에는 "수동 FK 생성"뿐 아니라 "DDL import / code sync로 새 edge가 생성되는 경우에도 routingType 기본값 또는 복원값이 반영되는지"를 반드시 포함한다.
- P1 구현 검증에는 legacy JSON -> Y.Doc migration 이후에도 기존 `relationType`과 새 `routingType`이 모두 유지되는지 확인을 포함한다.

### 구현 원칙

- 기본값은 `smoothstep`으로 유지한다.
- `relationType`과 별개로 동작해야 한다.
- `routingType` 변경은 React Flow local mutation이 아니라 Y.Doc transaction으로 반영한다.

### UX

- 엣지 우클릭 메뉴는 기존 custom `div`를 확장하지 않고, 우클릭 좌표에 맞춰 열 수 있는 `menu semantics` 기반 컨텍스트 메뉴로 교체한 뒤 "라우팅 타입"을 추가한다.
- 구현 수단은 `ContextMenu primitive` 또는 좌표 기반 접근성 메뉴 래퍼 중 현재 코드 구조에 더 자연스러운 쪽을 택한다.
- 현재 저장소에는 `dropdown-menu`만 있고 `context-menu` UI 프리미티브는 없다. 따라서 `ContextMenu primitive`를 택하면 공용 UI 래퍼 파일 및 필요 시 의존성 추가를 포함한 범위로 본다.
- 옵션
  - 직각 `smoothstep`
  - 곡선 `bezier`
  - 직선 `straight`

### 액션 경계

- 새 액션은 별도 `canvasEdgeActions.ts`를 만드는 것보다 현재 store 구조에 맞게 아래 경계 중 하나로 넣는다.
  - `canvasStoreTypes.ts`
  - `canvasSyncActions.ts`
- 예시 계약

```typescript
updateEdgeRoutingType(edgeId: string, routingType: EdgeRoutingType): void
```

### 수정 파일

| 파일 | 변경 |
|------|------|
| `client/src/types/erd.ts` | `EdgeRoutingType`, `ERDEdgeData.routingType` 추가 |
| `client/src/components/erd/ErdRelationEdge.tsx` | path 계산 분기 |
| `client/src/components/erd/EdgeContextMenu.tsx` | 접근성 있는 컨텍스트 메뉴로 교체 + 라우팅 타입 메뉴 추가 |
| `client/src/components/ui/*` | 필요 시 context-menu 공용 프리미티브/래퍼 추가 |
| `client/src/stores/canvas/canvasStoreTypes.ts` | edge update 액션 계약 추가 |
| `client/src/stores/canvas/canvasSyncActions.ts` | routingType 변경 transaction 구현 |
| `client/src/collaboration/yjsBridge.ts` | routingType read/write + JSON migration 반영 |
| `client/src/stores/canvas/canvasTableActions.ts` | 신규 edge 생성 시 기본값 일관화 |
| `client/src/stores/canvas/canvasStoreHelpers.ts` | DDL 기반 edge 생성 기본값 일관화 |
| `client/src/lib/erd-diff-plan.ts` | 현재 edge snapshot 확장 |
| `client/src/lib/erd-diff-builder.ts` | diff 비교 시 커스텀 메타 보존 정책 반영 |
| `client/src/lib/erd-diff-apply.ts` | update/add 시 routingType 보존 또는 기본화 |
| `client/src/i18n/locales/*/translation.json` | 메뉴 번역 추가 |

### 보존 정책

- 동일 edge가 update되는 경우 `routingType`은 유지한다.
- `replaceFromDdl` 또는 `full-replace-fallback`이 발생해도 아래 조건을 만족하면 `routingType`을 복원한다.
  - 우선순위 1: diff update로 같은 edge가 유지되는 경우
  - 우선순위 2: full replace 후 관계 키 `parentTable.parentColumn -> childTable.childColumn` exact match
- exact match가 없거나 다의적이면 새 edge는 기본값 `smoothstep`으로 시작한다.

## P2. 테이블 단위 핸들 레이아웃 변경

### 목표

테이블 단위로 핸들 레이아웃을 변경할 수 있게 한다.

- `split`: 현재와 동일, `target=left`, `source=right`
- `left`: source/target 모두 왼쪽 면 사용
- `right`: source/target 모두 오른쪽 면 사용

### 왜 축소하는가

초안의 `Column.handleSide`는 UX와 데이터 모델이 맞지 않는다. 문서의 UX는 테이블 단위 일괄 변경인데, 컬럼 단위 필드를 도입하면 저장 구조와 렌더링 복잡도만 커진다.

또한 이번 단계는 "양쪽 모두에 동시 연결 가능한 복수 핸들 제공"이 아니다. 현재 handle ID 체계는 `-source` / `-target` 한 쌍 기준이므로, 진짜 양면 동시 지원은 별도 작업이다.

### 데이터 변경

```typescript
type TableHandleLayout = 'split' | 'left' | 'right';

interface TableNodeData {
  label: string;
  logicalTableName?: string;
  tableTermId?: number;
  headerColor?: TableHeaderColor;
  handleLayout?: TableHandleLayout; // 기본값: 'split'
  columns: Column[];
}
```

### 구현 원칙

- 1차 구현은 handle ID를 바꾸지 않는다.
- 기존 edge는 동일 handle ID를 유지한 채 `Position`만 변경한다.
- 따라서 "핸들을 제거할 때 기존 연결 차단" 로직은 1차 범위에서는 불필요하다.
- `useUpdateNodeInternals`는 `ERDCanvas`가 아니라 해당 노드 경계인 `TableNode`에서 호출하는 편이 자연스럽다.

### UX

- 테이블 헤더의 기존 조작 패턴에 맞춰 Popover 또는 메뉴로 제공
- 옵션
  - 기본 `split`
  - 왼쪽 정렬 `left`
  - 오른쪽 정렬 `right`

### 수정 파일

| 파일 | 변경 |
|------|------|
| `client/src/types/erd.ts` | `TableHandleLayout`, `TableNodeData.handleLayout` 추가 |
| `client/src/stores/canvas/canvasStoreTypes.ts` | `updateTableMeta` 계약에 `handleLayout` 포함 |
| `client/src/stores/canvas/canvasTableActions.ts` | `handleLayout` 저장/갱신 |
| `client/src/stores/canvas/canvasStoreHelpers.ts` | DDL/code sync 기반 table 생성 기본값/복원 payload 일관화 + 기존 table meta 회귀 방지 |
| `client/src/collaboration/yjsBridge.ts` | table Y.Map read/write + JSON migration 반영 |
| `client/src/lib/erd-diff-plan.ts` | current table snapshot에 `handleLayout` 및 기존 table meta 반영 |
| `client/src/lib/erd-diff-apply.ts` | diff update/full replace 복원 시 `handleLayout` 및 기존 table meta carry-over 반영 |
| `client/src/components/erd/TableNode.tsx` | `useUpdateNodeInternals(nodeId)` 연동 |
| `client/src/components/erd/TableNodeHeader.tsx` | 레이아웃 변경 UI 추가 |
| `client/src/components/erd/StaticColumnRow.tsx` | handle position 분기 |
| `client/src/components/erd/EditableColumnRow.tsx` | handle position 분기 |
| `client/src/i18n/locales/*/translation.json` | 메뉴 번역 추가 |

### 보존 정책

- 기존 문서/다이어그램은 `handleLayout`이 없으면 `split`으로 해석한다.
- 새 table meta carry-over는 `handleLayout`만 별도로 다루지 않는다. 기존 `headerColor`를 포함한 table meta 묶음을 함께 보존하고, `handleLayout` 추가가 기존 `headerColor` sync/복원을 회귀시키면 안 된다.
- diff update에서 같은 table이 유지되면 `handleLayout`을 보존한다.
- `replaceFromDdl` 또는 `full-replace-fallback`이 발생한 경우에도 아래 조건을 만족하면 `handleLayout`을 복원한다.
  - 우선순위 1: diff plan의 table update/rename 매칭 결과
  - 우선순위 2: 물리 테이블명 exact match
  - 우선순위 3: 논리 테이블명 exact match(유일할 때만)
- 매칭이 없거나 다의적이면 `split`으로 초기화한다.

### 이번 단계의 비목표

- 컬럼별 서로 다른 handle side
- 좌/우 양쪽에 동시에 source/target handle을 모두 노출하는 다중 핸들 체계
- edge별 source/target anchor 직접 선택
- 터치 입력 전용 조작 UX

## P3-spike. Waypoint 편집 설계 검증

### 목표

waypoint 편집을 바로 구현하지 않고, 현재 아키텍처에서 안전하게 넣을 수 있는 최소 설계를 검증한다.

### spike에서 반드시 답해야 할 질문

1. `straight` 외 라우팅에서도 waypoint를 지원할지
2. waypoint 편집 중 pointer capture와 edge selection을 어떻게 공존시킬지
3. 협업 중 동일 edge를 두 사용자가 동시에 수정할 때 `edge soft-lock` 충돌 UX를 어떻게 정의할지
4. code sync / DDL import로 edge가 재생성될 때 waypoint를 보존할지 초기화할지
5. 대형 다이어그램에서 SVG 핸들 수가 많아졌을 때 성능이 버틸지

### 현재 권장 방향

- 1차 구현 후보는 `routingType === 'straight'` 전용으로 제한한다.
- `smoothstep`, `bezier`의 수동 편집은 spike 결과가 나온 뒤 별도 판단한다.
- 협업 세션에서는 waypoint 드래그 중간 상태를 awareness preview로 실시간 공유한다. Y.Doc 영속화는 `pointerup` 시 최종 commit 1회만 수행한다.
- 충돌 제어는 테이블 락이 아니라 edge 단위 soft-lock으로 분리한다.
- 구조 변경 액션은 waypoint 편집보다 우선한다. `full-replace` 계열 충돌 시 drag abort 규칙을 먼저 정의한다.

## P3-impl. Waypoint 편집 구현

### 전제 조건

- P1이 완료되어 `routingType`이 영속화돼 있어야 한다.
- P3-spike에서 `straight` 전용 1차 구현이 승인돼야 한다.

### 데이터 변경

```typescript
interface Waypoint {
  x: number;
  y: number;
}

interface ERDEdgeData {
  relationType: 'identifying' | 'non-identifying';
  routingType?: EdgeRoutingType;
  waypoints?: Waypoint[];
}
```

### 저장 원칙

- waypoint는 `useCanvasStore` 로컬 상태가 아니라 `edge Y.Map`에 저장한다.
- Y.Doc 스키마

```text
edges.<edgeId>.waypoints: Y.Array<Y.Map<{x: number, y: number}>>
```

- `routingType !== 'straight'`인 경우 1차에서는 waypoint를 무시하거나 초기화한다.
- waypoint 드래그 중 intermediate position은 Y.Doc에 쓰지 않고 transient preview로만 유지한다.
- 협업 상대에게는 preview 좌표를 awareness payload로 실시간 공유한다.
- `edgeWaypointPreview`의 좌표계는 화면 좌표가 아니라 React Flow `flow 좌표`로 고정한다.
- 로컬 발행 시점에는 `screenToFlowPosition` 기준으로 변환하고, 원격 수신 측도 같은 flow 좌표를 그대로 렌더에 사용한다.
- preview payload는 현재 편집 중인 edge 1개에 대한 최소 좌표 집합만 담는다. 전체 edge 목록이나 불필요한 메타를 함께 싣지 않는다.
- preview 발행은 `requestAnimationFrame` 그대로 무제한 전송하지 않고, 최종 전송 상한을 둔 짧은 throttle로 샘플링한다.
- 1차 목표 전송 빈도 상한은 대략 `10~20fps` 수준으로 제한한다.
- `pointerup` 시점에만 최종 waypoint를 Y.Doc에 단일 transaction으로 commit한다.
- drag가 취소되면 preview만 폐기하고 Y.Doc에는 아무 변경도 남기지 않는다.
- preview는 lock과 생명주기를 같이한다. `pointerup`, drag abort, heartbeat TTL 만료, peer left, edge 삭제 시점에는 `edgeWaypointPreview = null`을 즉시 발행하거나 해당 preview를 무효화한다.
- 원격 preview 렌더는 "fresh edge lock이 존재하고 대상 edge가 아직 유효하다"는 조건에서만 허용한다.
- undo는 최종 commit 1회만 남기는 것을 목표로 한다. preview는 awareness/transient state만 사용하므로 local undo stack을 오염시키지 않는다.

### 협업 락 정책

- waypoint 편집 시작 시 해당 edge에 대해 `edge soft-lock`을 획득한다.
- soft-lock 키는 테이블 락과 분리된 edge 전용 키를 사용한다.
  - 예: `edge-lock-${edgeId}`
- lock 상태는 awareness로 전파하고 heartbeat/TTL로 관리한다.
- 다른 사용자가 같은 edge를 편집 중이면 waypoint 조작을 막고, 읽기 전용 하이라이트만 허용한다.
- 다른 edge나 테이블 편집은 계속 가능해야 한다.
- waypoint 편집 시작 시 `activeEditNodeId`와 `editingTableKey`는 해제한다.
- waypoint 편집 시작 시 `selectedNodeId`도 함께 `null`로 정리한다.
- awareness에는 `editingEdgeId`, `editingEdgeClientId`, `edgeLockHeartbeatAt`, `edgeWaypointPreview`를 추가하고, 테이블 편집 awareness와 동시 발행하지 않는다.
- `editingEdgeId`가 있는 동안 `selectedNodeId`는 락 해석에 사용하지 않는다.
- `edge soft-lock`가 막는 범위는 waypoint 이동만이 아니라 같은 edge에 대한 의미 변경/파괴적 액션 전체다.
  - waypoint 추가/이동/삭제
  - 경로 초기화
  - edge 삭제
  - 관계 재연결
  - `routingType` 변경
- 원격 사용자가 해당 edge를 lock 중이면 위 액션은 disable 처리하고 잠금 안내를 노출한다.
- lock 해제 시점
  - 기본: `pointerup`
  - 예외: 비정상 종료 대비 heartbeat TTL 만료 시 자동 해제
- "짧은 시간 후 unlock"은 pointerup 이후 후처리 버퍼 정도로만 쓰고, 협업 반영을 그 시점까지 지연시키지는 않는다.

### 구조 변경 차단 정책

- `useRemoteEditLocks`는 최소한 아래 소비 지점을 구분해 제공한다.
  - `hasTableLocks`
  - `edgeLocksById`
  - `hasAnyActiveEdgeDrag`
  - `hasBlockingStructureLocks = hasTableLocks || hasAnyActiveEdgeDrag`
- 코드 에디터의 일반 타이핑/미리보기/보조 동기화는 `hasTableLocks` 기준만 본다.
- `Apply`, `DDL import`, `replaceFromDdl`, `full-replace-fallback`처럼 구조를 바꾸는 액션만 `hasBlockingStructureLocks` 기준으로 차단한다.
- 따라서 edge 하나를 드래그 중이라고 해서 코드 편집 전체를 과도하게 막지 않는다.
- 고빈도 preview 갱신이 참여자 바, 일반 커서 렌더, 기타 협업 UI를 불필요하게 흔들지 않도록 preview/edge-lock은 `remoteCursors`와 분리된 전용 slice/맵으로 구독 경계를 둔다.

### 1차 UX

- 선택된 edge에서만 waypoint 핸들을 노출한다.
- 조작
  - midpoint 드래그: waypoint 추가
  - waypoint 드래그: 이동
  - 더블클릭: 삭제
  - 우클릭 메뉴: 경로 초기화
- 입력 장치 범위: mouse/trackpad
- 다른 사용자가 해당 edge를 편집 중이면 잠금 배지/툴팁을 노출하고 조작을 차단한다.

### 보존 정책

- 동일 edge가 유지되는 update에서는 waypoint를 보존한다.
- `replaceFromDdl` 또는 `full-replace-fallback`에서는 waypoint를 초기화한다.
- edge가 delete/add로 재생성되면 waypoint는 초기화한다.
- code sync / DDL import로 relation key가 바뀌면 새 edge로 간주하고 초기화한다.
- 이유: waypoint는 절대 좌표 기반 화면 결과물이므로 full replace 이후 자동 레이아웃/노드 크기/핸들 면 변경에 취약하다.

### 충돌 해소 정책

- 구조 변경이 waypoint 편집보다 우선한다.
- 로컬 waypoint drag 중 `replaceFromDdl`, `full-replace-fallback`, edge delete/add, relation key 변경이 발생하면 현재 drag는 즉시 abort한다.
- abort 시 수행할 후처리
  - 로컬 preview 폐기
  - edge soft-lock 해제
  - 선택/핸들 overlay 정리
  - 구조 변경 적용
  - "코드/DDL 동기화로 경로 편집이 취소됨" 안내 노출
- 현재 편집 중인 edge와 무관한 일반 변경은 drag를 유지할 수 있다.

## 검증 계획

### 정적 검증

- `./gradlew compileJava`
- `cd client && npm run build`

### 자동화 우선 항목

- `yjsBridge` 직렬화/역직렬화에서 `routingType`, `handleLayout`, `waypoints` 보존 여부
- diff/apply에서 동일 edge update 시 커스텀 메타 유지 여부
- edge 컨텍스트 메뉴 조작 후 reload 시 설정 유지 여부
- `full-replace` / `full-replace-fallback`에서 `handleLayout`, `routingType` 복원과 `waypoints` 초기화가 정책대로 동작하는지
- waypoint 드래그 중 실시간 협업 반영이 awareness preview 기반으로 자연스럽게 보이는지
- waypoint drag 중에는 Y.Doc waypoint가 중간 좌표로 오염되지 않고 `pointerup` 최종 commit만 남는지
- waypoint 편집 1회가 undo 1회로 닫히는지
- edge soft-lock이 같은 edge 편집만 막고 다른 테이블/엣지 편집은 과도하게 막지 않는지
- `edgeWaypointPreview`가 flow 좌표 기준으로 동작해 서로 다른 pan/zoom 상태에서도 같은 위치에 보이는지
- 원격 edge lock 중 `routingType 변경`, `경로 초기화`, `edge 삭제`가 disable 처리되는지
- edge 편집 awareness가 켜진 동안 `selectedNodeId` fallback 때문에 ghost table lock이 생기지 않는지
- `pointerup`, TTL 만료, peer left, edge 삭제 후 stale preview가 남지 않고 즉시 사라지는지
- waypoint preview 고빈도 갱신 중에도 `DiagramCollaboratorsBar` 같은 비관련 협업 UI가 과도하게 리렌더되지 않는지
- 구조 변경 액션이 `hasBlockingStructureLocks` 기준으로만 차단되고 일반 코드 타이핑은 계속 가능한지
- `full-replace` 충돌 시 drag abort / preview 정리 / unlock / 안내 문구가 정책대로 동작하는지

### 수동 점검 포인트

- 엣지 라우팅 타입 변경 후 undo/redo가 정상 동작하는지
- 두 클라이언트 동시 접속 시 라우팅 타입 변경이 실시간 반영되는지
- handle layout 변경 후 기존 edge가 끊기지 않고 재배치되는지
- code sync / DDL import 후 커스텀 메타가 정책대로 유지 또는 초기화되는지
- waypoint 편집 중 edge 선택/삭제 UX가 충돌하지 않는지
- waypoint 드래그 중 다른 클라이언트에서 중간 이동 경로가 awareness preview로 실시간으로 보이는지
- 다른 사용자가 같은 edge를 편집 중일 때 lock 안내가 보이고 중복 편집이 차단되는지
- edge 편집 시작 시 기존 table edit가 즉시 해제되고, 코드 에디터 전체가 불필요하게 막히지 않는지
- edge 편집 시작 시 `selectedNodeId`가 남아서 테이블 락처럼 보이지 않는지
- 드래그 종료/취소/상대 이탈 후 preview 잔상이 남지 않는지
- waypoint drag 중 code apply / DDL import를 시도하면 구조 변경 차단 또는 drag abort가 일관되게 동작하는지
