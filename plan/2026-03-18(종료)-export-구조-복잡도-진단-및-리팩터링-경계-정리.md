# Export 구조 복잡도 진단 및 리팩터링 경계 정리

작성일: 2026-03-18

## 목적

현재 export 기능은 성능 개선, 포맷별 처리 분기, 진행 UI 가시화가 짧은 기간에 연속으로 들어가면서 구조 복잡도가 높아졌다.

이 문서는 다음 판단을 팀 기준으로 남기기 위한 것이다.

1. 현재 상태를 "스파게티"로 볼 정도인지
2. 실제 위험 지점이 어디인지
3. 언제, 어떤 경계로 리팩터링해야 하는지

주의:

- 이 문서는 **지금 당장 코드 이동을 시작하는 문서가 아니다**
- 현재 작업 중인 수정이 끝난 뒤, export 영역을 별도 정리할 때 참고하는 기준 문서다

---

## 현재 판단

결론부터 말하면 다음과 같다.

- 현재 상태는 **완전히 스파게티는 아니다**
- 다만 export 영역은 **god hook / 과집중 구조**로 넘어가는 중이다
- 따라서 다음 export 관련 기능을 더 얹기 전에 정리하는 것이 맞다

즉, 문제의 본질은 "로직이 사방에 흩어졌다"라기보다,
"한 파일과 한 훅이 너무 많은 책임을 가져가기 시작했다"에 가깝다.

---

## 근거

### 1. `useExportDiagram.ts`에 책임이 과도하게 집중됨

현재 [client/src/hooks/useExportDiagram.ts](../client/src/hooks/useExportDiagram.ts)는 다음 책임을 한 파일에서 모두 맡고 있다.

- React Flow 노드 바운드 계산
- export 캡처용 viewport/style 계산
- `html-to-image` 모듈 lazy import 및 캐시
- 폰트 embed CSS 캐시
- 공통 렌더 옵션 생성
- Blob URL 다운로드 유틸
- SVG data URL -> Blob 변환
- PNG/JPG canvas blob 변환
- PDF 단일 페이지/타일 분기 정책
- export progress 상태머신
- 포맷별 export 파이프라인 실행
- toast 정책

핵심 구간:

- 상태/진행 UI 제어: `163~246` 라인
- 공통 유틸/정책: `286~472` 라인
- 포맷별 처리:
  - PNG: `474~538`
  - JPG: `540~604`
  - SVG: `606~668`
  - PDF: `670~840`

이 구조는 "한 번에 보면 이해는 되지만", 이후 수정 포인트가 계속 여기로 몰리는 형태다.

### 2. 포맷별 처리 흐름이 유사하지만 한 곳에서 장문으로 반복됨

PNG/JPG/SVG/PDF는 세부 구현은 다르지만 공통 뼈대가 매우 비슷하다.

- capture option 획득
- 진행 상태 갱신
- `html-to-image` 렌더
- Blob/PDF 변환
- 다운로드/저장
- 완료/실패 처리

공통 골격은 비슷한데 각 포맷이 한 함수씩 길게 늘어져 있어서,
다음 수정 시 같은 성격의 변경을 여러 함수에 반복 반영할 가능성이 높다.

### 3. `ERDCanvas.tsx`는 원래 큰 파일이고, 여기에 더 로직을 얹으면 위험해짐

[client/src/components/erd/ERDCanvas.tsx](../client/src/components/erd/ERDCanvas.tsx)는 이미 매우 큰 편이다.
현재 export 연결은 비교적 얇다.

- 훅 사용: `281~286`
- 툴바/다이얼로그 연결: `844~860`

즉, **지금 export 스파게티의 중심은 ERDCanvas가 아니라 export 훅**이다.

### 4. UI는 비교적 잘 분리됐음

[client/src/components/erd/ExportProgressDialog.tsx](../client/src/components/erd/ExportProgressDialog.tsx)는
표시 전용 컴포넌트로 남아 있어서, 이 부분은 상대적으로 건전하다.

현재 컴포넌트 책임:

- stage -> step 매핑
- determinate / indeterminate 렌더 구분
- 텍스트/바 표시

즉, UI 표시 자체가 문제라기보다, 상태 공급자가 너무 많은 맥락을 같이 들고 있는 구조가 더 큰 문제다.

---

## 지금 당장 "스파게티"로 보지 않는 이유

아직 완전한 스파게티로 단정하지 않는 이유는 다음과 같다.

- export 로직이 여러 파일에 무질서하게 흩어져 있지 않다
- UI 컴포넌트는 별도 파일로 분리돼 있다
- `ERDCanvas`는 연결만 하고 실질 로직은 export 훅에 몰려 있다
- 성능 정책과 진행 UI 정책이 적어도 같은 도메인(export) 안에는 묶여 있다

즉, **정리 포인트가 명확하게 보인다**는 점에서 아직 구조 회복 가능성이 높다.

---

## 실제 위험 신호

다음 중 하나라도 추가되면 복잡도는 체감상 급격히 나빠질 가능성이 크다.

- export 포맷 1개 추가
- "빠른 export / 고품질 export" 같은 프로파일 옵션 추가
- 서버 export 또는 background job export 추가
- export 취소/cancel 기능 추가
- export 상태를 다른 컴포넌트에서도 소비하기 시작함
- perf 측정용 분기나 telemetry가 훅 안에 더 들어감

즉, 현재 구조는 "지금 기능까지는 버티지만, 다음 기능부터는 위험"한 단계다.

---

## 권장 리팩터링 경계

리팩터링 시에는 "파일을 많이 쪼개기"보다 **책임을 기준으로 분리**하는 것이 맞다.

### 1. `useExportProgress`

책임:

- export 진행 상태 모델
- 시작/완료/실패 상태 전이
- determinate / indeterminate 정책
- progress 관련 text/model 생성

의도:

- export 실제 처리 코드와 UI 상태머신을 분리

### 2. `export-core`

책임:

- `getCaptureOptions`
- `getCaptureStyle`
- `getSafePixelRatio`
- `getSinglePagePdfPixelRatio`
- `buildRenderConfig`
- `downloadFile`
- `downloadBlobFile`
- `renderCanvasBlob`
- `convertSvgDataUrlToBlob`

의도:

- 포맷과 무관한 계산/변환 로직을 한 곳에 모음

### 3. `export-images`

책임:

- PNG/JPG 공통 처리
- image 계열 export 후처리

의도:

- PNG/JPG 중복 축소

### 4. `export-svg`

책임:

- SVG 렌더/Blob 변환
- SVG 전용 예외 처리

### 5. `export-pdf`

책임:

- 단일 페이지 PDF
- 타일 PDF
- 타일 진행률 계산

의도:

- 가장 복잡한 분기를 독립시켜 관리

### 6. `useExportDiagram`

최종 목표 책임:

- 외부에서 쓰는 public API 제공
- 포맷별 실행기 호출
- 다이어그램 이름 주입

즉, 최종적으로는 "오케스트레이션 레이어"만 남는 형태가 이상적이다.

---

## 권장 순서

현재 작업이 끝난 뒤 정리한다면 순서는 이렇게 가는 것이 안전하다.

1. 타입/상수/유틸 분리
2. progress 상태머신 분리
3. PDF 실행기 분리
4. PNG/JPG 공통 실행기 분리
5. SVG 실행기 분리
6. 마지막에 `useExportDiagram` 얇게 정리

이 순서가 좋은 이유는, public API를 거의 유지한 채 내부 구조만 정리하기 쉽기 때문이다.

---

## 지금 하지 말아야 할 것

현재 수정이 진행 중인 상태라면 아래는 피하는 것이 좋다.

- export 전부를 한 번에 갈아엎는 대규모 이동
- `ERDCanvas`까지 같이 정리하려는 욕심
- 성능 개선과 구조 정리를 한 PR/한 커밋에 섞는 것
- perf harness 정리까지 동시에 시작하는 것

지금은 진단만 남기고, **현재 기능 수정이 안정화된 뒤 export 구조만 별도 정리**하는 것이 맞다.

---

## 실행 기준

다음 중 하나가 생기면 이 문서를 기준으로 실제 리팩터링을 시작한다.

- export 관련 추가 요구사항이 들어온다
- `useExportDiagram.ts` 수정이 또 필요하다
- export 버그 수정 시 여러 포맷을 동시에 건드려야 한다
- progress/state 정책을 다시 바꿔야 한다

그 전까지는 현재 구조를 유지하되,
"다음 export 수정부터는 분리 작업을 먼저 한다"를 팀 규칙으로 보는 편이 좋다.

---

## 한 줄 결론

현재 export 코드는 "이미 스파게티라서 즉시 응급수술이 필요한 상태"는 아니다.
하지만 **다음 변경을 더 얹기 전에 경계를 나눠야 하는 과집중 구조**는 맞다.

따라서 지금은 문서만 남기고,
현재 수정이 끝나는 시점에 export 도메인만 별도 리팩터링하는 것이 가장 안전하다.
