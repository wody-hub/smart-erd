# 02. 편집 모델

## 이 문서의 핵심

마크다운 플러그인에서 TextInputPipeline과 DraftState는 보조 기능이 아니라 **전체 편집 흐름의 핵심**이다. 모든 텍스트 편집은 이 파이프라인을 거친다.

## 1. TextInputPipeline 전체 흐름

코어 05-상세-흐름도의 **흐름 A(텍스트형 편집기 입력)**를 마크다운에 구체화한다.

```text
[Monaco Editor]
    │ 사용자 타이핑
    ▼
[Local Draft Store]
    │ dirty=true, draftText 갱신
    │ debounce 300ms 시작
    ▼
[300ms idle 후]
    │
    ▼
[MarkdownTextInputPipeline.parse(draftText)]
    │ remark 파서 실행
    ├─ 파싱 실패 → diagnostics 갱신, parseStatus='invalid'
    └─ 파싱 성공 → ParseResult(ast, diagnostics) 생성
    ▼
[MarkdownTextInputPipeline.validate(parseResult)]
    │ 중복 anchor, 깨진 링크, frontmatter 스키마 검증
    ├─ 검증 실패 → diagnostics 추가, parseStatus='invalid'
    └─ 검증 성공 → ValidationResult(valid, diagnostics)
    ▼
[MarkdownTextInputPipeline.buildCommands(parseResult)]
    │ 이전 AST vs 현재 AST diff → DocumentCommand[] 생성
    ▼
[Mutation Policy]
    │ DocumentCommand → DocumentMutation (Y.Text 변경)
    ▼
[DocumentStore]
    │ 공유 상태 반영 (Y.Text 업데이트)
    │ revision 증가
    ▼
[ChangeBus] ── emit ──┬──────────────┬──────────────┬─────────────────┐
                      │              │              │                 │
                      ▼              ▼              ▼                 ▼
               [Projector]  [CollabRuntime] [UndoManager] [PersistenceCoord]
                  │
                  ▼
            MarkdownViewModel
            (rawText, ast, previewHtml, toc, diagnostics)
```

## 2. parse — remark 파싱

```typescript
interface ParseResult {
  ast: MdastRoot;             // mdast 표준 AST
  sections: Section[];        // heading 기반 섹션 분할
  frontmatter: Frontmatter;   // YAML 파싱 결과
  diagnostics: Diagnostic[];  // 파싱 경고/에러
}

interface Diagnostic {
  severity: 'error' | 'warning' | 'info';
  message: string;
  position: SourcePosition;
  code: string;               // 'unclosed-code-block', 'invalid-yaml' 등
}
```

```text
파싱 단계:
  1. frontmatter 추출 (--- ... --- 블록)
  2. YAML 파싱 (gray-matter 또는 remark-frontmatter)
  3. remark.parse(body) → mdast AST 생성
  4. GFM 플러그인 적용 (테이블, 취소선, 체크리스트)
  5. AST에서 heading 기반 Section 트리 구축
  6. 파싱 중 발생한 경고를 diagnostics에 수집
```

### 파싱 에러 유형

| 에러 코드 | 심각도 | 예시 |
|---|---|---|
| `unclosed-code-block` | error | 닫히지 않은 ``` 블록 |
| `invalid-yaml` | error | frontmatter YAML 구문 오류 |
| `nested-heading-skip` | warning | h1 다음에 h3 (h2 생략) |
| `empty-heading` | warning | `##` (텍스트 없는 heading) |
| `duplicate-anchor` | warning | 같은 텍스트의 heading 중복 |

## 3. validate — 의미 검증

파싱이 성공한 AST에 대해 의미적 검증을 수행한다.

```typescript
interface ValidationResult {
  valid: boolean;
  diagnostics: Diagnostic[];
}
```

```text
검증 규칙:
  1. 중복 heading anchor 검사
     - 같은 level에 같은 텍스트의 heading이 있으면 warning
     - anchor 충돌 시 -1, -2 접미사로 자동 해결하되 경고 표시

  2. 깨진 내부 링크 검사
     - [텍스트](#anchor) 형식의 내부 링크가 존재하지 않는 anchor를 참조하면 warning
     - 섹션 삭제로 인해 기존 내부 링크가 깨질 수 있음

  3. 이미지 참조 검사 (후속 phase)
     - ![alt](asset://xxx) 형식의 asset URI 검사는 이미지/asset 도메인 도입 후 추가
     - 이번 구현 범위에서는 이미지 업로드와 asset 참조 검증을 수행하지 않음

  4. frontmatter 스키마 검사
     - status 필드가 허용된 enum 값인지 확인
     - date 필드가 유효한 날짜 형식인지 확인
```

## 4. buildCommands — AST diff → DocumentCommand[]

이전 AST와 현재 AST를 비교하여 변경 사항을 DocumentCommand로 변환한다.

```typescript
// buildCommands가 생성하는 command key
type MarkdownCommandKey =
  | 'markdown:body-replace'         // 전체 본문 교체 (1단계 기본 전략)
  | 'markdown:section-update'       // 특정 섹션 내용 변경
  | 'markdown:frontmatter-update'   // frontmatter 필드 변경
  | 'markdown:format-apply'         // 포맷팅 적용 (Bold, Italic 등)
  ;
```

`section.move`는 1차 범위에서 제외한다. 초기 릴리즈의 아웃라인 rail은 navigation과 현재 섹션 동기화만 담당하고, 구조 재정렬은 후속 phase에서 별도 command로 추가한다.
`image.insert`도 현재 phase의 active command가 아니다. 이미지/asset 도메인이 도입되면 별도 command key로 추가한다.

```text
1단계 전략 — 전체 교체:
  이전 텍스트와 현재 텍스트가 다르면 markdown:body-replace 커맨드 하나 생성
  Y.Text의 CRDT가 문자 단위 diff를 자동 처리하므로, 전체 교체도 실질적으로는 변경분만 전파됨

2단계 전략 — 섹션 단위 diff:
  이전 AST와 현재 AST를 섹션 단위로 비교
  변경된 섹션만 markdown:section-update 커맨드 생성
  변경되지 않은 섹션은 건드리지 않음
```

### 1단계 buildCommands 구현

```typescript
function buildCommands(
  prevBody: string,
  currentBody: string,
  prevFrontmatter: Frontmatter,
  currentFrontmatter: Frontmatter,
): DocumentCommand[] {
  const commands: DocumentCommand[] = [];

  // 본문 변경
  if (prevBody !== currentBody) {
    commands.push({
      pluginId: 'markdown',
      key: 'markdown:body-replace',
      payload: { text: currentBody },
      meta: { source: 'text-editor', clientId, requestId: uuid(), issuedAt: Date.now() },
    });
  }

  // frontmatter 변경
  const changedFields = diffFrontmatter(prevFrontmatter, currentFrontmatter);
  if (changedFields.length > 0) {
    commands.push({
      pluginId: 'markdown',
      key: 'markdown:frontmatter-update',
      payload: { fields: changedFields },
      meta: { source: 'text-editor', clientId, requestId: uuid(), issuedAt: Date.now() },
    });
  }

  return commands;
}
```

## 5. DraftState 상태 머신

코어 04-Command-Event-설계의 DraftState 계약을 마크다운에 구체화한다.

```typescript
interface MarkdownDraftState {
  draftId: string;
  dirty: boolean;
  parseStatus: 'idle' | 'parsing' | 'valid' | 'invalid';
  lastAcceptedRevision?: number;
  pendingRemoteRevision?: number;
  reconcileState: 'clean' | 'dirty-valid' | 'dirty-invalid' | 'remote-pending';
  diagnostics: Diagnostic[];
  draftText: string;          // 현재 에디터 버퍼의 텍스트
}
```

### 상태 전이 다이어그램

```text
clean
  │
  ├─ 사용자 타이핑 → dirty-valid (파싱 성공 시) / dirty-invalid (파싱 실패 시)
  │
  └─ 원격 변경 수신 → clean (dirty가 아니므로 즉시 projector 갱신)

dirty-valid
  │
  ├─ 사용자 계속 타이핑 → dirty-valid / dirty-invalid (debounce 후 재파싱)
  ├─ 커맨드 생성 → Mutation → clean (공유 상태 반영 완료)
  └─ 원격 변경 수신 → remote-pending

dirty-invalid
  │
  ├─ 사용자 계속 타이핑 → dirty-valid (파싱 성공 시) / dirty-invalid (유지)
  └─ 원격 변경 수신 → remote-pending

remote-pending
  │
  ├─ acceptRemote
  │   → local draft 폐기
  │   → remote revision 반영
  │   → 에디터 텍스트를 원격 최신 상태로 교체
  │   → clean
  │
  ├─ keepLocalAndRebase
  │   → latest shared state를 새 base로 잡음
  │   → Y.Text CRDT 자동 병합 결과를 새 base text로 사용
  │   → local draft를 재파싱
  │   → 성공 시 dirty-valid
  │   → 실패 시 dirty-invalid
  │
  └─ compareLater
      → pending 상태 유지
      → 에디터 본문 overwrite 금지
      → 저장/release 제한
```

### 각 상태에서의 UI 동작

| 상태 | 에디터 | 프리뷰 | 상태 바 | 저장 |
|---|---|---|---|---|
| clean | 편집 가능 | 최신 상태 | "저장됨" | 불필요 |
| dirty-valid | 편집 가능 | draft 기준 갱신 | "변경됨" | 가능 |
| dirty-invalid | 편집 가능 | 마지막 valid 유지 | "구문 오류" + diagnostics | 비활성 |
| remote-pending | 편집 가능 | 마지막 상태 유지 | "원격 변경 있음" + 3버튼 | 비활성 |

### remote-pending에서의 3가지 선택지 UI

```text
┌──────────────────────────────────────────────────────┐
│ ⚠ 다른 참여자가 이 섹션을 수정했습니다.                  │
│                                                      │
│ [원격 변경 수락]  [내 편집 유지 + 리베이스]  [나중에 비교] │
└──────────────────────────────────────────────────────┘
```

## 6. Debounce 정책

```text
타이핑 시작
  │ 300ms 타이머 시작
  │
  ├─ 300ms 내 추가 타이핑 → 타이머 리셋
  │
  └─ 300ms idle 경과
      │ parse() 호출
      │
      ├─ 파싱 성공 → validate() → buildCommands() → Mutation
      └─ 파싱 실패 → diagnostics 갱신, dirty-invalid
```

300ms를 선택한 근거:

- 100ms: 너무 빠름. 빠른 타이핑 중 불필요한 파싱 다수 발생
- 300ms: 타이핑 중단 감지에 적합. 단어 단위 입력 후 자연스러운 간격
- 500ms+: 너무 느림. 사용자가 변경이 반영되지 않는다고 느낌

## 7. 증분 파싱 전략

### 1단계: 전체 재파싱

```text
모든 변경에 대해 전체 텍스트를 remark로 재파싱한다.
  - 장점: 구현 단순, 파싱 결과의 정확성 보장
  - 단점: 대용량 문서에서 파싱 비용 증가
  - 현실적 판단: 300ms debounce + 전체 재파싱으로 1000줄 이하 문서는 충분
```

### 2단계: 섹션 단위 증분 파싱

```text
변경된 섹션만 재파싱하고, 나머지 섹션은 캐시된 AST를 재사용한다.

증분 파싱 흐름:
  1. 변경된 텍스트 범위를 offset으로 감지
  2. sectionIndex에서 해당 offset이 속한 섹션 식별
  3. 해당 섹션의 텍스트만 추출하여 재파싱
  4. 파싱 결과를 기존 AST에 병합
  5. sectionIndex 갱신

증분 파싱의 복잡도:
  - 섹션 경계 변경 (heading 추가/삭제)은 전체 재파싱 필요
  - 섹션 내부 변경은 해당 섹션만 재파싱 가능
  - 2단계에서만 구현, 1단계에서는 전체 재파싱
```

## 8. 원격 변경 병합

마크다운의 원격 변경 병합은 **2중 레이어**로 처리한다.

### 레이어 1: Y.Text CRDT 자동 병합

```text
Y.Text의 CRDT 엔진이 문자 삽입/삭제를 자동으로 병합한다.
  - 두 사용자가 다른 위치에 타이핑: CRDT가 자동 병합
  - 두 사용자가 같은 위치에 타이핑: CRDT가 두 삽입을 모두 보존 (순서는 clientId 기준)
  - 한 사용자가 삭제한 텍스트를 다른 사용자가 수정: 삭제 우선 (Y.Text 기본 동작)
```

### 레이어 2: AST 레벨 Projector 갱신

```text
Y.Text 변경 후 Projector가 AST를 재파싱하여 뷰 모델을 갱신한다.
  - 원격 변경 → Y.Text 업데이트 → ChangeBus 이벤트 → Projector 트리거
  - Projector는 Y.Text 최신 값을 remark로 재파싱
  - 재파싱 결과로 previewHtml, toc, sectionIndex 갱신
```

### dirty draft가 있을 때의 원격 변경 처리

```text
코어 05-상세-흐름도 흐름 D(dirty draft 재조정) 준수:

1. clean 상태에서 원격 변경 수신
   → 즉시 에디터 텍스트 갱신 (Y.Text 최신 값)
   → Projector 재파싱
   → clean 유지

2. dirty 상태에서 원격 변경 수신
   → remote-pending 전이
   → 에디터 본문 overwrite 금지
   → "원격 변경 있음" 상태 표시
   → 사용자 선택 대기 (acceptRemote / keepLocalAndRebase / compareLater)

3. keepLocalAndRebase 선택 시
   → Y.Text의 CRDT 병합 결과를 새 base text로 설정
   → local draft에서 변경한 부분만 추출
   → 새 base text에 local 변경 적용
   → 재파싱 후 dirty-valid 또는 dirty-invalid
```

### 마크다운 특유의 병합 이슈

```text
텍스트 CRDT의 한계:
  - 구조적 의미를 모름: "## " 삽입이 heading인지 일반 텍스트인지 구분 불가
  - 블록 경계 충돌: A가 heading 삭제 + B가 같은 heading 아래 내용 추가 → 고아 콘텐츠
  - 코드 블록 경계: A가 ``` 열기 + B가 같은 줄에 텍스트 추가 → 깨진 코드 블록

대응 전략:
  - Y.Text CRDT 병합 후 반드시 AST 재파싱으로 구조 무결성 확인
  - 파싱 실패 시 diagnostics로 사용자에게 알림
  - 자동 수정 제안 기능은 2단계 이후
```

## 9. 툴바 입력 처리

포맷팅 툴바(Bold, Italic 등)는 TextInputPipeline과 별도 경로를 탄다.

```text
[Toolbar] Bold 버튼 클릭
    │
    ▼
[ToolbarAdapter]
    │ 현재 선택 영역 확인
    │ 선택된 텍스트를 **text** 로 감싸는 command 생성
    ▼
[DocumentCommand]
    { key: 'markdown:format-apply', payload: { format: 'bold', range: { start, end } } }
    ▼
[Mutation Policy]
    │ Y.Text에서 해당 range의 텍스트를 **text**로 교체
    ▼
[DocumentStore]
    │ 공유 상태 반영
    ▼
[ChangeBus] → Projector → 에디터/프리뷰 갱신
```

툴바 입력은 이미 유효한 마크다운 구문을 삽입하므로 DraftState를 dirty-invalid로 만들지 않는다. 하지만 DraftState가 dirty 상태일 때 툴바를 사용하면 현재 draft에 포맷팅이 즉시 적용되고, debounce 후 전체 파이프라인을 거친다.

## 10. 구현 가드레일

다음은 금지한다.

- 매 keystroke마다 파싱 (debounce 필수)
- 파싱 실패한 텍스트를 Y.Text에 기록 (DraftState 계약 위반)
- Y.Text를 에디터가 직접 수정 (반드시 Mutation Policy 경유)
- AST diff 없이 전체 Y.Text 교체 (CRDT 이점 상실)
- Projector가 dirty draft 상태에서 에디터 본문 overwrite (루프 발생)

다음은 허용한다.

- 1단계에서 전체 재파싱 (증분 파싱은 2단계)
- 300ms debounce 값 조정 (런타임 설정으로 외부화)
- frontmatter 파싱 실패 시 본문 파싱은 계속 진행
