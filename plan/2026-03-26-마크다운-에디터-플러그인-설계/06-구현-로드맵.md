# 06. 구현 로드맵

## 전제 조건

이 로드맵은 **협업 문서 플랫폼 코어 구현이 완료된 후** 시작한다. 코어가 없으면 플러그인을 올릴 수 없다.

필수 선행 작업:
- `plan/finish/2026-03-25-1153(종료)-다이어그램-동기화-아키텍처-재설계/`의 코어 구현 완료
- ERD 플러그인이 코어 위에서 동작하는 상태
- PluginRegistry에 세 번째 플러그인을 등록할 수 있는 상태
- TextInputCapablePlugin SPI가 코어에 구현되어 있는 상태

## 단계별 계획

### 1단계: 기본 텍스트 편집 (1~2주)

**목표:** Monaco 에디터에서 마크다운을 작성하고 라이브 프리뷰를 볼 수 있는 최소 환경

#### 구현 범위

```text
[플러그인 골격]
├─ MarkdownPlugin 등록 (PluginRegistry)
├─ 기본 Mutation Policy (`markdown:body-replace`)
├─ 기본 Projector (Y.Text("body") → remark 파싱 → HTML)
└─ 기본 Scope Resolver (document/root 단일 scope)

[Y.Doc 매핑]
├─ Y.Text("body") — 마크다운 본문
├─ Y.Map("frontmatter") — YAML 메타데이터
└─ Y.Map("metadata") — 문서 설정

[UI]
├─ Monaco 에디터 (마크다운 구문 하이라이팅)
├─ 라이브 프리뷰 (remark → rehype → HTML)
├─ 분할 뷰 / 에디터 전체 / 프리뷰 전체 토글
├─ 에디터-프리뷰 스크롤 동기화 (heading 기반)
└─ 하단 상태 바 (커서 위치, 저장 상태)
```

#### 제외 범위

- TextInputPipeline (parse/validate/buildCommands)
- DraftState 상태 머신
- 아웃라인 패널
- Frontmatter 폼 편집
- 협업 커서/선택 영역 표시
- Scope Lock (heading 단위)
- 내보내기 (HTML/원문 MD)
- 이미지 업로드
- 포맷팅 툴바

#### 검증 기준

- [ ] `markdown` 플러그인이 코어 수정 없이 PluginRegistry에 등록된다
- [ ] Monaco 에디터에서 마크다운 텍스트를 입력하고 Y.Text에 동기화된다
- [ ] 라이브 프리뷰에서 HTML 렌더링 결과를 확인할 수 있다
- [ ] GFM(테이블, 체크리스트, 취소선)이 프리뷰에 정상 렌더링된다
- [ ] 코드 블록에 구문 하이라이팅이 적용된다
- [ ] 분할 뷰/에디터/프리뷰 모드 전환이 동작한다

### 2단계: TextInputPipeline + DraftState (1~2주)

**목표:** 텍스트 편집의 안전망인 DraftState와 parse/validate/buildCommands 파이프라인 가동

#### 구현 범위

```text
[TextInputPipeline]
├─ MarkdownTextInputPipeline 구현
│   ├─ parse: remark 파서 (전체 재파싱)
│   ├─ validate: heading anchor 중복, 깨진 내부 링크, frontmatter 스키마 검사
│   └─ buildCommands: `markdown:body-replace` 생성
├─ 300ms debounce 정책 적용
└─ diagnostics → 에디터 인라인 경고 표시

[DraftState 상태 머신]
├─ clean → dirty-valid → clean (정상 흐름)
├─ clean → dirty-invalid (구문 오류)
├─ dirty-valid → remote-pending (원격 변경 감지)
└─ 상태별 하단 상태 바 아이콘/색상 표시

[포맷팅 툴바]
├─ Bold, Italic, Strikethrough
├─ Heading (드롭다운 h1~h6)
├─ Inline Code, Code Block
├─ Link, Horizontal Rule
├─ Task List
└─ Table 삽입 다이얼로그

[포맷팅 동작]
├─ ToolbarAdapter → MutationPolicy → Y.Text
├─ 선택 영역 감싸기 / 커서 위치 삽입
└─ 토글 (이미 적용된 포맷 제거)
```

주: `image.insert`와 asset 참조 검증은 현재 단계에 포함하지 않는다. 이미지/asset 도메인 도입 후 별도 phase에서 추가한다.

#### 검증 기준

- [ ] 텍스트 입력 후 300ms 후에 자동 파싱이 수행된다
- [ ] 구문 오류(깨진 코드 블록 등) 시 dirty-invalid 상태가 표시된다
- [ ] dirty-invalid 상태에서는 공유 상태에 커밋되지 않는다
- [ ] 포맷팅 단축키(Cmd+B, Cmd+I 등)가 동작한다
- [ ] 테이블 삽입 다이얼로그에서 마크다운 테이블이 생성된다
- [ ] DraftState 상태 전이가 하단 상태 바에 실시간 반영된다

### 3단계: 실시간 협업 (1~2주)

**목표:** 다른 참여자와 동시 편집 시 섹션 단위 락과 커서/선택 영역 표시

#### 구현 범위

```text
[ScopeResolver 확장]
├─ section/{id} scope (heading 기반)
├─ document/root scope (frontmatter, 구조 변경)
├─ Y.Map("sectionIndex") 갱신 (Projector 연동)
└─ FocusContext → ScopeRef 변환

[Presence]
├─ MarkdownPresenceMapper 구현
│   ├─ 커서 위치 (line, column, offset)
│   ├─ 선택 영역 (startOffset, endOffset)
│   └─ 편집 중 섹션 ID
├─ Monaco 에디터 내 원격 커서 표시 (색상 라벨)
├─ 원격 선택 영역 하이라이트 (반투명 배경)
└─ 참여자별 고유 색상 할당

[원격 변경 처리]
├─ remote-pending 상태 UI
│   ├─ "원격 변경 수락" 버튼
│   ├─ "내 편집 유지 + 리베이스" 버튼
│   └─ "나중에 비교" 버튼
└─ Y.Text CRDT 자동 병합 + AST Projector 갱신

[잠긴 섹션 UI]
├─ 읽기 전용 표시 (배경색 변경)
├─ 상태 바 메시지 ("이 섹션은 {참여자}님이 편집 중입니다")
└─ 타이핑 시도 시 피드백
```

#### 검증 기준

- [ ] 두 사용자가 다른 섹션을 동시에 편집할 수 있다
- [ ] 한 섹션에 scope lock이 걸리면 다른 사용자는 읽기 전용이 된다
- [ ] 다른 사용자의 커서 위치와 선택 영역이 실시간으로 표시된다
- [ ] 원격 변경으로 인한 remote-pending 상태에서 3가지 선택이 가능하다
- [ ] heading 추가/삭제 시 sectionIndex가 자동 갱신된다

### 4단계: 아웃라인 + 메타데이터 (1주)

**목표:** 문서 구조 네비게이션과 on-demand 메타데이터 편집

#### 구현 범위

```text
[아웃라인 rail]
├─ heading 기반 TOC 트리 자동 생성
├─ 항목 클릭 → 에디터/프리뷰 스크롤
├─ 현재 커서 위치 섹션 하이라이트
├─ 잠긴 섹션 🔒 아이콘 표시
└─ 편집 중인 참여자 표시 ([👤A])

[Info Drawer / Sheet]
├─ Frontmatter 폼 편집
│   ├─ 제목, 작성자, 날짜 입력
│   ├─ 상태 드롭다운 (draft/review/approved/published)
│   └─ 태그 관리 (추가/삭제)
├─ 문서 설정
│   ├─ 프리뷰 모드 선택
│   ├─ 자동저장 토글
│   └─ 글꼴 크기 설정
└─ drawer 입력 ↔ canonical frontmatter buffer 동기화

[MarkdownStatusStrip]
├─ 현재 section / draft state / autosave 표시
└─ diagnostics와 collaboration status 요약
```

#### 검증 기준

- [ ] 아웃라인 rail에서 heading 기반 트리가 자동 생성된다
- [ ] 아웃라인 항목 클릭 시 에디터와 프리뷰가 해당 섹션으로 스크롤된다
- [ ] 아웃라인 rail은 현재 섹션과 참여자 상태를 안정적으로 표시한다
- [ ] Info Drawer에서 메타데이터를 편집하면 canonical frontmatter buffer에 반영된다
- [ ] 협업 참여자가 아웃라인 rail에 표시된다

### 5단계: 내보내기 + 템플릿 + Artifact (1~2주)

**목표:** 산출물 생성, 템플릿, artifact fallback

#### 구현 범위

```text
[내보내기]
├─ HTML: remark → rehype → rehype-highlight → sanitize → 단일 HTML 파일
└─ 원문 MD: canonical buffer(frontmatter + body) → .md 파일

[Artifact]
├─ MarkdownArtifactSerializer (canonical buffer → JSON)
├─ MarkdownArtifactCodec (JSON → Y.Doc 복원)
└─ ArtifactFallbackCapablePlugin 구현

[문서 템플릿]
├─ 빈 문서
├─ 회의록
├─ 기술 설계 문서 (RFC)
├─ API 문서
├─ README
└─ 릴리스 노트
```

#### 검증 기준

- [ ] HTML로 내보내면 스타일이 포함된 단일 파일이 생성된다
- [ ] 원문 MD로 내보내면 canonical frontmatter + body가 유지된다
- [ ] 새 문서 생성 시 템플릿을 선택할 수 있다
- [ ] Artifact 기반으로 문서를 복원할 수 있다

| 상태 관리 | DocumentStore (코어) + Zustand (로컬 UI) | 공유 상태는 코어, 로컬 UI 상태는 Zustand |
| 텍스트 diff | diff-match-patch | MutationPolicy에서 Y.Text 증분 적용 |

### 파서 라이브러리 선택 근거

```text
remark (unified) 선택 근거:
  1. mdast 표준 AST — 도메인 모델과 1:1 대응
  2. remark-gfm으로 GFM(테이블, 체크리스트, 취소선) 즉시 지원
  3. rehype 파이프라인으로 HTML 변환 비용 최소
  4. 향후 Mermaid, KaTeX 확장 시 remark/rehype 플러그인만 추가
  5. unified 생태계 전체 재사용 (remark-stringify, rehype-highlight 등)

대안 검토:
  marked — 빠르지만 AST 접근 불가, 플러그인 확장 어려움
  markdown-it — 플러그인 체계 있지만 AST가 비표준
  → remark가 확장성과 표준 준수 면에서 최적
```

## 백엔드 플러그인 구현 범위

코어 백엔드 구조(`plan/finish/2026-03-25-1153(종료)-다이어그램-동기화-아키텍처-재설계/07-백엔드-구조.md`)에서 정의한 `domain/markdown/collaboration/` 패키지에 마크다운 백엔드 플러그인을 구현한다.

### Capability 구현

```text
MarkdownCollaborationPlugin
  implements BaseCollaborationPlugin                    (필수)
  implements ArtifactFallbackCapableCollaborationPlugin  (마크다운 원문 fallback)
```

마크다운 플러그인은 **2개의 capability**를 구현한다:

| Capability | 구현 이유 |
|---|---|
| Base | 필수. pluginId, schemaVersion, ScopeResolver, ValidationHook |
| ArtifactFallback | 마크다운 원문 + frontmatter를 JSON으로 직렬화하여 fallback 복원 지원 |

`SchemaMigratableCollaborationPlugin`과 `ArtifactMigratableCollaborationPlugin`은 1단계에서 미구현. schemaVersion이 1이므로 마이그레이션이 불필요하다.

### ScopeResolver 매핑

| scope type | scope id 예시 | lock 의미 |
|---|---|---|
| `section` | `section/개요` | heading 기반 섹션 편집 중 |
| `document` | `document/root` | frontmatter 또는 구조 변경 중 |

백엔드 ScopeResolver는 프론트엔드 ScopeResolver와 동일한 scope 체계를 사용한다. lock acquire/release 시 서버가 scope 의미를 해석하여 충돌 판정한다.

이미지/asset 도메인은 이번 구현 범위에서 제외한다. `AssetCapableCollaborationPlugin`, `AssetReferenceExtractor`, `asset://` GC 연동은 후속 phase에서 추가한다.

### ArtifactSerializer/Codec 구현

```text
Artifact 포맷 (JSON):
  {
    "version": 1,
    "content": "# API 설계 문서\n\n## 개요\n...",
    "frontmatter": {
      "title": "API 설계 문서",
      "author": "홍길동",
      "date": "2026-03-26",
      "status": "draft",
      "tags": ["api", "rest"]
    }
  }

Serializer (snapshot → artifact):
  1. Y.Doc snapshot에서 Y.Text("body") 추출
  2. Y.Map("frontmatter")에서 메타데이터 추출
  3. JSON 직렬화

Codec (artifact → snapshot):
  1. JSON에서 content, frontmatter 역직렬화
  2. 빈 Y.Doc 생성
  3. Y.Text("body")에 마크다운 본문 삽입
  4. Y.Map("frontmatter")에 메타데이터 설정
  5. Y.Doc를 snapshot 바이트로 인코딩
```

### Snapshot Codec과의 관계

스냅샷 직렬화/역직렬화는 **코어의 `DocumentSnapshotCodec`**가 담당한다. 마크다운 플러그인은 별도의 snapshot codec을 구현하지 않는다.

```text
코어가 담당하는 부분:
  DocumentSnapshotCodec
    → decodeToSnapshot(persisted) → 메모리 snapshot
    → encodeForPersistence(inMemory) → 영속화용 바이트
    → snapshotFormatVersion() → 코어가 관리하는 포맷 버전

  DocumentPersistenceCoordinator
    → checkpoint(DocumentCheckpoint) → 스냅샷 저장
    → load(documentId) → PersistedDocument 복원

마크다운 플러그인이 관여하는 부분:
  pluginSchemaVersion = 1 (플러그인이 관리)
  snapshotFormatVersion → 코어가 관리 (플러그인은 관여하지 않음)
  ArtifactSerializer → checkpoint 시 compatibility artifact 생성
  ArtifactCodec → snapshot 없을 때 artifact 기반 복원
  DomainValidationHook → 필요 시 도메인 무결성 검증
```

| 1단계 | MarkdownCollaborationPlugin 등록, ScopeResolver (document/root만), ValidationHook |
| 3단계 | ScopeResolver 확장 (section/{id} 추가) |
| 5단계 | ArtifactSerializer, ArtifactCodec |

## 3-플러그인 구현 일정 비교

| 항목 | ERD | 화면기획 | 마크다운 |
|---|---|---|---|
| 총 일정 | 코어와 동시 (코어 검증용) | 7~12주 | 5~9주 |
| 단계 수 | — | 5단계 | 5단계 |
| 핵심 단계 | — | 2단계 (컴포넌트 시스템) | 2단계 (TextInputPipeline) |
| 코어 SPI 의존 | 전체 | 전체 (TextInput 제외) | **Base + TextInput + Presence + ArtifactFallback** |
| Primary CRDT | Y.Map | Y.Map | **Y.Text** |
| 백엔드 Capability | Base + Artifact + Schema Migration | Base + Asset | Base + ArtifactFallback |

마크다운 플러그인이 화면기획보다 일정이 짧은 이유:
1. 컴포넌트/인스턴스/배리언트 같은 복잡한 도메인 모델이 없다
2. 마크다운의 CRDT 병합(Y.Text 문자 단위)이 Y.Map보다 단순하다
3. UI 복잡도가 상대적으로 낮다 (adaptive 3-zone editor vs 캔버스+라이브러리+편집 모드)
4. Monaco 에디터를 그대로 재사용한다

## 성공 기준

이 플러그인이 성공했다고 판단하는 기준은 아래와 같다.

1. **코어 수정 제로** — MarkdownPlugin을 추가하면서 `collaboration/core/` 디렉토리의 파일을 하나도 수정하지 않았다.
2. **TextInputPipeline 검증** — 코어의 TextInputCapablePlugin SPI가 마크다운 편집 시나리오에서 정상 동작한다. parse/validate/buildCommands 파이프라인이 기대대로 흐른다.
3. **DraftState 검증** — dirty-invalid 상태에서 공유 상태가 오염되지 않는다. remote-pending 상태에서 3가지 선택이 올바르게 동작한다.
4. **협업 동작** — 두 사용자가 동시에 다른 섹션을 편집하고, scope lock이 충돌을 방지한다. 같은 섹션 편집 시 Y.Text CRDT가 문자 단위로 병합한다.
5. **산출물 품질** — HTML/원문 MD 내보내기가 sanitize 정책과 canonical buffer 기준으로 일관되게 생성된다.
6. **플랫폼 검증** — 세 번째 플러그인의 존재 자체가 "협업 문서 플랫폼 코어"의 재사용성을 증명한다. 특히 Y.Map 중심(ERD/화면기획)과 Y.Text 중심(마크다운)이라는 근본적으로 다른 두 패러다임 위에서 코어가 동일하게 동작함을 확인한다.
