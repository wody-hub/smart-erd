# 05. UI 레이아웃

## 디자인 방향 요약

마크다운 플러그인은 새 제품처럼 보이면 안 된다. 기존 `Documents` 허브와 같은 제품 언어를 유지하되, ERD보다 더 조용하고 writer-first여야 한다.

- 문서 허브 안의 두 번째 본격 문서 타입이다.
- 시각 방향은 `DESIGN.md`의 `Technical Editorial`을 그대로 따른다.
- 에디터 셸은 기존 workspace header와 editor chrome을 재사용한다.
- 캔버스형 4패널 제품이 아니라, **기술 문서 작성용 adaptive editor**로 설계한다.

핵심 경험은 이렇다.

1. 사용자는 `Documents` 허브에서 `ERD`와 `Markdown`을 같은 곳에서 본다.
2. 새 문서 생성 시 문서 타입과 템플릿을 빠르게 고른다.
3. 편집기는 기본적으로 `Outline + Write + Preview` 경험을 제공한다.
4. 메타 정보와 문서 설정은 항상 열려 있는 고정 컬럼이 아니라 필요할 때 여는 보조 패널이다.

## 1. 문서 허브 진입 UX

## 1.1 허브에서의 위치

기존 [DiagramsPage](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/pages/diagram/DiagramsPage.tsx) 를 문서 허브로 확장한다.

- 상단 hero는 그대로 사용한다.
- 문서 목록 row에서 `pluginId` 기반 type badge를 노출한다.
- `ERD`와 `Markdown`이 같은 정렬/검색/액션 체계 안에서 공존한다.
- markdown 문서는 dictionary context 대신 template/use case 요약을 보여준다.

## 1.2 문서 생성 플로우

기존의 단일 입력 modal로는 부족하다. 생성 UX는 `2-step create flow`로 바꾼다.

### Step 1. 문서 유형 선택

```text
┌──────────────────────────────────────────────┐
│ 새 문서 만들기                               │
│ 어떤 종류의 문서를 만들까요?                 │
│                                              │
│ [ ERD 문서 ]         [ Markdown 문서 ]       │
│ FK, 사전 컨텍스트      설계 메모, API 문서,    │
│ 기반 구조 설계         운영 가이드, 리뷰 문서   │
└──────────────────────────────────────────────┘
```

### Step 2-A. ERD 선택 시

- 현재와 같이 dictionary context 선택
- 문서명 입력

### Step 2-B. Markdown 선택 시

- template 카드 선택
- 문서명 입력
- 필요 시 초기 메타(상태, 태그) 최소값만 선택

```text
[ API 설계 ]
REST 명세, 요청/응답 예시, 인증 규칙

[ 운영 가이드 ]
배포, 장애 대응, 체크리스트

[ 회의/리뷰 노트 ]
결정사항, TODO, 액션 아이템

[ 빈 문서 ]
템플릿 없이 새로 시작
```

## 1.3 왜 이렇게 바꾸는가

- `ERD`와 `Markdown`은 생성 시 필요한 정보가 다르다.
- dictionary selector를 markdown에도 노출하면 의미가 흐려진다.
- template 선택은 markdown의 첫 30초 경험을 훨씬 낫게 만든다.

## 2. 편집기 셸 구조

## 2.1 고정 원칙

- 기존 workspace header를 재사용한다.
- 새 bespoke top chrome을 만들지 않는다.
- 우측 헤더 액세서리만 markdown 전용으로 교체한다.
- 기본 레이아웃은 `3-zone adaptive layout`이다.

## 2.2 3-zone adaptive layout

### 데스크톱 기본형

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Header: Team / Project / Document        [mode] [collab] [save]     │
├───────────────┬───────────────────────────┬──────────────────────────┤
│ Outline Rail  │ Write Surface             │ Preview Surface          │
│               │                           │                          │
│ API 설계      │ # API 설계                │ API 설계                 │
│ - 개요        │                           │ rendered preview         │
│ - 인증        │ markdown editor           │ synced by section        │
│ - 응답 규격   │                           │                          │
│               │                           │                          │
├───────────────┴───────────────────────────┴──────────────────────────┤
│ Status Strip: section | draft state | autosave | diagnostics        │
└──────────────────────────────────────────────────────────────────────┘
```

구성 비율:

- outline rail: `220px` 고정, 접기 가능
- write surface: 기본 `minmax(0, 1.15fr)`
- preview surface: 기본 `minmax(360px, 0.85fr)`
- info drawer: 기본 닫힘, 열리면 overlay 또는 우측 inset panel

### 태블릿

```text
[Header]
[Toolbar]
[Write | Split | Preview]
[Outline drawer button]

기본: Write 100%
Split: Write 55 / Preview 45
Outline: overlay sheet
Info: side sheet
```

### 모바일

```text
[Header]
[Write] [Preview] [Outline]

현재 탭만 전체 화면 사용
문서 정보/설정은 bottom sheet
```

모바일에서 4열 유지 시도는 금지한다.

## 2.3 메타 패널 전략

기존 초안의 `메타·속성` 고정 우측 컬럼은 삭제한다.

이유:

- 문서 작성 화면에서 고정 4번째 컬럼은 너무 무겁다.
- 대부분의 시간에는 metadata보다 본문 작성과 preview가 중요하다.
- 현재 제품의 editor shell density와 맞지 않는다.

대신 다음으로 바꾼다.

- `문서 정보` 버튼 클릭 시 `Info Drawer` 열림
- 포함 내용:
  - 제목
  - 상태
  - 태그
  - 작성자/수정일
  - preview mode
  - auto save
  - line wrap
  - font size

`frontmatter.update`는 그대로 지원하되, UI는 helper surface일 뿐이고 항상 열려 있지 않다.

## 3. 편집 화면 상세

## 3.1 Outline Rail

```text
[문서 구조]
API 설계 문서
  - 개요
  - 인증
  - 엔드포인트
    - 사용자 API
    - 주문 API

─────────────────
[협업]
홍길동  개요
김철수  인증 🔒
```

역할:

- heading 기반 section navigation
- 현재 커서 섹션 active highlight
- 잠금 상태, 원격 편집 상태 표시
- 섹션 reorder는 1차에서는 넣지 않는다

초안의 `섹션 드래그로 순서 변경`은 후속 단계로 미룬다. 마크다운 구조 편집과 협업 lock이 동시에 걸린 상태에서 reorder까지 1차에 넣으면 복잡도만 커진다.

## 3.2 Write Surface

중앙의 Monaco가 주인공이다.

- markdown syntax highlight
- heading, list, code fence, table snippet auto-complete
- 원격 커서/선택 영역
- diagnostics gutter
- focused writing을 해치지 않는 최소 툴바

### 툴바 그룹

```text
[H] [B] [I] [Code] [Link] [Task] [Table] | [Write] [Split] [Preview] | [Info]
```

원칙:

- 모든 포맷팅 버튼을 상시 노출하지 않는다.
- 자주 쓰는 것만 남기고, 나머지는 dropdown/command menu로 뺀다.
- toolbar는 editor 상단의 operational strip로 처리한다.

## 3.3 Preview Surface

preview는 “예쁘게 렌더링된 문서”여야지 별도 앱처럼 보이면 안 된다.

- warm surface 위에 editorial typography 사용
- 코드 블록은 mono + calm dark inset
- table은 dense but readable
- heading anchor와 outline sync
- task list 체크는 1차에서는 read-only 또는 guarded interaction으로 시작

preview는 단순 렌더 영역이 아니라, 사용자가 문서 결과물을 믿게 만드는 surface다.

## 3.4 Status Strip

하단 상태 바는 유지하되 더 얇고 명확하게 간다.

```text
Ln 15, Col 8 | Section: 인증 | dirty-valid | 저장 24초 전 | 진단 1건
```

표시 우선순위:

1. 현재 섹션
2. draft 상태
3. 저장 상태
4. diagnostics 수

자동저장 문구를 과하게 떠들게 하지 않는다.

## 4. 협업 UI

## 4.1 헤더

기존 editor header accessory 패턴을 따른다.

- 연결 상태
- collaborators
- save
- preview mode
- info drawer trigger

새로운 `공유` 버튼 중심 헤더는 만들지 않는다. 현재 editor shell과 같은 utility rail 안에서 해결한다.

## 4.2 remote pending

`remote-pending`은 상단 큰 경고 카드가 아니라 editor 상단 slim banner로 처리한다.

```text
⚠ 다른 참여자의 변경이 도착했습니다. [수락] [내 편집 유지] [비교]
```

ERD에서 이미 정리한 banner 언어를 재사용한다.

## 4.3 section lock

outline에서 lock 상태를 먼저 보여주고, write surface에서 read-only feedback을 준다.

- outline: lock icon + collaborator chip
- editor: 해당 구역 muted background
- 상태 strip: 짧은 안내

별도 모달은 금지한다.

## 5. 프리뷰 모드

기본 모드는 `Split`이다.

| 모드 | 설명 | 기본 대상 |
|---|---|---|
| Write | 본문 작성 집중 | 작은 화면, 깊은 작성 모드 |
| Split | 작성 + 결과 동시 확인 | 기본 |
| Preview | 읽기/검토 중심 | 리뷰, 공유 전 확인 |

`Write / Split / Preview`는 toolbar와 mobile tab에 공통 언어로 사용한다.

## 6. 반응형 규칙

| 뷰포트 | 레이아웃 | 규칙 |
|---|---|---|
| `1440px+` | outline + write + preview | 기본 split, info drawer overlay |
| `1024~1439px` | write + preview | outline은 collapsible rail |
| `768~1023px` | write/split/preview 전환 | outline/info는 sheet |
| `<768px` | tabbed single-surface | write, preview, outline 3탭 |

모바일에서 보여야 하는 우선순위:

1. 문서 제목
2. 현재 모드
3. 저장/협업 상태
4. 본문 작성 또는 preview

## 7. 템플릿 UX

markdown는 template가 핵심이다. UI에도 반영한다.

### 기본 템플릿 카드

- API 설계
- 운영 가이드
- 회의/리뷰 노트
- 빈 문서

각 카드는 아래를 가진다.

- 이름
- 한 줄 설명
- 예상 구조 preview
- 생성 후 첫 heading 세트 예시

선택된 template는 생성 modal과 문서 row metadata에 반영된다.

## 8. 초안 대비 변경 사항

이번 재설계에서 버리는 것:

- 고정 4패널 레이아웃
- 항상 열려 있는 메타/속성 컬럼
- 섹션 드래그 reorder 1차 포함
- 마크다운 전용 독립 헤더

이번 재설계에서 새로 넣는 것:

- document hub 2-step create flow
- template 카드 선택 UX
- adaptive 3-zone editor
- info drawer / sheet 전략
- mobile 3-tab editor

## 9. 구현자가 바로 알아야 할 요점

- 새 페이지를 만들더라도 시각적 뼈대는 현재 workspace/editor shell에 붙여라.
- markdown 에디터는 `outline rail`, `write surface`, `preview surface`, `info drawer` 네 조각으로 구현하되, 고정 4열로 만들지 마라.
- 문서 생성 UX는 `ERD`와 `Markdown`을 같은 다이얼로그에 억지로 넣지 말고 step flow로 풀어라.
- `frontmatter`는 데이터 구조상 중요하지만, 화면에서 늘 주인공일 필요는 없다.
