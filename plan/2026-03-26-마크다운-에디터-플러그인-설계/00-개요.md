# 마크다운 에디터 플러그인 설계

> 작성일: 2026-03-26
> 상태: 초안
> 선행 문서: `plan/finish/2026-03-25-1153(종료)-다이어그램-동기화-아키텍처-재설계/`

## 이 문서의 목적

협업 문서 플랫폼 코어 위에 올라가는 세 번째 플러그인인 `MarkdownPlugin`을 설계한다.

ERD 플러그인이 테이블/컬럼/엣지를, 화면기획 플러그인이 컴포넌트/인스턴스/화면을 다루듯이, 마크다운 에디터 플러그인은 **마크다운 텍스트를 AST로 파싱하고, 섹션 단위로 협업하며, 다양한 형식으로 내보내는** 기능을 제공한다.

## 세 번째 플러그인의 의미

이 플러그인은 플랫폼 코어의 **TextInputCapablePlugin을 본격적으로 검증하는 최초의 순수 텍스트 기반 플러그인**이다.

| 플러그인 | 주 입력 경로 | TextInputPipeline | DraftState 활용 |
|---|---|---|---|
| ERD | 캔버스(시각) + DSL(텍스트) | DSL 파싱 (보조) | 코드 편집기 한정 |
| 화면기획 | 캔버스(시각) + 속성 패널(폼) | 미구현 | 미사용 |
| **마크다운** | **텍스트 편집기(주)** | **전체 편집 흐름의 핵심** | **모든 편집에 적용** |

ERD에서는 TextInputPipeline이 DSL 편집기라는 보조 입력 경로에만 사용되었다. 마크다운 플러그인에서는 TextInputPipeline이 **유일한 주 입력 경로**가 되어, 코어의 텍스트 편집 흐름(05-상세-흐름도 흐름 A)과 DraftState 재조정(흐름 D)이 완전히 검증된다.

## 기존 마크다운 에디터와의 차별점

이 플러그인은 Notion, HackMD, Obsidian 같은 범용 마크다운 에디터를 대체하려는 것이 아니다.

| 구분 | Notion / HackMD | 이 플러그인 |
|---|---|---|
| 목적 | 범용 문서 편집 | 프로젝트 내 기술 문서 협업 |
| 편집 방식 | WYSIWYG 또는 Split View | Split View (Monaco + 프리뷰) |
| 협업 방식 | 독자적 CRDT/OT 엔진 | 플랫폼 코어의 Y.Text CRDT |
| 락 모델 | 없음 또는 문서 전체 | 섹션(heading) 단위 scope lock |
| 자산 관리 | 독자적 | 후속 phase에서 코어 AssetRuntime 연동 |

핵심 가치는 **ERD, 화면기획과 동일한 코어 인프라 위에서 기술 문서를 실시간 협업으로 작성**할 수 있다는 점이다.

## 범위

### 이번 문서가 다루는 범위

- 마크다운 AST 도메인 모델과 Y.Doc 매핑
- TextInputPipeline 전체 흐름 (파싱, 검증, diff, 커맨드 생성)
- DraftState 상태 머신과 원격 변경 병합 전략
- 플랫폼 코어 SPI 구현 매핑 (현재 4개 capability + 후속 asset phase)
- 산출물 내보내기 (HTML, 원문 MD)
- 내장 문서 템플릿
- 문서 허브 생성 UX와 adaptive editor shell
- 단계별 구현 로드맵

### 이번 문서가 다루지 않는 범위

- WYSIWYG 완전 통합 (Notion 스타일 블록 에디터)
- MDX (JSX in Markdown)
- 코멘트/리뷰 시스템
- 코어 아키텍처 변경 (코어는 이미 설계 완료)
- Git 연동 / 버전 관리

## 설계 원칙

1. **코어 수정 제로** — 이 플러그인은 기존 코어 계약만으로 동작해야 한다. 코어에 마크다운 전용 코드가 들어가면 설계 실패다.

2. **TextInputPipeline이 주 입력 경로** — 모든 편집은 텍스트 입력 → 파싱 → 검증 → 커맨드 생성의 파이프라인을 거친다. 캔버스 adapter가 아니라 텍스트 adapter가 primary다.

3. **Y.Text 중심 CRDT** — 화면기획이 Y.Map 위주로 구조화된 데이터를 다루는 것과 달리, 마크다운은 Y.Text가 primary 공유 상태다. 텍스트의 문자 단위 CRDT 병합을 최대한 활용한다.

4. **DraftState 안전망** — 모든 텍스트 편집은 DraftState를 거친다. 불완전한 마크다운(닫히지 않은 코드 블록, 깨진 링크 등)은 로컬 draft에만 존재하고, 파싱/검증 성공 전에는 공유 상태에 반영하지 않는다.

5. **점진적 복잡도** — 1단계는 전체 재파싱, 5단계에서 증분 파싱. 한 번에 최적화하지 않는다.

## 핵심 설계 결정

| 결정 | 선택 | 근거 |
|---|---|---|
| Primary CRDT | Y.Text | 마크다운은 순수 텍스트. Y.Map은 구조화된 데이터에 적합하지만 텍스트 편집에는 오버헤드 |
| 에디터 | Monaco Editor | ERD DSL에서 이미 사용 중. 학습 비용 제로, 마크다운 구문 하이라이팅 기본 지원 |
| 파서 | remark (unified) | mdast 표준, 생태계 풍부(수백 개 플러그인), GFM 확장 용이 |
| Scope Lock 단위 | Heading 기반 Section | 마크다운의 자연스러운 구조 단위. Heading이 문서의 논리적 구역을 나눈다 |
| DraftState 정책 | 300ms debounce 파싱 | 매 keystroke 파싱은 비용 과다. 300ms idle 후 파싱이 UX와 성능의 최적 균형 |
| 프리뷰 | Split View (Monaco + HTML) | WYSIWYG는 2차 확장. Split View가 구현 비용 대비 효과 최적 |
| 1단계 파싱 | 전체 재파싱 | 증분 파싱은 1단계에서 불필요한 복잡도. 300ms debounce와 전체 재파싱으로 충분 |

## 3-플러그인 비교 요약

| 구성요소 | ERD | 화면기획 | 마크다운 |
|---|---|---|---|
| 주 입력 경로 | 캔버스 + DSL 텍스트 | 캔버스 + 속성 패널 | **텍스트 편집기** |
| Primary CRDT | Y.Map (구조화) | Y.Map (구조화) | **Y.Text (텍스트)** |
| TextInputPipeline | DSL 파싱 (보조) | 미구현 | **전체 편집의 핵심** |
| DraftState | 코드 편집기 한정 | 미사용 | **모든 편집에 적용** |
| Scope Lock | `table/{tableId}` | `component/{id}`, `screen/{id}` | **`section/{id}`** |
| Asset Binding | 없음 | 이미지 placeholder | **후속 phase에서 `![alt](asset://id)` 패턴 지원** |
| Artifact | content JSON (호환) | 미구현 (1단계) | **마크다운 원문 + frontmatter** |
