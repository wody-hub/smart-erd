# 대용량 ERD 동기화 개선 기획서 (Phase 1, Phase 2)

## 1. 배경
- 현재 코드 반영 경로는 `replaceFromDdl` 기반 전체 재생성 방식이다.
- 전체 재생성은 테이블/관계 삭제 후 재생성 + 전체 오토레이아웃까지 수행한다.
- 테이블 수가 200~500 규모로 증가하면 Apply 지연, 렌더링 프리즈, 협업 트래픽 급증 가능성이 크다.
- 그룹 정보(논리적 테이블 그룹)도 전체 교체 시 유실되거나 관리 비용이 커진다.

## 2. 문제 정의
- 성능: 전체 재생성 비용이 데이터 크기에 비례하여 급격히 증가한다.
- 안정성: 자동 동기화 중 반복 재생성으로 사용자 체감 품질이 저하된다.
- 사용성: 대형 다이어그램에서 편집 흐름이 끊기고 충돌 가능성이 올라간다.
- 확장성: 500 테이블 이상을 목표로 할 때 현재 방식은 운영 리스크가 높다.

## 3. 목표
- 1차 목표: 기존 구조를 유지하면서 즉시 체감 성능 저하를 줄인다.
- 2차 목표: 전체 재생성에서 디프 기반 증분 반영 구조로 전환한다.
- 공통 목표: 그룹 멤버십 및 주요 메타를 최대한 보존하고, 대형 다이어그램에서도 안정적으로 동작시킨다.

## 4. 범위
### 포함
- DDL/DSL Apply 경로 최적화
- 자동 동기화 정책 재정의
- 레이아웃 적용 전략 변경
- 대용량 보호장치(임계치/모드 전환/가드)
- 성능 계측 지표 및 회귀 검증

### 제외
- DB 서버 성능 튜닝
- React Flow 렌더러 교체
- 오프라인 배치 처리 아키텍처 변경

## 5. 반복 점검 운영 모델 (최대 20회)
- 목적:
  - 작업 티켓 분해 전, 계획서 품질을 반복 점검으로 안정화
- 반복 단위:
  - 1회 = 기획팀 점검 -> 구현팀 점검 -> 리뷰 삼총사 확인 -> 계획서 수정
- 최대 횟수:
  - 최대 20회
  - 단, 종료 조건 충족 시 조기 종료
- 반복 종료 조건:
  - Critical/High 이슈 0건
  - KPI/게이트/롤백/책임자/기한 항목 누락 0건
  - 동일 이슈 2회 연속 재발 0건
- 반복 산출물:
  - 회차별 이슈 목록(심각도/영향/조치)
  - 문서 변경 요약
  - 다음 회차 점검 포인트

## 6. 역할 분담 및 의사결정 체계
- 기획팀:
  - 목표/KPI/범위/우선순위/수용 기준 승인
- 구현팀:
  - 실행 가능성/복잡도/폴백/테스트 가능성 검증
- 리뷰 삼총사:
  - 아키텍처: 경계/확장성/리스크
  - 개발: 구현 경로/회귀/검증 가능성
  - 디자인: 사용자 흐름/정책 일관성
- 충돌 해소 규칙:
  - 사용자 영향/데이터 보존 리스크가 큰 안을 우선 반영
  - 동률이면 구현 복잡도가 낮고 롤백이 쉬운 안 채택

## 7. 단계별 추진 계획
## Phase 1 (빠른 완화, 1~2주)
### 핵심 전략
- `replaceFromDdl` 유지
- 대용량에서 자동 전체 레이아웃 금지
- 자동 동기화 시 Full Replace 제한
- 사용자에게 Apply 모드/경고 제공

### 주요 기능
- 노드 수 임계치 도입 (예: 150, 300)
- 임계치 이상에서 자동 Apply 비활성 또는 확인 다이얼로그 강제
- 신규/변경 테이블만 부분 배치하는 경량 레이아웃 옵션
- 성능 텔레메트리: Apply 소요시간, 노드수, 엣지수, 레이아웃 시간

### 성공 기준
- 200 테이블 기준 Apply p95 지연 40% 이상 감소
- UI 프리즈(체감 1초 이상 블로킹) 빈도 유의미 감소
- 기존 기능 회귀 없음 (빌드/단위/수동 시나리오 통과)

### Phase 2 착수 게이트 (필수 의사결정)
- 게이트 1: rename 판정 정책 확정
  - 기본 정책: 물리명 exact 매칭을 우선하고, 불확실한 경우 `delete+add`로 처리
- 게이트 2: 그룹 재매핑 강도 확정
  - 기본 정책: 보수 모드(확실한 매칭만 그룹 유지, 불확실 항목은 제외)
- 게이트 3: 대용량 임계치 기본값 확정
  - 기본값: 경고 150, 자동 Apply 제한 300
- 위 3개 게이트가 모두 확정되기 전에는 Phase 2 개발 착수 금지

### Phase 2 게이트 의사결정 표
- 게이트 1(rename 정책): 담당 PM 1명 + 리드 개발 1명, 목표 확정일 T+3영업일
- 게이트 2(그룹 재매핑): 담당 아키텍트 1명 + FE 개발 1명, 목표 확정일 T+4영업일
- 게이트 3(임계치 기본값): 담당 SRE/성능 담당 1명 + FE 개발 1명, 목표 확정일 T+5영업일

## Phase 2 (구조 개선, 3~5주)
### 핵심 전략
- `replaceFromDdl` 중심 흐름을 `applyDiffFromDdl`로 전환
- 테이블/컬럼/관계를 식별 키로 매칭하여 증분 업데이트
- 레이아웃도 변경 범위에 한정

### 주요 기능
- 엔티티 매칭 규칙: 물리명/논리명/정규화 키 기반 단계적 매칭
- 테이블/컬럼/엣지 단위 add/update/delete 디프 엔진
- ID/position/selected 상태 보존 정책
- 그룹 멤버십 보존 및 재매핑 정책
- 실패 시 안전 폴백: Full Replace로 즉시 전환

### 성공 기준
- 500 테이블 기준 Apply p95 2초 이내 목표
- 변경 없는 재적용(no-op)에서 실질 변경 0건 보장
- 그룹/레이아웃/협업 상태 보존율 향상

## 8. 성능 KPI 측정 프로토콜
- 목표:
  - KPI 판정을 환경/입력/절차 고정 상태에서 수행
- 환경 고정:
  - 브라우저: Chrome Stable
  - 장비: 팀 표준 개발 장비 1종 고정 (Apple Silicon 16GB급)
  - 네트워크: 로컬 단일 사용자 모드(협업 부하 제외)
- 데이터셋 고정:
  - `S50`, `S200`, `S500` 시나리오 SQL/DSL 샘플을 저장소에 고정
  - 각 시나리오의 테이블 수, 엣지 밀도, 컬럼 수 분포를 명시
- 측정 절차:
  - 각 시나리오 1회 워밍업 + 5회 본측정
  - 수집값: parse-to-apply, Yjs transact, layout, total blocking time
  - 결과는 p50/p95와 표준편차로 기록
- 합격 판정:
  - Phase 1/2 성공 기준을 모두 충족하고, 회귀 항목이 없을 것

## 9. 리스크 및 대응
- 매칭 오탐으로 인한 잘못된 업데이트
  - 대응: 보수적 매칭, 불확실 항목은 add/delete 처리
- 디프 엔진 복잡도 증가
  - 대응: 단계별 롤아웃 + 폴백 경로 유지
- 협업(Yjs) 충돌 시나리오 증가
  - 대응: 트랜잭션 경계 표준화 및 동시성 테스트 보강
- 폴백 시 그룹 보존 실패 가능성
  - 대응: Full Replace 폴백에서도 그룹 재매핑 규칙을 강제 적용

## 10. QA/리뷰 운영
- QA는 리뷰 삼총사(아키텍처/개발/디자인) 기준으로 단계 게이트 운영
- Phase 1/2 각각 머지 전 체크리스트 고정
- 성능 리그레션은 기준 샘플(50/200/500 테이블)로 정량 비교
- 반복 점검 회차마다 QA 체크리스트를 함께 갱신
