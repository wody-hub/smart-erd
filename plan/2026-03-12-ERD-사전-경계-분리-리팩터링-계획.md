# 2026-03-12 ERD 사전 경계 분리 리팩터링 계획

작성일: 2026-03-12
상태: 초안
우선순위: `2 -> 1 -> 3`

## 배경

현재 구조에서 ERD 편집 화면은 라우트 단위로는 분리되어 있지만, 기능 경계 관점에서는 아직 완전히 독립적이지 않다.

- 프런트에서 ERD 전용 UI 일부가 `components/layout`에 위치한다.
- ERD 화면은 `dictionarySetId`를 통해 사전 데이터를 직접 참조한다.
- 백엔드에서도 `Diagram`이 `DictionarySet`을 참조하고 있어 사전 관리 절차 변경이 ERD 메타데이터와 연결된다.

요구사항은 명확하다.

- 용어사전 관리 화면/절차 변경이 ERD 캔버스, 코드 에디터, 협업, 저장/복구 동작에 영향을 주면 안 된다.
- ERD는 사전 "관리 기능"에 의존하면 안 되고, 사전 "조회 데이터 계약"만 소비해야 한다.

## 목표

이번 작업의 목표는 다음과 같다.

1. ERD 기능이 사전 관리 UI/절차와 분리된다는 경계를 코드상에 명확히 만든다.
2. 다른 메뉴 수정이 ERD 편집 화면으로 전파되지 않도록 프런트 구조를 정리한다.
3. 이후 리뷰/개발 시 동일 원칙을 유지할 수 있도록 가드레일을 문서화한다.

## 비목표

이번 단계에서 아래는 즉시 하지 않는다.

1. 사전과 ERD 간 데이터 참조 자체를 제거하는 대규모 도메인 재설계
2. DB 스키마를 바꾸는 광범위한 마이그레이션
3. ERD 기능 자체의 UX 변경
4. 협업 프로토콜 변경

## 왜 `2 -> 1 -> 3` 순서인가

### 2. 실제 영향 없는 안전 리팩터링을 먼저 해야 하는 이유

폴더를 먼저 옮기거나 문서를 먼저 쓰면 보기만 좋아지고 실제 결합은 그대로 남을 수 있다.
먼저 코드상 의존 방향을 바로잡아야 이후 구조 정리와 문서화가 의미를 가진다.

핵심 원칙:

- ERD는 "사전 조회 인터페이스"만 안다.
- ERD는 "사전 관리 페이지/컴포넌트/절차"를 모른다.
- 공용 레이아웃은 ERD 내부 상태(store, react-flow, collaboration)를 직접 알지 않는다.

### 1. 폴더/네이밍 정리는 두 번째인 이유

실제 의존을 끊은 뒤 이름과 디렉터리를 맞춰야 구조가 진실을 반영한다.
반대로 먼저 옮기면 대규모 파일 이동만 생기고 회귀 위험이 커진다.

### 3. 가드레일 문서는 마지막인 이유

문서는 현재 구조를 기준으로 써야 오래 유지된다.
구조가 정리되기 전에 문서를 쓰면 다시 고쳐야 할 가능성이 높다.

## 단계별 실행 계획

## 2단계. 실제 영향 없는 안전 리팩터링

목표:
ERD가 사전 관리 기능과 직접 결합되지 않고, 사전 조회 데이터만 소비하도록 경계를 정리한다.

### 2-1. 프런트 의존 경계 식별

확인 대상:

- `client/src/pages/diagram/DiagramPage.tsx`
- `client/src/components/erd/*`
- `client/src/hooks/useDictionaryCache.ts`
- `client/src/components/erd/ErdDictionaryContext.tsx`
- `client/src/pages/dictionary/*`
- `client/src/api/dictionarySetApi.ts`
- `client/src/api/domainApi.ts`
- `client/src/api/termApi.ts`

검토 포인트:

- ERD가 정말 필요한 것은 무엇인가
- 사전 세트 선택/관리와 용어/도메인 조회 중 어떤 것이 ERD 내부 계약이어야 하는가
- `dictionarySetId` 전달 책임을 어느 계층이 가져야 하는가

### 2-2. ERD 전용 사전 접근 어댑터 정의

후보 방향:

- `ErdDictionaryProvider`를 ERD 전용 조회 어댑터로 명확히 승격
- ERD 내부는 `terms/domains/findTermById/findDomainById/searchTerms` 같은 조회 계약만 사용
- 세트 생성/수정/삭제/기본세트 변경 같은 관리 기능은 ERD 경계 밖에 둠

예상 산출물:

- ERD 전용 dictionary facade 또는 provider contract
- ERD 내부 import 경로 단순화
- dictionary 관리 화면과의 직접 의존 제거

### 2-3. 공용 레이아웃에서 ERD 전용 책임 제거

현재 위험 요소:

- `components/layout/Sidebar.tsx`는 사실상 ERD 전용 사이드바다.
- `Header.tsx`는 다이어그램 편집 맥락에서 협업 바를 직접 포함한다.

리팩터링 방향:

- ERD 편집용 보조 UI를 `erd` 또는 `diagram` 네임스페이스 아래로 이동
- `layout`은 공용 프레임 역할만 수행
- `useCanvasStore`, `useCollaborationStore`, `useReactFlow` 직접 참조는 ERD 전용 영역으로 국한

### 2-4. 백엔드 경계 재점검

즉시 대규모 재설계는 하지 않되, 계약을 명확히 한다.

검토 포인트:

- `Diagram`이 `DictionarySet`을 참조하는 이유와 최소 책임
- `DictionarySetService`의 삭제/기본세트 변경이 ERD 기능에 미치는 영향 범위
- ERD가 필요한 것은 "조회 가능한 사전 컨텍스트"인지, "사전 관리 수명주기"인지 구분

필요 시 후속 과제:

- Diagram용 사전 참조 정책 문서화
- 삭제 시 null 해제 외 추가 보호 규칙 정의

### 2-5. 검증

필수 확인:

- 사전 관리 화면 수정 없이 ERD 편집 화면 정상 동작
- ERD 편집 화면에서 용어/도메인 조회 기능 정상 동작
- 코드 에디터/캔버스/협업/자동백업에 회귀 없음
- 팀/프로젝트/사전/다이어그램 목록 화면에서 라우팅 회귀 없음

## 1단계. 폴더 및 네이밍 정리

목표:
정리된 경계를 디렉터리 구조와 이름에 반영한다.

### 1-1. ERD 전용 컴포넌트 재배치

우선 후보:

- `client/src/components/layout/Sidebar.tsx`
- `client/src/components/layout/CollaboratorsBar.tsx`
- `client/src/components/layout/CollaboratorsPopover.tsx`
- `client/src/components/layout/SidebarGroupItem.tsx`
- `client/src/components/layout/SidebarTableItem.tsx`

방향:

- `client/src/components/erd/*` 또는 `client/src/components/diagram/*`로 이동
- 이름도 역할 기준으로 재정의
  - 예: `Sidebar` -> `DiagramSidebar`

### 1-2. 스토어/훅 네임스페이스 정리

후보:

- `client/src/stores/useCanvasStore.ts`
- `client/src/stores/useCollaborationStore.ts`
- `client/src/hooks/useYjsCollaboration.ts`

방향:

- ERD 전용 상태는 별도 네임스페이스를 부여
- 공용 스토어처럼 보이지 않도록 구조를 명확히 함

### 1-3. import 규칙 안정화

정리 목표:

- ERD 페이지는 ERD 전용 모듈만 직접 조합
- dictionary 페이지는 dictionary 전용 모듈만 직접 조합
- layout은 공용 UI primitive만 사용

## 3단계. 가드레일 문서화

목표:
이후 기능 추가나 화면 수정 시 경계가 다시 무너지지 않도록 개발 규칙을 남긴다.

### 3-1. 문서화 대상

후보 위치:

- `README.md`
- `docs/`
- `plan/decisions/`

권장 문서 내용:

- ERD와 dictionary의 책임 분리
- 허용 의존 방향
- 금지 의존 예시
- 리뷰 체크리스트

### 3-2. 명문화할 규칙

예시:

- ERD는 사전 관리 UI를 import하지 않는다.
- 공용 layout은 ERD store/react-flow/yjs를 직접 사용하지 않는다.
- 사전 기능 변경 시 ERD 회귀 체크 포인트를 반드시 확인한다.
- 다이어그램 편집 경계 변경은 별도 아키텍처 리뷰 대상으로 본다.

## 위험 요소

1. `dictionarySetId`가 현재 다이어그램 조회/표시 UX와 연결되어 있어, 경계 정리 중 표시 정보가 누락될 수 있다.
2. 레이아웃 컴포넌트 이동 시 import churn이 커져 프런트 회귀 가능성이 있다.
3. ERD 협업/코드 에디터/캔버스는 상태 결합도가 높아, 얕은 리네이밍도 부수효과를 만들 수 있다.

## 작업 원칙

1. 먼저 의존을 끊고, 나중에 이동한다.
2. ERD 런타임 동작을 바꾸지 않는 리팩터링부터 한다.
3. 라우트, 저장, 협업, autosave 회귀를 최우선으로 막는다.
4. 한 번에 크게 바꾸지 말고, 경계 단위로 나눠 검증한다.

## 성공 기준

다음이 충족되면 이번 목표를 달성한 것으로 본다.

1. dictionary UI/절차 수정이 ERD 화면 코드에 직접 영향 주지 않는다.
2. ERD는 사전 조회 데이터 계약만 소비한다.
3. `layout` 네임스페이스에 ERD 전용 책임이 남지 않는다.
4. 경계 규칙이 문서와 리뷰 기준으로 남는다.
