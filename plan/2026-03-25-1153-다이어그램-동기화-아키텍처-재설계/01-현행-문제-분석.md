# 01. 현행 문제 분석

## 현행 구조 개요

```
Code Editor ←──── useBidirectionalCodeSync ────→ ERD Canvas
     ↕                      ↕                        ↕
 parseDsl()          useCanvasStore              yjsBridge
     ↕               (Y.Doc 직접 관리)               ↕
 generateDsl()            ↕                      Y.Doc
     ↕            useAutoBackup                     ↕
 diffPlan              ↕                     YjsProvider
     ↕           saveDiagram API                    ↕
 applyDiffToYDoc       ↕                     WebSocket
                  useCollaborationStore
```

## 핵심 문제 5가지

### 문제 1: 단일 책임 위반 (SRP 위반)

`useCanvasStore`가 담당하는 책임:

| 책임 | 파일 | 본래 소속되어야 할 계층 |
|------|------|------------------------|
| Y.Doc 생명주기 관리 | canvasSyncActions | Collaboration 계층 |
| Y.Doc → React Flow 동기화 | canvasSyncActions | Bridge/Adapter 계층 |
| History/Undo 관리 | canvasSyncActions | History 계층 |
| 노드 위치 큐 관리 | canvasSyncActions | 최적화 계층 |
| 테이블/컬럼 CRUD | canvasTableActions | Domain 계층 |
| 엣지/관계 관리 | canvasTableActions | Domain 계층 |
| DDL 임포트/파싱 | canvasTableActions | Command 계층 |
| 그룹 관리 | canvasGroupActions | Domain 계층 |
| 백업 해시 관리 | canvasSyncActions | Persistence 계층 |
| 코드 에디터 테이블 키 | canvasSyncActions | Lock 계층 |

하나의 store에 10개 이상의 책임이 혼재되어 있다.

### 문제 2: 양방향 동기화 루프

Code ↔ ERD 간 양방향 동기화를 위해 **4-Layer 방어**가 필요한 수준의 복잡도:

```
Layer 1: Origin Flag
  → 'user-code' / 'code-auto-sync' / 'erd-auto-sync' / null

Layer 2: Revision Hash Tracking
  → nodes/edges 구조 기반 해시 비교

Layer 3: Suppress Flag
  → suppressNextErdSyncRef (일시 억제 타이머)

Layer 4: Schema Hash Comparison
  → parsedSchemaHash vs persistedDiagramSchemaHash
```

4개 레이어가 모두 맞물려야 루프가 방지되며, 하나라도 타이밍이 어긋나면 무한 루프 또는 변경 누락이 발생한다.

### 문제 3: 저장 경로 분산

7개의 독립적인 저장 트리거가 각각 다른 조건과 방식으로 동작:

| # | 트리거 | 타이밍 | 저장 대상 | 방식 |
|---|--------|--------|----------|------|
| 1 | 주기 저장 | 60초 간격 | content JSON | REST PUT |
| 2 | Idle 저장 | 변경 후 10초 유휴 | content JSON | REST PUT |
| 3 | 탭 숨김 | visibilitychange | content JSON | REST PUT |
| 4 | 페이지 이탈 | pagehide | content + snapshot | fetch keepalive |
| 5 | 브라우저 종료 | beforeunload | content + snapshot | fetch keepalive |
| 6 | 수동 저장 | Ctrl+S | content + snapshot | REST PUT |
| 7 | WS Snapshot flush | 5초 간격 | accumulated updates | 백엔드 스케줄러 |

각 경로가 미묘하게 다른 데이터를 다른 방식으로 저장하므로, 엣지 케이스와 경합 조건이 발생한다.

### 문제 4: 이중 직렬화

같은 다이어그램 상태를 두 가지 형태로 동시에 관리:

```
Diagram 엔티티:
  content (TEXT)           ← React Flow JSON
  ydocSnapshot (BYTEA)     ← Yjs update 리스트 (YLPF)
  contentRevision (BIGINT) ← content 변경 카운터
  snapshotRevision (BIGINT)← snapshot 기준 revision

updateContent() → contentRevision++ → nullifySnapshot()
syncSnapshotRevision() → snapshotRevision = contentRevision
```

content와 snapshot의 revision이 불일치하면 stale 충돌(409)이 발생하고, 이를 방지하기 위한 reconcile 로직이 추가 복잡도를 만든다.

### 문제 5: View와 Data의 경계 부재

Code Editor와 ERD Canvas가 Y.Doc을 **직접** 조작한다:

```
canvasTableActions → yjsBridge → Y.Doc 직접 수정
canvasSyncActions  → Y.Map observers → 직접 등록
useBidirectionalCodeSync → applyDiffToYDoc() → Y.Doc.transact() 직접 호출
```

Data 계층이 존재하지 않아 모든 View가 데이터 저장소에 직접 손을 대는 구조이다.

## 의존성 관계도 (현행)

```
useCanvasStore
  ├→ canvasSyncActions
  │   ├→ yjsBridge (Y.Doc 직접 변환)
  │   ├→ constants/canvas-history
  │   └→ lib/*
  ├→ canvasTableActions
  │   ├→ yjsBridge (Y.Doc 직접 생성/수정)
  │   ├→ canvasStoreHelpers (DDL 처리)
  │   └→ lib/*
  └→ canvasGroupActions
      └→ yjsBridge

useCollaborationStore (Canvas Store와 분리됨)
  └→ types/collaboration

useYjsCollaboration (hook)
  ├→ useCanvasStore (selector)
  ├→ useDiagramCollaborationRuntime → useCanvasStore (selector)
  ├→ useDiagramCollaborationProvider
  └→ useSnapshotCompaction

useBidirectionalCodeSync (hook)
  ├→ useCanvasStore (직접 조작)
  ├→ parseDsl / parseDdl
  ├→ generateDsl / generateDdl
  ├→ buildErdTableDiffPlan
  └→ applyDiffToYDoc (Y.Doc 직접 transact)
```

순환 의존성은 없으나, 대부분의 모듈이 `useCanvasStore`와 `yjsBridge`에 강하게 결합되어 있다.
