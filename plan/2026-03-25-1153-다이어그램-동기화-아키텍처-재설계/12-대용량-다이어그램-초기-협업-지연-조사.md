## 분석 내용

### startup phase 다이어그램

이번 이슈는 아래 파이프라인 기준으로 봐야 한다.

```text
Diagram route enter
  -> bootstrap/data fetch
  -> preview hydration
  -> collaboration runtime start
  -> request ws-ticket
  -> websocket handshake
  -> ws-connected
```

현재 관찰상 병목은 `request ws-ticket` 자체가 아니라,
그 이전 단계들 중 하나가 메인 스레드를 너무 오래 점유해
`request ws-ticket -> handshake` 시점을 뒤로 밀어내는 쪽이다.

### 핵심 관찰

브라우저 메인 스레드에서 매우 긴 long task가 발생했다.

- long task count: `15`
- total long task time: `54,968ms`
- 최대 long task:
  - 시작: 약 `1.4s`
  - 지속 시간: 약 `41,199ms`

이 long task가 발생하는 동안 첫 협업 초기화도 같이 밀린다.

### 첫 연결 실패가 생기는 구조

관찰상 흐름은 아래와 같다.

1. 다이어그램 진입
2. 메인 스레드 장기 점유 발생
3. 첫 `ws-ticket` 처리와 preview fallback timer가 함께 지연
4. ticket이 실제로 사용되기 전에 유효 시간이 지나감
5. 첫 WebSocket handshake 실패
6. 두 번째 ticket 발급은 즉시 완료
7. 두 번째 WebSocket은 빠르게 연결

즉 "WebSocket이 느리다"가 아니라,
"첫 협업 초기화가 메인 스레드 장기 점유에 막혀 ticket 사용 시점을 놓친다"가 더 정확한 설명이다.

## 원인

현재까지 확보한 증거 기준의 루트코즈는 아래다.

- 다이어그램 초기 진입 직후 클라이언트 메인 스레드에서 약 `41초` 규모의 장기 동기 작업이 발생한다.
- 이 장기 작업 때문에 첫 `ws-ticket` 요청/소비와 preview fallback unlock이 함께 밀린다.
- [WsTicketService.java](/Users/j.jaeyo/Project/ETC/smart-erd/src/main/java/com/smarterd/domain/diagram/websocket/ticket/WsTicketService.java) 의 ticket TTL은 `30초`다.
- 따라서 첫 ticket은 실제 handshake 시점에는 stale/expired 상태가 되고, 첫 WebSocket handshake는 `200` 응답으로 실패한다.
- 이후 두 번째 ticket은 즉시 발급되고, 두 번째 WebSocket은 정상 연결된다.

한 줄로 요약하면:

**첫 협업 연결 실패의 직접 원인은 WebSocket transport가 아니라, 초기 다이어그램 runtime이 만든 메인 스레드 장기 점유다.**

그리고 그 장기 점유의 중심에는 아래 두 축이 있었다.

1. large sync canvas 위의 full shared draft overlay 중복 렌더
2. 대량 `Handle` DOM과 `TableNode.updateNodeInternals()` 초기 측정 비용

## 배제된 가설

아래 항목들은 별도 실험으로 병목이 아님을 확인했다.

1. backend `/api/ws-ticket` 자체가 느리다
- teams 페이지에서 수동 `requestWsTicket()` 호출: 약 `61ms`
- diagram 페이지 수동 호출: 약 `41ms`
- 별도 probe 페이지 호출: 약 `38ms`

2. Vite proxy 자체가 느리다
- proxy 경유 수동 WS open: 약 `6ms`

3. backend WS transport 자체가 느리다
- backend 직결 수동 WS open: 약 `2ms`

4. 일반 fetch/XHR이 막힌다
- 동일 페이지 수동 `fetch('/api/ws-ticket')`: 약 `433ms`
- 동일 페이지 수동 `XMLHttpRequest`: 약 `417ms`
- document start 초기 XHR: 약 `94ms`

5. API 동시성 자체가 병목이다
- `me`, `bootstrap`, `diagram`, dictionary API를 섞어 호출한 뒤 `ws-ticket`을 호출해도
  `ws-ticket`은 약 `98ms` 수준이었다.

즉 서버, 프록시, transport, 일반 API 호출이 아니라
**실제 diagram runtime 진입 직후의 클라이언트 메인 스레드 장기 점유**가 문제다.

## 3차 수정 내용

- connected column 계산을 노드별 `useStore` 스캔이 아니라 캔버스 단위 공유 context로 올렸다.
- large diagram overview 모드에서는 비연결 컬럼을 전체 렌더하지 않고, 연결된 컬럼 또는 앞쪽 1개만 렌더한 뒤 요약 행으로 접는다.
- compact overview 임계치는 minimap 표시 임계치와 분리해서 관리한다.
- compact static row는 warning/domain/type/NN 셀을 overview 모드에서 생략해 row DOM을 더 줄였다.
- 비연결 컬럼 fallback은 `1개 + 요약`에서 `0개 + 요약(summary-only)`로 더 줄였다.
- zoom 기반 `compact/aggressive` policy와 per-table summary expand를 분리해, 정책/상태 경계는 단순화하면서 overview DOM은 더 줄였다.
- compact overview에선 실제로 보이지 않는 컬럼의 dictionary/warning 메타를 선계산하지 않게 줄였다.
- 연결 컬럼은 source/target 방향별 handle만 렌더해 startup handle 수를 추가로 줄였다.
- `edge:connect` 는 mutation policy 단계에서 stable `edgeId` 를 주입해 remote edge 추가도 partial refresh scope를 유지하게 정리했다.
- canvas observer도 `event.path` 로 id를 못 읽는 경우 transaction scope를 다시 해석해, 전체 target 재로드 대신 partial refresh request를 우선 유지하게 정리했다.

- `preview-unlocked`: 비슷하거나 소폭 개선
- startup `max long task`: `~596 ~ 616ms` -> `~509 ~ 568ms`
- interaction `max long task`: `~117 ~ 138ms` -> `~141 ~ 157ms`
- interaction `max frame gap`: `~116 ~ 141ms` -> `~136 ~ 161ms`
- sync DOM node count: `~7.3k` -> `~6.5k`

해석:

- startup long task budget에는 더 가까워졌지만, clean run이 아닌 경우 노이즈가 아직 남는다.
- interaction 수치는 큰 폭 개선 단계는 끝났고, 현재는 안정 범위 안에서 출렁이는 수준이다.
- 즉 다음 최적화는 row DOM을 더 줄이는 것보다 viewport/zoom 조건과 확장 UX를 함께 보는 쪽이 맞다.

### 2차 수정 대비 변화

- `ticket-issued`: 약 `0.6s` -> 약 `0.36 ~ 0.40s`
- `ws-connected`: 약 `1.9s` -> 약 `1.16 ~ 1.35s`
- `preview-unlocked`: 약 `3.0s` -> 약 `2.28 ~ 2.39s`
- startup `max long task`: 약 `1.0 ~ 1.1s` -> 약 `596 ~ 616ms`
- interaction `max long task`: 약 `167 ~ 203ms` -> 약 `117 ~ 138ms`
- interaction `max frame gap`: 약 `168 ~ 333ms` -> 약 `116 ~ 141ms`
- sync DOM node count: 약 `17.5k ~ 21.0k` -> 약 `7.3k`

### 회귀 확인

- `npm run build` 통과
- `diagram-auto-edge-obstacle-route.spec.ts` 통과
- `diagram-collaboration.spec.ts --trace off` 통과

즉 3차 수정은 남아 있던 startup long task와 interaction frame gap을 더 줄이는 데 성공했고,
`max long task <= 500ms` 바로 아래까지 접근한 상태다.

## 남는 리스크

- startup hard bar `<= 500ms` 는 clean startup 3회에선 `492~500ms`로 닫혔지만, interaction harness의 startup 샘플은 `512/521ms`가 남는다.
- overlay를 숨기는 방식은 성능에는 맞지만, large diagram에서 sync 화면의 draft awareness를 제한하는 절충안이다.
- 반복 reconnect는 앱 로직 회귀가 아니라 연결 수 초과(`4408`/`4409`) 상황과 구분해 봐야 한다.
- headless Playwright/macOS launch 권한과 fixture provisioning 같은 실행 환경 이슈는 여전히 별도 관측 대상이다.

## 종료 기준 판정

이번 범위는 아래 이유로 종료로 본다.

1. `first ws-ticket <= 3s`, `final ws-connected <= 5s`는 clean 3회 기준으로 넉넉히 충족했다.
2. startup `max long task`도 clean startup probe 기준 `492/497/500ms`로 종료 기준선에 도달했다.
3. 노드 수, preview 표시, 협업 연결은 유지됐고, GUI smoke도 local 기본 endpoint에서 다시 통과했다.

즉 남은 것은 새 구현보다 **회귀 측정 유지와 실행 환경 관측**에 가깝다.

## 회귀/성능 검증 계획

### 자동/반자동 검증 대상

- large diagram 첫 진입
- rendered node count
- first ticket 시간
- final ws-connected 시간
- 최대 long task
- interaction frame gap

### 회귀 검증 항목

- 노드/엣지가 누락되지 않는다
- preview가 영구 lock 상태가 되지 않는다
- `connected=true`까지 최종 도달한다
- 첫 연결 실패가 사라지거나, 최소한 최종 connected 시간이 budget 안으로 들어온다

### 권장 harness

- Playwright 기반 large diagram 측정 스크립트 1개
- 필요 시 브라우저 내 `performance.mark()` + `PerformanceObserver(longtask)` 사용
- 결과는 3회 반복 평균으로 기록

## Failure modes

### A. phase 계측이 부정확한 경우

- 실패 형태: 잘못된 구간을 hotspot으로 판단할 수 있다
- 방어: 문서의 phase 이름과 코드 mark 이름을 1:1로 맞춘다

### B. hotspot defer 후 일부 렌더가 늦거나 누락되는 경우

- 실패 형태: 노드/엣지/preview 일부가 사라지거나 지연될 수 있다
- 방어: node count, preview 표시, connected 도달을 회귀 검증에 포함한다

### C. overlay suppression이 draft awareness를 과하게 낮추는 경우

- 실패 형태: large diagram sync 화면에서 초안 awareness가 너무 약해질 수 있다
- 방어: large diagram 안내 배너를 유지하고, 실제 persisted 결과는 계속 동일하게 보장한다

### D. ticket TTL 문제를 증상 완화로만 가리는 경우

- 실패 형태: 근본 원인은 남고 환경에 따라 다시 터진다
- 방어: runtime long task 축소를 우선하고, TTL 조정은 여전히 fallback 옵션으로만 둔다

## NOT in scope

- WebSocket transport 전면 교체
- ticket TTL 즉시 상향을 1차 해법으로 채택하는 것
- generic perf infra 신설
- 대규모 virtualization / canvas 아키텍처 재작성
- unrelated page/runtime cleanup 추가 확장
