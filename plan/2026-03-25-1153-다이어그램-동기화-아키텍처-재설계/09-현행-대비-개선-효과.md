# 09. 현행 대비 개선 효과

## 이번 재설계가 바뀌는 핵심

이 문서군의 변화는 단순한 리팩터링이 아니다.  
현재의 `ERD 중심 협업 구현`을 `재사용 가능한 협업 문서 플랫폼`으로 끌어올리는 것이 목적이다.

## 비교표

| 항목 | 현행 | 목표 |
|------|------|------|
| 공유 상태 모델 | ERD 중심 데이터와 뷰 로직이 혼재 | 문서 코어의 shared authoritative state |
| 로컬 입력 모델 | 텍스트/캔버스/저장 경로가 섞임 | adapter + command + mutation 정책 분리 |
| 원격 동기화 | ERD 도메인과 강하게 결합 | core runtime + delta transport |
| 락 | 테이블 중심 | generic scope lock + plugin resolver |
| 저장 | 기능별 경로가 분산 | persistence coordinator 일원화 |
| 확장성 | ERD 추가 기능에는 대응 가능 | 다른 문서 타입을 plugin으로 추가 가능 |
| SOLID 적용성 | 방향은 있으나 구현 경계가 흐림 | core/interface/plugin 기준으로 구현 가능 |

## 기대 효과

### 1. 유지보수성 향상

- 저장, 동기화, 락, 투영, 입력 파싱이 같은 곳에 몰리지 않는다.
- 장애를 볼 때 “어느 계층 문제인가”를 더 빨리 판단할 수 있다.
- 특정 버그 수정이 다른 기능을 덜 건드린다.

### 2. 신규 기능 추가 용이성 향상

ERD 내부 신규 기능뿐 아니라, 아예 다른 메뉴를 추가할 수 있어야 한다.

예시:

- 화면 기획서 플러그인 추가
- 디자인 문서 플러그인 추가
- wireframe canvas plugin 추가
- 플러그인별 텍스트 편집기/캔버스/폼 조합 추가

이때 기대하는 기준은 다음과 같다.

```text
새 문서 타입 추가
  = plugin 구현 + registry 등록
  != core 재설계
```

### 3. 업무영역 분리

이번 구조에서는 역할이 아래처럼 분리된다.

- 협업 코어 담당
- 문서 플러그인 담당
- View/UI 담당
- 저장/복구 담당
- backend transport/runtime 담당

이 분리가 있어야 팀 단위 작업도 충돌이 줄어든다.

### 4. SOLID를 실제 코드 수준으로 강제 가능

이번 문서의 중요한 차이는 “SOLID 지향”이 아니라 “SOLID 구현 가능”이라는 점이다.

이를 위해 반드시 아래 조건을 지킨다.

- core는 plugin interface만 의존
- plugin은 core port만 의존
- view는 adapter와 projection만 의존
- persistence는 serializer 계약만 의존

### 5. 향후 서비스 분리 준비

이번 설계의 목적은 즉시 MSA 전환이 아니라, 나중에 무리 없이 분리할 수 있는 모듈 경계를 먼저 세우는 것이다.

우선순위 높은 미래 분리 후보:

- `document-metadata`
- `collaboration-runtime`
- `document-persistence`
- `asset-lifecycle`
- `plugin-domain` (`erd`, `screen`, `design`)

초기 분리 금지 후보:

- `lock` 단독 서비스
- `presence` 단독 서비스
- `handoff` 단독 서비스

모듈 경계의 authoritative owner:

- `document-metadata` = `pluginId`, `engineId`, 접근 권한
- `collaboration-runtime` = live room state, live revision, lock, presence, handoff
- `document-persistence` = checkpoint snapshot / recovery material
- `asset-lifecycle` = binary asset와 reference 정합성
- `plugin-domain` = 도메인 규칙, serializer, resolver, validation

추가 경계 규칙:

- bootstrap 시 `document-metadata`와 `document-persistence` header 조회는 분리한다.
- future split 기준 checkpoint 전달은 `at-least-once + idempotent persistence`를 기본값으로 둔다.
- `plugin-domain`은 우선 in-process plugin SPI를 기본값으로 유지한다.

## 마이그레이션 순서

### Phase 1. 코어 계약 확정

- DocumentStore
- ChangeBus
- DocumentReadExecutor
- SharedDocumentEngine
- CollaborationRuntime
- PersistenceCoordinator
- ScopeLockRuntime
- PresenceRuntime의 ephemeral payload 계약
- AssetRuntime / asset lifecycle 계약
- PluginRegistry
- Base plugin + capability interface 분리
- Draft reconcile state machine
- PersistedDocument 메타(`pluginId`, `engineId`, revision, snapshot/artifact)
- Core snapshot codec 계약

이 단계의 목표는 이름과 계약을 generic하게 고정하는 것이다.

### Phase 2. ERD 플러그인 추출

- 현재 ERD 도메인 입력을 plugin command로 변환
- ERD projector 분리
- ERD serializer / scope resolver 분리
- ERD query adapter 분리
- dirty draft 보호 규칙 반영

### Phase 3. 저장 경계 정리

- snapshot primary 저장 경로 일원화
- compatibility artifact 생성 규칙 분리
- artifact fallback codec 계약 분리
- plugin schema / artifact migrator 계약 분리
- recovery/bootstrap 경계 정리
- legacy metadata backfill 전략 확정
- asset manifest / preload / orphan GC 경계 정리

### Phase 4. 백엔드 코어/플러그인 분리

- transport / router / handler / persistence 분리
- generic scope lock 도입
- plugin registry와 codec 연결

### Phase 5. 재사용성 검증

두 번째 문서 타입을 아주 작은 형태라도 붙여 본다.

예:

- 간단한 screen spec plugin
- 간단한 design draft plugin
- 간단한 wireframe canvas plugin

이 단계가 있어야 “재사용 가능한 모듈화”가 실제로 검증된다.

## 성공 판정 기준

아래가 만족되면 이번 설계는 성공으로 본다.

1. ERD 기능이 코어를 다시 오염시키지 않는다.
2. 코드 입력 overwrite/루프/저장 경로 충돌이 줄어든다.
3. 코어 패키지에 ERD 도메인 용어가 없다.
4. 플러그인 추가 시 core 수정이 최소화된다.
5. 저장/락/동기화/투영의 책임 분리가 코드 구조로 보인다.
6. bootstrap/load만으로 어떤 plugin을 써야 하는지 결정 가능하다.
7. `dirty-invalid`, `remote-pending` 상태의 저장/이탈 정책이 구현에 반영된다.
8. legacy 문서도 `pluginId/engineId/schemaVersion` 부여 후 새 구조로 진입 가능하다.
9. capability가 큰 plugin 인터페이스 하나에 뭉치지 않는다.
10. wireframe plugin이 pointer/selection/viewport/asset을 코어 재설계 없이 붙일 수 있다.
11. bootstrap/load만으로 plugin과 engine을 함께 결정할 수 있다.
12. 미래 분리 후보 모듈이 코드 구조와 책임표만 봐도 식별 가능하다.
13. 각 미래 분리 후보 모듈의 authoritative owner가 문서에 명시돼 있다.
14. metadata와 persistence bootstrap 범위가 문서에서 분리돼 있다.
15. runtime -> persistence 전달 규칙과 plugin-domain의 기본 운영 방식이 문서에 명시돼 있다.

## 리스크와 대응

| 리스크 | 대응 |
|------|------|
| 설계가 너무 추상적이어서 구현 난이도가 커짐 | core 계약을 먼저 고정하고 ERD를 첫 구현체로 바로 검증 |
| 추상화가 부족해 다시 ERD 전용 구조로 회귀 | core 패키지에 도메인 용어 유입 금지 규칙 적용 |
| `content` 소비자 때문에 저장 경계가 다시 꼬임 | snapshot primary / compatibility artifact secondary 원칙 유지 |
| dirty draft 문제를 문서만 쓰고 구현에 누락 | acceptance criteria에 draft overwrite 금지를 명시 |
| wireframe/design의 asset/presence 요구가 뒤늦게 들어와 코어 재설계가 발생 | asset lifecycle, rich presence 계약을 v1 코어 범위에 포함 |

## 최종 메시지

이번 재설계의 진짜 산출물은 “ERD를 더 깔끔하게 만든 코드”가 아니다.  
진짜 산출물은 “앞으로 다른 협업 메뉴도 같은 기반 위에 올릴 수 있는 문서 플랫폼 코어”다.
