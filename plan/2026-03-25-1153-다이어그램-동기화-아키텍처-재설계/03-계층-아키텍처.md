# 03. 계층 아키텍처

## 목표 구조

이번 설계의 핵심은 `공통 협업 플랫폼 코어`와 `문서 타입 플러그인`을 분리하는 것이다.

```text
App Shell
  └─ DocumentPageHost
      ├─ Collaboration Core
      │   ├─ DocumentSession
      │   ├─ DocumentStore
      │   ├─ SharedDocumentEngine
      │   ├─ ChangeBus
      │   ├─ CollaborationRuntime
      │   ├─ PresenceRuntime
      │   ├─ ScopeLockRuntime
      │   ├─ AssetRuntime
      │   └─ PersistenceCoordinator
      │
      ├─ Document Plugin
      │   ├─ Input Adapters
      │   ├─ Command Translator
      │   ├─ Mutation Policy
      │   ├─ Projectors
      │   ├─ Serializer / Codec
      │   └─ Scope Resolver
      │
      └─ View Adapters
          ├─ Text Editor Adapter
          ├─ Canvas Adapter
          ├─ Form Adapter
          └─ Presence Adapter
```

이 구조에서 코어는 문서 타입을 모르고, 플러그인은 코어의 계약을 구현한다.

## 계층별 책임

### 1. App Shell

| 모듈 | 책임 |
|------|------|
| DocumentPageHost | 문서 페이지 수명주기, plugin/engine 선택, core wiring |
| PluginRegistry | 문서 타입별 plugin 등록 및 조회 |
| EngineRegistry | `engineId`별 shared document engine 등록 및 조회 |

App Shell은 코어와 플러그인을 연결하지만, 도메인 규칙은 직접 구현하지 않는다.

### 2. Collaboration Core

| 모듈 | 책임 |
|------|------|
| DocumentSession | 문서 진입, 상태 전이, reconnect, leave |
| DocumentStore | 공유 권위 상태 관리. 내부 엔진은 `SharedDocumentEngine` 뒤에 숨김 |
| SharedDocumentEngine | 엔진별 snapshot hydrate, delta apply, snapshot export를 캡슐화 |
| ChangeBus | Store 변경 이벤트 발행 |
| CollaborationRuntime | 원격 delta 송수신, handoff, hydration |
| PresenceRuntime | 참여자/awareness + pointer/selection/viewport/tool 같은 ephemeral presence |
| ScopeLockRuntime | generic scope lock acquire/release/heartbeat |
| AssetRuntime | asset upload token, reference 정합성, preload, garbage collection |
| PersistenceCoordinator | checkpoint 저장, unload 저장, recovery bootstrap |

코어는 아래 사실만 안다.

- 문서에는 공유 권위 상태가 있다.
- shared state는 특정 엔진 구현이 아니라 `SharedDocumentEngine` 계약으로 다룬다.
- 원격 전파가 필요하다.
- 락/프레즌스/저장이 필요하다.
- 캔버스형 문서를 위한 ephemeral presence와 asset lifecycle이 필요하다.
- 각 문서 타입은 플러그인 계약으로 붙는다.

코어는 아래 사실을 몰라야 한다.

- 테이블/컬럼/엣지
- DSL/DDL
- React Flow/Monaco
- 화면 기획서의 블록 구조
- 디자인 문서의 프레임/레이어 의미

### 3. Document Plugin

플러그인은 문서 타입별 도메인 의미를 가진다.

| 플러그인 구성요소 | 책임 |
|------|------|
| Input Adapter | View 입력을 plugin command로 변환 |
| Text Input Pipeline | 텍스트형 입력의 파싱, 검증, diagnostics, diff 생성 |
| Mutation Policy | 공유 상태 변경 규칙 정의 |
| Typed Read Facade | core read executor를 plugin 읽기 모델로 감싸는 내부 helper |
| Projector | 공유 상태를 View 모델로 투영 |
| Artifact Serializer / Codec | compatibility artifact 생성, fallback 복원 |
| Asset Binding | 문서가 참조하는 asset 추출, preload 힌트, orphan 판정 |
| Presence Mapper | plugin UI의 pointer/selection/viewport/tool 상태를 generic presence payload와 연결 |
| Scope Resolver | 명령이 어떤 lock scope를 건드리는지 계산 |

ERD는 이 계약을 구현하는 첫 번째 플러그인이다.

미래 확장 예시:

- `ERDPlugin`
- `ScreenSpecPlugin`
- `DesignPlugin`

### 4. View Adapter

View는 plugin이 제공한 projection과 adapter를 통해서만 동작한다.

| View Adapter | 역할 |
|------|------|
| Text Editor Adapter | 코드/DSL/스펙 텍스트 입력 처리 |
| Canvas Adapter | ERD/디자인 캔버스 렌더링과 입력 |
| Form Adapter | 메타데이터 패널, 속성 편집 |
| Presence Adapter | 커서/참여자 UI 표시 |

핵심 규칙:

- View는 `DocumentStore`를 직접 수정하지 않는다.
- View는 transport를 직접 호출하지 않는다.
- View는 persistence를 직접 호출하지 않는다.

## 상태의 분리

이번 구조에서 상태는 세 종류로 나눈다.

| 상태 종류 | 예시 | 공유 여부 |
|------|------|------|
| Shared Authoritative State | 문서 구조, 협업 대상 데이터 | 공유 |
| Local Ephemeral State | 커서, selection, dirty draft, 임시 diagnostics | 비공유 |
| Derived State | canvas nodes, generated text, export JSON | 파생 |

이 분리가 중요한 이유는 다음과 같다.

- 커서/선택/타이핑 중 draft는 협업 권위 상태가 아니다.
- generated text나 canvas node는 저장 주체가 아니라 projection 결과다.
- shared state와 local draft를 섞으면 overwrite와 루프가 재발한다.

## 의존성 원칙

```text
View Adapter
  -> Plugin Input Adapter / Plugin Projector
  -> Core Ports

Document Plugin
  -> Core Ports
  -> 자기 플러그인 내부 모델

Collaboration Core
  -> Plugin Interface만 의존
  -> 특정 플러그인 구현은 모름
```

허용하지 않는 의존성:

- Core -> ERD 전용 구현
- View -> Y.Doc 직접 접근
- Plugin -> WebSocket 구현체 직접 의존
- Projector -> Save API 직접 호출

## 핵심 인터페이스 방향

```typescript
interface BaseDocumentPlugin {
  pluginId: string;
  schemaVersion: number;
  supportedEngineIds: string[];
  createInputAdapters(context: PluginContext): InputAdapters;
  createMutationPolicy(context: PluginContext): MutationPolicy;
  createProjectors(context: PluginContext): Projector[];
  createScopeResolver(context: PluginContext): ScopeResolver;
}

interface TextInputCapablePlugin extends BaseDocumentPlugin {
  createTextInputPipeline(context: PluginContext): TextInputPipeline;
}

interface ArtifactFallbackCapablePlugin extends BaseDocumentPlugin {
  createArtifactSerializer(context: PluginContext): CompatibilityArtifactSerializer;
  createArtifactCodec(context: PluginContext): CompatibilityArtifactCodec;
}

interface AssetCapablePlugin extends BaseDocumentPlugin {
  createAssetBinding(context: PluginContext): AssetBinding;
}

interface PresenceCapablePlugin extends BaseDocumentPlugin {
  createPresenceMapper(context: PluginContext): PresenceMapper;
}

type RegisteredDocumentPlugin = BaseDocumentPlugin;

interface TextInputPipeline {
  parse(input: string): ParseResult;
  validate(result: ParseResult): ValidationResult;
  buildCommands(result: ParseResult): DocumentCommand[];
}

interface SharedDocumentEngine {
  engineId: string;
  hydrate(snapshot: Uint8Array): void;
  exportSnapshot(): Uint8Array;
  applyRemoteDelta(delta: Uint8Array): void;
}

interface SharedDocumentEngineRegistry {
  require(engineId: string): SharedDocumentEngine;
}

interface AssetBinding {
  collectReferencedAssets(read: DocumentReadExecutor): AssetRef[];
  buildPreloadHints?(assets: AssetRef[]): AssetPreloadHint[];
}

interface AssetRef {
  assetId: string;
  kind: string;
  mimeType?: string;
  hash?: string;
}

interface AssetPreloadHint {
  assetId: string;
  priority: 'eager' | 'lazy';
}

interface PresenceMapper {
  toPresencePayload(state: LocalPresenceState): GenericPresencePayload;
  applyRemotePresence(payload: GenericPresencePayload, adapter: PresenceAdapter): void;
}

interface LocalPresenceState {
  pointer?: { x: number; y: number };
  selection?: string[];
  viewport?: { x: number; y: number; zoom: number };
  activeTool?: string;
  pluginState?: unknown;
}

interface GenericPresencePayload {
  pointer?: { x: number; y: number };
  selection?: string[];
  viewport?: { x: number; y: number; zoom: number };
  activeTool?: string;
  pluginPayload?: unknown;
}
```

핵심 규칙:

- 텍스트 입력 지원 여부의 source of truth는 `TextInputCapablePlugin` 구현 여부다.
- artifact fallback 지원 여부의 source of truth는 `ArtifactFallbackCapablePlugin` 구현 여부다.
- asset lifecycle 지원 여부의 source of truth는 `AssetCapablePlugin` 구현 여부다.
- rich presence 지원 여부의 source of truth는 `PresenceCapablePlugin` 구현 여부다.
- host는 null 반환이 아니라 capability interface/type guard로 분기한다.
- registry는 `BaseDocumentPlugin`만 보관하고, host가 capability interface로 narrowing 한다.
- plugin은 `supportedEngineIds`로 자신이 지원하는 shared document engine을 선언한다.
- 지원하지 않는 책임을 base interface에 억지로 매달지 않는다.

위 계약만으로는 부족하다.  
플러그인의 projector, serializer, scope resolver는 현재 공유 상태를 읽을 수 있어야 한다.

따라서 실제 구현에서는 write/read/subscribe 포트를 분리하고, read는 `executor + context` 구조로 고정한다.

```typescript
interface DocumentMutationPort {
  applyMutation(mutation: DocumentMutation, meta: MutationMeta): void;
}

interface DocumentReadExecutor {
  getRevision(): number;
  execute<T>(query: DocumentReadQuery<T>): T;
  exportSnapshot(): Uint8Array;
}

interface DocumentSubscriptionPort {
  subscribe(listener: (event: DocumentChangeEvent) => void): Unsubscribe;
}

interface DocumentReadQuery<T> {
  run(context: DocumentReadContext): T;
}

interface DocumentReadContext {
  getEntity(ref: DocumentEntityRef): DocumentEntity | null;
  listRelated(ref: DocumentEntityRef, relation: string): DocumentEntityRef[];
  getProperty(ref: DocumentEntityRef, key: string): unknown;
  findByKind(kind: string): DocumentEntityRef[];
  getRevision(): number;
}

interface DocumentEntityRef {
  kind: string;
  id: string;
}

interface DocumentEntity {
  ref: DocumentEntityRef;
  props: Record<string, unknown>;
}
```

핵심 규칙:

- 플러그인은 `DocumentReadExecutor`를 통해서만 현재 상태를 읽는다.
- `DocumentReadContext`는 저장소 내부 root/Y.Doc를 노출하지 않는 안정된 read context다.
- read model은 tree 전용이 아니라 graph/scene/entity 관계도 표현할 수 있어야 한다.
- asset binding과 presence mapper도 raw engine internals가 아니라 core 계약만 통해 동작한다.
- typed read facade는 plugin 내부 helper로 둘 수 있지만 core SPI는 아니다.
- 플러그인은 Y.Doc, raw transport buffer, persistence payload를 직접 읽지 않는다.
- projector/serializer/scope resolver가 별도 그림자 캐시를 만드는 것은 지양한다.

## 이 구조가 재사용 가능한 이유

ERD가 아닌 다른 메뉴를 붙일 때 바뀌어야 하는 것은 플러그인 내부다.

예를 들어:

- 화면 기획서는 `section`, `block`, `screen` 같은 scope를 정의한다.
- 디자인은 `frame`, `layer`, `component` 같은 scope를 정의한다.
- 텍스트 기반 스펙 문서는 parser와 projector만 교체할 수 있다.

하지만 아래는 그대로 재사용된다.

- 세션 관리
- 원격 delta 동기화
- reconnect / handoff
- presence
- asset lifecycle
- scope lock 프로토콜
- checkpoint 저장
- plugin registry

즉, 이번 구조는 `ERD를 잘 분리한 구조`를 넘어서 `문서 협업 플랫폼 코어`가 되도록 설계한다.
