# 06. 락 범위 설계

## 설계 원칙

1. 락은 공유 문서 본체와 별도 관심사로 관리한다.
2. 코어는 `무엇을 잠그는가`의 의미를 모른다.
3. 코어는 `어떤 범위를 잠그는가`만 안다.
4. 구체 scope 해석은 플러그인이 맡는다.
5. 하나의 WebSocket 연결에서 메시지 타입으로 채널 분리한다.
6. 네트워크 단절 시 자동 해제가 가능해야 한다.
7. 락은 코어 기능이지만, 모든 플러그인이 모든 변경에 락을 강제해야 하는 것은 아니다.

## 왜 테이블 락이 아니라 범위 락인가

현재 smart-erd에서는 테이블 락이 가장 자연스럽다.  
하지만 미래 메뉴를 생각하면 코어가 `tableId`를 아는 순간 재사용 가능성이 깨진다.

따라서 코어는 아래 형태만 안다.

```typescript
interface ScopeRef {
  pluginId: string;
  scopeType: string;
  scopeId: string;
}
```

ERD에서는 이 ScopeRef를 이렇게 해석한다.

- `pluginId='erd'`
- `scopeType='table'`
- `scopeId='table-123'`

미래 메뉴 예시:

- 화면 기획서: `scopeType='section'`
- 디자인: `scopeType='frame'` 또는 `scopeType='layer'`
- wireframe canvas: `scopeType='frame'`, `group`, 필요 시 `document`

## 프로토콜 정의

### 획득 요청

```typescript
interface LockAcquireRequest {
  scope: ScopeRef;
  source: 'text-editor' | 'canvas' | 'form';
  mode: 'exclusive';
}
```

### 응답

```typescript
interface LockAcquireResponse {
  scope: ScopeRef;
  granted: boolean;
  holder?: {
    userId: string;
    displayName: string;
    source: string;
  };
}
```

### 해제 / heartbeat

```typescript
interface LockReleaseRequest {
  scope: ScopeRef;
}

interface LockHeartbeat {
  scopes: ScopeRef[];
}
```

### 초기 스냅샷

```typescript
interface LockStateSnapshot {
  locks: Array<{
    scope: ScopeRef;
    holder: { userId: string; displayName: string; source: string };
    acquiredAt: number;
  }>;
}
```

## 플러그인 매핑 규칙

| 문서 타입 | scopeType 예시 | 비고 |
|------|------|------|
| ERD | `table` | 기존 테이블 선점과 동일 의미 |
| 화면 기획서 | `page`, `section`, `block` | 어떤 레벨을 잠글지는 plugin 정책 |
| 디자인 | `frame`, `layer`, `component` | 세분화 수준은 plugin 정책 |

즉, 코어는 락 시스템을 제공하고, 플러그인은 “이 변경이 어느 scope에 영향을 주는가”만 알려준다.

## 다중 범위 변경 규칙

ERD의 bulk import나 미래 문서의 대량 이동은 단일 scope로 끝나지 않을 수 있다.

이를 위해 코어는 아래 정책을 가진다.

1. 플러그인은 `resolveAffectedScopes(command)`를 제공한다.
2. 플러그인은 변경 유형별로 `lock-required` 또는 `optimistic` 정책을 선택할 수 있다.
3. 영향을 받는 scope가 여러 개면 정렬된 순서로 획득한다.
4. 하나라도 실패하면 전체 획득을 실패로 처리한다.
5. 플러그인이 필요하면 문서 전체 scope로 승격할 수 있다.

예시:

- ERD `bulk.import` -> 여러 table scope 또는 `document` scope
- 디자인 `frame duplicate` -> source frame + target frame scope
- wireframe `freehand draw` -> 기본은 optimistic, 필요 시 `document` scope

## 프론트엔드 구조

```typescript
interface ScopeResolver {
  resolveAffectedScopes(command: DocumentCommand): ScopeRef[];
  resolveFocusScope(context: FocusContext): ScopeRef | null;
}
```

```typescript
class ScopeLockRuntime {
  acquire(scope: ScopeRef, source: string): Promise<LockAcquireResponse>;
  release(scope: ScopeRef): void;
  heartbeat(scopes: ScopeRef[]): void;
  subscribe(listener: (snapshot: LockStateSnapshot) => void): Unsubscribe;
}
```

핵심 규칙:

- View는 직접 scope 계산을 하지 않는다.
- scope 계산은 플러그인의 `ScopeResolver`가 담당한다.
- lock runtime은 scope 의미를 해석하지 않는다.
- freeform canvas는 scope를 항상 잡는 대신, plugin 정책에 따라 no-lock + presence 조합을 선택할 수 있다.

## draft 충돌과 락의 상호작용

`remote-pending` 상태와 락이 같이 걸리면 indefinite hold가 되지 않도록 공통 규칙을 둔다.

1. local 사용자가 관련 scope lock을 보유한 상태에서 `remote-pending`에 진입하면 `reconcile hold` 상태로 본다.
2. `reconcile hold` 동안에는 서버가 정한 `reconcileHoldGraceMillis` 내에서만 heartbeat를 유지한다.
3. `acceptRemote` 또는 `keepLocalAndRebase`가 grace window 안에 끝나면 lock을 유지한다.
4. `compareLater`를 선택하거나 grace window가 끝나면 lock을 해제하고 readonly pending 상태로 전환한다.
5. grace window 만료 판정은 서버가 authoritative 하게 가진다.
6. 코어는 grace window 타이머와 release 규칙만 알고, 사용자 안내 문구는 플러그인이 결정한다.

## 백엔드 구조

```java
public record ScopeRef(
    @NonNull String pluginId,
    @NonNull String scopeType,
    @NonNull String scopeId
) {}
```

```java
public record LockRequester(
    @NonNull String userId,
    @NonNull String displayName,
    @NonNull String source
) {}
```

```java
public interface ScopeLockManager {
    LockResult acquire(@NonNull Long documentId, @NonNull ScopeRef scope, @NonNull LockRequester requester);
    void release(@NonNull Long documentId, @NonNull ScopeRef scope, @NonNull String userId);
    void heartbeat(@NonNull Long documentId, @NonNull Collection<ScopeRef> scopes, @NonNull String userId);
    List<LockEntry> snapshot(@NonNull Long documentId);
}
```

## 구현 가드레일

다음은 코어에 넣지 않는다.

- `tableId`, `sectionId`, `frameId` 전용 필드
- `ERD에서만 쓰는 충돌 문구`
- 특정 플러그인의 scopeType enum

다음은 플러그인이 맡는다.

- 테이블 편집 시작 시 어떤 scope를 잡을지
- bulk 변경 시 scope 승격 정책
- 충돌 UI 문구와 사용자 경험

이번 락 설계의 목적은 단순하다.  
`테이블 락`을 일반화해, 앞으로 어떤 문서 메뉴가 오더라도 같은 코어 위에서 동작하게 만드는 것이다.
