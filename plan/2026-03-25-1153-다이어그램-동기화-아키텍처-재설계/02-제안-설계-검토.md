# 02. 초기 제안 설계 검토

## 출발점 정리

최초 요구사항의 핵심은 아래 세 줄이었다.

1. 중앙의 `Diagram Data`를 두고 Code/ERD는 그 데이터를 기반으로 표현한다.
2. 프론트와 백엔드는 변경분만 주고받고, 유형/버전으로 루프를 줄인다.
3. 테이블 락은 데이터 동기화와 별도 관심사로 분리한다.

이 방향 자체는 맞다. 실제로 현재 구조의 가장 큰 문제도 `공유 상태`, `뷰`, `동기화`, `저장`, `락`의 경계가 없다는 점이기 때문이다.

다만, 지금 요구사항은 여기서 한 단계 더 나간다.

- ERD만 잘 되면 안 된다.
- 이후 화면 기획서, 디자인 문서 같은 다른 협업 메뉴도 같은 기반 위에 올라와야 한다.
- 그래서 설계는 `ERD 전용 재구조화`가 아니라 `재사용 가능한 협업 플랫폼` 수준이어야 한다.

## 선택지 비교

### 옵션 A. ERD 중심 재설계

구조를 깔끔하게 다시 나누되, 핵심 용어와 계약은 여전히 `Diagram`, `Table`, `ERD`, `Code` 기준으로 유지한다.

**장점**

- 현재 문제를 빠르게 정리하기 쉽다.
- 기존 코드와 이름을 많이 재사용할 수 있다.
- ERD 기능 안정화만 보면 가장 직접적이다.

**단점**

- 화면 기획서, 디자인, 다른 협업 메뉴로 확장할 때 다시 뜯어고칠 가능성이 높다.
- 코어에 ERD 도메인 용어가 스며들어 재사용 가능한 모듈화가 깨진다.
- SOLID 중 특히 OCP, DIP를 장기적으로 유지하기 어렵다.

### 옵션 B. 협업 플랫폼 코어 + ERD 플러그인

동기화, 세션, 락, 저장, 프레즌스, 공유 상태 관리는 코어로 올리고,  
ERD는 그 위에 도메인 플러그인으로 붙인다.

**장점**

- 다른 문서 타입을 같은 코어 위에 추가할 수 있다.
- 공통 관심사와 도메인 관심사가 분리된다.
- 재사용 가능한 모듈화와 SOLID 구현 가능성이 가장 높다.

**단점**

- 설계 난이도가 올라간다.
- 초기 명명과 인터페이스를 generic하게 다시 잡아야 한다.
- ERD만 급히 고치는 것보다 시간이 더 든다.

## 최종 선택

이번 문서는 **옵션 B. 협업 플랫폼 코어 + ERD 플러그인**을 채택한다.

선택 이유는 단순하다.

- 사용자 요구사항의 우선순위가 이미 `재사용 가능한 모듈화`에 있다.
- 앞으로 다른 화면/문서 메뉴를 추가할 계획이 분명하다.
- 지금 ERD 전용으로 정리하면 단기적으로는 편할 수 있어도, 다음 문서 타입 추가 시 다시 구조 충돌이 난다.

## 초기 제안에서 유지할 것

아래 항목은 그대로 살린다.

1. **중앙 공유 상태를 둔다.**  
   공유 상태의 유일한 진실 원천을 둔다는 생각은 유지한다.

2. **Code/ERD를 권위 상태의 표현 계층으로 낮춘다.**  
   양방향 루프를 줄이는 가장 중요한 방향이다.

3. **변경분 전송 프로토콜을 유지한다.**  
   전체 문서를 계속 밀어 넣는 구조는 성능과 복구 모두에서 불리하다.

4. **락을 동기화 본체와 분리한다.**  
   다만 코어는 generic scope lock으로 설계하고, `table lock`은 ERD 플러그인 구현으로 내린다.

## 초기 제안에서 바꿔야 할 것

### 1. `Diagram Data`를 `문서 플랫폼의 Shared Document`로 일반화한다

초기 제안은 ERD를 중심으로 매우 자연스럽다.  
하지만 `Diagram Data`라는 이름과 구조 그대로는 화면 기획서/디자인 문서에 재사용하기 어렵다.

따라서 최종 설계에서는 다음처럼 일반화한다.

- `Diagram Data` → `DocumentStore` 또는 `SharedDocument`
- `Code/ERD` → `Plugin View`
- `테이블 락` → `Scope Lock`

### 2. View 반영 성공 여부를 서버 전송의 조건으로 두지 않는다

View 반영 성공 응답을 기다린 뒤 서버에 전달하는 구조는 버린다.

이유:

- View는 projection일 뿐이고, 공유 상태 전파의 승인자가 되어서는 안 된다.
- View 렌더링 실패나 지연 때문에 협업 상태 전파가 막히면 전체 시스템이 더 꼬인다.

최종 설계에서는:

- 공유 상태 변경 즉시 원격 delta 전파
- View 반영은 각 projector가 독립적으로 처리

### 3. Command를 네트워크 canonical payload로 사용하지 않는다

초기 제안의 `유형 + 버전` 사고는 살리되, Command를 그대로 네트워크 표준으로 쓰지는 않는다.

최종 설계에서는:

- `Command` = 로컬 입력 계약
- `engine delta` = 원격 동기화 계약, v1 기본 구현은 `Yjs update`

이렇게 역할을 분리해야 현재 협업 축과 향후 확장성을 모두 지킬 수 있다.

### 4. invalid draft 문제를 명시적으로 다룬다

초기 제안에는 가장 중요한 공백이 하나 있었다.  
바로 `사용자가 타이핑 중인 불완전 상태`를 어디에 둘지 정의되지 않았다는 점이다.

최종 설계에서는 아래 규칙을 반드시 둔다.

- 불완전 텍스트는 로컬 draft에만 존재
- 파싱/검증 성공 전까지 공유 상태 반영 금지
- dirty draft 동안에는 projector가 생성한 텍스트로 에디터 본문 overwrite 금지

이 규칙이 없으면 커서 튐, 덮어쓰기, 원격 변경 충돌이 다시 발생한다.

### 5. 락은 별도 WebSocket이 아니라 단일 연결 내부 채널로 처리한다

초기 제안의 “락은 별도 연결”은 부하 분산 관점에서는 이해할 수 있지만, 연결 상태 일관성 측면에서는 불리하다.

최종 설계에서는:

- WebSocket 연결은 하나
- 메시지 타입으로 `document sync`, `lock`, `presence`, `handoff`를 분리
- 백엔드 내부 handler는 각 채널별로 분리

즉, 연결은 통합하고 책임은 분리한다.

### 6. 저장 단순화는 `snapshot primary + compatibility artifact secondary`로 간다

초기 제안은 구조 단순화 관점에서 맞지만, 현재 시스템에는 아직 `content`를 소비하는 경로가 남아 있다.

따라서 최종 설계에서는:

- 1차 저장 기준: snapshot
- 2차 파생 저장물: plugin이 제공하는 compatibility artifact

즉시 `content`를 제거하지 않는다.

## 최종 결정문

이 문서군은 아래 결정을 따른다.

`협업 플랫폼의 공통 책임은 코어로 올리고, ERD는 첫 번째 문서 플러그인으로 구현한다.`

초기 제안의 좋은 부분은 유지하되,  
재사용 가능한 모듈화와 SOLID 구현 가능성을 위해 `ERD 전용 개념`을 코어에서 제거한다.
