# WBS 목록 전속성 편집 설계

## 배경

- 현재 WBS 작업공간은 `이름`, `진척률`만 목록에서 바로 수정할 수 있다.
- `담당자`, `기간`, `예상 M/M`, `마일스톤`은 수정 다이얼로그를 열어야 바꿀 수 있다.
- `부모 변경`은 수정 다이얼로그에서 비활성화되어 있고, 사실상 드래그 재정렬로만 바꿀 수 있다.
- 사용자 요구는 "WBS 목록에서 보이는/관리되는 속성을 가능한 한 동일한 편집 경험으로 바꾸자"에 가깝다.

## 현재 상태 정리

### 프론트엔드

- `SortableWbsRow`는 `이름`, `진척률`만 인라인 편집을 지원한다.
- `WbsItemFormDialog`는 `parent` 필드를 렌더링하지만 edit 모드에서는 `disabled={isEdit}`로 막혀 있다.
- 전용 페이지의 quick-add row는 `이름`만 입력받고 나머지 컬럼은 `나중에 설정` placeholder로 남겨 둔다.

### 백엔드

- `PUT /wbs/{id}`는 `name`, `assigneeUserId`, `startDate`, `endDate`, `progressRate`, `estimatedMm`, `milestoneId`만 갱신한다.
- 구조 변경(`parentId`, `sortOrder`, `depth`)은 `PATCH /wbs/reorder`로만 처리한다.
- 즉, "속성 수정"과 "구조 수정"이 API 차원에서도 분리되어 있다.

## 설계 목표

- 목록에서 보이는 업무 속성은 모두 한 번의 클릭 흐름으로 수정 가능해야 한다.
- 구조 속성(`부모`, `순서`)은 일반 필드와 다른 제약이 크므로 별도 편집 흐름으로 제공하되, 더 이상 "숨겨진 기능"처럼 느껴지지 않게 한다.
- 기존 재정렬/검증 로직을 최대한 재사용해서 백엔드 규칙을 이중 구현하지 않는다.
- compact tab과 dedicated page가 같은 편집 모델을 공유해야 한다.

## 제안 UX

### 1. 목록 셀 인라인 편집 범위 확대

- `이름`: 현행 유지
- `담당자`: 셀 클릭 시 단일 선택 popover/select
- `기간`: 셀 클릭 시 `시작일`/`종료일` 2필드 popover
- `진척률`: 현행 유지
- `예상 M/M`: 숫자 input 인라인 편집
- `마일스톤`: 단일 선택 popover/select

원칙:

- 저장은 `blur` 또는 `Enter` 기준으로 즉시 반영한다.
- `Esc`는 편집 취소다.
- 저장 중에는 해당 row만 잠그고, 성공 시 토스트와 값만 갱신한다.
- 비어 있는 값도 편집 affordance를 유지한다. 예: `미지정`, `기간 없음`, `마일스톤 없음`도 클릭 가능 상태로 렌더링.

### 2. 구조 편집은 명시적 "이동" 액션으로 분리

`부모`, `순서`, `깊이`는 단순 값 수정이 아니라 트리 재배치다. 이 속성들을 일반 셀 편집으로 섞으면 아래 문제가 생긴다.

- 대상 sibling 집합 전체 재정렬이 필요하다.
- depth 제한과 자기 하위로의 이동 금지 검증이 필요하다.
- 사용자가 결과 위치를 예측하기 어렵다.

따라서 액션 컬럼에 `이동` 액션을 추가하고, 아래 플로우를 권장한다.

- row action `이동`
- popover 또는 dialog에서
  - 새 부모 선택 (`루트 포함`, 자기 자신/하위 제외)
  - 같은 부모 내 위치 선택 (`맨 위`, `이전 항목 다음`, `맨 아래`)
- 저장 시 프론트에서 reorder payload를 계산하고 기존 `PATCH /wbs/reorder` 호출

드래그 앤 드롭은 유지한다. 다만 `이동` 액션을 추가해서 키보드/정밀 편집 경로를 보완한다.

### 3. quick-add는 "빠른 생성"으로 유지

quick-add row까지 모든 필드를 한 번에 열면 전용 페이지의 장점인 속도가 사라진다. 그래서 quick-add는 아래처럼 유지하는 편이 낫다.

- 기본은 `이름`만 입력
- 생성 직후 row 하이라이트 유지
- 필요하면 바로 같은 row에서 나머지 셀을 연속 편집

즉, "생성은 빠르게 / 보강은 인라인으로" 흐름을 만든다.

## API / 도메인 설계

### 유지할 것

- 일반 속성 수정: `PUT /wbs/{id}`
- 구조 변경: `PATCH /wbs/reorder`

이 분리는 유지하는 쪽이 안전하다. 이유는 다음과 같다.

- 구조 변경은 단건처럼 보여도 실제로는 sibling 여러 건의 `sortOrder`를 함께 조정한다.
- 현재 `WbsService.reorderWbsItems`가 depth, 순환 참조, parent 유효성 검증을 이미 맡고 있다.
- `PUT /wbs/{id}`에 `parentId`/`sortOrder`를 억지로 합치면 서비스 경계가 흐려지고 테스트 조합이 급증한다.

### 프론트엔드 보강 포인트

- `UpdateWbsItemPayload` 기반 공통 `commitFieldEdit` helper 추가
- 셀 타입별 editor component 분리
  - `AssigneeCellEditor`
  - `PeriodCellEditor`
  - `EstimatedMmCellEditor`
  - `MilestoneCellEditor`
- `MoveWbsItemDialog` 또는 `MoveWbsItemPopover` 추가
- 목록/다이얼로그가 같은 validation 규칙을 공유하도록 form normalizer 추출

## 상태/오류 처리

- 숫자 필드: 빈 문자열은 `null`, 0 이상 규칙 유지
- 기간 필드: 둘 중 하나만 있어도 저장 가능, 단 `startDate > endDate`는 즉시 차단
- 담당자/마일스톤: `없음` 선택 허용
- 구조 이동 실패 시 기존 `reorderFailed` 토스트 재사용 가능, 가능하면 depth/순환 참조를 더 구체적으로 매핑

## 접근성 / 사용성

- 편집 가능한 셀은 hover뿐 아니라 focus ring과 키보드 진입점을 제공해야 한다.
- `button` 역할 셀은 aria-label에 항목명과 필드명을 함께 넣는다.
- 드래그를 못 쓰는 사용자도 `이동` 액션으로 동일 기능을 써야 한다.

## 구현 순서 제안

### Phase 1

- 목록 셀 인라인 편집을 `담당자`, `기간`, `예상 M/M`, `마일스톤`까지 확장
- 기존 수정 다이얼로그는 fallback으로 유지

### Phase 2

- `이동` 액션 추가
- 부모/위치 선택 UI 구현
- reorder payload 계산을 dialog action에서도 재사용

### Phase 3

- quick-add 이후 연속 편집 UX polish
- 토스트/포커스 복귀/낙관적 갱신 등 interaction polish

## QA 시나리오

- 루트 항목과 자식 항목 각각에서 모든 표시 컬럼 수정 가능
- 담당자 해제 / 마일스톤 해제 / 기간 partial 입력 가능
- 잘못된 날짜 범위 저장 차단
- 예상 M/M 음수 차단
- 이동 액션으로 루트 이동 / 형제 사이 이동 / 다른 부모 아래 이동 가능
- 자기 자신 하위로 이동 불가
- depth limit 초과 이동 불가
- compact tab과 dedicated page 동작 일치

## 결정

- "모든 속성을 같은 방식으로 한 화면 인라인 편집"이 아니라
  - 업무 속성은 셀 인라인 편집
  - 구조 속성은 명시적 이동 액션
  로 나누는 안을 기본안으로 제안한다.

이 안이 가장 작은 API 변경으로 요구사항을 충족하고, 현재 WBS 트리 제약도 안전하게 보존한다.
