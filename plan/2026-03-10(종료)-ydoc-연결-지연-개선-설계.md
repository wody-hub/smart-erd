# 2026-03-10(종료) Y.Doc 연결 지연 개선 설계

## 배경

현재 다이어그램 진입 시 체감 성능은 API preview로 크게 개선됐지만, 실제 편집 가능 상태로 전환되는
Y.Doc live handoff는 여전히 느리다.

현재 경로는 다음과 같다.

```text
REST detail 조회
→ POST /api/ws-ticket
→ WebSocket open
→ SNAPSHOT_REQUEST
→ DB ydoc_snapshot 로드
→ snapshot decode
→ SNAPSHOT_RESPONSE × N
→ client Y.applyUpdate × N
→ observeDeep
→ 편집 가능 상태 전환
```

즉, 문제의 본질은 "캔버스 렌더"가 아니라 "실시간 협업 상태 복원"이다.

## 실측 결과 업데이트

2026-03-11 기준 1차 계측 결과, 초기 가설과 달리 현재 체감 지연의 주원인은
`snapshot decode/send/apply`가 아니라 `ws-ticket` 요청 실패 후 5초 fallback 대기였다.

확인 내용:

- 브라우저(`http://127.0.0.1:3000`)에서 `POST /api/ws-ticket` 호출 시 `403 Invalid CORS request`
- 동일 API를 직접 호출하면 `200 OK`
- backend `snapshot-handoff` 로그는 샘플 기준 `totalMs=5`, `updateCount=8`, `snapshotBytes=8516`
- preview 계측에서는 실패 경로에서 `snapshot-fallback ~= 5003ms`, `preview-unlocked ~= 5006ms`

원인:

- backend 기본 CORS 허용 Origin이 `http://localhost:3000`만 포함
- 실제 개발 중에는 `http://127.0.0.1:3000`으로 접속하는 경우가 있었음
- 이 경우 `ws-ticket`가 브라우저에서만 차단되고, 클라이언트가 live handoff 대신 fallback 타이머를 기다림

조치:

- `application.yml` 기본 CORS Origin에 `http://127.0.0.1:3000` 추가

조치 후 재측정:

- `ticket-issued`: 약 `99ms`
- `ws-connected`: 약 `143ms`
- `preview-unlocked source=remote`: 약 `180ms`

결론:

- 현재 확인된 직접 원인은 CORS misconfiguration이며, 이 문제는 수정 완료
- 아래 최적화 계획(B/A/C/D)은 여전히 유효하지만, 우선순위는
  "환경/권한/네트워크 실패 제거 후 성능 최적화" 기준으로 해석해야 한다
- 즉, 지금 단계에서 구조 최적화는 "잔여 최적화"이며, 기존 5초 체감 지연의 주범은 아니다

## 구현 진행 현황

2026-03-11 기준 아래 항목까지 반영되었다.

### 1. Snapshot Handoff V2

- 클라이언트가 `SNAPSHOT_REQUEST_V2`를 사용
- 서버는 `SNAPSHOT_RESPONSE_V2`로 raw snapshot blob을 단건 전송
- 클라이언트는 length-prefixed snapshot을 파싱 후 `Y.mergeUpdates()`로 단일 apply 수행

효과:

- 기존처럼 `SNAPSHOT_RESPONSE × N`, `Y.applyUpdate × N`을 반복하지 않음
- 샘플 기준 기존 `updateCount=679` 다건 handoff가 `single payload`로 축소됨

### 2. Compact 저장 포맷 개선 1차

- 자동 컴팩션 트리거 임계치를 `100KB -> 32KB`로 하향
- flush 시점에 `snapshot-shape` 메트릭 로그 추가

효과:

- 조각 수는 많지만 크기는 중간인 snapshot도 더 빨리 compact 대상이 됨
- `updateCount`, `mergedBytes`, `encodedBytes`를 기준으로 handoff 비용을 추적 가능

### 3. Warm room handoff cache

- persisted snapshot을 메모리 cache로 유지
- flush/replaceSnapshot 성공 시 cache 즉시 갱신
- 활성 room 재접속 시 pending update가 없어도 cache가 있으면 `source=warm`으로 handoff
- pending update가 있으면 `cache + in-memory update` 조합으로 warm snapshot 생성

검증 결과:

- 활성 room 재접속에서 `source=warm` 확인
- flush 이후 재접속에서도 `source=warm snapshotBytes=47` 확인

결론:

- active room rejoin은 더 이상 DB 조회 의미에 묶이지 않음
- warm policy를 강화해 “이미 열려 있는 협업 방” 재진입의 최신성과 반응성을 높였음

## 목표

1. preview 이후 편집 가능 전환 시간을 줄인다.
2. snapshot 크기와 update 개수에 덜 민감한 구조로 바꾼다.
3. 기존 CRDT 정합성과 degraded fallback 안전성은 유지한다.
4. 단계별 도입이 가능해야 하며, 한 번에 대규모 프로토콜 전환은 피한다.

## 비목표

1. 전체 협업 프로토콜을 다른 엔진으로 교체하지 않는다.
2. REST preview 경로를 제거하지 않는다.
3. 첫 단계에서 서버/클라이언트 전체를 비호환 프로토콜로 갈아엎지 않는다.

## 현재 병목 정리

### 1. 연결 전 추가 왕복

- 클라이언트는 WS open 전에 `POST /api/ws-ticket`를 기다린다.
- 즉 WebSocket 연결 시작 자체가 REST 한 번 뒤로 밀린다.

### 2. snapshot의 요청 시점 DB 조회

- 새 클라이언트 진입 시마다 서버가 DB에서 `ydoc_snapshot`을 읽는다.
- warm room이어도 요청 시점 DB 조회 비용이 그대로 든다.

### 3. snapshot의 다건 update 재전송

- 서버는 저장된 snapshot을 decode 후 개별 update들로 분해한다.
- 각 update를 별도 `SNAPSHOT_RESPONSE`로 순차 전송한다.
- 클라이언트는 각 조각마다 `Y.applyUpdate`를 반복 수행한다.

### 4. snapshot compaction 편차

- snapshot이 충분히 compact되지 않으면 update 조각 수가 커진다.
- 조각 수가 커질수록 네트워크 메시지 수, apply 횟수, observe 비용이 같이 증가한다.

## 설계 옵션

### 옵션 A. snapshot compaction 강화만 먼저 적용

핵심 아이디어:
- 서버 DB에 저장되는 `ydoc_snapshot`의 update 조각 수를 적극적으로 줄인다.
- 프로토콜은 그대로 유지한다.

변경:
- compaction 트리거를 더 공격적으로 조정
- flush 시 병합 단위 개선
- room 종료 또는 주기 flush 직후 compact snapshot 유지율 높이기

장점:
- 서버/클라이언트 프로토콜 변경이 거의 없다.
- 리스크가 가장 낮다.

단점:
- ticket 왕복, DB read, multi-message 전송 구조는 그대로다.
- 큰 폭 개선이 아니라 편차 완화에 가깝다.

평가:
- 단기 안전책으로는 좋지만, 구조 병목 자체는 남는다.

### 옵션 B. snapshot 단건 전송 프로토콜 추가

핵심 아이디어:
- 서버가 `ydoc_snapshot`을 decode해서 update 여러 개로 나누지 말고,
  compacted single-update 혹은 encoded snapshot blob을 한 번에 보낸다.

변경:
- 새 메시지 타입 예: `SNAPSHOT_RESPONSE_V2`
- 서버는 compacted snapshot 또는 pre-compacted blob을 단건 전송
- 클라이언트는 단일 `Y.applyUpdate` 또는 single decode/apply 수행

장점:
- 가장 큰 병목인 `SNAPSHOT_RESPONSE × N`, `Y.applyUpdate × N`을 줄인다.
- client handoff 시간이 직접 줄어든다.

단점:
- 서버/클라이언트 동시 변경이 필요하다.
- 기존 snapshot 저장 포맷과의 호환 전략이 필요하다.

평가:
- 효과 대비 구현 복잡도가 가장 합리적이다.
- 이번 개선의 중심 옵션으로 적합하다.

### 옵션 C. room 메모리 snapshot 캐시 + warm handoff

핵심 아이디어:
- 이미 활성 room이면 DB를 거치지 않고 room 메모리의 최신 compact snapshot을 새 세션에 전달한다.

변경:
- room 단위 최신 handoff payload 유지
- 세션 join 시 DB fallback 전에 메모리 snapshot 우선 사용

장점:
- 활성 room 재진입/다중 접속에서 매우 빠르다.
- DB hit를 줄인다.

단점:
- room lifecycle, 메모리 사용량, invalidation 관리가 필요하다.
- cold start에는 효과가 없다.

평가:
- 옵션 B 이후 2단계 최적화로 적절하다.

### 옵션 D. ws-ticket 선발급 또는 REST detail과 병합

핵심 아이디어:
- detail 조회 응답에 ws ticket 메타를 포함하거나, 진입 직후 병렬로 선발급한다.

장점:
- 연결 시작 전 왕복 1회를 줄인다.

단점:
- ticket TTL/재사용/보안 모델 검토가 필요하다.
- 효과는 있지만 병목 1위는 아니다.

평가:
- 후순위 최적화로 적절하다.

## 상세 설계

### 1단계. Snapshot Handoff V2 도입

목표:
- snapshot 복원 시 `message count`와 `apply count`를 줄인다.

핵심 변경:

```text
기존:
SNAPSHOT_REQUEST
→ 서버 decode(snapshot)
→ SNAPSHOT_RESPONSE × N
→ client Y.applyUpdate × N

개선:
SNAPSHOT_REQUEST_V2
→ 서버 single-update handoff payload 생성
→ SNAPSHOT_RESPONSE_V2 × 1
→ client Y.applyUpdate × 1
```

서버 설계:
- DB의 기존 snapshot 포맷이 multi-update encoded blob이면, load 시 1회 decode 후 merge
- 가능하면 flush 저장 시점부터 single-update compact snapshot을 별도 유지
- v1/v2 동시 지원

클라이언트 설계:
- provider가 capability 또는 message type으로 v2 우선 사용
- v2 실패 시 기존 v1 flow fallback

가드레일:
- v1 완전 제거 전까지 하위 호환 유지
- snapshot apply 실패 시 즉시 기존 reconnect/error flow 재사용

### 2단계. Snapshot 저장 포맷 compact 우선화

목표:
- DB snapshot 자체를 "handoff-friendly"하게 만든다.

핵심 변경:
- flush 시 `merged update`를 single-update snapshot으로 저장하는 경로 우선
- compaction warn threshold 재검토
- room 종료 시 snapshot 조각 수/bytes 메트릭 로그 추가

추가 메트릭:
- `snapshot_bytes`
- `snapshot_update_count`
- `snapshot_handoff_decode_ms`
- `snapshot_handoff_send_ms`
- `client_snapshot_apply_ms`

### 3단계. Warm room handoff 캐시

목표:
- 이미 활성화된 다이어그램 방의 재진입 속도를 개선한다.

핵심 변경:
- `DiagramRoomManager`가 room별 latest compact handoff payload를 유지
- room dirty update drain/flush 시 캐시 갱신
- 신규 join 시 room cache 우선, 없으면 DB fallback

주의:
- 캐시는 정합성 원본이 아니라 handoff 가속용 파생 데이터여야 한다.
- room 종료 시 캐시 폐기

### 4단계. ws-ticket 왕복 축소

목표:
- 연결 시작 지연의 앞단 왕복을 줄인다.

후보:
- detail 응답에 short-lived ticket 포함
- 또는 detail 성공 직후 client가 ws-ticket을 병렬 prefetch

권장:
- 먼저 병렬 prefetch부터
- detail 응답 병합은 보안/TTL 모델 검토 후 결정

### Milestone 1. 측정 기반 가시화

변경:

성공 기준:

변경:
- flush/compaction 정책 조정
- snapshot update count 메트릭 기반 경고

성공 기준:
- 신규 snapshot의 update count 안정화
- 대형 다이어그램에서 편차 감소

### Milestone 4. Warm room cache

변경:
- room memory handoff cache

성공 기준:
- 동일 다이어그램 재접속 시 DB load 의존도 감소

## 요약

이번 작업 기준, 기존의 5초 체감 지연은 `ws-ticket` CORS 실패가 주원인이었고
그 문제는 해결됐다.

그 이후 단계로 `Snapshot Handoff V2`, `compact 저장 포맷 개선 1차`,
`warm room handoff cache 강화`까지 반영했다.

남은 후속 최적화는 `ws-ticket` 병렬 prefetch, 그리고 필요 시
warm handoff cache의 수명/무효화 정책을 더 정교하게 다듬는 일이다.
