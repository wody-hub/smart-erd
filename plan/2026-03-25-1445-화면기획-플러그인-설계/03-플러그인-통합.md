# 03. 플러그인 통합

## 이 문서의 목적

`ScreenSpecPlugin`이 협업 문서 플랫폼 코어의 SPI(Service Provider Interface)를 어떻게 구현하는지 매핑한다. 코어 수정 없이 플러그인만으로 동작해야 한다.

## ScreenSpecPlugin 등록

```typescript
const screenSpecPlugin: RegisteredDocumentPlugin = {
  pluginId: 'screen-spec',
  schemaVersion: 1,
  supportedEngineIds: ['yjs'],

  createInputAdapters(context: PluginContext): InputAdapters { ... },
  createMutationPolicy(context: PluginContext): MutationPolicy { ... },
  createProjectors(context: PluginContext): Projector[] { ... },
  createScopeResolver(context: PluginContext): ScopeResolver { ... },
};
```

화면기획 플러그인은 `BaseDocumentPlugin`을 기본으로 구현하고, 필요에 따라 capability interface를 추가 구현한다.

```text
ScreenSpecPlugin
  implements BaseDocumentPlugin          (필수)
  implements AssetCapablePlugin          (이미지 placeholder → 실제 이미지)
  implements PresenceCapablePlugin       (캔버스 커서, 선택 영역)
```

`TextInputCapablePlugin`은 구현하지 않는다. 화면기획은 텍스트 기반 DSL 편집이 없다.
`ArtifactFallbackCapablePlugin`은 1단계에서는 구현하지 않되, 나중에 JSON 내보내기/가져오기가 필요하면 추가한다.

### PluginContext가 제공하는 서비스

코어의 factory 메서드(`createInputAdapters`, `createMutationPolicy` 등)는 `PluginContext`를 받는다. 화면기획 플러그인이 이 컨텍스트에서 사용하는 코어 서비스는 아래와 같다.

```typescript
// PluginContext가 제공하는 코어 서비스 (플러그인은 이 계약만 의존)
interface PluginContext {
  readExecutor: DocumentReadExecutor;      // 공유 상태 읽기 (execute + DocumentReadQuery 패턴)
  mutationPort: DocumentMutationPort;      // 공유 상태 변경 (applyMutation)
  changeBus: ChangeBus;                    // DocumentChangeEvent 구독
  subscriptionPort: DocumentSubscriptionPort;  // 변경 이벤트 구독 (ChangeBus 래퍼)
}
```

```text
플러그인이 PluginContext를 사용하는 시점:

  MutationPolicy   → mutationPort로 공유 상태 변경
  Projector         → readExecutor.execute(query)로 상태 읽기 → 뷰 모델 생성
  ScopeResolver     → command 분석만 (PluginContext 불필요, 순수 함수)
  AssetBinding      → readExecutor로 asset 참조 수집
  PresenceMapper    → 순수 매핑 함수 (PluginContext 불필요)
  Input Adapters    → changeBus 구독으로 원격 변경 감지
```

## SPI 구현 매핑

### 1. Input Adapters

화면기획의 입력 경로는 캔버스와 속성 패널이다.

| Adapter | 입력 | 생성하는 Command |
|---|---|---|
| CanvasInputAdapter | 드래그, 리사이즈, 이동, 선택 | `instance.move`, `instance.resize`, `primitive.move` |
| LibraryDragAdapter | 라이브러리에서 캔버스로 드래그&드롭 | `instance.create`, `primitive.create` |
| PropertyPanelAdapter | 속성 패널 값 변경 | `instance.override`, `instance.variant-select` |
| ComponentEditorAdapter | 마스터 컴포넌트 편집 | `component.update-children`, `component.add-property` |
| AnnotationAdapter | 기획 메모 추가/편집 | `annotation.create`, `annotation.update` |
| ScreenManageAdapter | 화면 추가/삭제/순서변경 | `screen.create`, `screen.delete`, `screen.reorder` |

### 2. Mutation Policy

Mutation Policy는 Command를 공유 상태 변경으로 변환한다.

```typescript
class ScreenSpecMutationPolicy implements MutationPolicy {

  applyCommand(command: DocumentCommand, writer: DocumentMutationPort): void {
    switch (command.kind) {
      case 'instance.create':
        // Screen의 instances 배열에 새 ComponentInstance 추가
        break;

      case 'instance.override':
        // ComponentInstance의 overrides 배열에 Override 추가/갱신
        break;

      case 'component.update-children':
        // MasterComponent의 children 트리 수정
        // + 이 컴포넌트를 참조하는 모든 인스턴스의 경로 기반 오버라이드 정합성 확인
        break;

      case 'component.delete':
        // 인스턴스가 있으면 전부 Detach 처리 후 마스터 삭제
        break;

      case 'instance.detach':
        // 인스턴스 → 독립 노드 그룹 변환
        break;
    }
  }
}
```

### 핵심 규칙: 마스터 변경 시 오버라이드 정합성

마스터 children 구조가 변경되면 기존 인스턴스의 오버라이드 경로가 무효화될 수 있다.

```text
마스터에서 노드 삭제:
  → 해당 경로를 참조하는 오버라이드 엔트리도 함께 정리

마스터에서 노드 이름 변경:
  → 해당 경로를 참조하는 오버라이드 엔트리의 경로도 갱신

마스터에서 노드 추가:
  → 기존 오버라이드에 영향 없음 (새 노드에 대한 오버라이드가 없으므로)
```

이 정합성 유지는 `MutationPolicy` 내부에서 처리한다.

### 3. Projectors

```typescript
class ScreenSpecProjector implements Projector {

  /**
   * 코어의 DocumentReadExecutor.execute(query) 패턴을 사용한다.
   * DocumentReadQuery.run(context) 내부에서 DocumentReadContext API로 데이터를 조회한다.
   */
  project(readExecutor: DocumentReadExecutor): ScreenSpecViewModel {
    return readExecutor.execute({
      run(context: DocumentReadContext): ScreenSpecViewModel {
        return {
          screens: buildScreenList(context),
          currentScreen: buildCurrentScreenView(context),
          library: buildLibraryView(context),
        };
      }
    });
  }
}

// Projector 내부에서 DocumentReadContext를 사용하는 예시:
function buildScreenList(context: DocumentReadContext): ScreenListItem[] {
  const screenRefs = context.findByKind('screen');
  return screenRefs.map(ref => {
    const entity = context.getEntity(ref);
    const instanceRefs = context.listRelated(ref, 'instances');
    return {
      id: ref.id,
      name: entity?.props.name as string,
      instanceCount: instanceRefs.length,
    };
  });
}
```

Projector가 인스턴스를 렌더링 가능한 뷰 모델로 변환한다.

```text
인스턴스 뷰 모델 생성:
  1. instance.componentRef → MasterComponent 조회
  2. master.children + variant.overrides + instance.overrides 병합
  3. 최종 노드 트리를 flat render node 목록으로 변환
  4. 각 render node에 absolute position 계산 (인스턴스 position + 노드 상대 position)
```

#### Projector 성능 최적화

마스터 변경 시 모든 화면의 모든 인스턴스를 재계산하면 비용이 크다.

```text
최적화 전략:
  1. ChangeBus 이벤트의 affectedScopes에서 변경된 MasterComponent.id 확인
  2. 해당 컴포넌트를 참조하는 인스턴스만 뷰 모델 재생성
  3. 현재 열린 화면의 인스턴스만 즉시 렌더, 다른 화면은 열 때 lazy 재생성
```

#### ChangeBus 이벤트 활용

Projector와 Input Adapter는 코어의 `ChangeBus`를 통해 `DocumentChangeEvent`를 구독한다. 화면기획 플러그인은 아래 필드를 활용한다.

```typescript
// 코어가 발행하는 이벤트 구조
interface DocumentChangeEvent {
  documentId: string;
  pluginId: string;           // 'screen-spec'
  revision: number;
  origin: ChangeOrigin;       // 변경 출처 식별
  affectedScopes: ScopeRef[]; // 영향받는 scope 목록
  delta: DocumentDelta;
}

interface ChangeOrigin {
  cause: 'local' | 'remote' | 'system';   // 내 변경 vs 원격 변경
  source: 'text-editor' | 'canvas' | 'form' | 'toolbar' | 'runtime';  // 입력 경로
  // 화면기획은 TextInputCapablePlugin 미구현이므로 'text-editor' source는 발생하지 않음
  clientId?: string;
  requestId?: string;         // echo 방지용 — 내가 보낸 변경인지 식별
}
```

```text
화면기획 플러그인의 ChangeBus 구독 패턴:

  Projector:
    → origin.cause === 'remote'인 이벤트 수신 시
    → affectedScopes에서 변경된 component/screen scope 확인
    → 해당 scope의 인스턴스만 뷰 모델 재생성

  Input Adapter:
    → origin.cause === 'remote'인 이벤트 수신 시
    → 현재 캔버스에 표시된 요소가 변경되었으면 UI 갱신
    → origin.cause === 'local'인 이벤트는 이미 적용됨 → 무시

  루프 방지 규칙 (코어 04-Command-Event-설계 준수):
    → CollaborationRuntime: remote 이벤트 재전송 금지
    → Projector: dirty draft 보호 중이면 overwrite 금지
    → UndoManager: 원격 변경은 undo 스택 제외
```

### 4. Scope Resolver

화면기획의 락 범위는 **컴포넌트 단위**와 **화면 단위**다.

```typescript
class ScreenSpecScopeResolver implements ScopeResolver {

  /**
   * 명령이 영향을 미치는 scope를 반환한다.
   * 코어의 ScopeLockRuntime이 이 결과로 lock acquire를 수행한다.
   */
  resolveAffectedScopes(command: DocumentCommand): ScopeRef[] {
    switch (command.kind) {
      // 컴포넌트 편집 → 컴포넌트 단위 락
      case 'component.update-children':
      case 'component.add-property':
      case 'component.delete':
        return [{
          pluginId: 'screen-spec',
          scopeType: 'component',
          scopeId: command.payload.componentId,
        }];

      // 화면 내 인스턴스/요소 편집 → 화면 단위 락
      case 'instance.create':
      case 'instance.move':
      case 'instance.override':
      case 'primitive.create':
      case 'annotation.create':
        return [{
          pluginId: 'screen-spec',
          scopeType: 'screen',
          scopeId: command.payload.screenId,
        }];

      // 화면 메타 편집 → 화면 단위 락
      case 'screen.rename':
      case 'screen.resize':
        return [{
          pluginId: 'screen-spec',
          scopeType: 'screen',
          scopeId: command.payload.screenId,
        }];

      default:
        return [];
    }
  }

  /**
   * 현재 포커스된 요소가 속한 scope를 반환한다.
   * 코어의 ScopeLockRuntime이 포커스 기반 선점(proactive acquire)에 사용한다.
   *
   * FocusContext는 코어가 현재 UI 상태를 수집하여 전달하는 구조체다.
   * 화면기획 플러그인은 아래 필드를 사용한다:
   *   - focusedElementId: 현재 포커스된 인스턴스/요소 ID
   *   - screenId: 현재 활성 화면 ID
   *   - editingComponentId: 마스터 컴포넌트 편집 모드 시 대상 ID
   */
  resolveFocusScope(context: FocusContext): ScopeRef | null {
    // 캔버스에서 인스턴스/요소를 선택 중이면 해당 화면 scope
    if (context.focusedElementId && context.screenId) {
      return {
        pluginId: 'screen-spec',
        scopeType: 'screen',
        scopeId: context.screenId,
      };
    }

    // 컴포넌트 편집 모드이면 컴포넌트 scope
    if (context.editingComponentId) {
      return {
        pluginId: 'screen-spec',
        scopeType: 'component',
        scopeId: context.editingComponentId,
      };
    }

    return null;
  }
}
```

| scope type | scope id 예시 | 의미 |
|---|---|---|
| `component` | `comp-gnb` | GNB 마스터 컴포넌트 편집 중 |
| `screen` | `screen-user-list` | 사용자 관리 화면 편집 중 |

ERD에서 `table/주문`으로 테이블을 잠그듯이, 화면기획에서는 `component/GNB` 또는 `screen/사용자관리`로 잠근다.

### 6. Presence Mapper (PresenceCapablePlugin)

```typescript
class ScreenSpecPresenceMapper implements PresenceMapper {

  toPresencePayload(state: LocalPresenceState): GenericPresencePayload {
    return {
      pointer: state.pointer,                      // 캔버스 위 커서 좌표
      selection: state.selection,                   // 선택된 인스턴스/요소 ID 목록
      viewport: state.viewport,                     // 현재 보고 있는 영역
      activeTool: state.activeTool,                // 선택/사각형/텍스트/주석 등 현재 도구
      pluginPayload: {
        activeScreen: state.pluginState?.currentScreenId,  // 어떤 화면을 보고 있는지
      },
    };
  }

  applyRemotePresence(payload: GenericPresencePayload, adapter: PresenceAdapter): void {
    const activeScreen = (payload.pluginPayload as any)?.activeScreen;

    // 같은 화면을 보고 있는 참여자만 커서/선택 영역 표시
    adapter.updateRemoteCursor(payload.pointer);
    adapter.updateRemoteSelection(payload.selection);
    adapter.updateRemoteViewport(payload.viewport);
    adapter.updatePluginPresence({ activeScreen });
  }
}
```

## DocumentReadContext 매핑

코어의 `DocumentReadContext`는 `getEntity`, `listRelated`, `getProperty`, `findByKind`, `getRevision` 5개 메서드를 제공한다. 화면기획 도메인 모델은 아래와 같이 매핑한다.

### Entity Kind 정의

| kind | 대응 타입 | 예시 |
|---|---|---|
| `master-component` | MasterComponent | `{kind: 'master-component', id: 'comp-gnb'}` |
| `component-node` | ComponentNode | `{kind: 'component-node', id: 'node-title'}` |
| `screen` | Screen | `{kind: 'screen', id: 'screen-user-list'}` |
| `instance` | ComponentInstance | `{kind: 'instance', id: 'inst-1'}` |
| `primitive` | PrimitiveElement | `{kind: 'primitive', id: 'prim-rect-1'}` |
| `primitive-group` | PrimitiveGroup | `{kind: 'primitive-group', id: 'group-1'}` |
| `annotation` | Annotation | `{kind: 'annotation', id: 'ann-1'}` |
| `screen-link` | ScreenLink | `{kind: 'screen-link', id: 'link-1'}` |
| `category` | ComponentCategory | `{kind: 'category', id: 'cat-layout'}` |

### Relation 정의

| 출발 kind | relation | 결과 kind |
|---|---|---|
| `screen` | `instances` | `instance` |
| `screen` | `primitives` | `primitive` |
| `screen` | `groups` | `primitive-group` |
| `screen` | `annotations` | `annotation` |
| `screen` | `outgoing-links` | `screen-link` |
| `master-component` | `children` | `component-node` |
| `master-component` | `instances` | `instance` (역참조: 이 마스터를 사용하는 인스턴스) |
| `component-node` | `children` | `component-node` (재귀) |

### 조회 예시

```typescript
// 모든 화면 조회
const screenRefs = readContext.findByKind('screen');

// 특정 화면의 인스턴스 목록
const instanceRefs = readContext.listRelated(
  { kind: 'screen', id: 'screen-user-list' },
  'instances'
);

// 특정 마스터 컴포넌트의 속성 조회
const name = readContext.getProperty(
  { kind: 'master-component', id: 'comp-gnb' },
  'name'
);

// 특정 마스터를 참조하는 모든 인스턴스 (역참조)
const affectedInstances = readContext.listRelated(
  { kind: 'master-component', id: 'comp-gnb' },
  'instances'
);
```

이 매핑은 Projector, ScopeResolver, AssetBinding이 DocumentReadExecutor를 통해 데이터를 조회하는 계약이다. 플러그인 내부에서 Typed Read Facade를 만들어 이 raw API를 감싸는 것을 권장한다.

## ERD 플러그인과의 비교

| 구성요소 | ERD Plugin | ScreenSpec Plugin |
|---|---|---|
| Input Adapter | Canvas(테이블 드래그) + Text(DSL) | Canvas(인스턴스 배치) + PropertyPanel |
| TextInputPipeline | DSL 파서 + 검증 | 없음 (텍스트 DSL 미사용) |
| Mutation Policy | 테이블/컬럼/엣지 CRUD | 컴포넌트/인스턴스/화면 CRUD + 오버라이드 정합성 |
| Projector | ReactFlow 노드/엣지 뷰 모델 | 화면별 렌더 노드 트리 뷰 모델 |
| Scope Resolver | `table/{tableId}` | `component/{componentId}`, `screen/{screenId}` |
| Asset Binding | 없음 | ImagePlaceholder → 이미지 asset |
| Presence Mapper | 테이블 위 커서 | 캔버스 커서 + 활성 화면 |
| Artifact Serializer | content JSON (호환) | 미구현 (1단계) |

## 코어가 그대로 재사용되는 부분

| 코어 모듈 | 화면기획에서의 역할 |
|---|---|
| DocumentSession | 화면기획 문서 진입/나가기/reconnect |
| DocumentStore | 컴포넌트/인스턴스/화면 데이터의 공유 상태 관리 |
| SharedDocumentEngine | Y.Doc 기반 CRDT 동기화 |
| ChangeBus | 마스터 수정 → 인스턴스 갱신 이벤트 전파 |
| CollaborationRuntime | 원격 delta 송수신 |
| ScopeLockRuntime | 컴포넌트/화면 단위 편집 락 |
