# 06. 구현 로드맵

## 전제 조건

이 로드맵은 **협업 문서 플랫폼 코어 구현이 완료된 후** 시작한다. 코어가 없으면 플러그인을 올릴 수 없다.

필수 선행 작업:
- `plan/2026-03-25-1153-다이어그램-동기화-아키텍처-재설계/`의 코어 구현 완료
- ERD 플러그인이 코어 위에서 동작하는 상태
- PluginRegistry에 두 번째 플러그인을 등록할 수 있는 상태

## 단계별 계획

### 1단계: 기본 화면 편집 (2~3주)

**목표:** 화면에 요소를 배치하고 편집할 수 있는 최소 환경

#### 구현 범위

```text
[플러그인 골격]
├─ ScreenSpecPlugin 등록 (PluginRegistry)
├─ 기본 Mutation Policy (화면/요소 CRUD)
├─ 기본 Projector (화면 → 렌더 노드)
└─ 기본 Scope Resolver (화면 단위 락)

[도메인 모델]
├─ Screen (생성, 삭제, 이름 변경, 순서 변경)
├─ PrimitiveElement (사각형, 텍스트, 구분선)
└─ 화면 크기 프리셋

[UI]
├─ 좌측: 화면 목록 패널
├─ 캔버스: 요소 배치, 이동, 리사이즈, 삭제
├─ 우측: 화면 속성, 요소 속성
└─ 도구 모음: 선택, 사각형, 텍스트, 구분선
```

#### 제외 범위

- 컴포넌트 라이브러리
- 인스턴스/오버라이드
- 배리언트
- 슬롯
- 주석
- 화면 흐름
- 내보내기

#### 검증 기준

- [ ] `screen-spec` 플러그인이 코어 수정 없이 PluginRegistry에 등록된다
- [ ] 화면을 생성/삭제/전환할 수 있다
- [ ] 사각형, 텍스트, 구분선을 배치/이동/리사이즈/삭제할 수 있다
- [ ] 실시간 협업으로 다른 참여자의 변경이 반영된다
- [ ] 화면 단위 락이 동작한다

**목표:** Figma 스타일 컴포넌트 정의 → 인스턴스 재사용 → 수정 시 전체 반영

#### 구현 범위

```text

[컴포넌트 시스템]
```

## 백엔드 플러그인 구현 범위

코어 백엔드 구조(`plan/2026-03-25-1153-다이어그램-동기화-아키텍처-재설계/07-백엔드-구조.md`)에서 정의한 `domain/screen/collaboration/` 패키지에 화면기획 백엔드 플러그인을 구현한다.

### 구현 대상

```text
src/main/java/com/smarterd/domain/screen/collaboration/
├── ScreenSpecCollaborationPlugin.java      // BaseCollaborationPlugin + AssetCapableCollaborationPlugin
├── ScreenSpecScopeResolver.java            // component/screen 단위 scope 해석
├── ScreenSpecAssetReferenceExtractor.java  // snapshot에서 이미지 asset 참조 추출
└── ScreenSpecDomainValidationHook.java     // 도메인 무결성 검증 (순환 참조 등)
```

### Capability 구현

```text
ScreenSpecCollaborationPlugin
  implements BaseCollaborationPlugin               (필수)
  implements AssetCapableCollaborationPlugin        (이미지 asset 참조 추출)
```

`ArtifactFallbackCapableCollaborationPlugin`은 1단계에서 미구현. ERD 플러그인과 달리 레거시 `content` 호환이 필요 없으므로, artifact serializer/codec은 나중에 JSON 내보내기/가져오기 시 추가한다.

`SchemaMigratableCollaborationPlugin`과 `ArtifactMigratableCollaborationPlugin`도 1단계에서는 미구현. schemaVersion이 1이므로 마이그레이션이 불필요하다.

### ScopeResolver 매핑

| scope type | scope id 예시 | lock 의미 |
|---|---|---|
| `component` | `comp-gnb` | 마스터 컴포넌트 편집 중 |
| `screen` | `screen-user-list` | 화면 편집 중 |

백엔드 ScopeResolver는 프론트엔드 ScopeResolver와 동일한 scope 체계를 사용한다. lock acquire/release 시 서버가 scope 의미를 해석하여 충돌 판정한다.

### Snapshot Codec과의 관계

스냅샷 직렬화/역직렬화는 **코어의 `DocumentSnapshotCodec`**가 담당한다. 화면기획 플러그인은 별도의 snapshot codec을 구현하지 않는다.

```text
코어가 담당하는 부분:
  DocumentSnapshotCodec
    → decodeToSnapshot(persisted) → 메모리 snapshot
    → encodeForPersistence(inMemory) → 영속화용 바이트
    → snapshotFormatVersion() → 코어가 관리하는 포맷 버전

  DocumentPersistenceCoordinator
    → checkpoint(DocumentCheckpoint) → 스냅샷 저장
    → load(documentId) → PersistedDocument 복원

화면기획 플러그인이 관여하는 부분:
  pluginSchemaVersion = 1 (플러그인이 관리)
  snapshotFormatVersion → 코어가 관리 (플러그인은 관여하지 않음)
  AssetReferenceExtractor → checkpoint 시 asset 참조 목록 추출
  DomainValidationHook → 필요 시 도메인 무결성 검증

코어 persistence가 checkpoint할 때의 데이터 흐름:
  1. collaboration-runtime이 DocumentCheckpoint 생성
  2. checkpoint에 pluginId='screen-spec', engineId='yjs', pluginSchemaVersion=1 포함
  3. AssetReferenceExtractor로 snapshot에서 asset 참조 추출
  4. DocumentPersistenceCoordinator가 영속화
```

### 단계별 백엔드 구현

| 단계 | 백엔드 범위 |
|---|---|
| 1단계 | ScreenSpecCollaborationPlugin 등록, ScopeResolver, ValidationHook |
| 2단계 | AssetReferenceExtractor (이미지 asset 지원 시) |
| 5단계 | ArtifactSerializer (JSON 내보내기 서버사이드 지원 시, 선택) |

## 성공 기준

이 플러그인이 성공했다고 판단하는 기준은 아래와 같다.

1. **코어 수정 제로** — ScreenSpecPlugin을 추가하면서 `collaboration/core/` 디렉토리의 파일을 하나도 수정하지 않았다.
2. **컴포넌트 자동 반영** — 마스터 컴포넌트를 수정하면 10개 화면에 배치된 인스턴스가 즉시 갱신된다.
3. **협업 동작** — 두 사용자가 동시에 다른 화면을 편집하고, 한 사용자가 컴포넌트를 수정하면 다른 사용자의 화면에도 반영된다.
4. **산출물 품질** — PDF로 내보낸 기획서가 실무에서 전달용으로 사용할 수 있는 수준이다.
5. **플랫폼 검증** — 이 플러그인의 존재 자체가 "협업 문서 플랫폼 코어"의 재사용성을 증명한다.
