# 02. 컴포넌트 시스템

## 이 문서의 핵심

화면기획 도구의 존재 이유는 **컴포넌트 재사용과 자동 반영**이다. 이 문서는 Figma의 컴포넌트 시스템 5가지 핵심 개념을 우리 도메인 모델에 매핑하고, 각각의 동작 규칙을 정의한다.

## 1. 마스터 컴포넌트 (Main Component)

### Figma에서의 동작

- 마름모(◆) 아이콘으로 표시
- 수정하면 모든 인스턴스에 전파
- Assets 패널에서 검색/드래그 가능

### 우리 동작 규칙

마스터 컴포넌트는 두 가지 경로로 생성된다.

```text
경로 A: 빈 컴포넌트부터 시작
  1. 컴포넌트 라이브러리 패널에서 "새 컴포넌트" 클릭
  2. 빈 프레임 생성
  3. 내부에 노드(텍스트, 사각형, 그룹 등)를 배치
  4. 속성(PropertyDefinition) 정의
  5. 라이브러리에 등록

경로 B: 기존 요소를 컴포넌트로 승격
  1. 화면에서 여러 요소를 선택
  2. "컴포넌트로 만들기" 실행
  3. 선택한 요소들이 MasterComponent.children으로 이동
  4. 원래 위치에는 인스턴스가 배치됨
  5. 라이브러리에 자동 등록
```

### 마스터 수정 → 인스턴스 반영 흐름

```text
사용자가 ◆ GNB 마스터 수정 (메뉴 항목 추가)
    │
    ▼
Plugin Input Adapter
    │ canvas 이벤트 → DocumentCommand 변환
    ▼
Mutation Policy
    │ MasterComponent.children 변경
    ▼
DocumentStore
    │ shared state 반영, revision 증가
    ▼
ChangeBus.emit(DocumentChangeEvent)
    │
    ├─► ScreenSpec Projector
    │     │ 변경된 MasterComponent.id로 영향받는 인스턴스 검색
    │     │ 각 화면의 인스턴스 뷰 모델 재생성
    │     ├─ 📄 사용자 관리 화면의 ◇ GNB → 갱신
    │     ├─ 📄 주문 관리 화면의 ◇ GNB → 갱신
    │     └─ 현재 열린 화면이면 즉시 렌더링
    │
    ├─► CollaborationRuntime → 원격 전파
    └─► PersistenceCoordinator → 저장 예약
```

### 마스터 삭제 정책

마스터를 삭제하면 인스턴스가 고아가 된다. 정책은 아래와 같다.

```text
마스터 삭제 시도
    │
    ├─ 인스턴스가 0개 → 즉시 삭제
    └─ 인스턴스가 1개 이상
        → 확인 다이얼로그: "N개 화면에서 사용 중입니다. 삭제하면 모든 인스턴스가 분리(Detach)됩니다."
        → 확인 시: 모든 인스턴스를 Detach 처리 후 마스터 삭제
        → 취소 시: 아무 동작 없음
```

## 2. 인스턴스 (Instance)

### Figma에서의 동작

- 빈 마름모(◇) 아이콘으로 표시
- 마스터를 참조하되 개별 속성 오버라이드 가능
- 마스터가 바뀌면 오버라이드하지 않은 부분만 갱신

### 인스턴스 렌더링 알고리즘

인스턴스를 화면에 그리는 핵심 로직이다.

```text
renderInstance(instance):
  1. componentRef로 MasterComponent 조회
     → 없으면 "삭제된 컴포넌트" placeholder 표시

  2. selectedVariant로 해당 VariantSet 조회
     → VariantSet의 nodeOverrides를 base에 적용

  3. Master의 children 트리를 순회하며 렌더링
     각 노드마다:
       a. instance.overrides에서 해당 노드 경로 검색
       b. 오버라이드가 있으면 → 오버라이드 값 사용
       c. 오버라이드가 없으면 → 마스터 원본 값 사용
       d. propertyBinding이 있으면:
          → instance.overrides에서 해당 property 검색
          → 있으면 오버라이드 값, 없으면 PropertyDefinition.defaultValue

  4. slotSwaps 처리
     SlotNode를 만나면:
       a. instance.slotSwaps에서 해당 슬롯 경로 검색
       b. 교체가 있으면 → swappedComponentRef의 마스터로 렌더링
       c. 교체가 없으면 → defaultComponentRef로 렌더링
       d. defaultComponentRef도 없으면 → 빈 슬롯 placeholder
```

### 인스턴스 적용 우선순위

값이 결정되는 우선순위는 아래와 같다 (높은 것이 우선).

```text
1. Instance Override (최우선)
2. Variant Override
3. Property Default Value
4. Master Node Default Value (최하위)
```

### 인스턴스 생성

```text
경로 A: 라이브러리에서 드래그&드롭
  1. 좌측 컴포넌트 라이브러리 패널에서 마스터를 선택
  2. 캔버스로 드래그
  3. 드롭 위치에 ComponentInstance 생성
     - componentRef = 마스터 ID
     - position = 드롭 좌표
     - size = 마스터 defaultSize
     - overrides = [] (빈 배열)
     - selectedVariant = 각 축의 defaultValue

경로 B: 기존 인스턴스 복제
  1. 인스턴스 선택 후 Cmd+D
  2. 동일한 componentRef + 동일한 overrides로 새 인스턴스 생성
  3. 위치만 오프셋
```

## 3. 오버라이드 (Override)

### Figma에서의 동작

- 인스턴스에서 텍스트, 색상, 크기 등을 개별 변경
- 오버라이드한 속성은 마스터 변경에 영향받지 않음
- "Reset" 버튼으로 오버라이드 제거 → 마스터 값 복원

### 오버라이드 동작 규칙

```text
규칙 1: 오버라이드는 명시적이다
  - 인스턴스에서 값을 변경하면 Override 엔트리가 생성된다.
  - 값을 변경하지 않은 속성에는 Override가 없다.
  - Override가 없는 속성은 항상 마스터 원본을 따른다.

규칙 2: 마스터 변경과 오버라이드의 관계
  - 마스터에서 노드 추가 → 인스턴스에도 추가됨 (오버라이드 없으므로)
  - 마스터에서 노드 삭제 → 인스턴스에서도 사라짐 (해당 노드의 오버라이드도 정리)
  - 마스터에서 노드 이름 변경 → 경로가 바뀌므로 기존 오버라이드 매핑 갱신 필요

규칙 3: 오버라이드 리셋
  - 개별 속성 리셋: 해당 Override 엔트리 삭제 → 마스터 값 복원
  - 전체 리셋: 모든 overrides = [] → 마스터와 완전 동일
```

### 오버라이드 UI 표시

```text
속성 패널에서:

  제목: [사용자 목록]  ← 오버라이드됨 (볼드체 + 리셋 아이콘)
  컬럼: [#, 이름, 이메일, 역할, 작업]  ← 오버라이드됨
  행 수: 5             ← 마스터 원본 (일반체)
  페이지네이션: ✓       ← 마스터 원본

  오버라이드된 속성에는 "↩" 리셋 아이콘 표시
  클릭 시 해당 오버라이드 제거
```

## 4. 배리언트 (Variant)

### Figma에서의 동작

- 하나의 컴포넌트가 여러 상태를 가짐
- 배리언트 축(Property)별로 값을 선택
- 인스턴스에서 드롭다운으로 배리언트 전환

### 배리언트 정의 방식

```text
◆ 목록 테이블 컴포넌트
│
├─ 배리언트 축 정의:
│   ├─ 상태: [데이터있음, 비어있음, 로딩중, 에러]
│   └─ 크기: [기본, 컴팩트]
│
└─ 배리언트 조합:
    ├─ {상태: "데이터있음", 크기: "기본"}
    │   → 기본 렌더링 (변경 없음)
    │
    ├─ {상태: "비어있음", 크기: "기본"}
    │   → 테이블 본문 숨김
    │   → "데이터가 없습니다" 텍스트 표시
    │
    ├─ {상태: "로딩중", 크기: "기본"}
    │   → 테이블 본문을 스켈레톤으로 교체
    │   → 페이지네이션 비활성
    │
    └─ {상태: "에러", 크기: "기본"}
        → 테이블 본문 숨김
        → "오류가 발생했습니다" 텍스트 + 재시도 버튼 표시
```

### 배리언트 활용 시나리오

화면기획에서 배리언트의 핵심 가치는 **상태별 화면 기획**이다.

```text
📄 사용자 관리 - 데이터 있음
  └─ ◇ 목록 테이블 (배리언트: 상태=데이터있음)

📄 사용자 관리 - 비어있음
  └─ ◇ 목록 테이블 (배리언트: 상태=비어있음)

📄 사용자 관리 - 로딩 중
  └─ ◇ 목록 테이블 (배리언트: 상태=로딩중)

📄 사용자 관리 - 에러
  └─ ◇ 목록 테이블 (배리언트: 상태=에러)
```

이렇게 하면 하나의 컴포넌트로 4장의 상태별 화면을 기획할 수 있다. 컴포넌트 구조를 수정하면 4장 모두 자동 반영된다.

## 5. 슬롯 (Slot / Instance Swap)

### Figma에서의 동작

- Instance Swap Property
- 컴포넌트 내부의 특정 영역을 다른 컴포넌트로 교체
- 교체 가능한 타입을 제한할 수 있음

### 슬롯 동작 규칙

```text
◆ 카드 컴포넌트
├─ [Icon Slot]           ← acceptedCategories: ["아이콘"]
│   default: ◆ 문서 아이콘
├─ [Text] 제목
├─ [Text] 설명
└─ [Action Slot]         ← acceptedCategories: ["버튼", "링크"]
    default: ◆ 기본 버튼

인스턴스 A: 사용자 카드
├─ [Icon Slot] → ◆ 사용자 아이콘 (교체)
├─ [Text] "사용자명" (오버라이드)
├─ [Text] "이메일 주소" (오버라이드)
└─ [Action Slot] → ◆ 역할 변경 버튼 (교체)

인스턴스 B: 프로젝트 카드
├─ [Icon Slot] → ◆ 폴더 아이콘 (교체)
├─ [Text] "프로젝트명" (오버라이드)
├─ [Text] "마지막 수정일" (오버라이드)
└─ [Action Slot] → ◆ 기본 버튼 (기본값 유지)
```

### 슬롯 교체 제한

슬롯에 `acceptedCategories`를 지정하면 해당 카테고리의 컴포넌트만 교체 가능하다. 지정하지 않으면 모든 컴포넌트를 넣을 수 있다.

```text
슬롯 교체 시도:
  1. 교체 대상 컴포넌트의 카테고리 확인
  2. acceptedCategories가 비어있으면 → 허용
  3. acceptedCategories에 포함되면 → 허용
  4. 포함되지 않으면 → 거부 + "이 슬롯에는 [카테고리] 컴포넌트만 넣을 수 있습니다" 안내
```

### 슬롯 순환 참조 방지

컴포넌트 A의 슬롯에 컴포넌트 B를 넣고, B의 슬롯에 A를 넣으면 무한 렌더링 루프가 발생한다. 이를 두 단계에서 방지한다.

```text
1. MutationPolicy 사전 검증 (쓰기 시점)
   슬롯 교체(slot-swap) 또는 기본 슬롯 컴포넌트(defaultComponentRef) 설정 시:
     a. 대상 컴포넌트의 슬롯 트리를 재귀 탐색
     b. 현재 컴포넌트 ID가 슬롯 참조 체인에 포함되면 거부
     c. "순환 참조가 감지되었습니다: A → B → A" 안내

2. Projector 안전장치 (읽기 시점)
   인스턴스 렌더링 시 방문 스택(visited set)을 유지:
     a. 컴포넌트 렌더링 진입 시 ID를 스택에 추가
     b. 이미 스택에 있으면 "순환 참조" placeholder 표시
     c. 렌더링 완료 후 스택에서 제거
     d. 최대 중첩 깊이 제한: 10단계 (넘으면 placeholder)
```

사전 검증이 1차 방어선이고, Projector 안전장치는 데이터 불일치 상황(원격 변경 등)에서의 방어선이다.

## 6. 분리 (Detach)

### Figma에서의 동작

- 인스턴스를 마스터에서 분리
- 분리 후에는 독립 요소가 됨
- 마스터 수정이 더 이상 반영되지 않음

### Detach 동작

```text
Detach 실행:
  1. 인스턴스의 마스터를 조회
  2. 마스터 children + 배리언트 오버라이드 + 인스턴스 오버라이드를 병합
  3. 최종 상태를 PrimitiveElement 배열로 평탄화
  4. PrimitiveGroup 생성 (name: "목록 테이블 (분리됨)", children: 평탄화 결과)
  5. 인스턴스를 삭제하고, 같은 위치에 PrimitiveGroup을 Screen.groups에 추가
  6. componentRef 연결이 끊어짐 → 마스터와 무관한 독립 요소

결과:
  - 분리 전: ◇ 목록 테이블 (인스턴스, Screen.instances에 포함)
  - 분리 후: ■ 그룹 "목록 테이블 (분리됨)" (PrimitiveGroup, Screen.groups에 포함)
               ├─ [Text] "사용자 목록"
               ├─ [Rectangle] 테이블 헤더
               ├─ [Rectangle] 데이터 행
               └─ [Rectangle] 페이지네이션
```

### Detach 후 되돌리기

Detach는 Undo로 되돌릴 수 있다. 하지만 Undo 범위를 벗어나면 독립 요소를 다시 인스턴스로 만들 수 없다. 새로 인스턴스를 배치해야 한다.

## 컴포넌트 시스템 전체 흐름 요약

```text
[컴포넌트 정의]
  ◆ 마스터 생성 → 라이브러리 등록
    │
    ▼
[인스턴스 배치]
  ◇ 드래그&드롭으로 화면에 배치
    │
    ▼
[개별 조정]
  오버라이드: 텍스트, 스타일, 가시성 변경
  배리언트: 상태 선택 (기본, 비활성, 로딩 등)
  슬롯 교체: 내부 영역을 다른 컴포넌트로 교체
    │
    ▼
[마스터 수정 시]
  오버라이드하지 않은 부분만 자동 갱신
  모든 화면의 해당 인스턴스에 전파
    │
    ▼
[필요 시 분리]
  Detach로 독립 요소화 → 마스터와 연결 끊김
```

## Undo/Redo 정책

코어의 UndoManager는 로컬 변경만 undo 스택에 넣고, 원격 변경은 제외한다(코어 04-Command-Event-설계 참조). 화면기획 플러그인은 이 코어 정책을 그대로 따르되, 컴포넌트 시스템 특유의 규칙을 추가한다.

### 기본 규칙

```text
1. Undo 대상은 로컬 사용자가 직접 실행한 Command만 해당한다.
2. 원격 사용자의 변경은 undo 스택에 들어가지 않는다.
3. 마스터 수정에 의한 인스턴스 자동 갱신은 파생 효과이므로 별도 undo 대상이 아니다.
   → 마스터 수정을 undo하면 인스턴스도 자동으로 이전 상태로 돌아간다.
```

### 컴포넌트 시스템 특수 규칙

```text
Detach undo:
  - Detach를 undo하면 PrimitiveGroup이 삭제되고 원래 ComponentInstance가 복원된다.
  - componentRef 연결이 다시 맺어진다.

마스터 삭제 undo:
  - 마스터 삭제 시 모든 인스턴스가 Detach되었으므로,
    undo 시 마스터 복원 + 모든 Detach가 역순으로 undo된다.
  - 이는 단일 undo 단위(compound operation)로 처리한다.

컴포넌트 승격 undo:
  - 요소 → 컴포넌트 승격을 undo하면 마스터가 삭제되고
    원래 위치에 독립 요소들이 복원된다.
```

### Undo 범위 경계

```text
마스터 변경의 영향:
  사용자 A가 마스터를 수정하면:
    → A의 undo 스택: 마스터 수정 Command 1건
    → B의 화면에서 인스턴스가 자동 갱신되지만, B의 undo 스택에는 아무것도 들어가지 않음
    → A가 undo하면 마스터가 복원되고, B의 인스턴스도 자동으로 이전 상태로 갱신됨
```
