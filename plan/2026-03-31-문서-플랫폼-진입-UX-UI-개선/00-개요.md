## 목적

캔버스 내부 편집기보다 먼저, **캔버스에 들어가기 전까지의 제품 UX/UI**를 문서 플랫폼 기준으로 다시 정리한다.

현재 화면은 ERD 기능을 중심으로 점진적으로 붙은 상태라서,

- 팀
- 프로젝트
- 다이어그램 목록
- 데이터 사전
- 편집기 진입

이 각각 독립 페이지처럼 보인다.

하지만 앞으로는 ERD 외에도

- 마크다운 문서
- 화면기획 문서

같은 문서 타입이 추가될 예정이므로, 지금의 진입 구조를 그대로 두면
메뉴와 라우트가 계속 `diagram` 중심으로 고정되고 UX가 더 어수선해진다.

즉 이번 작업의 목표는 **예쁜 화면 만들기**가 아니라,
**“문서 플랫폼처럼 느껴지는 진입 경험”을 먼저 만드는 것**이다.

## 현행 문제

현재 기준 핵심 문제는 아래와 같다.

1. **공통 쉘이 약하다**
- [Header.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/components/layout/Header.tsx)는 앱명, 언어, 로그아웃 정도만 보여준다.
- 팀/프로젝트/문서 맥락을 유지하는 지속적인 탐색 구조가 없다.
- 각 페이지가 개별 화면처럼 분절돼 보인다.

2. **페이지 간 이동 맥락이 약하다**
- [ProjectsPage.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/pages/project/ProjectsPage.tsx)
- [DiagramsPage.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/pages/diagram/DiagramsPage.tsx)
- [DictionaryPage.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/pages/dictionary/DictionaryPage.tsx)
- 전부 `뒤로 가기 + 제목 + 카드` 패턴의 반복이다.
- 지금 내가 어느 팀, 어느 프로젝트, 어느 자산 영역에 있는지가 한 번에 안 읽힌다.

3. **정보구조가 ERD에 과적합돼 있다**
- [routes.ts](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/constants/routes.ts)는 `projects -> diagrams -> diagram` 흐름에 고정돼 있다.
- 앞으로 마크다운, 화면기획이 들어오면 `documents` 또는 `artifacts` 수준의 상위 개념이 필요하다.
- 지금 구조는 “문서 플랫폼”보다 “ERD 툴”에 가깝다.

4. **사전(Dictionary)의 위치가 어색하다**
- 현재는 프로젝트 목록 화면의 액션 버튼 중 하나로 들어간다.
- 하지만 데이터 사전은 프로젝트별 산출물이라기보다 팀 단위 자산/사전 허브에 가깝다.
- 플러그인이 늘어날수록 더더욱 별도 자산 영역으로 분리하는 편이 읽기 쉽다.

5. **목록 화면의 CTA와 의미가 약하다**
- 프로젝트 카드, 다이어그램 카드 모두 “무엇을 만들고 관리하는지”보다 “리소스 하나 더 추가” 수준의 경험에 가깝다.
- 문서 타입이 늘어나면 카드 기반 단순 반복 UI는 더 버거워진다.

## 설계 원칙

1. **문서 플랫폼처럼 보이게 만든다**
- ERD는 첫 번째 문서 타입일 뿐이다.
- 상위 UX는 `diagram`이 아니라 `document` 중심으로 재구성해야 한다.

2. **캔버스 전과 후를 분리한다**
- 이번 작업은 캔버스 내부 편집기를 건드리는 작업이 아니다.
- 진입 쉘, 목록, 네비게이션, 액션 구조를 먼저 정리한다.

3. **한 번에 정보구조를 일반화한다**
- 지금 UI를 다듬고 나중에 또 문서 타입 추가 때문에 다시 뜯는 건 비효율적이다.
- 이번에 최소한 라우트 개념과 메뉴 구조는 플러그인 확장을 견딜 수 있게 바꾼다.

4. **강한 주 액션과 명확한 보조 액션**
- 목록 화면에서는 “무엇을 만들 수 있는가”가 한눈에 보여야 한다.
- 보조 설정/삭제/멤버 관리가 주 액션을 압도하면 안 된다.

5. **사전/설정/멤버 관리는 작업 도구로 내린다**
- 메인 흐름은 문서 생성/탐색/진입이다.
- 부가 관리 기능은 작업 도구/유틸리티 영역으로 정리한다.

## 범위

### 이번 작업에 포함

1. **공통 앱 쉘 개선**
- 상단 헤더 재설계

- 문서/자산/설정으로 이어지는 상위 네비게이션 구조 정의

2. **팀/프로젝트/문서 진입 구조 재정리**
- 팀 선택 이후 프로젝트 홈 진입 UX 정리

- 현재 `DiagramsPage`를 장기적으로 `문서 목록 허브`로 확장 가능한 구조로 재설계

3. **사전(Dictionary) 위치 재정의**
- 팀 자산 또는 프로젝트 보조 도구로서의 위치를 명확히 정리
- 최소한 현재처럼 프로젝트 액션 버튼 묶음 안에 섞인 상태는 해소

4. **목록/빈 상태/생성 CTA 재설계**
- 프로젝트 목록
- 문서 목록
- 사전 화면
- 진입 전 empty state와 create CTA를 “무엇을 만들 수 있는지” 중심으로 재구성

5. **플러그인 확장 대응 정보구조 정의**
- ERD 전용 용어를 일반화
- 향후 마크다운 / 화면기획 문서가 같은 쉘 안에서 들어올 수 있게 상위 개념 정의
- 캔버스 문서(ERD, Screen Spec)와 텍스트 문서(Markdown)가 같은 상위 쉘에서 공존할 수 있는 기준 정의

6. **구현 가드레일 선잠금**
- 기존 [Header.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/components/layout/Header.tsx)에 문서 플랫폼 요구사항을 그대로 누적하지 않는다
- `DiagramsPage`를 CSS만 바꿔 문서 허브처럼 보이게 만들지 않는다
- Dictionary 왕복 동선은 상태 저장 방식까지 먼저 고정한 뒤 화면을 바꾼다
- 상위 visible label은 `document` 중심으로 바꾸되, 기존 route/file/API 이름은 당장 유지할 수 있게 매핑 계층을 둔다

## 제안 정보구조

### 현재

```text
Teams
  -> Projects
     -> Diagrams
        -> Diagram editor

Projects 화면 안에서
  -> Dictionary 버튼
```

### 개선 방향

```text
Workspace(Team)
  ├─ Projects
  ├─ Documents
  │   └─ Project별 문서 목록
  │       ├─ ERD
  │       ├─ Markdown (예정)
  │       └─ Screen Spec (예정)
  ├─ Dictionary
  └─ Members / Settings
```

핵심은 두 가지다.

- `diagram`은 상위 개념이 아니라 문서 타입 중 하나로 내린다.
- `dictionary`는 문서 목록 흐름 밖의 자산/도구 영역으로 올린다.
