# 01. 상세 설계

## 1. 설계 목표

이번 작업의 목적은 현재 제품을

- 팀 선택 화면
- 프로젝트 목록
- 다이어그램 목록
- 사전 페이지

의 단절된 CRUD 화면 모음에서,

**“여러 문서 타입을 담는 협업 문서 플랫폼”**처럼 보이는 제품 쉘로 바꾸는 것이다.

핵심은 두 가지다.

1. 지금 UX를 ERD 전용 툴처럼 보이게 만드는 상위 구조를 걷어낸다.
2. 향후 `markdown`, `screen-spec` 플러그인이 들어와도 상위 쉘을 다시 뜯지 않게 만든다.

즉 이번 설계의 성패는 캔버스가 아니라

- 진입 흐름
- 메뉴 구조
- 생성 액션 의미
- 목록 화면 정보 밀도

에서 결정된다.

## 2. 제품 정보구조

### 2.1 최상위 개념

개선 후 제품 정보구조는 아래처럼 본다.

```text
Team Workspace
  ├─ Projects
  │   └─ Project Workspace
  │       ├─ Documents
  │       │   ├─ ERD documents
  │       │   ├─ Markdown documents (future)
  │       │   └─ Screen Spec documents (future)
  │       └─ Project tools / context
  ├─ Dictionary
  ├─ Members
  └─ Settings
```

여기서 중요한 점:

- `diagram`은 상위 개념이 아니라 **문서 타입 하나**다.
- `dictionary`는 문서 타입이 아니라 **공통 자산/사전**이다.

### 2.2 현재 라우트와의 관계

현재 라우트는 [routes.ts](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/constants/routes.ts) 기준으로

- `/teams`
- `/teams/:teamId/projects`
- `/teams/:teamId/projects/:projectId/diagrams`
- `/teams/:teamId/projects/:projectId/diagrams/:diagramId`
- `/teams/:teamId/dictionary`

구조다.

이번 단계에서는 **URL을 즉시 전면 개편하지 않는다.**

대신:

- 라우트는 유지
- 화면의 IA와 용어를 먼저 일반화
- 필요하면 이후 차수에서 alias 또는 route rename 도입

으로 가는 게 맞다.

즉 `DiagramsPage`는 내부 구현 파일명은 유지해도,
**화면 역할은 “프로젝트 문서 허브”**로 바뀌어야 한다.

### 2.3 용어 전환표

이번 단계는 라우트를 즉시 바꾸지 않지만, 사용자에게 보이는 상위 용어는 아래 기준으로 정리한다.

| 현재 용어 | 새 용어 | 적용 범위 |
|-----------|---------|-----------|
| Diagram / Diagrams | Document / Documents | 상위 메뉴, breadcrumb, 페이지 제목 |
| New diagram | New ERD document | 생성 버튼, empty state, CTA |
| ERD list | Documents | 목록 허브 설명, section label |
| Dictionary | Dictionary | 기본 명칭 유지, 필요 시 `팀 사전 자산` 보조 설명 추가 |

원칙:

- 내부 파일명과 route segment는 당장 유지해도 된다
- 사용자에게 보이는 상위 IA는 `diagram`보다 `document` 중심으로 통일한다
- 단, 문서 타입 자체는 `ERD`라고 명확히 남긴다

## 3. 페이지 역할 재정의

### 3.1 TeamsPage

대상:
- [TeamsPage.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/pages/team/TeamsPage.tsx)

현재 역할:
- 팀 목록 카드 페이지

개선 후 역할:
- **워크스페이스 선택 화면**

핵심 경험:
- 사용자는 “어느 팀 워크스페이스에 들어갈지”를 선택한다.
- 단순 entity list가 아니라, “어느 협업 공간으로 들어가는지”가 읽혀야 한다.

개선 포인트:
- 팀 카드에 멤버 수 외에 “프로젝트/문서 작업 공간” 의미를 더 드러낸다
- 빈 상태도 “팀이 없다”보다 “협업을 시작할 워크스페이스를 만든다” 쪽으로 메시지를 바꾼다

### 3.2 ProjectsPage

대상:
- [ProjectsPage.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/pages/project/ProjectsPage.tsx)

현재 역할:
- 프로젝트 목록 + 사전/멤버/설정 버튼

개선 후 역할:
- **팀 워크스페이스 홈**

핵심 경험:
- 여기서 사용자는 프로젝트를 선택한다
- 동시에 팀 단위 자산/운영 기능에 접근한다

개선 포인트:
- 주 액션은 `새 프로젝트`
- 보조 액션은 `Dictionary / Members / Settings`
- 현재처럼 버튼이 한 줄에 수평 나열돼 주 액션과 섞이지 않게 분리
- 프로젝트 카드는 “문서 작업 공간”이라는 의미를 강화

권장 구성:

```text
Header
  ├─ Team context
  ├─ Current section: Projects
  └─ Utility actions

Main
  ├─ Workspace intro / team summary
  ├─ Primary CTA: New project
  ├─ Secondary tools: Dictionary, Members, Settings
  └─ Project grid/list
```

기본 표현 방식은 아래로 고정한다.

- **ProjectsPage는 카드형 grid를 기본으로 한다**
- 이유:
  - 프로젝트는 “무엇을 여는 공간인지”를 설명해야 해서 메타데이터 여백이 필요하다
  - 팀 홈 성격상 단순 dense list보다 선택지 탐색 경험이 중요하다
  - 최근 SaaS workspace UX에서도 프로젝트/공간 선택은 카드형, 실제 작업 항목은 리스트형으로 분리하는 패턴이 안정적이다
  - 즉 프로젝트는 **컨테이너 선택 UX**로 보고, 넉넉한 여백과 짧은 설명이 있는 카드가 더 맞다

카드 구성 원칙:

- 카드 전체가 주 클릭 영역이다
- 제목, 한 줄 설명, 최근 수정, 문서 수를 기본 메타로 둔다
- secondary action은 카드 본문이 아니라 외곽 menu로 밀어낸다
- 썸네일 중심 카드가 아니라 **텍스트 중심 workspace 카드**로 설계한다

### 3.3 DiagramsPage

대상:
- [DiagramsPage.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/pages/diagram/DiagramsPage.tsx)

현재 역할:
- ERD 다이어그램 목록

개선 후 역할:
- **프로젝트 문서 허브**

핵심 경험:
- 지금은 ERD만 있지만,
- 이 화면은 장기적으로 `ERD / Markdown / Screen Spec`을 모두 수용하는 문서 허브가 된다

이번 단계에서 바꿔야 하는 것:
- 제목, 설명, 빈 상태, 생성 버튼 의미를 문서 플랫폼 관점으로 정리
- 문서 카드에 타입 확장을 위한 자리 확보
- 지금은 ERD만 렌더해도, 정보구조는 “문서 목록”처럼 보여야 함

권장 구조:

```text
Project context header
  ├─ Project name
  ├─ Project-level description / recent activity
  └─ Primary CTA: New ERD

Document hub body
  ├─ Type filter area (initially fixed to ERD)
  ├─ Search / sort placeholder area
  └─ Document cards
      ├─ type badge
      ├─ title
      ├─ supporting metadata
      └─ secondary actions
```

여기서 중요한 건:
- 지금 단계에선 `새 ERD`만 있어도 됨
- 하지만 전체 화면 언어는 `ERD 목록`이 아니라 `문서 허브`에 가까워야 함

기본 표현 방식은 아래로 고정한다.

- **DiagramsPage는 dense list를 기본으로 한다**
- 이유:
  - 문서 허브는 카드보다 제목, 상태, 최근 수정 같은 비교 정보가 더 중요하다
  - 나중에 Markdown / Screen Spec이 들어와도 같은 list 패턴이 더 잘 확장된다
  - 문서는 “어디로 들어갈지”보다 “무엇이 최근에 바뀌었고 지금 어떤 상태인지”를 빠르게 훑는 일이 더 많다
  - 즉 문서는 **운영 목록 UX**로 보고, 비교 가능한 메타데이터를 한 줄에 압축하는 편이 맞다
- 모바일에서는 list를 유지하되, 메타데이터를 2줄 구조로 축약한다

리스트 구성 원칙:

- 첫 컬럼은 `type badge + title`
- 두 번째 묶음은 `최근 수정 / 협업 상태 / 연결 사전`
- 마지막은 secondary action
- row 전체 hover는 선택 강조만 하고, 카드처럼 부풀어 오르는 표현은 쓰지 않는다

문서 타입 노출 규칙은 아래로 고정한다.

- **목록 필터와 카드에는 구현된 타입만 노출한다**
- 아직 구현되지 않은 `Markdown`, `Screen Spec`은 목록 화면의 탭/필터에 비활성 상태로 미리 노출하지 않는다
- 대신 문서 허브 설명 문구와 정보구조는 미래 타입 확장을 견딜 수 있게 설계한다
- 추후 새 타입이 실제로 붙는 시점에만
  - 타입 badge
  - 타입 filter
  - `새 문서` 생성 옵션
  을 순차적으로 연다

즉 초기 문서 허브는 **ERD만 보이되, ERD 전용 화면처럼 보이지 않게 만드는 것**이 목표다

### 3.4 DictionaryPage

대상:
- [DictionaryPage.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/pages/dictionary/DictionaryPage.tsx)
- [DictionaryWorkspace.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/components/dictionary/DictionaryWorkspace.tsx)

현재 역할:
- 프로젝트 화면에서 들어가는 보조 페이지

개선 후 역할:
- **팀 자산/용어 사전 허브**

핵심 경험:
- 문서를 만들기 위한 사전 자산을 관리하는 공간
- 프로젝트 부속 화면이 아니라, 여러 문서 타입이 공유하는 기반 자산

개선 포인트:
- 상단 설명 영역에서 “문서와 어떻게 연결되는지”를 알려줌
- 세트 관리 액션과 실제 단어/용어/도메인 작업 영역을 시각적으로 분리
- 지금처럼 상단 액션이 다닥다닥 붙은 형태를 재구성

프로젝트 작업 흐름을 끊지 않기 위해 왕복 동선도 같이 고정한다.

- ProjectsPage와 DiagramsPage에는 `Dictionary`로 가는 **빠른 진입 액션**을 유지한다
- 다만 이 액션은 primary CTA가 아니라 utility cluster 또는 project context 영역에 둔다
- DictionaryPage 상단에는
  - 현재 팀 컨텍스트
  - 최근 진입 프로젝트가 있으면 `이전 프로젝트로 돌아가기`
  를 함께 노출한다
- 즉 정보구조는 팀 자산 허브로 올리되, 작업 흐름은 프로젝트 기준으로 빠르게 왕복 가능해야 한다

예외 규칙:

- 최근 진입 프로젝트가 없으면 `이전 프로젝트로 돌아가기`는 노출하지 않는다
- 최근 프로젝트가 삭제됐거나 접근 권한이 사라졌으면 해당 액션을 숨기고, 기본 팀 workspace 진입만 제공한다
- 다른 팀 컨텍스트에서 Dictionary에 직접 진입한 경우에도 “현재 팀 자산 허브” 기준으로만 동작하며, 잘못된 이전 프로젝트 링크를 추정하지 않는다

권장 구조:

```text
Dictionary header
  ├─ Team context
  ├─ Purpose copy
  └─ Export / manage actions

Workspace
  ├─ Set selector and set actions
  └─ Tabs: Words / Terms / Domains
```

## 4. 공통 쉘 설계

### 4.1 Workspace Header

대상:
- [Header.tsx](/Users/j.jaeyo/Project/ETC/smart-erd/client/src/components/layout/Header.tsx)

현재 문제:
- 앱명 + 유틸 정도만 보이고, 사용자가 현재 어디 있는지 약함

개선 방향:
- `Workspace Header`로 승격
- 현재 컨텍스트를 3단계 정도로 노출
  - Team
  - Project
  - Section / Document

예시:

```text
Smart ERD
  Team A / Project B / Documents
```

또는

```text
Smart ERD
  [Team A] [Project B] [ERD]
```

원칙:
- breadcrumb는 상단 고정
- 우측 유틸보다 현재 위치 인지가 우선
- 다이어그램 편집 화면의 연결 상태 점도 이 header 안에서 더 자연스럽게 배치

편집기 화면 Header 레이아웃은 아래 우선순위로 고정한다.

```text
좌측
  제품명
  Team / Project / Section

중앙
  현재 문서 제목

우측
  협업 상태
  검색/언어/사용자 유틸
```

세부 규칙:

- 편집기 화면에서는 `Section`보다 **현재 문서 제목**이 더 중요하다
- breadcrumb의 마지막 단계는 `Documents` 또는 `Dictionary` 같은 섹션명으로 두고, 실제 문서 제목은 중앙 영역에서 강조한다
- 협업 상태 점과 저장/동기화 배지는 우측 유틸 앞에 배치한다
- 모바일에서는
  - `Team / Project`까지만 기본 노출
  - 문서 제목은 1줄 truncate
  - 협업 상태는 아이콘 + 짧은 라벨만 유지
  로 축약한다

### 4.2 왼쪽 내비게이션 여부

이번 단계에서는 **상시 좌측 사이드바를 강제하지 않는다.**

이유:
- 현재 페이지 구조를 한 번에 과하게 흔들 수 있음
- 캔버스 편집 화면과 충돌 가능성 있음

대신:
- 헤더 + 컨텍스트 바 + 페이지 상단 섹션 네비
로 먼저 정리한다.

즉, 좌측 전역 nav는 2차 확장 대상이다.

## 6. 정보 밀도와 시각적 위계

현재 목록 화면은 대부분

- 큰 제목
- 카드 그리드
- hover 액션

패턴 반복이다.

문제:
- 전부 같은 중요도로 보여서, 페이지별 성격 차이가 약함
- 생성/탐색/관리/보조 액션이 같은 레벨에서 섞인다

개선 원칙:

1. **주 액션은 하나**
- 페이지당 primary CTA는 하나

2. **도구/설정은 별도 묶음**
- Dictionary, Members, Settings 같은 건 utility cluster로 내림

3. **목록 카드에는 목적형 메타데이터**
- 단순 날짜보다
  - 마지막 수정
  - 연결된 사전
  - 타입
  - 협업 상태
등이 더 의미 있음

4. **빈 상태는 생성 유도형**
- “없음”을 말하는 것보다
- “여기서 무엇을 시작할 수 있는지”를 말해야 함

### 6.1 화면별 first / second / third hierarchy

각 화면은 사용자가 첫 3초 안에 아래 순서로 읽혀야 한다.

#### TeamsPage

1. **내가 들어갈 워크스페이스**

2. **현재 선택된 사전 세트와 주요 액션**

- Words / Terms / Domains 탭과 테이블은 그 다음에 들어온다

### 6.3 사용자 여정과 감정 곡선

이번 설계는 단순히 페이지를 나열하는 것이 아니라, 사용자가 “이 제품이 정리돼 있다”고 느끼게 만들어야 한다.

| Scene | 사용자 행동 | 기대 감정 | 설계 장치 |
|-------|-------------|-----------|-----------|
| 1 | 팀 목록 진입 | “어디로 들어갈지 명확하다” | 워크스페이스 선택형 카피, 단순 CRUD 톤 제거 |
| 2 | 팀 홈 진입 | “이 팀에서 뭘 할 수 있는지 바로 보인다” | team hero, primary CTA 1개, utility 분리 |
| 3 | 프로젝트 진입 | “이 프로젝트는 문서를 만드는 공간이다” | project context header, document hub framing |
| 4 | 문서 생성/선택 | “다음 행동이 분명하다” | `새 ERD 문서` 주 액션, 문서 카드 메타 정리 |
| 5 | Dictionary 진입 | “문서 편집과 다른 성격의 도구다” | 자산 허브 포지션, purpose copy, set-first layout |

감정 목표는 세 가지다.

- **정돈감**: 지금 내가 어디 있는지 헷갈리지 않는다
- **확장 신뢰감**: 나중에 문서 타입이 늘어나도 구조가 무너지지 않을 것 같다
- **행동 명확성**: 매 화면에서 “지금 해야 할 한 가지”가 보인다

### 6.4 화면기획 플러그인 대응 규칙

이번 설계는 화면기획 플러그인을 나중에 붙여도 상위 UX를 다시 뜯지 않는 것을 목표로 한다.

따라서 아래 규칙을 고정한다.

1. **상위 생성 언어는 문서 타입 중립적으로 유지**
- 지금은 `새 ERD 문서`만 보여도, 생성 진입 구조는 `새 문서` 계층을 전제로 설계한다

2. **문서 카드 메타에는 타입 슬롯을 항상 확보**
- ERD만 있을 때도 type badge 자리를 유지한다

3. **캔버스 문서와 텍스트 문서가 공존 가능해야 한다**
- ERD와 Screen Spec은 캔버스 문서
- Markdown은 텍스트 문서
- 따라서 상위 쉘은 편집기 성격과 무관하게 동일한 진입 경험을 제공해야 한다

4. **Dictionary는 문서 타입으로 취급하지 않는다**
- Screen Spec이 들어와도 Dictionary는 여전히 공통 자산 허브다

### 6.5 반응형 / 접근성 기준

이번 단계는 진입 쉘 개선이므로, 캔버스보다 상위 화면의 사용성을 먼저 잠근다.

#### 반응형

- Desktop: team/project/document context를 한 줄에 유지
- Tablet: breadcrumb는 유지하되 utility cluster를 접는다
- Mobile: context는 2단계까지만 기본 노출하고, 나머지는 drawer 또는 overflow로 보낸다
- 카드 그리드는 모바일에서 단순 1열 stack으로 끝내지 말고, 카드 내부 정보 우선순위를 다시 조정한다

#### 접근성

- Header breadcrumb와 section nav는 키보드로 모두 이동 가능해야 한다
- primary CTA는 페이지 진입 후 빠르게 포커스 가능해야 한다
- empty/error state는 screen reader가 즉시 읽을 수 있는 heading + body + action 구조를 가진다
- 문서 타입 badge는 색만으로 구분하지 않고 텍스트를 포함한다
- utility cluster의 아이콘 버튼은 모두 명시 라벨을 가진다

## 7. 시각 방향

이번 작업은 새 디자인 시스템 전체를 만드는 단계는 아니지만, 최소한 아래 톤은 고정해야 한다.

- **제품 캐릭터**: diagram tool이 아니라 calm document workspace
- **레이아웃**: 상단 컨텍스트는 단단하게, 본문은 넓고 숨 쉬게
- **타이포그래피**: 제목은 문서성, 본문은 실무 도구성
- **색 사용**: 주 액션과 상태 강조에만 집중, 페이지 전체를 색으로 채우지 않음
- **모션**: 리스트 로드와 컨텍스트 전환에만 절제해서 사용

금지:

- 의미 없는 카드 남발
- 모든 페이지가 같은 hero + grid 패턴으로 보이는 구조
- utility action이 primary CTA처럼 보이게 만드는 배치
