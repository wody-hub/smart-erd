# Export 성능 실측 및 개선 방안

작성일: 2026-03-17

## 목적

ERD 다이어그램 export 기능의 현재 체감 성능을 실측하고, 병목 구간과 개선 우선순위를 정리한다.

이번 문서는 다음 두 가지를 포함한다.

1. 2026-03-17 기준 브라우저 실측 결과
2. JPG export 이상 동작 원인과 수정 결과
3. PDF 성능 개선 및 export 진행 UI 적용 결과

---

## 실측 환경

- 프런트엔드: `http://localhost:3000`
- 백엔드: `http://localhost:8190/api`
- 측정 방식:
  - Playwright headless Chromium으로 실제 다이어그램 페이지 진입
  - export 메뉴를 실제 클릭하여 포맷별 내보내기 수행
  - `cold`: 새 브라우저 컨텍스트에서 첫 export
  - `warm`: 같은 페이지에서 즉시 한 번 더 export
- 완료 기준:
  - PNG/JPG/SVG: 브라우저 다운로드 트리거 감지
  - PDF: 성공 토스트 감지

## 측정 시나리오

- 테이블 수: 128
- 엣지 수: 232
- 테이블당 컬럼 수: 4
- 다이어그램 추정 바운드: `8820 x 1724` px
- 저장 content 크기: `134,735` bytes
- 배치: `16 x 8` 그리드

## JPG 이상 동작 확인

### 증상

- JPG export 결과 파일명은 `.jpg`
- 하지만 실측된 Blob MIME은 `image/png`
- 파일 크기도 PNG와 동일 (`3,525,406` bytes)

즉, JPG export가 실제로는 PNG Blob을 내려주고 있었다.

### 원인

현재 구현은 `html-to-image`의 `toBlob()`를 사용하고 있었는데, 라이브러리 내부 구현상 `toBlob()`가 최종 `canvasToBlob()` 호출에 `type`과 `quality` 옵션을 전달하지 않는다.

확인 위치:

- `client/node_modules/html-to-image/src/index.ts`
- `client/node_modules/html-to-image/src/util.ts`

핵심적으로 `toBlob()`는 `canvasToBlob(canvas)`만 호출하고 있고, `canvasToBlob(canvas, options)`로 넘기지 않는다.

그 결과 `image/jpeg`를 요청해도 기본값인 `image/png`가 사용된다.

## JPG 수정 후 재실측

재실측 리포트 경로:

- `/tmp/smart-erd-export-jpg-check.json`

### 결과

| 포맷 | cold | warm | MIME | 파일 크기 |
| --- | ---: | ---: | --- | ---: |
| JPG | 7132ms | 5472ms | `image/jpeg` | `6,140,381` bytes |

### 해석

- JPG가 이제 실제 `image/jpeg`로 내려온다.
- warm 기준 시간도 `6661ms -> 5472ms`로 내려갔다.
- PNG와 동일 Blob이 내려가던 기능 오류는 해소됐다.

주의:

- JPEG 파일 크기가 PNG보다 더 크다.
- 이 다이어그램에서는 텍스트/선/도형이 많아서, 손실 압축 JPEG가 PNG보다 반드시 작아지지 않는다.
- 따라서 JPG는 “더 작은 파일” 포맷이라기보다 “손실 압축 이미지” 포맷으로 보는 편이 맞다.

- 단일 페이지 PDF는 안전한 `pixelRatio`와 렌더 면적 기준으로 판단
- SVG 다운로드를 `data:` URL에서 SVG Blob URL 다운로드로 변경
- export 진행 상태를 훅에서 관리하고, 단계별 progress bar 모달을 추가
- tiled PDF는 페이지 단위로 progress를 갱신하고 각 단계 사이에 브라우저 페인트를 양보

### progress UI 설계 원칙

- export는 DOM clone/canvas 렌더 특성상 완전한 워커 오프로딩이 어렵다.
- 대신 `preparing -> rendering -> encoding -> downloading` 단계로 쪼개고, 각 단계 전후에 `requestAnimationFrame` 기반 양보를 넣어 UI가 먼저 그려지게 했다.
- 사용자는 export 중 모달 progress bar, 단계 문구, 현재 퍼센트를 확인할 수 있다.
- PDF 분할 export는 페이지 단위 progress를 표시하므로 긴 작업도 실제로 진행 중임을 알 수 있다.

### 2차 해석

    - warm 약 `8130ms` (`38.3%`)

- `PNG/JPG` raw 시간은 progress 상태 갱신과 완료 UI 노출 때문에 소폭 불리해졌지만, 사용자는 이제 export 진행 여부를 명확히 인지할 수 있다.

## 현재 병목 해석

### 1. DOM 복제 + 스타일 계산 + 폰트 임베드

`html-to-image`는 export마다 다음 작업을 수행한다.

- 노드 트리 clone
- computed style 복사
- 폰트 embed
- 이미지 embed
- SVG foreignObject 생성
- 캔버스 렌더

다이어그램이 커질수록 이 비용이 지배적이다.

### 2. PDF의 과도한 tiled 경로 진입

초기 구현은 고정 `8000px` 기준을 넘기면 tiled PDF로 내려갔다.

이번 실측 시나리오는:

- width: `8820`
- height: `1724`

으로, 캔버스 제한(`16384`)에는 충분히 여유가 있었지만, 기존 `8000` 기준 때문에 단일 페이지 대신 분할 PDF 경로를 탔다.

초기에는 이 때문에:

- `toCanvas`가 타일마다 반복되고
- `jsPDF.addPage()`가 반복되며
- 전체 시간이 `~20초` 수준으로 증가했다.

현재는 이 분기를 `safe pixelRatio + 렌더 면적` 기준으로 바꿨고, 이번 시나리오는 단일 페이지로 처리되면서 `~13초` 수준까지 내려왔다.

### 3. SVG의 Data URL 다운로드

SVG는 시간은 빠르지만, 다운로드가 `data:` URL로 이뤄진다.

이번 실측에서 SVG 다운로드 문자열 크기는 약 `118MB` 수준으로 관측됐다.
브라우저 메모리와 문자열 복사 비용 관점에서는 좋지 않다.

## 개선 우선순위

### 우선순위 1. PNG/JPG raw 시간 추가 최적화

progress UI 추가 이후에도 PNG/JPG가 추가로 빨라질지는 아직 남은 과제다.

개선 방향:

- progress 상태 업데이트 횟수 최소화
- PNG/JPG 전용 경량 progress 모드 검토
- `html-to-image` 렌더 옵션 경량화 실험

### 우선순위 2. SVG를 Blob URL 다운로드로 변경

이 항목은 이번 패치로 적용 완료했다.

적용 결과:

- 매우 큰 data URL 직접 다운로드를 피하게 됨
- MIME이 명확히 기록됨
- 다운로드 안정성이 좋아짐

### 우선순위 3. export 옵션 프로파일 분리

사용자가 원하는 품질과 시간을 명시적으로 선택할 수 있도록 분리하는 방안이다.

예시:

- `PNG (표준)`
- `PNG (고해상도)`
- `PDF (단일 페이지 우선)`
- `PDF (대형 다이어그램 분할)`

기대 효과:

- 사용자가 긴 대기 시간을 의도적으로 선택 가능
- 대형 다이어그램에서 “왜 느린지”를 UX로 설명 가능

### 우선순위 4. `html-to-image` 스타일 복사 범위 최소화 검토

라이브러리는 `includeStyleProperties` 옵션을 제공한다.

개선 방향:

- ERD 노드/엣지 렌더에 꼭 필요한 CSS 속성만 포함하도록 제한 가능성 검토

리스크:

- 누락된 스타일 때문에 export 결과가 깨질 가능성 높음
- 시각 회귀 검증이 필요

우선순위는 낮지만, 성공 시 전체 포맷에 공통 이득이 있다.

### 우선순위 5. 리포지토리 내 export perf 스크립트 정식화

이번 실측은 `/tmp` 임시 스크립트로 수행했다.

개선 방향:

- `client/scripts/perf/` 아래에 export 성능 측정 스크립트를 정식 추가
- 시나리오 크기와 포맷을 인자로 받도록 구성
- 리포트를 JSON으로 남기도록 유지

기대 효과:

- 이후 최적화 전후 비교가 쉬워짐
- 회귀 감지 가능

## 결론

2026-03-17 기준 export 개선은 두 단계로 진행됐다.

첫 번째는 JPG 기능 오류 수정이었고, 두 번째는 PDF 분기 기준 재설계와 progress UI 추가였다.
이 문제는 `html-to-image.toBlob()`의 옵션 누락 때문에 발생했고, export 훅에서 직접 `canvas.toBlob('image/jpeg')`를 호출하도록 바꿔 해결했다.

가장 큰 성능 병목이던 PDF는 이번 시나리오에서 `20초 안팎 -> 13초 안팎`까지 줄었다.
동시에 사용자는 이제 export 진행 상태를 모달 progress bar로 확인할 수 있다.

현재 남은 과제는 raw 시간이 아직 긴 PNG/JPG 경로를 더 가볍게 만들고, 필요하면 “빠른 export / 고품질 export”를 분리하는 것이다.
